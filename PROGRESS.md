## Standing Rules for This Project

1. **Always maintain this progress tracker.** Update "Current Phase" / "Status Summary" as work completes, and always write a dated entry in "Notes / Handoff" before stopping work for the session — even (especially) if the task was interrupted mid-way. Never leave the repo in a state where the next person/session has to reverse-engineer what was in progress.
2. **One standard design system, no exceptions.** Every page (builder, dashboard, submissions inbox, settings, public form runtime) uses the same shared app shell, component library, and design tokens (styles, buttons, forms, lists, inputs, etc.) — see Main Feature #6 in the plan and the future UI/UX Design System Reference (doc #19). No page invents its own one-off layout or component styling. Any exception requires an explicit, documented rationale, not a default under time pressure.
3. **Styling default — don't re-ask (confirmed with the user 2026-07-05).** Do not ask "backend-only / minimal-unstyled vs. fully styled?" per increment. The default is **every page is built fully styled, assembled from the shared design-system components**. The only increments with no styling work are those with **no pages at all** (a pure data-model / API / backend step). The bare pages parked in B1/B2b/B2c (login, register, password-reset, invite-accept, super-admin console, 2FA setup) are brought up to standard in Increment C, which builds out the shared component library itself (only `Button` exists in code today; the color/border/radius/type tokens are complete). Earlier increments were unstyled only because the component library didn't exist yet and styling then would have been rework — not because styling was ever optional.
