## Context

This project is a brand-new, greenfield multi-tenant SaaS form-builder / data-collection platform, explicitly influenced by KoboToolbox, Fillout.com, and lessons drawn from a direct code audit of our own legacy system, `dev_pk_new` ("Purok Kalusugan") — a Laravel 11 + Inertia + Vue 3 application built for the Philippine DOH on **MySQL** (InnoDB). The legacy codebase is a rich source of proven feature ideas but was never designed to be multi-tenant, and its choice of database engine was never a deliberate decision for this project — it was inherited from whatever the original single-tenant government-reporting tool happened to start on.

We must choose our primary relational datastore before Phase 0 (repo/infra scaffolding) begins, because the choice materially shapes the schema, the multi-tenancy enforcement model, and the geo/JSON field types built into the core data model from day one — retrofitting a database engine change after migrations, RLS policies, and JSONB query patterns are baked into application code would be far more expensive than deciding now.

### What legacy actually did, and why it doesn't carry forward as-is

Direct inspection of `dev_pk_new`'s migrations and services (not just its internal docs, which were found to have drifted from the code) surfaced three concrete, MySQL-shaped gaps that this new product cannot inherit:

**1. No tenant isolation below the application layer.** Legacy was single-organization — there is no `tenant_id` anywhere in its schema, and there was never a need for cross-tenant data isolation. The closest analogous control that *did* exist, `users.id === 1` as an implicit "super admin" convention, illustrates the risk of relying on application-layer-only enforcement: that single fragile check was duplicated across four separate code layers and would have silently granted god-mode privileges to any future user who happened to be reassigned ID `1` (e.g., after a deletion and ID reuse). MySQL and MariaDB have **no built-in row-level security (RLS) mechanism** — the closest approximations (views with `WITH CHECK OPTION`, `DEFINER`-scoped stored procedures, or trigger-based enforcement) are workarounds bolted onto a system that was never designed for per-session, per-tenant predicate enforcement, and none of them give a database-level guarantee that survives a forgotten `WHERE tenant_id = ?` clause, a raw query, a queue worker running outside the normal request/global-scope lifecycle, or an Eloquent global scope a future developer forgets to attach to a new model. For a system whose entire commercial model is now multi-tenant SaaS — where a tenant-isolation bug means one customer's health/survey data leaking to another — "the application always remembers to filter" is not an acceptable sole control.

**2. Geo data stored as inert JSON, with no spatial querying.** Legacy's geographic modeling (`catchment_level_id`, `psgc_level_id` on `indicators`, plus a full `regions → provinces → cities → barangays` hierarchy seeded from JSON, 43,000+ rows at the lowest level) stores location as plain reference-table foreign keys and, for actual geo-point answer data, as JSON strings with **zero spatial query capability** — no "is this point inside this catchment polygon," no distance/radius queries, no bounding-box search, no geometry validation. Catchment-area assignment itself was resolved via an app-level `switch` statement with no real database foreign key at all — a documented anti-pattern this project's plan explicitly replaces with a real polymorphic `morphTo` wherever an equivalent scoping need exists. The new product's roadmap (Phase 2) commits to Kobo-parity `geopoint` / `geotrace` / `geoshape` field types, which are only genuinely useful with real spatial querying (containment, distance, area) behind them — a capability MySQL's spatial extension does not offer with anywhere near PostGIS's maturity (topology operators, geometry validity, `ST_*` functions, spatial indexing via GiST).

**3. A weaker JSON story that pushed legacy toward workarounds.** Legacy's own schema shows the symptoms of MySQL's JSON limitations:
   - `form_submissions.ocr_data` is stored as `JSON`, but the team *also* kept a separate `raw_ocr_data LONGTEXT` column alongside it — a duplicative, ad hoc pattern consistent with not fully trusting MySQL's JSON column for round-trip fidelity and query needs simultaneously.
   - `submission_values` — the flat per-answer-cell table — stores every field's answer as **type-erased `text`**, one row per (submission, field) pair: a fully normalized Entity-Attribute-Value (EAV) design. EAV is a well-documented anti-pattern at scale (query complexity, join fan-out, poor aggregate performance), and part of why legacy leaned into it is that MySQL's JSON column type only supports secondary indexing on a *specific* path via generated/virtual columns — not a general-purpose inverted index over arbitrary keys — so a single flexible JSON payload column couldn't cheaply serve both "store anything" and "query efficiently on whatever the report needs" at once. The new app's hybrid model (§2.2 of the architecture plan: one JSONB `answers` document per submission plus a selective typed projection, `submission_answer_index`, for fields flagged queryable) needs a **GIN-indexed JSONB** column to make that hybrid actually performant — a capability MySQL's JSON type does not match. Postgres's `@>`, `?`, `?&`, and `?|` JSONB containment/existence operators, backed by a GIN index, give sub-linear lookups over arbitrary keys inside the payload without requiring a pre-declared generated column per field — exactly what a form-builder with an open-ended, tenant-defined field schema needs.

None of this is a criticism of the original engineering decision in isolation — MySQL was a reasonable default for a single-tenant government reporting tool with no geo-query requirement in 2019. It is, however, a poor foundation for a multi-tenant SaaS product whose core differentiators (safe tenant isolation, Kobo-parity geo field types, and a flexible-but-queryable submission model) each land on exactly the three gaps above.

### Decision drivers, in priority order

1. **Tenant-isolation defense-in-depth** — a database-level backstop is now a hard requirement, not a nice-to-have, because a breach directly damages customer trust in a SaaS product handling potentially sensitive survey/health/business data across many organizations.
2. **First-class geo field types** — `geopoint`/`geotrace`/`geoshape` are committed roadmap items (Phase 2) that require real spatial querying to be useful, not just storable.
3. **A queryable-but-flexible submission model** — the JSONB-hybrid design in §2.2 of the architecture plan is only viable with genuine binary JSON storage and inverted indexing.
4. **Ecosystem fit with the chosen stack** — Laravel's Eloquent, `stancl/tenancy` v4, and Spatie Laravel-Permission all fully support Postgres, so this is not a trade against the rest of the stack decision (ADR-adjacent: Laravel + Inertia/Vue, §1 of the architecture plan).
5. **Minimizing unforced re-platforming risk later** — choosing correctly now avoids a mid-flight database migration once tenant data, RLS policies, and geo data exist in production.

## Decision

**We will adopt PostgreSQL as the single, primary relational datastore for the entire application** — all tenant, identity/RBAC, form/version/submission, billing, audit, and webhook data across every environment (local, staging, production) — replacing MySQL/MariaDB, which was legacy's choice and is explicitly *not* carried forward.

Concretely:

- **Engine and version**: PostgreSQL **16 or later** in every environment (local Docker Compose, CI, staging, production), so the team standardizes on one guaranteed-available feature set (native JSONB, GIN/GiST indexing, RLS, `gen_random_uuid()`, robust window functions/CTEs). *(The architecture plan does not pin an exact minor version; PostgreSQL 16+ is a concrete, reasonable floor chosen here to guarantee full compatibility with the PostGIS 3.x line and the RLS/JSONB features this decision depends on — treat "or later" as intentional, not a hard ceiling.)*
- **Row-Level Security (RLS) is enabled on every tenant-scoped table** as a database-enforced backstop, driven by a per-request session variable (e.g., `SET LOCAL app.tenant_id = '<uuid>'`, set by early tenant-resolution middleware) — layered *underneath*, not instead of, Eloquent's automatic global tenant scope. This directly targets the class of bug the legacy `users.id === 1` incident represents: even a forgotten global scope, a raw query, or a queue-worker context that mishandles tenant context still hits a hard database wall.
- **PostGIS** is enabled as a required extension from the point Phase 2's geo field types (`geopoint`, `geotrace`, `geoshape`) are implemented, giving real `ST_*` spatial operators, geometry validity, and GiST spatial indexing — replacing legacy's plain-JSON-string, non-queryable geo storage.
- **JSONB + GIN indexing** is the storage mechanism for the `submissions`/`submission_answers` hybrid model (§2.2 of the architecture plan): one JSONB `answers` document per submission for the free-form payload, a GIN index for containment/existence queries, and a selective typed projection table (`submission_answer_index`) for the specific fields a given form flags as queryable/filterable/sortable — deliberately avoiding both legacy's fully-normalized EAV (`submission_values`) approach and a naive "everything in one opaque JSON blob, nothing indexed" approach.
- **Additional extensions enabled by default**: `pgcrypto` (or native `gen_random_uuid()` in PG13+) for UUID generation (client-generated `client_submission_uuid` for offline-sync idempotency depends on reliable UUID handling on both client and server); `citext` for the small set of columns that need case-insensitive uniqueness (e.g., a form's public share slug, user email) — since Postgres text comparison is case-sensitive by default, unlike MySQL's typical `utf8mb4_general_ci` collation, this is a deliberate, explicit replacement rather than an accidental behavior change; `pg_trgm` reserved as an option for fuzzy/partial-text search over form/field labels if full-text search needs grow beyond Postgres's built-in `tsvector` (not required at MVP, noted here as a documented future option since the plan is silent on search implementation specifics).
- **Hosting alignment**: this decision is directly compatible with the plan's hosting options (§1) — Laravel Cloud bundles first-party serverless Postgres, Laravel Forge provisions Postgres on Hetzner/DigitalOcean/Vultr just as easily as MySQL, and Fly.io offers Fly Managed Postgres; and the actually-chosen host — **self-managed PostgreSQL on Windows Server (ADR-0005)** — runs Postgres natively with full RLS/PostGIS support, so no hosting option is foreclosed by this choice.
- **No polyglot persistence at this stage**: we are not introducing a second database engine (e.g., MongoDB for JSON flexibility, or keeping MySQL for one subsystem) — a single Postgres instance/cluster per environment is the whole answer to both the relational (tenants, RBAC, forms, billing) and semi-structured (submission answers, form schema snapshots) needs, per the plan's "start simple, add complexity only when justified" theme.

This decision applies from Phase 0 onward: the multi-tenancy + RLS foundation and the `form_versions` draft/publish model are both built on Postgres from the very first migration, so tenant isolation and versioning are structural from day one rather than retrofitted (per §3, Phase 0 of the architecture plan).

## Consequences

### Positive

- **A real, database-enforced tenant-isolation backstop.** RLS policies mean a bug in application-layer scoping (a missed global scope, a raw query, a queue job that mishandles tenant context) fails closed at the database instead of leaking cross-tenant data — the single most valuable capability MySQL cannot offer, and the direct structural fix for the class of risk legacy's `users.id === 1` hack represented.
- **PostGIS unlocks the committed Kobo-parity geo field types.** `geopoint`/`geotrace`/`geoshape` become genuinely queryable (distance, containment, bounding box, validity) rather than legacy's opaque JSON strings — a real product capability, not just a storage upgrade.
- **JSONB + GIN gives the hybrid submission model its performance story.** The §2.2 design (JSONB payload + typed projection for hot fields) depends on efficient containment/existence queries over an open-ended, tenant-defined schema; this is the mechanism that lets us avoid both legacy's EAV table (`submission_values`) and a naive unindexed JSON blob.

  > **Implementation status, recorded 2026-08-03 (ADR-0011 / H1e).** The *capability* claim above is correct and the decision stands, but **the GIN index was never built.** As of Increment H, `submission_answers` carries exactly one index — a B-tree on `(tenant_id, form_version_id)` — and `grep "USING GIN"` over `database/migrations/` returns nothing. In practice the hybrid model's read path has been carried entirely by the *typed projection* half (`submission_answer_index`, five typed columns with four B-trees) and by whole-document reads by primary key; no shipped feature has yet issued a containment/existence query over `answers`. This note exists because the same claim was being read as as-built in `docs/architecture/technical-architecture.md` (now corrected), and because ADR-0011 §D3 had to decide what cross-form answer aggregation may promise — it promises only what the typed projection can serve. Adding the GIN index is a live option for whichever increment first needs a containment query; it is not a defect in this decision, but it is not a mechanism anything can rely on today.
- **Better general JSON ergonomics.** Native binary JSONB storage, richer operators (`->`, `->>`, `#>`, `@>`, `?`, `?&`, `?|`), and `jsonb_path_query`/`jsonb_set` give the application layer (form schema snapshots in `form_versions.schema_snapshot`, OCR extraction payloads, webhook payload logs) a materially more capable query surface than MySQL's JSON functions.
- **Transactional DDL.** Postgres migrations run inside a real transaction (a failed migration rolls back cleanly), reducing the risk of partial-schema states during deploys compared to MySQL, where most DDL statements are not transactional.
- **Stronger analytics primitives for later phases.** Window functions, recursive CTEs, and more mature query planning benefit the cross-form/cross-version analytics work committed to Phase 3 (advanced dashboards) and the geographic-hierarchy queries that replace legacy's `regions → provinces → cities → barangays` lookup pattern.
- **No ecosystem trade-off inside the chosen stack.** `stancl/tenancy` v4, Spatie Laravel-Permission, and Laravel Cashier are all Postgres-compatible with no feature gap versus MySQL, so this decision doesn't fight the rest of §1's stack recommendation.
- **Hosting compatibility preserved.** Every shortlisted hosting option in the plan (Laravel Cloud, Forge + Hetzner/DigitalOcean/Vultr, Fly.io) — as well as the actually-chosen **self-hosted PostgreSQL on Windows Server (ADR-0005)** — supports Postgres at parity with MySQL (with full RLS/PostGIS), so this decision doesn't narrow the hosting ADR's options.

### Negative

- **The team must build genuine Postgres-specific operational knowledge it does not currently have**, since the legacy stack's hands-on experience is MySQL. Concretely: autovacuum tuning and bloat monitoring (no MySQL equivalent concept), connection-pooling design (Postgres's one-process-per-connection model is materially heavier than MySQL's threads, so a pooler such as PgBouncer — or a managed offering with built-in pooling — becomes a **required infrastructure component**, not an optional one), RLS policy authoring and debugging (a new skill with real footguns, e.g., policies that silently exclude rows for superuser/table-owner connections unless `FORCE ROW LEVEL SECURITY` is set), PostGIS extension/version management, and reading `EXPLAIN (ANALYZE, BUFFERS)` output, which differs meaningfully from MySQL's `EXPLAIN`. *Mitigation, to be captured in the Deployment & Infrastructure Doc and Non-Functional Requirements Doc (§4, items 22 and 10 of the architecture plan): a documented Postgres ops runbook, RLS testing as a standing checklist item in the Multi-Tenancy & RBAC Design Doc (§4 item 9), and using the Phase 0 Docker Compose environment as the team's first hands-on ramp-up, not production.*
- **Legacy MySQL-specific patterns and assumptions do not port as-is**, and re-implementing "the same idea" naively will produce subtly wrong behavior. Concretely, grounded in the legacy schema itself:
  - MySQL's default collation (`utf8mb4_general_ci`/`utf8mb4_unicode_ci`) makes string comparisons case-insensitive by default; Postgres `text`/`varchar` comparison is case-sensitive by default. Any lookup that unconsciously relied on that (e.g., matching a form's `public_slug`, or a user email at login) needs an explicit fix — this ADR specifies `citext` for exactly those columns rather than leaving it to be discovered as a bug later.
  - MySQL's `AUTO_INCREMENT` and Postgres's sequence/`IDENTITY`-backed columns behave similarly at the Eloquent layer but differ in edge cases (gaps after rollback, explicit sequence resets after bulk-loading legacy-style seed data such as the 43,000+-row PSGC-style geographic tables) — anyone hand-seeding reference data needs to be aware of this.
  - MySQL's `INSERT ... ON DUPLICATE KEY UPDATE` (implicitly used by some Eloquent `upsert()` calls) maps conceptually to Postgres's `INSERT ... ON CONFLICT ... DO UPDATE`, and while Eloquent abstracts most of this, any raw SQL carried over from legacy muscle memory will not run unmodified.
  - MySQL's traditionally more permissive defaults (implicit type coercion, historically permitting zero-dates like `'0000-00-00'` in non-strict mode) have no Postgres equivalent — this is a net data-quality improvement, but it means any legacy-derived seed/import script must be reviewed rather than copied, since Postgres will reject what MySQL silently accepted.
  - Legacy's `ocr_data JSON` + `raw_ocr_data LONGTEXT` duplication and the `submission_values` EAV table are patterns this ADR's decision is explicitly designed to retire (via JSONB + GIN + selective typed projection) rather than reimplement — but that means the OCR Pipeline Design Doc and Data Dictionary (§4 items 17 and 5) must define the *new* pattern explicitly rather than defaulting to "however legacy did it."
- **Connection pooling becomes a mandatory piece of infrastructure**, not an optional optimization — a consequence of Postgres's per-connection process model versus MySQL's lighter-weight thread model, especially relevant once Horizon queue workers, web workers, and Reverb realtime connections all hold concurrent database connections. This must be sized and documented explicitly in the Deployment & Infrastructure Doc (or satisfied by a managed Postgres offering that bundles pooling, such as Laravel Cloud's serverless Postgres).
- **RLS policies must be kept in sync with schema changes as a matter of process discipline.** Every new tenant-scoped table requires an explicit RLS policy attached in the same migration that creates it — a step that has no equivalent "forgettable" analog in a MySQL-only, application-scoping-only world, precisely because MySQL never offered this control to forget. This is a positive trade-off overall (it converts a silent failure mode into a checklist item) but is worth naming as new process overhead: it should be enforced via a Phase 0 CI check or migration-review checklist referenced from the Multi-Tenancy & RBAC Design Doc (§4 item 9).
- **Smaller ambient familiarity with "one-click" Postgres tooling in the very cheapest hosting tiers** compared to the ubiquity of MySQL + phpMyAdmin-style tooling on budget shared/VPS hosting. This is a minor consideration given the plan's actual hosting shortlist (§1) already standardizes on Postgres-first options (Laravel Cloud, Forge, Fly.io), but is noted for completeness since it could matter if the team ever considers an unlisted, ultra-low-cost hosting fallback. In practice the chosen host is **self-managed PostgreSQL on Windows Server (ADR-0005)**, where the team installs and controls Postgres directly, so this budget-tier tooling concern does not apply to the actual deployment.

## Alternatives Considered

### 1. Stay on MySQL/MariaDB with JSON columns and application-level-only tenant scoping — **Rejected**

This is the "do nothing different" option: keep the legacy engine, store the flexible submission payload in a MySQL `JSON` column (as legacy already does for `ocr_data`), and enforce tenant isolation purely through Eloquent global scopes and disciplined query review, exactly as legacy enforced its (weaker, single-tenant) invariants.

**Why it was rejected:**
- **No RLS equivalent.** MySQL and MariaDB have no native row-level security. The nearest workarounds — `DEFINER`-scoped views, stored-procedure gatekeeping, or trigger-based enforcement — are all bolted-on, harder to reason about, harder to test, and easy to bypass via a forgotten code path or a new raw query. For a multi-tenant SaaS product where a cross-tenant leak is a severe trust and (potentially) compliance failure, "the application always remembers" is not an acceptable sole control, and legacy's own `users.id === 1` incident is direct evidence that "the application always remembers" is not a safe assumption to build a new product on.
- **No PostGIS-equivalent maturity.** MySQL/MariaDB spatial extensions exist but lag PostGIS significantly in geometry/topology operators, validity checking, and spatial indexing maturity — insufficient for the committed `geopoint`/`geotrace`/`geoshape` Phase 2 roadmap item.
- **Weaker JSON indexing story.** MySQL's `JSON` type supports indexing only via generated/virtual columns tied to a specific, pre-declared JSON path — not a general-purpose inverted index over arbitrary keys. This directly undermines the JSONB-hybrid submission model (§2.2), which needs to support ad hoc, tenant-defined field schemas efficiently without a schema migration every time a new field becomes "the one we need to filter on."
- **MariaDB specifically** was also considered as a MySQL-compatible alternative (Galera clustering, dynamic columns) but shares the same two structural gaps — no RLS, no PostGIS-caliber spatial support — so it does not change the conclusion.

This alternative would have avoided the "team must learn new Postgres ops knowledge" cost named in Consequences above, but at the cost of every positive consequence listed — an unacceptable trade for a product whose core bets are multi-tenant safety, geo field types, and a flexible-but-queryable submission model.

### 2. Polyglot persistence — Postgres for core relational data, plus a document database (e.g., MongoDB) for submission payloads — **Rejected**

Considered briefly because submission answers are semi-structured. Rejected because it introduces a second datastore, a second set of operational skills, and a second failure domain for no compensating benefit once JSONB + GIN already gives Postgres a first-class semi-structured-query story. It would also fragment transactional integrity between the relational core (tenants, forms, versions) and the submission payload, undermining the plan's explicit preference for one unified `SubmissionPipeline` with a single transactional persist step (§2.2). Not consistent with the plan's "start simple, add complexity only when justified" theme.

### 3. Distributed/NewSQL engine (e.g., CockroachDB, Yugabyte) for future horizontal scale — **Rejected for now**

Considered as a hedge against future multi-region/high-scale needs. Rejected at this stage as premature complexity: this is an MVP-stage greenfield product, none of the plan's Phase 0–2 scale targets require distributed-SQL guarantees, the RLS/PostGIS/JSONB ecosystem maturity on these engines lags vanilla Postgres, and the hosting shortlist (§1) is built around standard managed Postgres. If genuine multi-region write-scaling needs emerge (Phase 4, "dedicated-DB tenancy option" / "data-residency options"), that should be evaluated as its own future ADR against real, measured scale data — not decided speculatively now.

### 4. Defer the decision to a Phase 0 spike, decide per-subsystem as needed — **Rejected**

Considered because the plan explicitly timeboxes a Phase 0 spike for the *form-rendering engine* (SurveyJS/Form.io vs. custom) and asks that decision be made via ADR after a spike rather than by default. The same approach was considered for the database engine. Rejected because, unlike the rendering-engine choice, the database decision is a **structural prerequisite** for Phase 0 itself — RLS policies and the `form_versions` draft/publish model must be designed into the very first migrations, and multi-tenancy is explicitly called out as a system-wide constraint enforced from the first line of infrastructure code (§2.1, §3 Phase 0). Deferring this decision would leave Phase 0 unable to start on solid ground, whereas the rendering-engine choice only affects the builder/runtime UI layer built on top of an already-settled data layer.

## Notes on Assumptions Made Where the Plan Was Silent

The architecture plan is explicit that PostgreSQL is the chosen database and names the specific reasons (JSONB+GIN, RLS, PostGIS) but does not pin an exact version, extension list, or collation/case-sensitivity handling. To keep this ADR concrete and actionable rather than leaving genuine open questions as "TBD," the following reasonable, plan-consistent decisions were made explicitly for this document and should be treated as the working default until revisited:

- **PostgreSQL 16+** as the minimum supported version across all environments (concrete floor chosen to guarantee full JSONB/GIN/RLS/PostGIS-3.x compatibility; not stated as an exact version in the plan itself).
- **`citext`** for the specific columns needing case-insensitive uniqueness (form share slugs, user email) — a direct, necessary consequence of Postgres's case-sensitive default collation versus MySQL's typically case-insensitive one, called out because it is a legacy behavior that would otherwise silently change.
- **`pgcrypto`/native `gen_random_uuid()`** for UUID generation, needed for `client_submission_uuid` (offline-sync idempotency, §2.4 of the plan) and generally preferred over serial IDs for any client-generated or externally-exposed identifier.
- **`pg_trgm`** noted as an available, not-yet-required option for fuzzy text search, since the plan does not specify a search implementation.
- **PgBouncer or an equivalent managed connection pooler** as a required infrastructure component, called out explicitly here because it is a direct, non-optional consequence of choosing Postgres that the plan's tech-stack table does not separately itemize.

Any of the above may be superseded by a more specific future ADR (e.g., a dedicated ADR on connection pooling/infra sizing, or the JSONB-hybrid-vs-EAV ADR referenced in §4 item 7 of the plan) without reopening this decision's core conclusion: **PostgreSQL, not MySQL/MariaDB, is this project's primary database.**
