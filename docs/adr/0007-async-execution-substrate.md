# ADR-0007: Async Execution Substrate (queues, workers, scheduler, tenant context)

## Status

**Accepted — 2026-07-21.** Phase 3 (Increment H) is the first phase in which asynchronous work is load-bearing: six of its twelve verticals dispatch jobs, and every rollup, reaper and sweep it introduces is **cross-tenant** — a pattern with no precedent anywhere in the codebase. Auditing the foundation those features were to be built on found it substantially thinner than four documents claim, and found one **live defect that two documents describe as already mitigated**. **Decision: run the queue on the `database` driver over the existing Postgres with a plain `queue:work` worker and no Horizon; route all tenant-scoped work through a `TenantAwareJob` base class that re-establishes RLS context under a runtime payload assertion; express cross-tenant work exclusively as a `MaintenanceJob` that holds no tenant context and whose only side effect is fanning out one `TenantAwareJob` per tenant; and reset the process-lifetime tenant statics on both edges of every job.** This closes Risk **R6** (per-tenant fairness) in §9 of the Technical Architecture Doc and unblocks **H2**, the first code increment of Phase 3.

- **Deciders:** Founding engineering (architecture owner) + product.
- **Related ADRs:** **ADR-0002** (multi-tenancy via shared DB + RLS — its §D3 makes the queue an explicit enforcement layer and its §D6 promises a job-payload gate that was never built; this ADR discharges both), **ADR-0005** (self-hosted Windows Server — its Memurai/Horizon rows are **superseded in part** here), and **ADR-0001** (PostgreSQL — the `database` queue driver and the fairness limiter both land on the instance it chose). Depends on ADR-0002 for correctness; it *operationalizes* §D3's job row and *narrows* ADR-0005's runtime topology.
- **Related docs:** `docs/architecture/technical-architecture.md` §5/§7.4/§9 (the layer table, webhook reliability, and Risks R6/R9); `docs/deployment-infrastructure.md` §6/§8 (the five-queue catalog and the Windows service topology); `docs/security-threat-model.md` (the worker-context leak row); `docs/observability-incident-response.md` (queue metrics, now known to be Horizon-mediated and therefore unbuilt); `docs/non-functional-requirements.md` (per-tenant limiting, no longer deferred); PROGRESS.md Phase-3 decomposition (H1a → H2).

---

## Context

Phase 3 commits to a visual workflow builder, save-and-resume, queued PDF generation, scheduled forms, webhook delivery with a retry ladder, native integrations, and two OCR channels. Every one of those either dispatches jobs or is driven by a scheduler. Before designing any of them, the async substrate they assume was audited against source. **The substrate is almost entirely prose.**

1. **Exactly one queued job exists.** `app/Jobs/ScanAttachmentJob.php` is the only `ShouldQueue` class in the repository. It is `final` (`:28`) and defines **none** of `$queue`, `$tries`, `$backoff`, `$timeout`, `failed()` or `middleware()` — it is 68 lines with a constructor, `handle()`, and a placeholder `scan()`. Yet its `handle()` (`:40-58`) already contains the seed of the whole contract, and its docblock (`:23-26`) already states the rule this ADR must generalize: *"a queue worker has no ambient request GUC, so the update must run inside `DB::transaction` or RLS would scope it to zero rows."*

2. **Nothing consumes the queue.** `docker-compose.yml` defines `app`, `web`, `postgres`, `redis`, `mailpit` and `node` — **no worker service and no scheduler service**. The only committed worker invocation in the repository is `queue:listen --tries=1 --timeout=0` inside `composer.json`'s `dev` script (`:59`). Outside `QUEUE_CONNECTION=sync`, `jobs` rows accumulate forever and nothing reserves them.

3. **The scheduler does not exist.** `routes/console.php` is 8 lines of stock `inspire`; `bootstrap/app.php` (314 lines) has no `withSchedule`; there is no `app/Console/` directory. **Four documents assert a live scheduler.** The most direct is `docs/feature-backlog.md:85`, which states outright that *"Enabling infra (scheduler + email + async export) already exists."* None of the three does.

4. **Zero named queues in code.** `onQueue(` has **no hits repository-wide**, against a five-name catalog (`submissions`, `webhooks`, `exports`, `ocr-processing`, `scheduled-maintenance`) documented as binding in `docs/deployment-infrastructure.md` §6 (`:73-76`) and mirrored in `docs/observability-incident-response.md:32`.

5. **The supporting stack is absent or unused.** No Horizon (`laravel/horizon` is in neither `composer.json` nor `composer.lock`); no Redis composer package and **no Redis-backed queue in use** — Redis exists in the infrastructure (`docker-compose.yml:50-53`, `docker/Dockerfile:19-20`, `config/queue.php:67-74`) but nothing routes work through it; **no first-party outbound HTTP call site** (`Http::`, `GuzzleHttp`, `curl_init` have zero hits in `app/`, though guzzle is present transitively at `composer.lock:802`); and no `app/Mail` directory. `composer.json` has 9 `require` entries. `deploy.ps1:49-54` restarts NSSM services `meridian-horizon` and `meridian-reverb` behind a `Get-Service … -ErrorAction SilentlyContinue` guard — a silent no-op on a box that has neither.

6. **The sharpest finding — a live defect two documents call mitigated.** `TenantContext::$tenantId` is a **process-lifetime PHP static** (`app/Support/Tenancy/TenantContext.php:39`). `applyLocal()` (`:46-49`) makes only the *database* GUC transaction-scoped; the private `set()` it delegates to assigns the static unconditionally at `:108-109` and nothing rolls it back. A `flush()` exists (`:86-90`) but is documented for test isolation and is called by no job. There is **no `Queue::before`/`Queue::after`/`JobProcessing`/`JobProcessed` listener anywhere in the repository**. So on a long-lived `queue:work` worker, once `ScanAttachmentJob` commits, the DB GUC is NULL while the static still holds tenant A — and the next context-less job gets `BelongsToTenant` injecting `tenant_id = A` into its reads and auto-filling `tenant_id = A` on `creating`, while RLS sees NULL. Reads return zero rows; inserts fail with a confusing `QueryException`. Both **ADR-0002 `:125`** and **`docs/security-threat-model.md` §3** describe this as *"fails fast (explicit exception)"*. **It does not fail fast today** — it fails obscurely, and only escapes notice because no second job type exists. Phase 3 adds a dozen.

7. **The gate ADR-0002 §D6 promised was never built.** `:151` commits to *"a static check (or a runtime assertion in the base job class)"* that every queued job handling tenant-scoped data declares a `tenant_id`. Neither exists: there is no base job class, and `scripts/controller-gate.php:29` targets only `app/Http/Controllers`.

8. **Risk R6 carries three mutually contradictory commitments.** `docs/architecture/technical-architecture.md:522` mitigates R6 by citing §7.4 — but §7.4 (`:475-487`) is *webhook reliability* and contains no rate-limit mechanism at all, making the pointer dangling. `:373` claims *"rate-limiter buckets are per-tenant, never global"*, which is untrue: `app/Providers/AppServiceProvider.php:105-127` keys every limiter on token-hash or IP. And `docs/non-functional-requirements.md:48` defers per-tenant limiting to "Phase 2–3 … not before."

**The core tension:** the documented substrate (Redis + Horizon + Task Scheduler + five prioritized queues + per-tenant fairness) is a coherent design that is **installed nowhere, exercised by nothing, and unverifiable in CI** — so building Phase 3 against it would land a second layer of untested prose on top of the first. But the austere alternative — keep improvising per job, as `ScanAttachmentJob` does — does not scale past one job and leaves a real cross-tenant leak in the one place the threat model says is closed. This ADR must choose a substrate that is **buildable and CI-verifiable this phase**, while stating honestly which parts of the inherited design are being deferred rather than delivered.

## Options on the table

**Queue backend:**
1. **`database` driver on the existing Postgres, plain `queue:work`** — zero new infrastructure, works identically in local Docker, CI and on the Windows box, and is testable in CI today.
2. **Redis (Memurai on Windows) + Horizon** — the inherited ADR-0005 design. Per-queue dashboards, better throughput, mature fairness tooling; but nothing is installed, Memurai is unverified, and Horizon's dashboard is a cross-tenant surface with no auth story here.
3. **SQS or another managed broker** — contradicts ADR-0005's self-hosted posture and adds a recurring bill and an external dependency.

**Tenant context on the worker:**
1. **Per-job improvisation** — each job does what `ScanAttachmentJob` does, by convention. Status quo.
2. **A `TenantAwareJob` base class + a worker-edge flush listener** — context re-establishment and teardown become structural, enforced by a runtime assertion plus a lint gate.
3. **A global queue middleware that infers tenant from the payload** — implicit, and silently does the wrong thing for a job that legitimately has no tenant.

**Cross-tenant work:**
1. **A job that iterates tenants and switches context inside one transaction** — not expressible: the GUC is a scalar and `TenantIsolation`'s predicate is flat equality (`TenantIsolation::tenantMatch()` in `app/Support/Tenancy/TenantIsolation.php` — cited by symbol, because the line range this used to carry was already wrong before M8 grew the file) with no set or any-tenant mode.
2. **A `MaintenanceJob` that holds no context, touches only RLS-exempt tables, and fans out one child per tenant** — one shape, auditable, and consistent with the standing rule at `docs/architecture/technical-architecture.md:184` that a scheduled task *"dispatches to the queue rather than running inline."*
3. **Raw `pgsql_superadmin` sweeps** — bypasses RLS wholesale; appropriate only for the RLS-free tables (§D12), never as the general pattern.

---

## Decision drivers

- **CI-verifiability outranks throughput.** Every increment in this project is gated on six CI jobs. A substrate CI cannot exercise is a substrate that regresses silently — which is precisely how the current gap was created.
- **Nothing may depend on software that is not installed.** ADR-0005's Memurai/Horizon rows have been prose for three phases and have already produced one dead artifact (`deploy.ps1:49-54`). Adding more would repeat the failure, not fix it.
- **The tenant boundary is the product's core invariant.** ADR-0002 makes RLS the enforcement authority; anything that can silently place a worker in the wrong tenant is a security defect, not an ergonomics issue.
- **Cross-tenant is a new capability, not a variation.** It needs its own named shape with its own rules, or it will be improvised per feature.
- **The ADR must distinguish what it delivers from what it defers.** The corpus's current problem is documents asserting built capability. Every unbuilt element named here is labelled unbuilt.
- **Assumptions must be labelled as assumptions.** Nothing has ever consumed this queue, so no throughput data exists. Any number chosen here is a planning assumption carrying a revisit trigger.

---

## Decision

> **Queue = the `database` driver on the existing Postgres, driven by a plain `queue:work` process; no Horizon, no Redis-backed queue. Tenant-scoped work = `TenantAwareJob`, which asserts its payload carries a uuid `tenantId`, re-establishes RLS and Spatie team context, and runs inside `DB::transaction`. Cross-tenant work = `MaintenanceJob`, which holds no tenant context, may read only RLS-exempt tables, and whose sole side effect is dispatching one `TenantAwareJob` per active tenant. Both edges of every job flush the process-lifetime tenant statics.** The five inherited queue names become binding on code. Per-tenant fairness is job middleware, not HTTP middleware, and introduces no new table.

| Concern | Choice |
|---|---|
| Queue backend | **`database` driver on Postgres** (`config/queue.php`), plain `php artisan queue:work`. Supersedes-in-part ADR-0005 rows `:27-28`. |
| Worker supervision | Dev: a new compose `worker` service. Track B: an NSSM service — **not currently provisioned by `deploy.ps1`**, recorded as a gap. |
| Scheduler | `Schedule::job(...)` declarations in `routes/console.php` (the Laravel 11+ idiom — no `withSchedule` closure, no `app/Console/Kernel.php`). Dev: a compose `scheduler` service. Track B: Windows Task Scheduler — **not currently provisioned**. |
| Tenant-scoped work | `TenantAwareJob` (§D2) — payload assertion, RLS + Spatie context, `DB::transaction`. |
| Cross-tenant work | `MaintenanceJob` (§D3) — no context, RLS-exempt tables only, fan-out per tenant. |
| Context hygiene | A `Queue::before`/`Queue::after` listener flushing `TenantContext` and the Spatie team id on **both** edges (§D4). |
| Fairness | `RateLimited` job middleware keyed `tenant:{id}:queue:{name}` (§D9); state in the cache store, **no new table** (§D10). |
| Observability | Structured `failed()` logging (§D12). Dashboards deferred with Horizon. |

### The thirteen sub-decisions

- **D1 — Queue backend: the `database` driver on Postgres, plain `queue:work`, no Horizon.** This **supersedes in part** [ADR-0005](0005-hosting-self-hosted-windows-server.md) rows `:27` (Redis via Memurai as the queue backend) and `:28` (`php artisan horizon` as an NSSM service); the rest of ADR-0005 — nginx, PHP 8.4, PostgreSQL, Reverb, TLS, storage, the self-hosted-runner deploy — remains fully in force. Rationale: nothing is installed, nothing is CI-verifiable, and depending on it would land as untested prose exactly the way `docs/deployment-infrastructure.md` §6 already did. The `database` driver runs identically in local Docker, on Linux CI and on the Windows box, and puts the queue under the same backup and RLS-aware operational story as everything else. **Redis + Horizon is named as a documented, non-blocking upgrade path**, not a rejection: the migration is a connection change plus a supervisor swap, and jobs written against this ADR need no edit. **Revisit trigger:** sustained queue depth that a single `queue:work` cannot drain, or the point at which per-queue observability becomes load-bearing rather than nice to have (see §When to Revisit).

- **D2 — `TenantAwareJob`: the single-tenant base class.** Generalizes the pattern `ScanAttachmentJob` improvises. Its contract, in order: (a) the payload carries a **non-nullable `string $tenantId`**; (b) `handle()` opens with a **runtime assertion** that it is a non-empty uuid, throwing a named exception on failure — **this is the "fails fast (explicit exception)" that ADR-0002 §D3 (`:125`) already promises and §D6 (`:151`) already requires, finally delivered**; (c) the tenant is re-resolved as the **first** act, before any tenant-scoped query; (d) work runs inside `DB::transaction` → `TenantContext::applyLocal()`, because `applyLocal` is transaction-scoped and a worker has no ambient request GUC. It **also** sets Spatie's `setPermissionsTeamId()`, which `app/Http/Middleware/EstablishTenantDatabaseContext.php:52` sets on the HTTP path (resetting at `:65` on terminate) and **no job sets today** — without it any job calling `hasPermissionTo()` fails closed, a bug that cannot surface until a job checks a permission. `ScanAttachmentJob` is refitted onto this base in H2.

- **D3 — `MaintenanceJob`: the cross-tenant base class.** Runs with **no tenant context**; may touch only RLS-exempt tables (`tenants`, `domains`, and — when it exists — `plans`); its sole side effect is **dispatching one `TenantAwareJob` child per tenant**. A cross-tenant transaction is *not expressible* in this architecture and the ADR states so explicitly: the GUC is a scalar and `TenantIsolation`'s predicate is flat equality (`tenantMatch()`), with no set or any-tenant mode — the only widenings are `nullableGlobal` (SELECT-only), the role-gated `superAdminBypassSql`, and (since M8) the role-gated `authRoleReadSql`, none of which is a tenant set. ⚠️ Cited by SYMBOL: this sentence carried three bare line ranges into `TenantIsolation.php` that were already wrong before M8 grew that file by +54, and re-numbering them would only have bought the next author the same surprise. `Tenant` is RLS-exempt and does not use `BelongsToTenant` (`app/Models/Tenant.php:27-29`; also in `scripts/migration-lint.php:34`'s exempt list), so `Tenant::query()->where('status', Active)->cursor()` is legal with no GUC set. This satisfies the standing rule at `docs/architecture/technical-architecture.md:184` that a scheduled task *"dispatches to the queue rather than running inline."*

- **D4 — Worker context hygiene: flush on both edges.** A `Queue::before`/`Queue::after` (equivalently `JobProcessing`/`JobProcessed`) listener calls `TenantContext::flush()` and `setPermissionsTeamId(null)` on **both** edges of every job.
  > **Corrected in H2 (as-built).** Two details of this decision were wrong against laravel/framework 13.18.1 and are superseded by `App\Listeners\Queue\ScopeTenantContextToJob`:
  > **(a) the after-edge is `JobAttempted`, not `JobProcessed`.** `Worker::process()` raises `JobProcessed` on the **success path only** (`:561`) and diverts to `handleJobException()` on a throw; it dispatches `JobAttempted` from the `finally` (`:566-570`). A listener on `JobProcessed` therefore leaks the tenant static out of **every job that throws or is released** — the exact defect §Context 6 describes, merely relocated. Proven by mutation: implementing this decision literally fails `WorkerContextHygieneTest`'s "clean after a job that THREW" and only that test.
  > **(b) it saves and restores; it does not flush.** Under `QUEUE_CONNECTION=sync` — every CI job — `SyncQueue` raises these events **inline in the caller's stack**, so a blind flush wipes the ambient request context mid-request and breaks the dispatching code. A LIFO save/restore stack is correct under both a worker (saved value null ⇒ restore *is* flush) and sync. Deliberately **not** gated on `connectionName`: that would make the listener dead code in every CI job, which is the unverifiability this ADR was written to end. `flush()` already exists for exactly this purpose (`TenantContext.php:86-90`) and is currently called by no job. Flushing *before* means a job cannot free-ride on a predecessor's leftover static; flushing *after* means a completed job leaves the worker clean even if it threw. This is the decision that closes the Context §6 defect and makes ADR-0002 `:125` and `docs/security-threat-model.md` §3 **true rather than aspirational** — both documents are corrected in this same increment to cite this mechanism rather than assert an unbuilt one.

- **D5 — Payload rule: scalar ids only, never Eloquent models.** Job payloads carry uuid strings plus `tenantId`. The reason is mechanical, not stylistic: `SerializesModels::__unserialize` runs inside `CallQueuedHandler::call` — **before `handle()`**, and therefore before any base-class context re-establishment — on a worker whose GUC is NULL, so `restoreModel()` finds zero rows under RLS and throws `ModelNotFoundException` as a **permanent** failure. The trait stays (inert and idiomatic once no model properties exist), but model-typed properties are forbidden. **The `$deleteWhenMissingModels` interaction is stated explicitly** so a future author cannot "fix" that failure by flipping it to `true`: doing so would convert a loud RLS-visibility signal into a job that silently deletes itself, i.e. silent data loss in place of an error.

- **D6 — Queue taxonomy: the five inherited names, now binding on code.** Adopt `submissions`, `webhooks`, `exports`, `ocr-processing` and `scheduled-maintenance` **verbatim** from `docs/deployment-infrastructure.md` §6 (`:73-76`) and `docs/observability-incident-response.md:32`.
  > **Corrected in H2 (as-built): a job declares its queue with `#[Queue(QueueName::X)]`, never a `$queue` property.** "Every job MUST declare `$queue`" is not implementable as written — `Illuminate\Bus\Queueable:29` declares `public $queue;` **untyped**, so redeclaring it with a different initial value is a **fatal error** in any class using that trait. The framework's `Illuminate\Queue\Attributes\Queue` accepts a `UnitEnum`, is read first by `Dispatcher::pushCommandToQueue()`, and is inherited from a parent class — so `MaintenanceJob` names its queue once for every sweep. It is also *more* statically checkable than a string literal: `scripts/job-payload-lint.php` asserts a `ClassConstFetch` on `App\Enums\QueueName`, needing no cross-class constant evaluation.

  They cease to be prose: **every job MUST declare its queue**, `default` remains only the un-annotated fallback, and `ScanAttachmentJob → submissions`. Priority order is expressed as the `--queue=` ordering string in the documented `queue:work` invocation until a supervisor with real per-queue weighting exists. This is what makes `onQueue(`'s current zero hit-count a lint-checkable condition rather than an observation.

- **D7 — Retry, backoff and timeout.**
  > **Corrected in H2 (as-built): `TenantAwareJob` declares NO `$tries`.** `$tries = 3` **inverts §D9**. `RateLimited` enforces a ceiling by calling `$job->release()`, and `DatabaseQueue::release()` (`:328`) re-pushes the row **preserving the already-incremented `attempts`** — so three fairness *deferrals* send the job to `failed_jobs`, turning "this tenant is being throttled" into "this tenant's jobs permanently failed". Replaced by `retryUntil()` (time-based, blind to releases) + `$maxExceptions = 3` (counts only genuine exceptions); `backoff()`/`$timeout` stand as written. Proven by mutation: `$tries = 3` with no `retryUntil()` fails `QueueFairnessTest`'s deferral-survival case. Note also that once `retryUntil()` is non-null, `maxTries` is **dead code** in the worker, so a `$tries` left alongside it would be documentation that lies. **Caveat inherited:** `retryUntil` is frozen at dispatch and does not slide across releases, so a job born into a backlog deeper than `queue-fairness.retry_window_hours` fails on its first pop.
  > **Also corrected: `MaintenanceJob`'s overlap lock needs `->dontRelease()`.** `WithoutOverlapping`'s constructor defaults `$releaseAfter` to `0`, **not null**, so with `$tries = 1` the first overlapping tick fails the sweep within milliseconds instead of skipping it.

  Original text: `$tries = 3`; `backoff() => [30, 120, 600]` with jitter, satisfying `docs/architecture/technical-architecture.md:481`'s requirement that retries are *"never a naive immediate re-queue loop"*; `$timeout = 60`, with `retry_after` raised **90 → 120** (`config/queue.php:43`) so that `timeout < retry_after` holds — otherwise the queue can hand the same job to a second worker while the first is still running it. `MaintenanceJob` takes `$tries = 1` plus `WithoutOverlapping` keyed on class name: a scheduler tick that overlaps a still-running sweep must not double the fan-out. **Named revisit:** those overlap locks land in Postgres `cache_locks`, on the same instance as `jobs` — acceptable at this scale, and a reason to revisit if lock contention appears.

- **D8 — `after_commit => true`.** Today `after_commit` is `false` (`config/queue.php:44`) and `app/Services/Attachments/AttachmentStorageService.php:82` dispatches `ScanAttachmentJob` with no enclosing transaction at that level — so a worker can reserve the job before the attachment row is visible, hit `$attachment === null`, take the early return at `ScanAttachmentJob:47-49`, and leave `virus_scan_status` stuck at `pending` **forever**. It is structurally untestable under `QUEUE_CONNECTION=sync`, which is every current CI job, which is why it has never surfaced. **The ruling is made here; the one-line config change is implemented in H2** — a config flip belongs with the code, but the decision belongs in the ADR, and stating both together is what stops it being lost between the two.

- **D9 — Per-tenant job-rate ceiling (closes R6).** **Job middleware** (`RateLimited`) keyed `tenant:{id}:queue:{name}`, counting **job executions started, per tenant, per queue, per minute** — not HTTP requests, not rows. Chosen over HTTP middleware (wrong layer: it throttles requests, not work, and the work outlives the request), over a counter table (see §D10), and over Horizon's fairness tooling (unavailable per §D1). It is the only candidate that **defers** excess work rather than rejecting it, which is the correct semantics for a queue. Ceilings live in a new `config/queue-fairness.php` with a plan-tier override hook and **no Cashier dependency** (neither `laravel/cashier` nor `stripe/stripe-php` is installed, and payments are deferred to Phase 4). **The values are unvalidated planning assumptions** — nothing has ever consumed this queue, so no throughput data exists; they are labelled as such in the config file itself and carry the revisit trigger below. This replaces R6's dangling `§7.4` citation at `docs/architecture/technical-architecture.md:522`, and supersedes the inaccurate claim at `:373` that limiter buckets are already per-tenant (they key on token-hash/IP — `app/Providers/AppServiceProvider.php:105-127`).

- **D10 — No new tables.** Ceiling and lock state live in the limiter/cache store, never in a bespoke table. This is decisive rather than aesthetic: a `job_rate_*` table carrying a literal `tenant_id` **will** trip `scripts/migration-lint.php`'s isolation rule (`:105-117`), and both escapes are worse than the problem. Calling `withTenantIsolation()` on it would put RLS policy evaluation in the hot path of every job reservation — a self-inflicted instance of Risk R9. Adding an `EXEMPT_TABLES` entry (`:33-42`) would repeat the `failed_jobs` hazard of tenant identifiers living in an RLS-free table, which per ADR-0002 §D2 requires ADR-level justification. For the avoidance of doubt: `jobs`, `job_batches` and `failed_jobs` are already exempt at `:40` and declare no `tenant_id`, so the queue's own tables cannot trip the linter.

- **D11 — Forbidden connections.** The `deferred`, `background` and `failover` connections shipped in `config/queue.php:76-90` are **out of bounds for tenant-scoped work**. The `deferred` connection is the dangerous one: a job runs in-process after the response, where the HTTP session GUC is *still live* — so a job that correctly re-establishes context and one that silently free-rides on ambient request context become **indistinguishable in testing**, and `applyLocal()` overwrites the process static without restoring it, corrupting the terminating request. They are annotated as forbidden in config; deleting them outright is the cleaner option and is left to H2's judgment.

- **D12 — Failure surfacing.** Every `TenantAwareJob` implements `failed(Throwable)` logging structured context `{job, tenant_id, queue, attempts, exception_class}`, and **never re-enters tenant context** — by the time `failed()` runs, the database is frequently the thing that just failed, so re-establishing a GUC is both unreliable and a way to turn one failure into two. A `MaintenanceJob` sweeps `failed_jobs` older than N days on `scheduled-maintenance`. A tenant-facing failure **UI** is deferred, but the ADR records the constraint that governs it whenever it is built: `failed_jobs` is an RLS-free table, so any tenant-facing view of it is a **cross-tenant read**, sanctioned only via `pgsql_superadmin` + `superadmin_bypass`, never by a tenant-scoped query. **No document states this today.**

- **D13 — Tenant lifecycle inside jobs.**
  > **Corrected in H2 (as-built) — this one was a live footgun.** The status test below reads naturally as `$tenant->status !== TenantStatus::Active`, but `tenants.status` is a stancl virtual-column attribute that is **explicitly not cast** (`app/Models/Tenant.php`, `app/Enums/TenantStatus.php` both say so) — it is a plain `?string`. Comparing it to an enum **object** is therefore **always true**, which would release-then-delete **every job for every tenant on the platform**: a silent, total queue outage that no existing test would have caught. H2 adds `Tenant::isActive()` and `Tenant::scopeActive()` (comparing `TenantStatus::Active->value` / `tryFrom()`, matching `SuperAdminService`) so §D3's fan-out and §D13's guard share one definition. `TenantLifecycleInJobsTest`'s active-tenant case is the mutation guard.
  > **Load-bearing coupling:** `scopeActive()` is only real SQL while `'status'` remains in `Tenant::getCustomColumns()`. Remove it and stancl relocates the value into the `data` json column, at which point the predicate matches **nothing** — pinned by `JobContractTest`.

  Tenant row missing ⇒ `$this->delete()` plus an info log, not a failure (a job for a hard-deleted tenant is correctly a no-op, and failing it would fill `failed_jobs` with noise). Tenant `status !== Active` ⇒ `release()` with backoff for a bounded window, then `delete()` — a suspension is usually temporary, but must not retry forever. `MaintenanceJob` filters to Active at enumeration, so suspended tenants are never fanned out to in the first place. **Explicit non-goal:** request-path suspension enforcement. Today `tenants.status` is read by **no** middleware, policy or RLS predicate, so a suspended tenant's queued work — and its HTTP traffic — runs normally. This ADR names that gap rather than silently inheriting it, and does not close it; the queue-side handling above is not a substitute for the request-side control.

**Companion CI gate.** ADR-0002 §D6 (`:151`) promises *"a static check (or a runtime assertion in the base job class)"* and neither exists — `scripts/controller-gate.php:29` targets only `app/Http/Controllers`. This is discharged **twice over**: by the §D2 runtime assertion, and by a small `scripts/job-payload-lint.php` added to `composer run quality` asserting that every `ShouldQueue` class either extends `TenantAwareJob` or is explicitly annotated cross-tenant. Belt and braces is deliberate here — the assertion catches a wrong payload at runtime, the linter catches a wrong *base class* before merge.

**Scheduler wiring, three tiers.** Schedules are declared in `routes/console.php` via `Schedule::job(...)` (the Laravel 11+ idiom — no `withSchedule` closure, no `app/Console/Kernel.php`), each dispatching a job and never running work inline. **Dev:** new `worker` and `scheduler` compose services on the existing `php:8.4-fpm-alpine` image, which already has `pcntl`. **CI:** the existing suites keep `QUEUE_CONNECTION=sync`; **one** integration test drives a real `queue:work --once` under `QUEUE_CONNECTION=database` to prove serialize → enqueue → reserve → unserialize → context-re-entry — the one path `sync` can never exercise, and therefore the only test that can catch a regression in §D2/§D4/§D5. **Track B:** `deploy.ps1` provisions **no** Task Scheduler task and **no** worker service; this is recorded as a named gap in `docs/deployment-infrastructure.md` §8 rather than assumed capability.

**Method note.** This ADR is a **source audit plus design**, not a spike: no prototype was built and no throughput was measured, so — unlike ADR-0006 — it carries no weighted scorecard, because there is nothing measured to score and a rubric here would manufacture precision that does not exist. What *is* evidence is the as-is inventory in §Context: every claim of the form "X exists" or "X does not exist" was grepped against source at authoring time, and several inherited claims were refuted in the process (notably the `horizon:terminate` step that `deploy.ps1` does not perform, and the assertion that limiter buckets are already per-tenant). What is *reasoning* is everything downstream of that: the choice of the `database` driver, the two base-class shapes, and above all the §D9 ceiling values, which are **unvalidated planning assumptions on a queue that has never been consumed**. The §D8 `after_commit` defect and the §6 stale-static defect were both derived by reading the framework's execution order rather than by observing a failure — they are structurally untestable under `sync`, which is why H2's single `database`-driver integration test matters more than its line count suggests.

## Consequences (chosen path: **`database` queue + `TenantAwareJob` / `MaintenanceJob`**)

### Positive
- **A live cross-tenant leak is closed.** The §D4 flush listener plus the §D2 assertion make ADR-0002 `:125` and `docs/security-threat-model.md` §3 accurate for the first time, instead of describing a mitigation that was never implemented.
- **Risk R6 is resolved with a real mechanism.** The dangling `§7.4` pointer is replaced by §D9, and the contradiction between `:373` (claims per-tenant) and `AppServiceProvider:105-127` (keys on token-hash/IP) is recorded rather than left to mislead.
- **Everything is CI-verifiable.** The `database` driver runs on Linux CI, local Docker and the Windows box identically; the one `queue:work --once` integration test covers the whole serialize/reserve/context path that `sync` structurally cannot.
- **Cross-tenant work gets one auditable shape.** `MaintenanceJob` makes "which code may run without a tenant" a reviewable property of a class rather than a per-feature judgment call, before twelve verticals each invent their own.
- **No new infrastructure and no new tables.** No Memurai to install, no Horizon to secure, and nothing that trips the migration linter or puts RLS in the job-reservation hot path.
- **ADR-0002 §D6's promised gate finally exists**, and the five-name queue catalog stops being prose.

### Negative / accepted trade-offs
- **No queue dashboard.** Horizon's per-queue depth/throughput views are deferred with Horizon, so `docs/observability-incident-response.md`'s queue metrics remain unbuilt; §D12's structured logging is the interim contract, and it is strictly less than what that document currently implies.
- **`database`-driver throughput is lower than Redis.** Job reservation is a Postgres row lock on the same instance serving application traffic. Acceptable at Phase-3 scale; explicitly a revisit trigger, not a permanent posture.
- **ADR-0005 is now partially superseded**, which is a documentation state this project has not used before (only whole-ADR supersession, ADR-0005→ADR-0003). It costs a scoping annotation on two rows and the discipline to keep it accurate.
- **The §D9 ceilings are guesses.** They will be wrong in one direction or the other on first contact with real traffic; the mitigation is that they are labelled as assumptions and live in config, not code.
- **Track B gains two named gaps** — no worker service and no scheduler task are provisioned by `deploy.ps1`. Standing up the Windows box now requires more than the existing script performs.
- **Suspension enforcement stays open.** §D13 handles suspended tenants queue-side but explicitly does not close the request-path gap, so `tenants.status` remains read by no middleware, policy or RLS predicate.

### Risks & Mitigations
| Risk | Mitigation |
|---|---|
| `database`-driver contention degrades application queries under load | Single `queue:work` at Phase-3 scale; monitor `jobs` table growth; the Redis+Horizon upgrade path is a connection change plus a supervisor swap, with jobs unmodified |
| A future job bypasses `TenantAwareJob` and reintroduces the context leak | Two independent gates — the §D2 runtime uuid assertion and `scripts/job-payload-lint.php` in `composer run quality`; the §D4 listener also flushes *before* each job, so a bypassing job fails closed rather than inheriting context |
| The §D4 listener is registered but silently stops firing | Covered by the `queue:work --once` integration test, which asserts context re-entry rather than merely job completion |
| §D9 ceilings set wrong — too low starves a tenant, too high defeats the purpose | Values in `config/queue-fairness.php`, labelled unvalidated, tunable without a deploy of code; revisit on first real traffic |
| Overlap locks in `cache_locks` contend with `jobs` on one instance | `MaintenanceJob` uses `$tries = 1` + `WithoutOverlapping` keyed on class name; named as a revisit trigger in §D7 |
| A future author flips `$deleteWhenMissingModels` to silence `ModelNotFoundException` | §D5 states the interaction and its consequence (silent data loss replacing a leak signal) explicitly, so the change cannot be made unknowingly |
| Track B is stood up without a worker or scheduler, so nothing drains the queue in production | Recorded as a named gap in `docs/deployment-infrastructure.md` §8 item 7 and in ADR-0005 `:30`, not as assumed capability |

## Alternatives Considered
- **Redis (Memurai) + Horizon, as ADR-0005 specifies** — genuinely better at throughput, per-queue observability and fairness, and it remains the intended destination. Rejected *for now* because none of it is installed, Memurai on Windows Server 2016 is unverified, Horizon's dashboard is a cross-tenant surface with no auth story in this codebase, and adopting it would put Phase 3 on infrastructure CI cannot exercise. Named as the upgrade path in §D1 rather than as a rejected option.
- **A managed broker (SQS or similar)** — rejected: it contradicts ADR-0005's self-hosted posture, adds a recurring bill the project chose self-hosting to avoid, and introduces an external dependency for a queue that currently handles one job type.
- **Per-job improvisation (status quo)** — what `ScanAttachmentJob` does, and adequate for exactly one job. Rejected: it is what produced the §6 leak, it cannot be linted, and Phase 3 adds a dozen jobs plus the first cross-tenant work in the codebase.
- **HTTP middleware for per-tenant fairness** — rejected as the wrong layer. It throttles requests, whereas the resource under contention is worker time; a single request can enqueue a great deal of work, and scheduled fan-out has no request at all.
- **A `job_rate_*` counter table** — rejected per §D10: it trips the migration linter, and both escapes (RLS in the reservation hot path, or an exempt table holding tenant identifiers) are worse than keeping the state in the cache store.
- **Inferring tenant from the payload via global queue middleware** — rejected: implicit, and it cannot distinguish a job that legitimately has no tenant from one that forgot its `tenantId`, which is exactly the distinction §D2 and §D3 exist to make explicit.

## When to Revisit
- **When sustained queue depth exceeds what one `queue:work` process drains**, or job latency becomes user-visible — move to Redis/Memurai + Horizon per §D1. Jobs need no change; it is a connection and supervision swap.
- **When per-queue observability becomes load-bearing** — i.e. when §D12's structured logs stop being enough to answer "why is `ocr-processing` behind" — adopt Horizon, or build the metrics `docs/observability-incident-response.md` already assumes.
- **On first real traffic against the §D9 ceilings** — retune `config/queue-fairness.php` against measured throughput and replace the "unvalidated assumption" label with data.
- **If `cache_locks` contention appears** between `WithoutOverlapping` locks and job reservation on the same Postgres instance — move locks to a separate store, or revisit §D1.
- **When Track B is stood up** — the worker service and the scheduler task must be provisioned as part of that work, since `deploy.ps1` does not do it today.
- **When request-path tenant-suspension enforcement is designed** — §D13's queue-side handling should be revisited alongside it so the two agree.
- **If payments return in Phase 4** — §D9's plan-tier override hook is the intended integration point, and the hidden-field/untrusted-input constraint recorded for H7 becomes relevant to amount handling.
