# ADR-0009: OAuth Connector Token Custody (encryption at rest, central-domain callback, signed `state`, refresh & revocation)

## Status

**Accepted — 2026-07-27.** Phase 3's next vertical (H15) is the **native-connector framework** — Slack first, Google Sheets and Airtable behind it (H16) — and it inverts the trust direction of every outbound integration the platform has shipped so far. A webhook is a credential the *tenant* gave *us* to prove our payloads are ours (`webhook_endpoints.secret`, HMAC-signed, blast radius = "someone can forge deliveries to a URL the tenant chose"). An OAuth connector is a credential the *third party* gave *us* to act as the tenant: leaking one escalates to **"the tenant's Slack workspace is compromised."** Today the repo has no OAuth code, no OAuth client library (`composer.json` has neither `laravel/socialite` nor `league/oauth2-client`), no `connections` table, no third-party-credential row in the threat model, and exactly one app-owned `encrypted` cast to learn from. It also has a topology problem the design must solve before any of that is written: tenants live on subdomains, an OAuth app registers **one fixed redirect URI**, and this application's session cookie is **host-only**, so the callback lands on a host that has neither a session nor a tenant. **Decision: hold connector credentials as `encrypted`-cast `text` columns on a strict-RLS `connections` table that no API surface ever returns in any form, masked or not; land every provider callback on the single central domain; carry tenant + user identity through the OAuth `state` parameter as a signed, domain-separated, short-TTL HMAC token that a pre-RLS middleware verifies before any tenant GUC is set; derive the post-callback return host from the `domains` table rather than echoing anything from the request; refresh tokens proactively on the `MaintenanceJob` fan-out substrate and never lazily inside a delivery attempt; and treat disconnect as "local tokens are destroyed unconditionally, provider revocation is best-effort."** This unblocks **H15a** (the connector framework + Slack backend) and, transitively, H15b and H16.

- **Deciders:** Founding engineering (architecture owner) + product.
- **Related ADRs:** **ADR-0002** (multi-tenancy via shared DB + RLS — `connections` is an ordinary strict-RLS tenant table, and §D4 below exists solely because a central-domain request has *no* tenant GUC, so an INSERT under FORCE RLS would silently write zero rows). **ADR-0007** (async execution — the token-refresh sweep is a cross-tenant `MaintenanceJob` fan-out under its §D3, and connector deliveries ride its `TenantAwareJob` contract and §D9 fairness limiter). **ADR-0008** (entitlement & metering — its §D7 already ratified `native_connectors` as one Starter+ flag key, so this ADR inherits the gate rather than coining one). **ADR-0009 was originally earmarked for payments**, which product cancelled out of Phase 3 (`PROGRESS.md` decision 2; `docs/adr/0008-entitlement-and-metering.md:8`, `:152`); that ADR was never written, so the number is taken here rather than left as a permanent hole. It depends on ADR-0002 for correctness and *narrows* ADR-0007's outbound-HTTP surface from "one call site" to "one call site plus a provider adapter."
- **Related docs:** `docs/webhook-integration-design.md` §4 (`:56-64`, the phased native-connector list — Slack is row 3, "a dedicated OAuth-based connector … built as its own small service on top of the same underlying event catalog (§3), not a replacement for it") and §6 (`:79`, which explicitly defers the connectors' own auth-flow design to Phase 3 — i.e. to here); `docs/pricing-feature-gating-matrix.md` §3 (`:47`, `:60` — `native_connectors` Starter+ uniformly); `docs/security-threat-model.md` §2/§5/§9 (the attack-surface inventory and residual-risk list this ADR extends); `docs/data-privacy-gdpr-compliance.md` §7 (`:70`, the sub-processor list a connector adds to); `docs/audit-compliance-logging-spec.md` §1–§2 (the auditable-type catalog and the unconditional-redaction list); `docs/data-dictionary.md` §14–§15 (the webhook pair whose shape `connections` follows).

## Context

The H-map sequences this ADR **immediately before** H15a and after the whole webhook vertical (H13a/H13b/H14) is merged, which is deliberate: the webhook engine is the closest built analogue, so the as-is evidence below is unusually concrete — most of the mechanisms this ADR rules on exist in the repo already, just not for this purpose.

1. **There is exactly one app-owned encryption-at-rest precedent, and it comes with a schema trap.** `app/Models/WebhookEndpoint.php:89-90` casts `secret` and `secret_previous` as `encrypted`, with both listed in `$hidden` (`:81`). The columns are `text`, not `varchar(255)`, and the migration says why: "the model `encrypted` cast inflates even a short secret to ~290 chars (base64(JSON{iv,value,mac})), so the data-dictionary's varchar(255) — which assumed plaintext — cannot hold the at-rest form" (`database/migrations/2026_07_26_000002_create_webhook_endpoints_table.php:38-41`). An OAuth access token is longer than a webhook secret before encryption, so this is not a marginal call.

2. **Audit redaction is a hand-maintained registry keyed by auditable-type alias.** `app/Support/Audit/AuditRedactor.php:34-39` holds `SECRETS` — `'webhook_endpoint' => ['secret', 'secret_previous']` and three siblings — and `docs/audit-compliance-logging-spec.md:29-35` states the list is "Always redacted, unconditionally … Not tenant-configurable." A new credential-bearing auditable type that is *not* added to that map is silently un-redacted; nothing detects the omission.

3. **The session cookie is host-only, so a central-domain callback cannot see a tenant session.** `config/session.php:159` reads `env('SESSION_DOMAIN')`, and both `.env.example:59` and the working local `.env:56` set it to `null` — a host-only cookie, bound to the exact host that set it. A session established at `acme.meridian.test` is therefore **not** sent to `meridian.test`. **Two comments in the repo claim the opposite** — `routes/tenant.php:49` and `routes/admin.php:15` both say "session established centrally; SESSION_DOMAIN spans subdomains" — and they are wrong against the config they describe. (The standing corpus lesson applies verbatim: prose describes intent, config and code describe reality. Practice agrees with the config, not the comments: `playwright.config.ts` logs in at the tenant subdomain and captures `storageState` there.)

4. **The one existing central-domain route group runs with no tenant context at all.** `routes/admin.php:24` is the super-admin console, `Route::domain((string) config('tenancy.central_domain'))`, and its header states the property outright: "The console runs with NO tenant context (it is cross-tenant by nature)." `app/Http/Middleware/EstablishTenantDatabaseContext.php:74-83` confirms the mechanism — tenant resolution "returns null on the central domain, where no tenant is bound." Under FORCE RLS with `app.current_tenant_id` unset, an INSERT into a tenant table matches no policy and writes **zero rows, without erroring**. Any callback that writes a credential must therefore establish context explicitly, from something it can trust.

5. **The platform already has a proven "host-agnostic request that still gets a correct tenant GUC" mechanism.** API Group C (`routes/api.php:283-292`) deliberately carries neither `web` nor `PreventAccessFromCentralDomains`; the tenant comes from a signed token verified by middleware **before** any context is applied (`app/Http/Middleware/EstablishGuestDraftContext.php:37-52`, paired with `TenantContext::forget()` in `terminate()`). The token service (`app/Support/Guest/GuestShareTokenService.php:182-232`) recomputes the MAC over the received body with `hash_equals` and decodes **after** verification, so "any tamper flips the signature and 401s before the payload is even decoded, and long before any RLS tenant context is set." Its two keys are domain-separated derivations of `APP_KEY` (`app/Providers/AppServiceProvider.php:51-70`), each independently overridable for rotation.

6. **Redirecting back to the tenant after the callback is an open-redirect question, and there is already a right answer in the repo.** H9b faced the same "build an absolute URL on the tenant's own host from a context that isn't on it" problem and solved it by reading the `domains` table, never the request: `app/Http/Controllers/Public/GuestDraftController.php:117-124`.

7. **The threat model has no row for a stored third-party credential.** `docs/security-threat-model.md` §5 covers webhook forgery (`:68`), replay (`:69`), SSRF (`:70`) and secret leakage (`:71`) — all about a secret the *tenant* holds. §2's attack-surface inventory lists "Outbound webhooks | Tenant-configured third-party endpoints | Platform → external, not inbound"; there is no surface row for an inbound third-party callback, and no residual-risk entry (§9) for a credential whose compromise reaches outside the platform.

8. **Laravel's encryption-key rotation seam exists, and what is missing is the procedure.** `config/app.php`'s `previous_keys` entry populates from `APP_PREVIOUS_KEYS`. Rotating `APP_KEY` without populating it silently makes every `encrypted` column unreadable — at authoring time that was two webhook secrets; after H15a it is every tenant's live workspace credential. ⚠️ **Corrected by Increment M46 (2026-08-29): this bullet said the variable "appears in no `.env.example` block and in no document".** It is declared in `.env.example` with a warning naming this exact failure and citing §D9, and it is discussed in this ADR and in `docs/security-threat-model.md`. **The gap that survives is a written rotation runbook** — `docs/deployment-infrastructure.md` lists the secrets that live in the server's hand-maintained `.env` and its key-rotation section defers the connector lane as still open. The old citation `config/app.php:99-106` was also wrong by the time it was read: that range is the locale block. **Cited by key name here rather than by line, because a line number in a config file is a pointer with a shelf life.**

9. **The gate and its flag already exist and are unused.** `native_connectors` is seeded into `PlanCatalog` (`database/seeders/Data/PlanCatalog.php:34`, enabled from Starter at `:54`) and ratified Starter+ uniformly by ADR-0008 §D7 / `docs/pricing-feature-gating-matrix.md:47`, `:60`. Nothing consumes it: there is no `feature:native_connectors` usage anywhere. This ADR coins no new gate.

**The core tension:** the mechanism that makes an OAuth connector valuable — the platform holding a durable credential that lets it act inside the tenant's workspace — is the same mechanism that makes it the highest-blast-radius secret in the system, and the deployment topology forces the most sensitive step of its acquisition (the callback) onto the one host that has neither a session to authenticate the user nor a tenant context to scope the write. The tempting fixes are both wrong: widening `SESSION_DOMAIN` to span subdomains would make every tenant's session cookie visible to every other tenant's host to solve a problem that occurs twice per connection, and inferring the tenant from a query parameter would let anyone write a credential into any tenant. This ADR instead reuses the mechanism the platform already proved for exactly this shape of problem — a signed, domain-separated token verified pre-RLS — and spends its remaining decisions on what happens to the credential afterwards.

## Options on the table

**Callback topology:**
1. **One central-domain callback for all tenants** — a single registered redirect URI per provider; the callback carries the tenant in `state`. Works with every provider; costs one context-adoption mechanism.
2. **Per-tenant subdomain callbacks** — `https://acme.meridian.test/oauth/slack/callback`, so the session and tenant are both already present. Requires registering a redirect URI per tenant with every provider; Slack and Google do not accept wildcard hosts. Unshippable at more than a handful of tenants.
3. **Central callback that redirects to the subdomain to complete the exchange** — the `code` becomes a URL parameter on a second hop, i.e. an authorization code in a referrer-leakable, log-visible location. Strictly worse than (1) for no gain.

**Carrying tenant + user across the host boundary:**
1. **A signed, domain-separated HMAC `state` token** (the `GuestShareToken` shape) — stateless, verifiable pre-RLS, tamper-evident, self-expiring.
2. **A widened `SESSION_DOMAIN`** so the tenant session is readable centrally — one config line, and it makes every tenant's session cookie a cross-host artifact permanently.
3. **A server-side `oauth_states` table** keyed by an opaque nonce — enables single-use replay protection, at the cost of a table, a reaper, and a write on a path that must work before any tenant context exists.

**Token storage:**
1. **`encrypted`-cast `text` columns on a strict-RLS tenant table** — the `webhook_endpoints.secret` precedent, one mechanism to reason about.
2. **Plaintext columns, relying on RLS + disk encryption** — RLS does not protect against a leaked backup or an over-broad `SELECT` in a support tool.
3. **An external secret manager (Vault/KMS)** — stronger key custody, but a new production dependency on a self-hosted single-box deployment (ADR-0005) that does not have one, and nothing in CI can exercise it.

---

## Decision drivers

- **Blast radius, not convenience, sets the storage rules.** A leaked connector token is authority inside someone else's SaaS tenancy. Every ergonomic affordance the webhook secret gets (revealed once, masked suffix in the API) is refused here unless it survives that reframing.
- **Reuse the mechanism the platform already proved.** The signed-token-verified-pre-RLS pattern is built, tested, and understood (guest share + resume tokens). A second, subtly different scheme for the same shape of problem is how invariants drift.
- **Never widen a boundary to solve a narrow problem.** The callback needs tenant identity twice per connection; that is not a reason to make session cookies cross-host for every request forever.
- **Fail closed, and write nothing when unsure.** A tampered, expired, or provider-mismatched `state` must be refused before any tenant GUC is set — never "best-effort resolve the tenant and continue."
- **Refresh is a scheduled concern, not a request-path concern.** A token refreshed lazily inside a delivery attempt turns a provider outage into a thundering herd and a partial write inside a delivery transaction.
- **Deferrals are labelled.** The corpus's standing problem is documents asserting built capability; every narrowing here (no nonce store, no secret manager, `APP_PREVIOUS_KEYS` undocumented) is named, not implied.

---

## Decision

> **Connector credentials live on a strict-RLS `connections` table as `encrypted`-cast `text` columns, hidden on the model and never returned by any API, presenter, or audit payload — not even masked. Every provider's OAuth callback lands on the single central domain at `/oauth/{provider}/callback`, outside the `web` middleware group, and carries tenant + user identity in a signed, domain-separated, ~10-minute HMAC `state` token that a pre-RLS middleware verifies before applying the tenant GUC and forgets in `terminate()`. The post-callback return host is derived from the `domains` table and the outcome is handed back as a query parameter, because the central host cannot set a tenant-session flash. Tokens are refreshed proactively by a cross-tenant `MaintenanceJob` fan-out with a configurable lead time, never lazily inside a delivery attempt; a refresh rejection marks the connection dead and notifies the tenant owner instead of retrying forever. Disconnect destroys the local credential unconditionally and calls the provider's revoke endpoint best-effort. Scopes are least-privilege and stored for display; app credentials live only in `.env`; every connect, refresh-failure, and disconnect is audited under a new `connection` alias with both token columns in the unconditional redaction list.** This ADR is docs-only; H15a builds the framework and the Slack provider, H15b the UI, H16 the remaining providers.

| Concern | Choice |
|---|---|
| Token storage | **`encrypted`-cast `text` on strict-RLS `connections`**, `$hidden`, never returned in any form (§D1). |
| Callback topology | **One central-domain callback per provider**, no session, no CSRF token, outside `web` (§D2). |
| Tenant/user across hosts | **Signed, domain-separated, short-TTL HMAC `state`**, provider-bound (§D3). |
| RLS context on the callback | **Adopted from the verified `state`, pre-RLS**, forgotten in `terminate()` (§D4). |
| Return to the tenant | **Host from the `domains` table; outcome as a query parameter**, never an echoed redirect target (§D5). |
| Refresh | **Proactive `MaintenanceJob` fan-out with lead time**; never lazy, never inside a delivery (§D6). |
| Revocation / disconnect | **Local destruction is unconditional; provider revoke is best-effort** (§D7). |
| Scopes | **Least-privilege, stored on the row** for display and re-consent detection (§D8). |
| App credentials | **`.env` only**, never in the database, never per-tenant; `APP_PREVIOUS_KEYS` gap recorded (§D9). |
| Audit | New **`connection` alias**, both token columns unconditionally redacted (§D10). |

### The ten sub-decisions

- **D1 — Credentials are `encrypted`-cast `text`, hidden, and never returned.** `connections.access_token` and `connections.refresh_token` follow the `webhook_endpoints.secret` precedent exactly: `text` columns (never `varchar` — the cast inflates the value past 255 chars, §Context 1), the `encrypted` cast, and both names in the model's `$hidden`. The deliberate **divergence** from the webhook secret is that there is **no reveal-once and no masked suffix**: a webhook secret is shown once because the tenant must configure their receiver with it, whereas a connector token has no user-facing purpose whatsoever — the platform is its only consumer — so no API resource, Inertia presenter, or audit payload emits it in any form. `ConnectionResource` exposes provider, account label, scopes, status and expiry; a test asserting the tokens are absent from every response is the guard. **Revisit trigger:** a provider requiring the tenant to paste the token elsewhere (none of Slack/Sheets/Airtable does).

- **D2 — The callback lands on the central domain, outside `web`.** One registered redirect URI per provider, `https://{central}/oauth/{provider}/callback`, with the host read from `config('tenancy.central_domain')` (not `env()` — the `routes/admin.php:24` precedent exists because a raw `env()` call does not survive `route:cache`). Per-tenant redirect URIs are unshippable: Slack and Google require exact, pre-registered URIs and reject wildcard hosts. The route group carries **no `web` middleware** — a third-party GET arriving from an external redirect has no session and no CSRF token, and demanding either would break the flow, not secure it; CSRF protection for this hop is `state` (§D3), which is what the OAuth spec assigns it to. It also carries no `PreventAccessFromCentralDomains`, mirroring API Group C. **Revisit trigger:** a provider that supports per-tenant or wildcard redirect registration, or the platform moving to per-tenant custom domains for the app itself (Business-tier `custom_domain` covers public forms, not the admin app).

  > **⚠ EXTENDED BY J3c2 (2026-08-14) — §D2 NOW BINDS A FLOW THAT IS NOT A CONNECTOR.** First-party Google
  > sign-in takes the same topology for the same reason: Google rejects wildcard redirect URIs for an
  > identity client exactly as it does for a Sheets client, so there is one registered callback on the
  > central domain. **What it does NOT take is `web`-less-ness.** A connector callback only writes a row;
  > a sign-in callback must be able to *establish a session* on the central host (the central arm of the
  > flow signs in there directly), so `/auth/google/callback` carries `web`. That is a divergence, not an
  > oversight: the CSRF argument §D2 makes still holds — the hop is protected by `state`, and a top-level
  > GET carries no CSRF token to check — but the response needs a session cookie the connector flow never
  > wanted. ⚠️ And it deliberately declares **no `Route::domain()`**, unlike `routes/connectors.php`:
  > `routes/web.php:12-17` records that `config('tenancy.central_domain')` does not match `localhost`
  > locally, and J3c2 must be exercisable against its fake on a dev box. `RequirePlatformHost` is what
  > keeps a tenant custom domain from serving it, and Fortify's own `'domain' => null` is the precedent.

- **D3 — `state` is a signed, domain-separated, provider-bound HMAC token, not a session nonce.** It reuses the `GuestShareTokenService` wire format (`v1.<base64url(payload)>.<base64url(mac)>`, constant-time compare, decode-after-verify) with a **third** independently-rotatable key derived as `hash_hmac('sha256', 'connector-oauth-state.v1', APP_KEY)` and overridable by config, exactly as the share and resume keys are (`app/Providers/AppServiceProvider.php:51-70`). Claims: `{tid, uid, prov, nonce, exp}` — the tenant it may write into, the user who started the flow (recorded as `connected_by` and used for the audit actor), the provider it is valid for, a random nonce for uniqueness, and a **~10-minute expiry** (an interactive consent screen, not a 24-hour share link). `prov` is load-bearing: it prevents a state minted for one provider's flow being replayed against another provider's callback. **Accepted narrowing: `state` is stateless, so it is replayable within its TTL.** Replay is bounded by the provider's authorization `code` being single-use — a replayed callback fails at the token exchange — and the consequence of a successful replay would be re-writing the same tenant's own connection. A server-side single-use nonce store was rejected as a table plus a reaper on a path that must work before any tenant context exists. **Revisit trigger:** a provider with non-single-use codes, or a flow where the callback has a side effect beyond writing the connection it names.

  > **⚠ EXTENDED BY H16c (2026-08-13): the state token now has a SECOND job — it is also the seed for the PKCE `code_verifier`.** Airtable requires PKCE, and this ADR's two-hosts-two-requests topology leaves nowhere to remember a verifier between the halves; `ConnectorOAuthStateService::codeVerifierFor()` derives one under the same key, domain-separated by prefix. **Consequence to keep in mind before changing anything here:** the state token is now load-bearing for a provider's token exchange, not only for tenant identity, so altering its wire format, its TTL or its key derivation breaks in-flight Airtable consents as well as in-flight identity claims. The full argument, including why deriving from a value the attacker can see is still sound, is in §When to Revisit.

  > **⚠ AMENDED BY J3c2 (2026-08-14) — §D3's OWN REVISIT TRIGGER HAS FIRED, AND IT FIRED AGAINST ONE OF
  > TWO LEGS RATHER THAN THE WHOLE FLOW.** The trigger reads "a flow where the callback has a side effect
  > beyond writing the connection it names". **A sign-in establishes a session — the largest side effect in
  > the application** — so the stateless-`state` reasoning cannot carry it unchanged. ADR-0016 already made
  > this argument once, at
  > `database/migrations/2026_08_14_000002_create_sso_auth_requests_table.php:15-26`: *an HMAC proves WE
  > MINTED a token; it cannot prove the token has not been presented before. Single-use IS replay
  > protection, single-use requires remembering, and remembering requires a store.*
  >
  > **But the split is finer than "so J3c2 needs a store".** The Google flow has two hops that could be
  > replayed, and only one of them creates the session. The **`state`** on the outbound leg stays a
  > stateless HMAC of exactly this shape — replaying it only re-opens a consent screen, and the
  > authorization `code` behind it is single-use at Google, which is §D3's existing bound. The **handoff**
  > from the central callback back to the tenant host is what carries the flow into a session, and *that*
  > is a database row with a hashed, 60-second, single-use token redeemed by a conditional UPDATE whose
  > affected-row count is the check. So §D3 is not overturned; it is **scoped to the leg it was always
  > describing**, and the nonce store it named as the eventual fix exists as the handoff row.
  >
  > ⚠️ **The central-host arm of J3c2 has no handoff at all and therefore no row**, and that is a
  > consequence of RLS rather than a shortcut: `TenantIsolation::nullableGlobalSql()` widens SELECT only —
  > *"every write stays strict: a tenant connection cannot create/alter a global row"* — so a tenant-less
  > row is unwritable on the app connection. It needs no hop because callback and session share a host,
  > and its replay bound is Google's single-use `code` plus the state's own expiry, which is precisely
  > §D3's original bargain.

- **D4 — Tenant context is adopted from the verified `state`, before RLS, and forgotten on terminate.** A dedicated middleware — the `EstablishGuestDraftContext` shape (`app/Http/Middleware/EstablishGuestDraftContext.php:37-52`) — verifies `state`, then calls `TenantContext::apply(tenantId, userId)`, stashes the decoded claims on the request, and pairs the session-scoped apply with `TenantContext::forget()` in `terminate()` so context can never survive onto a pooled connection (ADR-0002 §D2). The tenant is **never** inferred from the request host (there isn't one — it is the central domain, §Context 4) and **never** read from an unverified parameter. A tampered, expired, or provider-mismatched state throws before any GUC is set; the rendered outcome is a redirect to `config('app.url')` with no indication of whether the named tenant exists (the `superadmin` non-disclosure posture). Because the user id is carried too, the callback's audit entry names a real actor rather than a system write. **Revisit trigger:** any second central-domain route that writes tenant data — it must reuse this middleware, not re-derive context.

  > **⚠ THE §D4 TRIGGER FIRED TOO (J3c2, 2026-08-14), AND THE ANSWER IS A SIBLING RATHER THAN A REUSE.**
  > `/auth/google/callback` is exactly the "second central-domain route that writes tenant data" this
  > trigger names, and it does adopt context from a verified `state` with a `terminate()` that forgets —
  > the shape is copied deliberately. It is a **separate class** because strip
  > `ConnectorProviderKey` resolution and `ConnectorOAuthStateService` out of
  > `EstablishConnectorOauthContext` and nothing provider-agnostic is left: the two share a pattern, not a
  > body. Recorded here so the divergence reads as a decision rather than as drift.

- **D5 — The return host comes from the `domains` table; the outcome is a query parameter.** After the exchange the callback redirects to `https://{tenant host}/integrations?connected={provider}` (or `?connect_error={code}`), with the host read from the tenant's `domains` row — the `GuestDraftController::resumeUrl` precedent (`:117-124`) — and **never** echoed from the request or from a `ret`-style claim in the state payload. That is what closes the open-redirect: even a validly-signed state cannot steer the browser anywhere but the tenant's own host. The outcome rides a **query parameter rather than a session flash** because the central host cannot write the tenant host's session cookie (§Context 3); the receiving page reads the parameter and renders the toast (H15b). **Revisit trigger:** if a tenant may hold multiple domains, the choice of which to return to becomes a real decision rather than "the one row."

- **D6 — Refresh is proactive, scheduled, and provider-driven.** A cross-tenant `MaintenanceJob` fan-out (ADR-0007 §D3) sweeps connections whose `token_expires_at` falls inside a configurable lead window and whose provider issued a refresh token, refreshing them ahead of expiry. It is explicitly **not** lazy: refreshing inside a delivery attempt would put a second outbound call and a credential write inside the delivery transaction, and would let a provider outage stampede every queued delivery at once. A provider that issues non-expiring tokens (Slack's default, absent token rotation) simply has a null expiry and is skipped — the sweep exists for the framework, and Google Sheets (H16a) is its first heavy user. A refresh rejection (`invalid_grant` and friends) marks the connection dead rather than retrying indefinitely, stops its subscriptions delivering, and queues **one** owner notification on the H3 mail substrate (the `WebhookAutoDisabledNotification` edge-triggered recipe). **Revisit trigger:** a provider whose tokens expire faster than the sweep interval, which would force a lazy pre-flight refresh after all.

  > **⚠ AMENDED BY H16a (2026-08-05) — THIS §D6 REVISIT TRIGGER FIRED.** Google's access tokens live **~1 hour** against an **hourly** sweep, so a grant minted just after one sweep and delivered against before the next is dead on arrival, and no retuning of the sweep interval closes a window that a single missed run reopens. The amendment is **narrow and additive, not a reversal**: the sweep remains the mechanism, and `ConnectionTokenRefresher::ensureFresh()` is a **guard on top of it**, called by `DeliverConnectorMessageJob` before each attempt and returning immediately unless the token is already expired or inside `connectors.delivery_refresh_lead_seconds` (**120s**, versus the sweep's 7200s). A healthy connection therefore never reaches it, and the stampede this clause warns about now requires the sweep to have failed first rather than being one provider outage away permanently. `ensureFresh()` reuses `refresh()`, so there is still exactly one place that writes a credential and decides a grant is dead.
  >
  > **Two corrections this amendment also carries, both found by building it.** **(1) "A refresh rejection marks the connection dead" was implemented as *any* `ConnectorOAuthException`, including a transport timeout** — so one unreachable moment at a provider's token endpoint would clear both tokens, pause every rule and require a human to re-run OAuth. Unreachable through H15a (Slack's tokens never expire, so nothing refreshed); reachable on every Google delivery from H16a. The exception now carries a `$terminal` flag the adapter sets, and only a terminal code marks the grant dead. **(2) A provider API's own 401 is NOT evidence the grant is dead.** Google returns `authError` / "Invalid Credentials" for an expired access token and a revoked grant alike; only the token endpoint distinguishes them, by answering `invalid_grant`. `GoogleSheetsConnector` therefore classifies 401 as *retryable*, and the naive mapping would have revoked a live connection roughly once an hour.

  > **⚠ AMENDED BY M6 (2026-08-19) — §D6's OTHER HALF, WHICH H16a DID NOT ANSWER.** §D6 named the hazard of a lazy refresh in two parts: the **stampede** (many queued deliveries refreshing at once) and the **credential write in the delivery path**. H16a answered the first — the pre-flight only fires inside a 120s window, so a stampede needs the sweep to have failed first — and left the second standing. It is the more serious half.
  >
  > **A TOKEN REFRESH IS AN IRREVERSIBLE SIDE EFFECT AT THE PROVIDER, AND IT WAS BEING PERFORMED INSIDE A TRANSACTION THAT COULD UNDO OUR HALF OF IT.** Airtable returns a new access+refresh pair on every renewal and **invalidates the previous pair**, so the instant its token endpoint answers, the credential still stored in `connections` is dead. Both callers ran that exchange inside a `TenantAwareJob` transaction that went on to do more work: the sweep batched **every due connection for a tenant** into one, and the delivery job refreshed as a pre-flight and then made up to three further outbound calls. **Any later throw — including the job's 60s `$timeout`, which several due Airtable grants can genuinely reach at 5s connect + 10s read apiece — rolled our write back while the provider stayed rotated.** The next sweep then presented a destroyed refresh token, was answered `invalid_grant`, and that is terminal by §D6's own rule: the grant is marked dead, its tokens cleared, every rule on it paused and the owner emailed. **The batching is what made it plural — one slow run could kill every Airtable grant a tenant had.**
  >
  > **THE DECISION: A ROTATION OWNS A TRANSACTION THAT CONTAINS NOTHING ELSE.** `RefreshOneConnectionJob` renews exactly one grant; the base class still opens the transaction, because that is where RLS scoping comes from (`SET LOCAL`), but its entire body is "write the grant we were just handed" and it commits before the job returns. `sweep()` becomes a dispatcher rather than a rotator, and the delivery path **hands the rotation off and defers one ladder step** instead of performing it — H16a's reasoning for pre-flighting at all is unchanged and still right; only the place the irreversible call happens has moved.
  >
  > **AND THE LOCK, WHICH IS A DIFFERENT DEFECT WITH THE SAME CURE.** `ensureFresh()` was a plain read-check-then-refresh with no lock, so two workers could spend the SAME rotating refresh token: the first wins, the second is answered `invalid_grant` and kills a healthy grant. Latent only because `docker-compose.yml` runs exactly one `queue:work` — and that same line names more workers as the scaling path, so it was latent by deployment accident rather than by design. One connection, one lock holder, taken **without waiting**: a concurrent refresh of the same grant is not work to queue behind, it is work already being done.
  >
  > ⚠️ **WHAT IS NARROWED RATHER THAN CLOSED.** The window between the provider committing the rotation and us committing the write is now one UPDATE wide instead of a whole batch, but it is not zero — a database failure in exactly that gap still loses a rotated token. Closing it entirely needs a two-phase protocol no provider here offers. **Revisit trigger:** a provider that supports either a rotation the client can confirm, or a grace period in which the previous refresh token still works.
  >
  > ➕ **ONE THING THIS AMENDMENT FIXED THAT §D6 NEVER NAMED.** Moving the pre-flight out exposed a latent loop: a delivery against a revoked grant was returned from silently, leaving its `next_retry_at` set and `attempt_count` untouched, so `WebhookRetrySweeper`'s `attempt_count < max_attempts` predicate stayed true and it was re-dispatched every five minutes for the life of the row. It had been masked because the pre-flight caught the revocation one attempt earlier and dead-lettered it. The guard now checks the **grant before the rule**, because the two are different kinds of thing: a dead grant is terminal and is settled, a paused rule is reversible and stays silent so an un-pause resumes its queued deliveries.

- **D7 — Disconnect destroys the local credential unconditionally; provider revocation is best-effort.** The order is: call the provider's revoke endpoint, ignore its outcome, then clear both token columns, mark the connection revoked, and soft-delete it. Inverting that order — or making local destruction conditional on a successful revoke — would leave a live token in the database whenever the provider is unreachable, which is precisely when a tenant is most likely to be disconnecting. The delivery history in the shared ledger survives the disconnect (soft delete), because a tenant's outbound-delivery record is operational history, not credential material. **Revisit trigger:** a compliance requirement to prove provider-side revocation succeeded, which would need a verification retry rather than best-effort.

- **D8 — Least-privilege scopes, stored on the row.** Each provider adapter requests the narrowest scope set that supports the connector's actual function — for Slack, posting to a chosen channel and listing channels for the picker (`chat:write`, `channels:read`), never message-history or user-data read scopes. The granted scopes are stored on the connection so the UI can show what was authorized and so a later scope expansion is detectable as "this connection needs re-consent" instead of failing opaquely at delivery. Scope sets live in `config/`, not in code, so tightening them is an operational change. **Revisit trigger:** any feature that wants to *read* from the provider (Sheets' drift detection, H16a) — that is a genuine scope expansion and a re-consent event, to be decided there.

  > **⚠ AMENDED BY H16a (2026-08-05) — THIS §D8 REVISIT TRIGGER FIRED, and the answer is narrower than the trigger implied.** Drift detection must read the destination's header row before appending, so Google Sheets is the framework's first provider with a read scope. It requests **`https://www.googleapis.com/auth/drive.file` and nothing else** — per-file access to spreadsheets this app created or the tenant explicitly picked. Verified against Google's own scope table at implementation time (per this ADR's method note): `drive.file` is classified **Recommended, Non-sensitive** for the Sheets API, while `spreadsheets` is **Sensitive** and `drive.readonly` is **Restricted**. Adding `spreadsheets` would therefore have granted "see, edit, create and delete *all* your spreadsheets" *and* moved this app into Google's sensitive-scope verification tier, in exchange for nothing `drive.file` does not already permit on a file the tenant chose. So the "genuine scope expansion" this clause anticipated is real in kind but minimal in degree, and no user-data or identity scope was taken.
  >
  > **Two consequences are accepted rather than worked around.** Per-file access means we **cannot enumerate** a tenant's existing spreadsheets server-side, so Google Sheets registers **no `channel_lister`** — the registry's null-not-throw contract already covers "this provider offers no picker", and a real picker is H16b's (client-side Google Picker). And because no identity scope is taken, `external_account_id` is a constant, so the `connections_tenant_provider_account_unique` partial index allows a tenant exactly **one live Google connection**; connecting a second Google account replaces the first rather than sitting beside it. Lifting that narrowing means buying an identity scope, which is its own re-consent decision.

  > **⚠ AMENDED BY H16b (2026-08-12) — "A REAL PICKER IS H16b's (CLIENT-SIDE GOOGLE PICKER)" WAS WRONG, AND `config/connectors.php` HAD ALREADY SAID SO.** H16b ships **no client-side Google Picker**. That clause was written as an aside and became a plan of record by repetition; the config file's own note, written in the very same increment, states the real alternative — *"the destination is created by us or named by id"*. Only the first half of that actually works, and it is what H16b built.
  >
  > **Why the Picker was rejected, on evidence rather than preference.** It needs a **browser API key** the tenant must mint in Google Cloud Console — an input only the user possesses, which is the definition of a blocked row under the standing build rule — and it would be **the app's first third-party script** (`apis.google.com` plus Google Identity Services). `FormBotChallenge`'s docblock already records that exact trade being refused for reCAPTCHA / Turnstile / hCaptcha: a key only the user holds, plus `script-src` and `frame-src` additions to a CSP whose test asserts the *absence* of those directives as a deliberate tripwire. Taking the opposite decision here, for a convenience rather than a capability, would contradict a rule this codebase already applies.
  >
  > **What replaced it, and why it is strictly better under this scope.** `spreadsheets.create` **is permitted under `drive.file`** — the scope covers "specific Drive files you use with this app", and a file this app created is one of them permanently. So the platform creates the spreadsheet and writes its header row (`GoogleSheetsDirectory::create()`), making the destination reachable **by construction** rather than by hoping the tenant pastes an id we happen to already hold a grant on. The "named by id" half survives as a secondary path with server-side verification at SETUP time, so an unreachable sheet fails in the form the tenant is standing in rather than at delivery, where `blocked` pauses the rule and reads as an outage.
  >
  > **The Picker is not ruled out forever** — it becomes the natural "use a sheet I already have" path the day an API key exists. A future row with a named prerequisite, not a silent drop.

- **D9 — App credentials live in `.env` only; the key-rotation gap is recorded.** A provider's `client_id`/`client_secret` are platform-wide, not per-tenant, and are never stored in the database — they join the hand-maintained server `.env` list in `docs/deployment-infrastructure.md`'s environment-secrets bullet. They are deliberately kept out of `config/services.php`'s stock `slack` block, which is Laravel's unrelated log-notification channel, to prevent the two being conflated. Separately and importantly: **every stored connector token is encrypted under `APP_KEY`, and `config/app.php`'s `previous_keys` entry supports rotation.** ⚠️ **Corrected by Increment M46 (2026-08-29): this bullet said `APP_PREVIOUS_KEYS` is "documented nowhere".** It is declared in `.env.example` with an inline warning citing this sub-decision. **The fix this ADR assigned was two things and only one of them is still owed** — the `.env.example` entry landed; the **documented rotation procedure has not**, and `docs/deployment-infrastructure.md`'s key-rotation section explicitly defers the connector lane. Rotating `APP_KEY` without populating the variable still silently bricks every connection at once, in a way that surfaces as mass delivery failure rather than as a decryption error at boot. **Revisit trigger:** the first real `APP_KEY` rotation, or any move to an external key manager.

- **D10 — Connect, refresh-failure, and disconnect are audited under a new `connection` alias.** The H4 `AuditLogger` records each event with `auditable_type = 'connection'`, and both `access_token` and `refresh_token` are added to `AuditRedactor::SECRETS` under that alias **in the same increment that creates the table** — an unregistered credential-bearing alias is silently un-redacted and nothing detects it (§Context 2). The delivery ledger stores no `Authorization` header and no bearer token; a provider's error response is recorded as the same truncated excerpt a webhook response gets. `docs/audit-compliance-logging-spec.md` §1 and §2 are updated with the alias and the redaction entry. **Revisit trigger:** any new credential-bearing table — the registry is hand-maintained by construction.

**Method note.** Like ADR-0007 and ADR-0008, and unlike ADR-0006, this is a **source audit plus design**, not a spike: nothing was prototyped and nothing was measured, so it carries **no weighted scorecard** — a rubric here would manufacture precision that does not exist. What is *evidence* is §Context: every claim was checked against source at authoring time (`SESSION_DOMAIN=null` in `.env.example:59` and `.env:56`; the two contradicting route-file comments; no `laravel/socialite` or `league/oauth2-client` in `composer.json`; no `connections` table in `docs/data-dictionary.md` §1–§23; no OAuth code anywhere in `app/`; `APP_PREVIOUS_KEYS` absent from `.env.example` and every doc; `native_connectors` seeded but consumed by nothing). What is *reasoning* is everything downstream — the storage rules, the callback topology, the state design, and the refresh/revocation semantics. One external fact this design leans on is **provider behaviour** (fixed redirect URIs, single-use authorization codes, Slack's non-expiring bot tokens by default and its `{"ok":false}`-on-HTTP-200 error convention); per this project's standing caveat, re-verify each against the provider's current documentation at implementation time rather than trusting this ADR's summary of it.

## Consequences (chosen path: **encrypted-at-rest tokens + central-domain callback + signed `state`**)

### Positive
- **A leaked database row is not a workspace compromise.** Tokens are ciphertext at rest and absent from every response, log line, and audit payload; the reader must hold `APP_KEY` as well as the row.
- **One callback per provider, forever.** Onboarding tenant number ten thousand requires no provider-side registration change, and the redirect URI is a constant the provider console can be configured with once.
- **No new boundary was widened.** Session cookies stay host-only; the cross-host problem is solved by a token that is verifiable, expiring, provider-bound and tamper-evident, on the same mechanism the guest runtime already trusts.
- **The write cannot land in the wrong tenant.** Context is adopted from a signed claim before RLS engages; a forged or altered state never reaches a GUC, and a valid one is scoped to exactly the tenant it names.
- **Open-redirect is closed by construction**, because the return host is a database lookup rather than an input.
- **The connector framework inherits an already-ratified gate** (`native_connectors`, Starter+) instead of coining a tier decision at build time.

### Negative / accepted trade-offs
- **`state` is replayable within its TTL** (§D3). Accepted: provider codes are single-use and a successful replay only rewrites the tenant's own connection. A nonce store is the fix if that changes.
- **The outcome hand-off is a query parameter, not a flash.** Slightly less elegant than the rest of the app's Inertia flash convention, and the reason is a cookie boundary that cannot be crossed without widening it (§D5).
- **Tokens are unreadable to operators.** Support cannot inspect a token to debug a provider rejection; the delivery ledger's error excerpt is the only diagnostic. Deliberate.
- **`APP_KEY` rotation is now a much sharper edge** and is documented as a gap rather than solved here (§D9).
- **Every provider needs its own adapter.** No OAuth client library is adopted, so `authorizeUrl`/`exchangeCode`/`refresh`/`deliver` are written per provider — bounded (~one small class each) but not free.
- **Adding a connector adds a sub-processor.** Tenant submission metadata flows to Slack; the DPA's sub-processor list must say so (`docs/data-privacy-gdpr-compliance.md:70`), which is a compliance obligation this feature creates rather than inherits.

### Risks & Mitigations
| Risk | Mitigation |
|---|---|
| A forged `state` writes a credential into another tenant | HMAC-signed with a domain-separated key, verified constant-time and decoded only after verification, before any tenant GUC is set (§D3/§D4); a test mints a state for tenant A and asserts nothing is written into tenant B |
| The callback writes zero rows because no tenant context exists | §D4 makes context adoption the middleware's only job; a callback test asserts the row exists *and* is readable only under that tenant's context |
| An attacker steers the post-callback redirect off-platform | Return host is read from the `domains` table, never echoed from request or state (§D5) |
| A leaked backup exposes every tenant's workspace credential | `encrypted` cast at rest (§D1); the backup holds ciphertext, and `APP_KEY` lives in the server `.env`, not in the dump |
| A token appears in an audit payload or an error log | Registered in `AuditRedactor` under the `connection` alias in the same increment that creates the table (§D10); the delivery ledger records no auth header |
| `APP_KEY` is rotated and every connection breaks at once | Recorded as an open gap with a named owner doc (§D9); `previous_keys` already exists in `config/app.php` and only needs populating + documenting |
| A provider outage causes a refresh stampede inside deliveries | Refresh is a scheduled `MaintenanceJob` fan-out with `WithoutOverlapping`, never lazy in the request or delivery path (§D6) |
| A revoked-at-the-provider connection retries forever | A refresh/delivery credential rejection marks the connection dead, stops its subscriptions, and notifies the owner once (§D6/§D7) |
| Scope creep grants the platform read access it never needed | Least-privilege scope sets live in config and are stored per connection; any expansion is an explicit re-consent decision (§D8) |

## Alternatives Considered
- **Per-tenant subdomain callbacks** — rejected per §D2: Slack and Google require exact pre-registered redirect URIs and reject wildcard hosts, so this does not survive the second tenant.
- **Widening `SESSION_DOMAIN` to span subdomains** so the central callback can read the tenant session — rejected per §Context 3 / §D3: it makes every tenant's session cookie a cross-host artifact on every request, permanently, to solve a problem that arises twice per connection.
- **A server-side `oauth_states` table with single-use nonces** — rejected for now per §D3: a table plus a reaper on a path that must run before any tenant context exists, buying protection against a replay whose only effect is rewriting the tenant's own connection. Named as the fix if provider codes ever stop being single-use.
- **`laravel/socialite` (+ a community Slack provider)** — rejected: Socialite is built around a same-host, session-backed redirect and would have to be bent around the stateless central-domain callback; the Slack driver is a third-party package; and the adapter it replaces is roughly one small class per provider. Recorded so the choice is not re-argued as an oversight.

  > **⚠ CARVED OUT BY J3c2 (2026-08-14) — THE REJECTION STANDS FOR CONNECTORS AND DOES NOT REACH
  > FIRST-PARTY SIGN-IN.** J3c2 adds `laravel/socialite` for Google sign-in only. Taking this bullet's
  > three reasons one at a time, because a carve-out that does not answer them is just a reversal:
  >
  > 1. *"Built around a same-host, session-backed redirect… would have to be bent."* Socialite's
  >    `->stateless()` is its own supported mode for exactly this topology: it emits no `state` and reads
  >    none back, so ADR-0009's signed token is passed in with `->with([...])` and remains the sole trust
  >    anchor. Nothing is bent — the library is used as an HTTP/wire-format client and is never asked to
  >    carry identity across the hop.
  > 2. *"The Slack driver is a third-party package."* Google's driver is **first-party and in the box**.
  >    No `socialiteproviders/*` package is taken. That clause was about supply chain, and it does not
  >    apply.
  > 3. *"The adapter it replaces is roughly one small class per provider."* True — and **J3c2 writes that
  >    class anyway**, as `App\Support\Auth\GoogleIdentityProvider` with `SocialiteGoogleIdentityProvider`
  >    behind it. So the cost of being wrong is one binding line, and the seam is what makes the flow
  >    testable against a fake with no live credentials.
  >
  > **What Socialite buys that `GoogleSheetsConnector` (which already speaks Google OAuth) does not:** the
  > `sub` + `email_verified` mapping off `oauth2/v3/userinfo`. That mapping is the security-load-bearing
  > half of a sign-in — `sub` is the identity key and `email_verified` is this flow's analogue of a
  > signature check — and it is the part worth not hand-rolling.
  >
  > ⚠️ **STATED COST, because it is not free:** Socialite pulls four transitive packages, of which
  > `league/oauth1-client`, `phpseclib/phpseclib` and `paragonie/random_compat` exist for OAuth**1**
  > providers this product will never use. `firebase/php-jwt` is the only one on our path. That is real
  > dependency surface accepted for one driver, and it is the strongest remaining argument for the
  > hand-rolled adapter if this is ever revisited.
  >
  > ⚠️ **`ConnectorProvider` DOES NOT ADOPT SOCIALITE AND MUST NOT.** The connector lane holds a *durable
  > third-party credential that lets the platform act as the tenant inside the tenant's own workspace*;
  > this flow reads an identity once and discards the token. Different custody problem, different answer,
  > and `app/Support/Connectors/ConnectorProvider.php:23-25` still says so correctly.
- **An external secret manager (Vault/KMS) for token custody** — rejected for this phase: ADR-0005's self-hosted single-box deployment has no such service, and nothing in CI could exercise it. The `encrypted` cast is the same protection the platform already relies on for webhook secrets.
- **Plaintext tokens protected only by RLS** — rejected per §D1: RLS protects a query, not a backup, a support tool, or a mis-scoped export.
- **Reveal-once / masked-suffix token display, mirroring the webhook secret** — rejected per §D1: the affordance exists for webhooks because the tenant must paste the secret into their receiver; a connector token has no user-facing consumer, so displaying it is pure downside.

## When to Revisit
- ~~**When the second and third providers land (H16 — Sheets, Airtable)** — validate that the `ConnectorProvider` contract survived contact with a provider that has genuinely expiring tokens and read scopes; §D8's "no read scopes" narrowing is expected to be re-decided there.~~ **ANSWERED by H16a (2026-08-05) for the second provider; still open for Airtable (H16c).** The four-method `ConnectorProvider` contract **survived unchanged** — Google Sheets needed no fifth method. What did have to change sat *around* it, and each is recorded above or below: a **fourth delivery outcome** (`blocked` — the destination is unusable but the credential is healthy, so pause one rule rather than revoking the grant), the **§D6 pre-flight guard**, the **§D8 read scope**, and a **per-provider `config` validation seam**, because H15a's four request classes hard-coded Slack's `channel_id` in the shared layer and would have rejected a Sheets rule before any adapter saw it. Two capabilities stayed correctly OPTIONAL and off: `ListsChannels` (no server-side enumeration under `drive.file`) and message templating. Airtable should re-ask only whether `blocked` and `isTabular()` fit a base/table destination.

  > **⚠ FULLY ANSWERED BY H16c (2026-08-13) — AND THE ANSWER IS "NOT UNCHANGED", WHICH IS WHY THIS LINE EXISTED.** The trigger asked whether the contract survived a third provider. It did **in count** — still four methods, no fifth — but **two signatures moved**: `authorizeUrl()` and `exchangeCode()` each take a `$codeVerifier`. Airtable **requires PKCE** (`code_challenge_method=S256`; `plain` is refused), and the verifier has to survive the hop between two calls that this ADR deliberately put on **different hosts in different requests**: the authorize on a tenant subdomain with a session, the exchange on the central domain with none (§D2). That is not a provider quirk landing on an unrelated design — it is §D2/§D3's topology being tested by the one OAuth extension that assumes a client can remember something between the two halves.
  >
  > **The fix is derivation, not storage, and it is §D3's own mechanism applied once more.** `ConnectorOAuthStateService::codeVerifierFor($state)` returns `base64url(HMAC-SHA256('connector-pkce.v1.' + state, stateKey))` — 43 characters, the RFC 7636 §4.1 minimum, in its unreserved set. Both halves already hold the state token, so **no session, no cache entry and no `oauth_states` table** is introduced; §D3's rejection of a server-side nonce store therefore stands unweakened, which it would not have if PKCE had forced one. The derivation is domain-separated by prefix from the state signature, per the convention `AppServiceProvider` already uses to derive this service's key from `APP_KEY`.
  >
  > **The obvious objection, answered explicitly because it will be raised again:** an attacker who intercepts the redirect sees both `code` and `state`, so deriving the verifier from the state looks like deriving a secret from a public value. It is not — the derivation is an HMAC under a key the attacker does not hold. What is public is the state; what protects the exchange is the key. An attacker holding that key can already mint states for any tenant, and PKCE was never the control standing between them and this endpoint. The property PKCE actually buys here is that a code intercepted in transit cannot be redeemed by anyone who did not start the flow, and that holds.
  >
  > **`blocked` fits, unchanged.** A base or table that was deleted, renamed past its id, or is unreachable under the granted scopes is precisely "the destination is unusable and the credential is healthy" — pause the one rule, do not revoke the grant. Airtable adds one new *reason* rather than a new *outcome*: a 422 `INVALID_VALUE_FOR_COLUMN` when a text answer will not coerce into a typed field.
  >
  > **`isTabular()` fits for what it was built for and had quietly grown a second job.** It correctly selects the destination-key set and the `submission.*` event narrowing for a base/table. But H16a had also used it to pick *copy* — "Choose a spreadsheet to write into", "A spreadsheet can only receive submission events" — which silently made "tabular" and "spreadsheet" synonyms. Airtable is tabular and has no spreadsheets, so every one of those strings would have named the wrong product to the tenant. A boolean cannot carry a noun: `ConnectorProviderKey::destinationNoun()` now does, and the shared validation layer interpolates it.
  >
  > **One capability moved from optional-and-off to optional-and-on, in the direction H16a predicted.** `ListsChannels` was off for Sheets because `drive.file` cannot enumerate; Airtable's `schema.bases:read` can, so H16c registers a base lister and reuses the H15b picker sidecar rather than adding a route. And `ProvisionsTabularDestinations` — H16b's create+inspect capability — was **split**, because Airtable needs inspection and deliberately not provisioning (see §D8 below); `InspectsTabularDestinations` is the base interface and `ProvisionsTabularDestinations` extends it, so `GoogleSheetsDirectory` needed no edit.
  >
  > **§D8, re-verified rather than inherited.** Scopes are **`schema.bases:read` + `data.records:write`**, checked against Airtable's live scope table and endpoint references on 2026-08-13 per this ADR's method note. `schema.bases:write` was **refused**, and the reasoning is the important part: H16b creates the Sheets destination, and the argument for that was specific to Google — `drive.file` cannot enumerate, so "paste an id" fails for most tenants and creating the file was the only way to make the destination reachable by construction. Airtable can enumerate, so the premise is gone and the conclusion does not carry. A scope letting the platform alter a tenant's base structure buys nothing they cannot do themselves. Ratified by the user on 2026-08-13. `data.records:read` is likewise absent: the connector appends and never reads back stored records. **One honest disclosure:** `typecast: true` on a record write can cause Airtable to add an option to a single-select field — a schema side effect Airtable permits on the data scope alone. It is accepted because the alternative is a rule that fails on its first real submission against any non-text field, and it is recorded in `docs/data-privacy-gdpr-compliance.md` §7 rather than left for someone to discover.
  >
  > **Still off, still correct:** message templating; `user.email:read` (a nicer account label is not worth a scope — the same trade §D8 made for Google, though here `whoami` supplies a real account id for free, so unlike Google the one-connection-per-tenant narrowing does **not** apply).
- **On the first real `APP_KEY` rotation** — §D9's gap must be closed (documented procedure + `.env.example` entry) *before* the rotation, not after.
- **If a provider's authorization codes become replayable**, or a callback gains a side effect beyond writing the connection it names — §D3's stateless `state` becomes insufficient and the nonce store is the answer.
- **When the platform gains a second central-domain route that writes tenant data** — reuse §D4's middleware; a second context-adoption path is how the invariant drifts.
- **If per-tenant OAuth apps become necessary** (an enterprise wanting its own Slack app) — §D9's "platform-wide credentials in `.env`" assumption breaks and client secrets become tenant data with the same custody rules as tokens.
- **When token-bearing connections are held for tenants that later suspend or delete** — retention of a third-party credential past tenant lifecycle is a privacy question this ADR does not rule on.
