# ADR-0011: The Analytics Substrate (aggregate what already exists; no engagement event stream in Phase 3; in-house data-viz primitives)

## Status

**Accepted — 2026-08-03.** Phase 3's last unbuilt PRD item is Feature #4's *advanced cross-form analytics* (H24a backend, H24b UI), and it is the only vertical in the phase with no design artifact of any kind: the substring "analytics" does not occur in `app/` at all, `form_events`/`analytics_rollups`/`saved_report_views` match nothing in the repository, there is no charting dependency, no chart design token, no data-bound SVG, and the `advanced_analytics` plan flag exists in exactly two lines of one seeder with zero consumers. The tempting way to build it is to start collecting a new class of data from respondents — the H-map's own row for H24a specifies a `form_events` table fed by a rate-limited unauthenticated beacon, with retention and partitioning designed in from day one. **Decision: it collects nothing new.** Phase 3's analytics aggregates only data the platform already stores; the form-engagement event stream — and with it view counts, per-step drop-off, time-on-step and any true completion funnel — is deferred to Phase 4 with its cost written down; cross-form aggregation is promised over *submission metadata*, which is fully populated, while answer-value aggregation is disclosed as opt-in and prospective-only because the typed answer index is written only at finalize and is never backfilled; aggregation is bounded live SQL under RLS with materialization reserved as a fallback triggered by a measured budget breach, never chosen up front; the two Phase-1 acceptance criteria that were never built are **amended to what is computable rather than left aspirational**; the analytics surface is hidden rather than locked-with-upsell because its tier cannot be purchased; and charting is built as design-system SVG primitives over new `--mds-chart-*` tokens rather than by adding a charting library. This unblocks **H24a** and, transitively, **H24b**.

- **Deciders:** Founding engineering (architecture owner) + product.
- **Related ADRs:** **ADR-0001** (PostgreSQL over MySQL — its "no polyglot persistence at this stage" constraint (`:58`) is why aggregation is Postgres-native, and its "stronger analytics primitives for later phases" clause (`:73`) named this work by name; §D3 below also records that one of its performance claims is unmet). **ADR-0002** (shared-DB RLS — every aggregate query runs under the tenant GUC, which is what makes Risk R9 this ADR's concern rather than a later one). **ADR-0005** (self-hosted single box — the reason a highest-write-volume table is a real cost and not an abstraction). **ADR-0006** (geospatial storage — §D3's scoped-CSP narrowing is the only CSP precedent in the repo, and §D11 below records that this ADR needs none). **ADR-0007** (async execution — a materialization fallback would be a `MaintenanceJob` fan-out under its §D3, and the export path stays off the queue entirely). **ADR-0008** (entitlement & metering — its §D6 held Business from sale, which is precisely why §D9 hides the surface instead of upselling it; the `advanced_analytics` key it coined is inherited here, not re-coined). **ADR-0010 is reserved for H1d** (the OCR provider bake-off, blocked on a document sample and still expected); this ADR deliberately does **not** take that number, because unlike the cancelled payments ADR whose hole ADR-0009 §Status filled, 0010's hole is temporary.
- **Related docs:** `docs/PRD.md` Feature #4 (`:190-206` — the Phase-1 and Phase-3 acceptance criteria, two of which §D5 amends); `docs/non-functional-requirements.md` §1 (`:20`, the only analytics performance budget in the corpus); `docs/architecture/technical-architecture.md` §9 Risk **R9** (`:525`, which stays OPEN) and §7 (`:423`, cross-version alignment on a stable `form_fields.key`); `docs/form-versioning-schema-migration.md` §7 (`:140-152`, whose advisory §D4 makes normative); `docs/data-dictionary.md` §9 (`:384`, the typed projection §D3 constrains); `docs/pricing-feature-gating-matrix.md` (`:51`, the Business-tier row); `docs/ux/design-system-reference.md` §1.3, §4.1 (`:559`) and §5 (`:667`, which already placed this surface); `docs/data-privacy-gdpr-compliance.md` §4 (retention, which the deferred event stream would have had to answer).

## Context

1. **Nothing exists.** `grep -ri analytics app/` returns no match at all — no service, controller, route, page or tab. `form_events`, `analytics_rollups` and `saved_report_views` return zero matches repository-wide; they are named only in the Phase-3 decomposition plan. There is no charting dependency in either `package.json` (the root's production dependencies are `@inertiajs/vue3`, `@meridian/design-system`, `dexie`, `leaflet`, `vue`), no `--mds-chart-*` token under `packages/design-system/tokens/`, no `<canvas>` and no data-bound SVG anywhere in `resources/`.

2. **The gate exists and is unwired.** `advanced_analytics` occurs in exactly two places in the repository, both in one seeder: `database/seeders/Data/PlanCatalog.php:37` (inside `FEATURE_KEYS`) and `:56` (`$business = [...$professional, 'custom_domain', 'advanced_analytics']`, inherited by `$enterprise` at `:57`). Nothing consumes it. `docs/pricing-feature-gating-matrix.md:51` gates the capability by human label only — it is the one capability row in that table that never names its code key. The `read:analytics` ability named by the decomposition plan does not exist in any spelling; `app/Support/Api/ApiAbilities.php` holds eleven constants (`:24-68`), none analytics-related.

3. **H11 already established the aggregation doctrine, and wrote it down.** `app/Services/Dashboard/DashboardMetricsService.php:18-22`: *"Live COUNT-under-RLS, never a maintained running aggregate: the same doctrine as `EntitlementService::computeGauge()` — a synced counter drifts (a form is archived, a member removed) whereas a COUNT under the tenant's RLS GUC is always correct. **No new table, no rollup job; if these counts ever grow too heavy, materialization is a MaintenanceJob fan-out away.**"* Its entire public surface is one method, `forUser(User): array{forms, submissions, members}` (`:43`), scoped by `$user->can('dashboard.org.view')` (`:45`) with the non-org-wide arm reusing `ResourceGrantResolver::grantedFormIdsQuery()` so the Forms and Submissions numbers agree on which forms a scoped role can reach (`:60-62`). There is no presenter in `app/Services/Dashboard/`.

4. **A respondent who abandons a form leaves no trace on the server.** Exactly two call sites create a `submissions` row: `app/Services/Submissions/SubmissionPipeline.php:149` (`status=submitted`, all six ingest channels) and `app/Services/Submissions/SubmissionDraftService.php:235` (`status=draft`). The draft path is reachable from one HTTP surface, `POST /api/v1/public/f/{shareToken}/draft` (`routes/api.php:344`), which requires the route's `feature:save_and_resume` gate **and** the form's own `forms.save_and_resume` flag (`app/Http/Controllers/Public/GuestDraftController.php:60`, a 403 `save_resume_disabled`), and it fires only when the respondent clicks "Save and finish later" (`resources/public-runtime/components/SaveForLater.vue`). Ambient autosave is device-local Dexie and never posts (`resources/public-runtime/composables/useAutosave.ts`). So "started" is unobservable, and the population that *is* observable is a self-selected subset — which the daily reaper then **hard-deletes**: `app/Jobs/Submissions/ReapTenantDraftsJob.php:34-37` calls `forceDelete()` on drafts past `draft_expires_at`, scheduled at `routes/console.php:57`.

5. **No timestamp measures how long a respondent spent filling.** For a direct submit, `submitted_at` is set in the same transaction that creates the row, so `submitted_at − created_at` is approximately zero. For a promoted draft it measures first-explicit-save to promotion, excluding every minute before the first click. `finalized_at` is a **reviewer** timestamp, written by `app/Services/Submissions/SubmissionReviewService.php` on approve and archive. `docs/PRD.md:198` nonetheless lists *"a completion rate where measurable (started vs. completed), average completion time"* as Phase-1 acceptance criteria; H11 shipped neither, and the phrase "where measurable" was never made precise.

6. **The typed answer index is opt-in, prospective-only, and has no backfill.** `app/Services/Submissions/AnswerIndexProjector.php:31-36` projects a value only if `is_queryable` is set *and* an `indexed_data_type` is declared *and* the answer is a non-empty non-array; `app/Services/Submissions/SubmissionFinalizer.php:160-164` iterates top-level answer keys only and `continue`s on any array, so a field nested inside a repeatable section is never reached even when flagged and scalar. `is_queryable` defaults to `false` in the migration (`database/migrations/2026_07_06_000205_create_form_fields_table.php:41`), in `FormBuilderService`, in every seeder, and is hard-coded `false` by `app/Models/FieldLibrary.php:117`. The projector runs only inside `SubmissionFinalizer`, so **flipping the flag indexes future submissions only** — and flipping it is classified a breaking-but-permitted change (`app/Services/Forms/SchemaChangeClassifier.php:71`, `'indexing changed'`), so it also requires a new form version. Nothing prevents an author flagging a field that can never project: `app/Services/Forms/StructuralValidationGate.php:45-47` checks only that a queryable field declares a type.

7. **Cross-version aggregation has a documented silent-failure mode that no code prevents.** `docs/form-versioning-schema-migration.md:152` records that when a key's `indexed_data_type` changes between versions, `value_number` is populated for some versions and `value_text` for others, so a naive `AVG(value_number)` *"silently drops (rather than errors on) the non-numeric-typed rows"*, and advises that a reporting feature *"should consult the classification"*. It is advice addressed to a feature that did not exist yet. It does now.

8. **There is no tenant-authored grouping label on forms.** `docs/PRD.md:203` asks for *"cross-form aggregation and filtering within a tenant (e.g., all forms tagged to one program or campaign)"*, but none of the schema's tables is a tag, label, category, folder, project or workspace model (`form_templates.category` and `field_library.category` categorise blueprints, and templates instantiate by cloning with no back-pointer from `forms`). What does exist is `forms.scope_node_id` — nullable, indexed `(tenant_id, scope_node_id)`, composite FK to `scope_nodes` — over a hierarchy with a self-inclusive materialized `path` queried as a constant-prefix `LIKE`. It is single-valued, it is NULL until someone explicitly assigns it, and the two existing subtree queries disagree about deactivated nodes: `ResourceGrantResolver::nodeReach()` (`:214-228`) filters `scope_nodes.is_active` and excludes inactive branches, while `ScopeNodeService::deletionImpact()` does not.

9. **The read path has no index for the shape analytics needs.** `submissions` carries `(tenant_id, form_id)`, `(tenant_id, form_version_id)` and `(tenant_id, status)` (`database/migrations/2026_07_09_000301_create_submissions_table.php:62-64`) and **no time-ordered index**, so every date-bucketed aggregate is a filtered scan under the RLS predicate — against a budget of `< 400ms` target / `< 1.5s` max (`docs/non-functional-requirements.md:20`), on the single box of ADR-0005, in the exact area Risk **R9** is still open about (`docs/architecture/technical-architecture.md:525`, whose "high-cardinality tables" list is `submissions`/`submission_answers`). The table also uses `softDeletesTz()` (`:61`), so every aggregate must exclude trashed rows, and `submission_answer_index` rows survive a soft delete because its cascade is hard-delete only.

10. **The design system can already render a chart, and cannot already theme a library.** `packages/design-system/build-tokens.mjs`'s `meridian/ts` formatter emits `{ colorActionPrimaryBg: 'var(--mds-color-action-primary-bg)' }` — CSS `var()` **references**, not resolved values — and `resources/js/composables/useTheme.ts:24-30` flips `data-theme-mode` and `data-accent` on the root element live, with no reload. SVG consumes `fill="var(--mds-chart-series-1)"` natively and re-paints for free on that flip; a canvas renderer cannot resolve a `var()` and goes stale until someone wires an observer. Meanwhile the merge-blocking axe job runs `test-storybook` over every story in `packages/design-system`, so a chart with a story is under that gate by construction and a chart rendered by a library inside `resources/js` is not.

11. **No Content-Security-Policy stands in the way, and the reason is narrower than it looks.** `app/Http/Middleware/PublicRuntimeSecurityHeaders.php` is the only CSP-setting mechanism in the repository — no other middleware, no nginx `add_header`, no `<meta http-equiv>`, no CSP package, no nonce plumbing — and it emits `img-src`/`media-src`/`worker-src`/`manifest-src` only, deliberately leaving `default-src`, `script-src` and `connect-src` unset (`:25-27`). It is registered at exactly two sites: the guest runtime group (`routes/tenant.php:405`) and, notably, the **authenticated** manual-encode page (`:264`, for Leaflet tile origins). `/dashboard` (`:70`) carries none. `docs/piping-output-encoding-design.md:262` records a standing deferral of `default-src` hardening, because introducing it forces enumerating every directive at once.

12. **Business cannot be bought.** `PlanCatalog.php:119` seeds the Business tier `active: false` — *"Built and gated; held from sale until the production host is stood up (ADR-0008 §D6)"* — so `advanced_analytics` is reachable only by a super-admin plan assignment or a `legacy_overrides` row. `app/Exceptions/Entitlements/FeatureGateException::forKey()` (`:32-41`) has no arm for the key, so a direct visit today would render the raw snake_case string in user-facing copy.

**The core tension:** every genuinely interesting analytics question — why did people leave, where, and how long did it take — is a question about *behaviour*, and this platform records only *outcomes*. Closing that gap means opening a fourth unauthenticated ingress class that writes, at the highest volume of any table in the system, onto a single self-hosted box, into an RLS-scoped table whose retention and partitioning would have to be designed before its first row — and doing it for a phase whose written acceptance criteria ask for none of it. The opposite failure is just as real and much quieter: shipping the aggregates that *are* computable while labelling them with the words the PRD used, so that a rate over a self-selected, nightly-deleted denominator is presented as "completion rate" and reads as fact. This ADR spends its decisions on refusing both — declining the event stream with its cost written down, and pinning exactly what each surviving number is allowed to be called.

## Options on the table

**On what to collect.**
- **(A1) Full engagement event stream now** — `form_events` plus a rate-limited Group-C beacon, offline-queued through Dexie, rolled up by a `MaintenanceJob`, partitioned and retention-bounded from the first migration. Buys real funnels. Costs a fourth ingress class, the highest-write-volume table on a single box, an unauthenticated write into an RLS table, a systematic undercount of offline respondents, and a split of H24a into capture and aggregate halves.
- **(A2) Server-side view counter only** — no client beacon; count renders on the existing guest path into a small per-form-per-day counter. Cheaper, and makes "views vs submissions" real. Still a new write on the public render path, still cannot see step-level drop-off, and still needs a retention answer.
- **(A3) Aggregate only what exists** — **chosen.** Satisfies all three written Phase-3 acceptance criteria, adds no write path, and makes the deferral explicit rather than accidental.

**On how to compute.**
- **(B1) Rollup tables from day one**, citing the NFR's permission to use precomputed aggregates. Contradicts the doctrine this codebase has ratified twice, and buys a permanent drift surface against zero measurements.
- **(B2) Bounded live SQL under RLS** — **chosen** — with materialization as a fallback triggered by a *measured* budget breach.
- **(B3) A read replica or a separate analytics store.** Excluded by ADR-0001's no-polyglot constraint and by ADR-0005's single box.

**On how to render.**
- **(C1) A JavaScript charting library**, wrapped in Meridian components. Fastest to rich chart types. Every visual token must be re-mapped by hand into the library's theming API for both accents and both modes, its markup must satisfy the axe gate from outside the design system, and its transitive advisories become merge-blocking under a production-only audit gate.
- **(C2) Design-system SVG primitives** — **chosen.**
- **(C3) No charts at all** — tables and stat tiles only. Defensible on the letter of the Phase-3 criteria, which never say "chart", but leaves the Phase-1 "submission-volume trend" unmet for a second phase and pushes the same undecided fork into Phase 4.

## Decision drivers

1. **Honesty over completeness.** A metric whose denominator is a self-selected subset, and whose subset is deleted nightly, is worse than no metric: it is a number that looks like fact and rises on its own.
2. **The written acceptance criteria are the scope**, not the decomposition plan's guess at them. Three criteria, all computable from stored data.
3. **Do not open a new ingress class for a feature that did not ask for one.** Each existing class (session, bearer, share token) took an increment to get right.
4. **Ratify the doctrine already in the code**, rather than inventing a second one three files away.
5. **One shared design system, no exceptions** (Standing Rule 2 / DSR §1.3) — and an accessibility gate that only reaches what lives inside it.
6. **Every decision must name the downstream decision it prevents from being made twice**, or it does not belong in this ADR.

---

## Decision

Phase 3 ships analytics that aggregate existing data, computed live under RLS, gated on the entitlement key that already exists, rendered by primitives built inside the design system, and described in language that matches what the numbers actually are. The event stream is deferred, once, with its cost recorded.

### The thirteen sub-decisions

- **D1 — No form-engagement event stream in Phase 3.** No `form_events` table, no analytics beacon, no client telemetry, no new ingress class. H24 aggregates only data already stored. This supersedes the H24a row of the Phase-3 decomposition plan, which specified all four. The deferral carries two costs, recorded here so that Phase 4 inherits them rather than rediscovering them: **(a)** offline respondents sync completed submissions but would emit no engagement events, so any future funnel systematically undercounts them; **(b)** the step graph is a *total order filtered by relevance* (`docs/workflow-branching-design.md`), so "step 3" is not the same node for two respondents — funnel semantics over a branching graph is an unsolved design problem in its own right, not an implementation detail of the beacon.

- **D2 — One countable-submission predicate, named once, binding on H11 and H24a alike.** A submission counts when its `status` is not `draft` and it is not soft-deleted. Analytics may **never** read `submission_answer_index` without joining `submissions`: the projection rows survive a soft delete, because the cascade is a hard-delete FK. This prevents the two surfaces drifting into two definitions of "a response", which is the failure that makes a dashboard and an inbox disagree in front of a customer.

  > **Amendment (Increment I9a) — there is now a SECOND predicate, and D2's own "deliberate non-adopters" paragraph is why that is not a violation.** `Submission::scopeConsumesCapacity()` (`status` not in `draft`, `screened_out`) was added beside `scopeCountable()`. D2 says one predicate for *"a response"*, binding on the two ANALYTICS surfaces; it never claimed jurisdiction over *"a response that consumed a purchased `max_responses` slot"*, and the `Submission` model docblock has named that as a different question, with named non-adopters, since H24a. I9a is the increment where the two questions stopped agreeing: `screened_out` (a respondent finalized having been shown no questions — `docs/workflow-branching-design.md` §4.1) is a real row the tenant received and the inbox lists by default, so it **is** countable; it did not consume a paid slot, so it does **not** consume capacity.
  >
  > **`scopeCountable()` is unchanged and D2 still binds every analytics surface.** The reason to record this rather than leave it inferred is that the obvious tidy-up — folding the two into one — would reintroduce exactly D2's failure mode from the other direction: a customer's paid cap would then move whenever an analytics definition moved. It would also be a migration, because `submissions_analytics_series_idx` is partial on `scopeCountable()`'s predicate.
  >
  > One consequence accepted rather than fixed: `draftMetrics()`'s §D5 conversion numerator counts a draft that promoted to `screened_out` as *converted*. The respondent did finish — they pressed the terminal screen's Submit — so this is defensible, and it is a measurement rather than a cap. Revisit if the conversion figure ever reads high on a branching-heavy tenant.

- **D3 — Phase-3 cross-form aggregation is promised over submission *metadata*; answer-value aggregation is opt-in and prospective-only.** Metadata — form, `submissions.source` channel, status, scope node, period, locale — is populated for every submission ever made and needs no author action, so it is what the acceptance criterion is honoured with. Answer-value aggregation is offered on top, with an explicit coverage disclosure naming the version from which a question became indexed, and is **never** silently partial. No backfill ships in Phase 3; a backfill job is a named Phase-4 candidate. Three properties H24b's field picker must encode rather than discover: **(i)** the projected set is `is_queryable` **and** top-level scalar, which *includes* `likert_scale` (its answer is a single chosen value) and excludes `multi_select`, `cascading_select`, the five media types, both grid types, and every field nested in a repeatable section; **(ii)** an author can flag a field that can never project and publish successfully, so the authoring surface must say *"this question cannot be reported on"* rather than letting "Indexed for reporting" promise something it will not deliver; **(iii)** the projector drops rows silently *within* a flagged field — a non-numeric answer under a `number` index, an unparseable date — so a count over the index under-counts against `submissions` per field, and any answer-level surface must show its own coverage. The three geo types are excluded from this index but are not unindexed: they have their own GiST-indexed `submission_geo_index`.

- **D4 — A mixed-type key is a visible refusal, never a silent average.** Aggregates over `submission_answer_index` partition by the *populated* value column, and coercion across partitions is forbidden. Where a key's `indexed_data_type` changed between versions, the surface reports the drift and names the version at which it happened — *"this question changed type in version 4; values before it cannot be averaged with values after"* — instead of returning a number computed from whichever rows happened to survive. This makes `docs/form-versioning-schema-migration.md` §7's advisory normative and closes the loop it left open.

- **D5 — `PRD.md:198`'s two orphaned metrics are amended to what is computable, not left aspirational.** Neither is computable *for any form*, per Context 4–5. What ships instead is a **draft-conversion rate** and a **median time from first save to submission**, both computed over rows that were once explicitly saved as drafts. The durable marker is `submissions.last_saved_at IS NOT NULL`: it survives promotion, because `SubmissionDraftService::promote()` rewrites only `status`, `submitted_at` and `draft_expires_at`, and the fresh-submit path never writes it. Both metrics state their denominator on the face of the tile, and both are **suppressed rather than estimated** for any period extending beyond the tenant's draft-retention window, because abandoned drafts are hard-deleted at expiry. The hazard this exists to prevent is specific: a naive completion funnel built on `count(status='draft')` returns 100% on a default-configured form and **rises every night as the reaper deletes its own denominator**. A true completion rate and average fill time require the deferred event stream.

  > **Amendment (Increment I9b) — the denominator's POPULATION changed, though its definition did not.** `last_saved_at IS NOT NULL AND source IN (guest, manual)` always admitted `manual`, but until I9b no manual draft could exist, because the encode channel had no save endpoint. Both §D5 metrics were therefore guest-only in practice while claiming to be channel-agnostic in prose. They are now genuinely mixed, and the two populations are not alike: a guest's "time from first save to submission" measures a respondent's deliberation, a keyer's measures a transcription shift and can span a lunch break. Left MIXED rather than split, because the metric is stated as "from first save to submission" and both are that; recorded here so a tenant whose median jumps after this increment finds the reason instead of a mystery, and so a future split is a decision rather than a discovery. The suppression rule is unaffected.

- **D6 — The grouping axis is `forms.scope_node_id`; no tag model is coined.** A tenant that models programs as scope nodes selects a subtree; one that does not selects an explicit set of forms. Both are served with no new schema. Three properties are stated rather than assumed: the column is **single-valued**, so it cannot express the multi-membership "tagged" implies; it is **NULL for every form** until explicitly assigned, so every grouped result needs an explicit *Unassigned* bucket rather than a silently short total; and analytics adopts `nodeReach()`'s semantics — **a deactivated node and its branch are excluded** — because an analytics total that counts branches the authorization layer treats as gone would disagree with every other number on the screen. Secondary axes that already exist and may be offered alongside it: `forms.status`, `forms.owner_user_id`, `forms.default_locale`, and on submissions `source`, `locale`, `source_batch_id`. A tag model earns its migration when a tenant needs a grouping *orthogonal to authorization* — one form in two campaigns — and not before.

- **D7 — Aggregation is bounded live SQL under RLS: no rollup table, no cache, in Phase 3.** This ratifies `DashboardMetricsService`'s doctrine at cross-form scale and reads `docs/non-functional-requirements.md:20`'s "may use precomputed/cached aggregates" as what it is — *permission, not instruction*. "Bounded" is enforceable, not aspirational: every analytics query is **(a)** time-bounded by a mandatory date range with a stated maximum span, **(b)** form-bounded by an explicit form set or a scope subtree, and **(c)** fixed-cardinality in its result — a bucketed series or a top-N, never a per-row scan projected to the client. Materialization is a **triggered** fallback: a measured p95 breach of the 1.5s maximum on real tenant data, implemented as a `MaintenanceJob` fan-out. The invariant governing any such revisit: *a rollup must never be able to disagree with the inbox* — the moment one exists, D2's predicate becomes a synchronisation problem instead of a property of the query. H24a owns one index addendum, because Context 9's absence is load-bearing for the budget above.

- **D8 — `saved_report_views` is a strict-RLS tenant table carrying a `user_id`, never the `belongs_to_user` isolation variant.** The variant has no tenant predicate; adopting it here — the obvious move, given `user_ui_preferences` and the PRD's own words "per user" — would be a cross-tenant metadata leak for any consultant who belongs to two tenants. The row stores a *declaration* (filters, grouping, date range) resolved at read time, so a saved view naming a `field_key` that no longer exists in the current version degrades to D4's reported refusal rather than to a wrong number.

- **D9 — The surface is hidden, not locked-with-upsell; and `read:analytics` is a new ability.** H24 coins no new entitlement key: `advanced_analytics` already exists and this ADR inherits it. Because Business is held from sale (Context 12), an upgrade call-to-action would point at a plan that cannot be purchased — a dead end presented as an offer — so the nav item and the dashboard's analytics tab are **hidden** for tenants without the feature, matching the `NavItem.feature` precedent. The API ability is **new**, never a widening of `read:submissions`, per the doctrine in `ApiAbilities.php:42-67`: folding it into an existing ability would retroactively grant analytics access to every token already minted. It needs **no new RBAC permission** — `dashboard.org.view` and `dashboard.form.view` are already seeded and already in the role matrix. Two obligations are assigned to H24 rather than left to be found: add the `advanced_analytics` arm to `FeatureGateException::forKey()`, whose absence would render the raw key in a 402 body; and **seed a Business-entitled tenant in the e2e fixture**, without which the merge-blocking accessibility job cannot reach the new surface at all and stays green over a page it never loaded.

  > **Amendment (Increment I10c, 2026-08-08) — a second analytics surface now exists OUTSIDE the gate, and that is deliberate.** `GET /forms/{form}/analytics` ships with `can:view,form` and **no** `feature:advanced_analytics`, because `docs/PRD.md:198`'s Form Owner/Editor view is a **Phase-1** acceptance criterion — the same unbundling `DashboardMetricsService::trendsForUser()` already records for the dashboard, and the one `ToggleableModules`' own hint states ("the dashboard and per-form statistics are unaffected"). What D9 gates is unchanged: arbitrary axis selection, scope-subtree selection, saved views, answer-value aggregation and the streamed export. The same increment also put the channel breakdown PRD:198 asks for on the ungated dashboard.
  >
  > The risk this creates is drift — an ungated page acquiring gated capabilities one convenient prop at a time — so it is bounded **structurally rather than by discipline**, and the five mechanisms are listed here so a later increment cannot dismantle one without noticing: **(1)** `FormAnalyticsPresenter`'s constructor takes ONE dependency, `AnalyticsReportBuilder`; `AnswerValueAggregator`, `SavedReportViewService`, `AnalyticsExporter` and `AnalyticsPresenter` are all absent, so every gated surface is unreachable by construction and adding one is a visible constructor change in review. **(2)** The controller takes `Request`, never a FormRequest, and reads nothing from it — the axis, granularity, timezone, top-N and window are literals, so there is no input to widen; a Pest case GETs the route with widening query parameters and asserts the report is unchanged. **(3)** `selection: Forms` with exactly one id, and `AnalyticsQuery` throws on `Forms` with an empty `formIds`, so a one-form selection cannot silently degrade to `All` and serve a tenant total under a form's title. **(4)** One route, and deliberately no `/export` sibling. **(5)** `AnalyticsReportBuilder` omits `forms_accepting` — a workspace-wide count that would be confidently wrong on a one-form page — so a form-scoped caller cannot inherit it by accident.
  >
  > Two consequences worth stating rather than leaving to be found. The extraction of `AnalyticsReportBuilder` out of `AnalyticsPresenter` is a pure refactor whose proof is that the existing analytics suites pass with no test file edited — `AnalyticsPageTest` and `AnalyticsIndexShapeTest` being the two that actually assert the report's shape key-by-key, and so the two that would notice (`AnalyticsWebExportTest` never calls `report()` at all, and `AnalyticsWebRefusalTest` asserts refusal status codes rather than the payload; they are regression cover, not the proof); it exists because `resources/js/components/analytics/types.ts` documents its shapes as derived from PHP `@return` annotations, and a second PHP author of the same shape is exactly what that sentence exists to prevent. One difference is worth recording so nobody reads “pure” as stronger than it is: `forms_accepting` is now appended after the spread, so it serialises LAST rather than before `week_starts_on`. Every key and value is identical and no consumer reads the prop positionally, but a byte-comparison of the `/analytics` `report` prop against `phase1-completion` would differ. And the audience is narrower than the dashboard's on purpose: `FormPolicy::view` refuses a Reviewer and a tenant Viewer, so a Viewer who can read every org-wide KPI on `/dashboard` is still refused here. That asymmetry is pinned by `FormAnalyticsGateTest` rather than left implicit — widening it is an authorization change and wants a decision, not a refactor.

- **D10 — Charting is in-house SVG primitives inside `@meridian/design-system`; no charting library is added.** Four components: `MdsTimeSeriesChart` (line/area, one to five series), `MdsBarChart` (horizontal, categorical), `MdsChartLegend`, and `MdsStatTile` extended with a delta and an `unavailable` state. Geometry is expressed as SVG presentation attributes and colour as `fill`/`stroke` referencing custom properties — never `:style` bindings, never runtime colour computation, so the primitives cannot be the reason a future `default-src` policy has to permit inline styles. Scales are roughly forty lines of in-repo arithmetic; **do not add a scale library "because it is small"** — it would be a production dependency under the audit gate for forty lines. Explicitly **not** built, recorded so a later increment does not assume otherwise: pie and donut, stacked bars, scatter, heatmap, sankey, zoom/brush, and automatic axis-label collision avoidance. One trap worth naming: **`Tabs` is specified in DSR §3.4 but does not exist** in the component library, so the "secondary tab" placement of DSR §5 means building it or using `MdsSegmentedControl`.

- **D11 — The chart token contract.** A new `--mds-chart-*` semantic family. **The categorical series scale is five, and five is derived rather than chosen:** charts sit on `--mds-color-bg-surface`, which is white in light and `#123350` in dark, and satisfying WCAG 1.4.11's 3:1 against *both* grounds with one token set confines a mark to a narrow luminance band that leaves no room for marks to be distinguishable from each other — which is why **the dark re-point of the series tokens is mandatory, not optional**, and why five is where mutual distinguishability under both grounds and common colour-vision-deficiency simulations stops being defensible. Series tokens alias none of the primary, success, warning, danger or accent scales, and **no `[data-accent]` rule touches them** — the exact inverse of the argument already written into `theme-overrides.css` for why Moss and Brass are excluded from the accent whitelist: a data series encodes meaning, and two colleagues looking at one screenshot must see the same series in the same colour. Past five categories the caller ships the top four plus a single aggregated *Other (N)* bucket painted a **neutral**, never a recycled hue, so "Other" never reads as a peer category; the full breakdown remains in the paired data table and in the export, so nothing is hidden, only un-plotted. Gridlines are decorative scaffolding, **exempt** from 1.4.11 and deliberately below 3:1 so they do not compete with the data; axis tick labels are text and take 4.5:1. The sequential scale is specified here as a construction rule — single hue, five monotonic-luminance steps, step 1 clearing 3:1 against the surface, adjacent steps exempt from mutual 3:1 — but is **not emitted** until a real consumer lands. Emitting an unconsumed token is precisely how the corpus came to contain a true-sounding false claim that chart tokens already existed. **This ADR states constraints and prints no contrast ratios**; H24b computes the measured table and records it in DSR §4.1 beside the existing rows, because an ADR that prints ratios nobody computed is worse than one that prints none.

- **D12 — Every chart ships a non-visual equivalent, and a unit test guards it because the accessibility gate cannot.** Each primitive renders `role="img"` with a summarising `aria-label` **and** a real table of the plotted data. The reason this is a decision and not a style note: **axe cannot detect a *missing* text alternative for an SVG that carries a plausible `aria-label`**, so the merge-blocking job will pass a chart that is a beautiful, unreadable picture. The contract is therefore pinned by a Vitest assertion per primitive, not by the axe gate — a distinction worth writing down, because "axe is merge-blocking" is otherwise read as "accessibility is covered". Colour is never the only channel: a single-series chart uses no categorical colour at all (its categories are distinguished by their axis labels, which is why the six-value `source` breakdown never strains the palette), and multi-series charts carry hue **plus** a redundant channel — a dash pattern, or a shared `--mds-chart-pattern-*` primitive rather than something private to one chart, because OCR confidence tiers will need the same mechanism and a second private implementation would be DSR §1.3's third silent fork.

- **D13 — The streamed export reuses `SubmissionExporter`'s shape, and the three lines that make it correct are named here.** Not the outer shape — these three: capture the tenant and user ids *before* the closure (`:74-76`); call `TenantContext::applyLocal()` *inside* it (`:85`), because the closure fires during `Response::send()`, after the middleware has torn context down; and meter before the stream (`:59-61`), because a streamed response cannot reliably increment on completion. Omitting the middle one ships an **empty file with HTTP 200** — a defect every status-only test passes. The export stays synchronous and streamed, matching `docs/PRD.md:206`'s "same export pattern as submission exports"; a queued analytics export is deferred.

## Consequences (chosen path: **aggregate what exists, live, drawn in-house**)

### Positive

- H24a adds **no new ingress class, no new write path, and no new high-write table**, so the phase's remaining risk is concentrated in read performance — measurable, bounded, and reversible — rather than in an unauthenticated write under RLS.
- H24a stays **one increment** instead of splitting into capture and aggregate halves, which is the difference between one `L` PR and two.
- R9's exposure does not grow. `form_events` would have displaced `submissions` as the highest-cardinality table in the system; nothing here does.
- Every number the surface shows can be derived from a table a tenant can already export, so a customer can check it.
- The charting decision buys back a merge-blocking accessibility gate that a library would have escaped, adds zero production dependencies under a production-only audit gate, and re-paints correctly on a live theme flip for free.
- Four false or misfiled statements in the corpus are corrected in the same change (see References).

### Negative / accepted trade-offs

- **The most-requested analytics feature is not in this phase.** Drop-off is what a form builder asks for first; `docs/PRD.md:67` names it in Persona B's goals. This ADR ships none of it, and says so on the surface rather than approximating it.
- **`PRD.md:198` is amended, which is a written commitment being narrowed.** The substitutes are real but narrower, and one of them — draft conversion — is only meaningful on forms with save-and-resume enabled, i.e. on Starter-and-above tenants who opted a form in.
- **Answer-value analytics will be empty for essentially every form that exists today**, because `is_queryable` is off by default and there is no backfill. Turning it on helps only future submissions, and requires a new version. This is a real product limitation surfaced now rather than discovered by the first customer who asks why their chart is blank.
- **Charting capability is capped by what we build.** Five categorical series, no stacked bars, no pie, no brushing. A genuine need beyond that becomes a design-system increment, not an afternoon's dependency install.
- **A live-SQL posture means the first slow tenant is a real incident**, not a config change. It is mitigated by a stated trigger and a pre-authorised fallback, but the fallback is unbuilt.
- **`submission_answer_index` has no `form_id`** and **`value_boolean` has no B-tree**, so per-form answer aggregation must join out through `form_version_id`, and grouping a yes/no question is unindexed. Both are recorded for H24a rather than fixed here.

### Risks & Mitigations

| Risk | Mitigation |
|---|---|
| A dashboard number disagrees with the inbox | D2's single countable-submission predicate, binding on both surfaces; D7's invariant forbids any future rollup that could drift from it |
| A cross-version average silently drops rows | D4 makes the drift a visible refusal naming the version; forbidden to coerce across partitions |
| A completion metric is presented as fact over a self-selected, nightly-deleted denominator | D5 renames it, prints its denominator on the tile, and suppresses it beyond the retention window |
| An author ticks "Indexed for reporting" on a field that can never project | D3(ii) requires the authoring surface to refuse the promise; the publish gate cannot, and is not changed here |
| The analytics query blows the NFR budget on a large tenant | D7's bounded-query rules; the measured p95 trigger and the pre-authorised `MaintenanceJob` materialization path |
| The new surface ships with zero accessibility coverage while the gate stays green | D9's e2e fixture obligation — a Business-entitled tenant — stated as a blocking requirement on H24b |
| A chart passes axe and is still unreadable | D12's data-table contract, pinned by a unit test rather than by the axe gate |
| A future `default-src` policy is forced to allow inline styles because of charts | D10 forbids `:style` bindings and runtime colour computation in the primitives |
| Phase 4 rebuilds the deferred event stream without its known caveats | D1 records both — the offline undercount and the branching-graph funnel problem — in this document |

## Alternatives Considered

**1. Ship the event stream now (A1) — rejected for this phase, not forever.** It is the only way to answer the questions users actually ask, and it is where Phase 4 should start. It is rejected here because none of the phase's three written acceptance criteria need it; because it opens a fourth unauthenticated ingress class on a single self-hosted box; because its retention and partitioning would have to be right in the first migration, in an area where the corpus has no precedent at all (no partitioned table, no trigger, no pruning job outside the framework's own, and no batched-delete pattern anywhere); and because the two fidelity caveats in D1 mean the funnels it produces would need heavy qualification even once built.

**2. A server-side view counter (A2) — rejected as the worst trade.** It carries most of the write-path cost of A1 (a new table, a new write on the public render path, a retention answer) for the least of its value: it makes "views vs submissions" real but still cannot see where anyone left. If a write path is going to be opened, it should be the one that answers the question.

**3. Rollup tables from day one (B1) — rejected on evidence, not taste.** `docs/non-functional-requirements.md:20` permits precomputed aggregates *if the target is not met*; it is a conditional permission that has never been evaluated, because no analytics query exists to measure. Building a rollup before the measurement contradicts the doctrine this codebase has ratified twice and buys a permanent drift surface for a performance problem nobody has observed.

**4. A charting library (C1) — rejected on four grounds, of which the first is decisive and repository-specific.** The token pipeline emits `var()` references rather than resolved colours and the theme flips live on the root element, so a canvas-rendering library goes stale on a theme change unless someone remembers to wire an observer — a defect class we would be choosing. Beyond that: a design-system component with a story is under the merge-blocking axe job by construction and a library inside `resources/js` is not; DSR §1.3 makes a library a documented exception rather than a default, and charting is a recurring need (tenant dashboard, per-form analytics, the backlog's geo heatmap, OCR confidence display) that would otherwise accumulate three of them; and the npm-audit gate is production-only, so a library's transitive advisories are merge-blocking indefinitely. **Bundle size is the weakest argument and is not relied on** — `GeoInput.vue` already lazy-loads Leaflet, so a chart library could have cost zero first-paint bytes.

**5. No charts at all (C3) — rejected as a deferral wearing a decision's clothes.** The Phase-3 criteria never say "chart", so this is defensible on the letter; but `PRD.md:197-198` asks for a volume trend and a per-form time series, DSR §5 already placed this surface in the dashboard's view-switcher, and declining to decide would push the identical fork into Phase 4 having spent a phase pretending it was closed.

**6. A tag model on forms — rejected as premature.** It would be a new tenant table plus a new authorization question ("can a Form Editor see a tag's aggregate?"), invented inside an already-large increment to satisfy one word of an example in an acceptance criterion, when an indexed, grant-integrated, subtree-queryable axis already exists.

## When to Revisit

- **Immediately, on any of:** the first customer who cancels or churns over drop-off visibility; Business going on sale (which turns D9's hidden surface into a genuine upsell question); or Phase 4 opening the engagement event stream, at which point D1's two recorded caveats are the starting point rather than a rediscovery.
- **On measurement, not suspicion:** D7's materialization fallback opens when a real tenant's analytics query is measured above the 1.5s maximum — not when someone expects it to be.
- **When answer-value analytics is asked for on historical data**, which is the moment the backfill job deferred by D3 becomes worth its migration.
- **When a tenant needs a grouping orthogonal to authorization** — one form in two programs — which is when D6's tag model earns its table.
- **When a chart need genuinely exceeds five categorical series or the four primitives of D10**, which is a design-system increment, and should be weighed against C1 again with a real requirement in hand rather than a hypothetical one.
