# ADR-0012: Custom-Domain Resolution (public forms only; TXT proves control; an operator, not the tenant, puts a host into service)

## Status

**Accepted — 2026-08-04.** Authored inside its own code increment (**H22a**), as the Phase-3 decomposition plan specified: the data model already existed, the middleware swap is a documented stancl feature, and `EstablishTenantDatabaseContext::resolveTenant()` was already resolution-agnostic, so the only genuinely open decisions were small enough to belong with the code rather than ahead of it. Those decisions turned out to be TXT-vs-CNAME, **which route groups a custom host may serve**, and what stands between a verified hostname and a served one while per-domain TLS does not exist. This unblocks **H22b** (the domain admin UI).

- **Deciders:** Founding engineering (architecture owner) + product.
- **Related ADRs:** **ADR-0002** (shared-DB RLS — `:121`/`:136` deferred custom domains to Phase 3 and predicted they would "reuse the same middleware pipeline with a domain-to-tenant lookup table instead of subdomain parsing", which is exactly what §D1 does). **ADR-0005** (self-hosted Windows Server — its `win-acme` TLS story is Track B, and Track B being deferred is what forces §D6). **ADR-0008** (entitlement & metering — §D6 there holds Business from sale, so nothing this ADR ships can be bought in Phase 3; §D9 below inherits the `custom_domain` key rather than coining one). **ADR-0009** (OAuth connector token custody — its §D2 revisit trigger already scoped this feature, and §D1 below is that scoping honoured rather than re-litigated). **ADR-0007** (async execution — §D8's sweep is a `MaintenanceJob`, and it is the first one that legitimately does its work inline). **ADR-0010 is reserved for H1d** (the OCR provider bake-off, still blocked on the user's filled paper-form samples); this ADR takes 0012 rather than filling that hole, because 0010's gap is temporary and deliberate.
- **Related docs:** `docs/data-dictionary.md` §1 (the `domains` section, added by H22a — the table had never had one); `docs/deployment-infrastructure.md` §8 (the manual-certificate runbook this ADR requires); `docs/architecture/technical-architecture.md` §7.4 (the SSRF authority §D11 declines to unify with); `docs/pricing-feature-gating-matrix.md` (the Business-tier `custom_domain` row).

---

## Context

1. **The data model existed; the feature did not.** `domains` shipped in Increment A with five columns — `id`, `domain` (globally unique), `tenant_id`, timestamps — and is deliberately **RLS-exempt**, because it is the table read *before* any tenant context exists in order to decide which tenant a request belongs to; scoping it by tenant would be circular. It had no verification columns, no discriminator, and — critically — **no production write path at all**. Every row in the repository was written by `E2eSeeder` or a test fixture. Tenant onboarding created a `tenants` row and nothing else.

2. **`domains.domain` holds a subdomain LABEL, not a hostname.** Under `InitializeTenancyBySubdomain`, stancl passes `$parts[0]` — the first label — to `DomainTenantResolver`, so every one of the ~60 fixture sites correctly writes `'domain' => 'acme'`. That is not legacy and does not change: after H22a the same rows are still what the subdomain arm resolves.

3. **Two live defects had been recorded and deferred.** `TenantMembershipService::buildInviteAcceptUrl()` and `GuestDraftController::resumeUrl()` both interpolated that bare label into `"https://{$domain}/…"`, so **every invitation email and every respondent resume link the platform has ever sent carried a URL that resolves nowhere**, with a hard-coded scheme that is also wrong in local development. H17 wrote the defect down in `TenantUrl`'s docblock and deliberately did not retrofit them.

4. **H17 guessed at H22's shape, and got half of it right.** `TenantUrl::host()` treated any stored value containing a dot as a complete host — "that is the shape H22 will introduce" — pinned by a passing test. Right about the storage. Wrong about the consequence: see §D1.

5. **The gate exists, is unsellable, and is not the constraint.** `custom_domain` has been a seeded `FEATURE_KEYS` entry since H5a, on Business, which ADR-0008 §D6 seeds `is_active = false` — built and gated, held from sale until the production host exists. So no tenant can buy this in Phase 3.

6. **There is no TLS story for a custom domain, and will not be one this phase.** Per-domain certificate issuance is `win-acme` at nginx on the Track B box (`docs/deployment-infrastructure.md` §8), which is not stood up and is deferred by product decision. The phase's own scope boundary says H22 ships "verification + routing + a manual-cert runbook, **failing closed**" — but did not say what mechanism makes it fail closed.

---

## Decision

Custom domains serve **public forms only**. A tenant proves control of a hostname by publishing a **TXT** record, entirely self-serve. An **operator** — not the tenant — puts a verified hostname into service, and only after installing a certificate for it by hand. Visibility of a not-yet-live domain is closed off by **one global scope on the model**, so no reader has to remember the rule.

### The twelve sub-decisions

- **D1 — A custom host serves the PUBLIC GUEST RUNTIME and nothing else.** Only `routes/tenant.php`'s guest group gets the new identification middleware. The authenticated app, the invitation group and both `/api/v1` groups keep `InitializeTenancyBySubdomain`, where a custom host throws `NotASubdomainException` and `bootstrap/app.php` already renders that as a redirect to the central app — **fail-closed with no new code**. This is not a narrowing invented here: ADR-0009 §D2 already states that "Business-tier `custom_domain` covers public forms, not the admin app", listing the platform moving its app onto custom domains as a *future* revisit trigger. Honouring it deletes six hazards by construction rather than defending against them: two-origin CSRF, cross-host session (`SESSION_DOMAIN` is null, so cookies are host-only), the OAuth-return open redirect, the invite-link open redirect, the PDF-link open redirect, and Sanctum bearer tokens being accepted on a hostname the tenant controls.

- **D2 — Identification is a SUBCLASS, because stancl's host predicate is wrong twice.** `App\Http\Middleware\InitializeTenancyByPublicHost` overrides only `isSubdomain()`. Stancl's is a bare `Str::endsWith($host, config('tenancy.central_domains'))`, which (a) has **no dot boundary**, so `evilmeridian.test` "ends with" `meridian.test` and would be resolved by the label `evilmeridian` — an attacker owning that real domain could serve that tenant's forms on their own hostname; and (b) sends a **bare-label host** (`Host: acme`) to the full-host arm, where the lookup matches the literal string `acme`, which is exactly what a subdomain tenant stores — making every tenant's label reachable as a raw Host header from any network position, since `TrustHosts` is not enabled. Both were only reachable once the domain arm was enabled; neither was caught by any existing test.

- **D3 — The DOT is the discriminator; there is no `kind` or `status` column.** After D2 the dot is an *exact* partition of the two producers rather than a heuristic: the subdomain arm can only ever pass a single dotless label, and D2 guarantees the domain arm only ever receives a dotted host. A `kind` column would be a second source of truth that can disagree with the first — and would disagree on day one, since an existing test already writes `forms.acme.com` and would take any sane default; without a default it breaks sixty write sites in one commit. `domains_custom_requires_token_chk` makes the two unable to drift. If a materialised discriminator is ever wanted, `GENERATED ALWAYS AS (position('.' in domain) > 0) STORED` is the zero-risk addition.

- **D4 — State is DERIVED from three nullable timestamps, so no default can be fail-open.** `verified_at`, `activated_at`, `verification_checked_at`. `pending` → `verified` → `live`. A `status VARCHAR DEFAULT …` invites exactly one class of bug, and every possible default value is the wrong one.

- **D5 — TXT proves control, at a `_`-prefixed leaf. Not CNAME.** Four reasons, in order of weight. (1) **A CNAME cannot exist at a zone apex** (RFC 1034 §3.6.2 — it may not coexist with the SOA and NS a zone always has), and branding customers ask for apexes. (2) **CNAME conflates proof with traffic.** H22 explicitly does not own routing: the certificate is installed by hand, so a CNAME-as-proof scheme would require the customer to repoint live traffic at a box holding no certificate for them *before* we agree to serve it — a self-inflicted outage. TXT is out-of-band: prove, then we issue the certificate, then the customer cuts over last, with zero downtime. That ordering is the entire reason the scope boundary reads "verification + routing + a manual-cert runbook". (3) Re-checking a CNAME re-checks routing; re-checking a TXT re-checks **control**, which is what dangling-DNS is about. (4) The `_meridian-challenge` leaf (RFC 8552) cannot collide with a hostname and keeps the challenge out of the crowded apex TXT set, where SPF, DMARC and other vendors' verification records live and registrar UIs are prone to merging or replacing wholesale. **Rejected:** HTTP `/.well-known/` verification, which has CNAME's chicken-and-egg problem and would have to punch through the very unverified-domain refusal it is trying to satisfy; and DNS-over-HTTPS to a public resolver, which would reuse the existing `Http::fake()` seam for free but adds a third-party trust anchor to a security control.

- **D6 — Activation is an OPERATOR action, and it is the fail-closed mechanism.** `php artisan domains:activate` is the only code path in the application that can set `activated_at`; there is deliberately **no API endpoint**, and `OpenApiContractTest` asserts its absence so a resource-route reflex cannot add one. Rationale: until Track B automates issuance, a certificate is installed by hand, so a tenant able to activate its own domain could put its respondents on a plaintext origin — and the resume link they receive would carry that origin. Requiring a human who has just done the nginx work turns a runbook instruction into a mechanism. There is no `activated_by` column: the only actor is someone on the box, and a nullable FK that is always null would be worse than the gap it pretends to close.

- **D7 — One GLOBAL SCOPE is the chokepoint, not a filter at each call site.** `App\Models\Domain` hides any custom domain that is not live. It closes five readers at once, including two the increment never edits: stancl's `DomainTenantResolver` builds its `whereHas` subquery from `newQueryWithoutRelationships()`, which registers global scopes, so the vendor resolver fails closed with no patch; and `ConnectorRedirector::tenantHost()` — the file whose docblock calls itself "the open-redirect control: the host is looked up from the tenant's own `domains` row and NEVER echoed from the request" — keeps that claim true with **zero edits**. Without this, "looked up from the tenant's own row" would have *become* the attack the moment a tenant could write that row. `unscopedQuery()` drops one *named* scope rather than all of them, so a scope added later is not silently discarded by the service and the sweep.

- **D8 — The sweep is a `MaintenanceJob` that does its work INLINE, and its batch bound is a correctness property.** It is the first such job in the codebase, and it is correct rather than a violation: ADR-0007 §D3 rule 2 explicitly permits `domains`, and rule 3's "sole tenant-touching side effect" is satisfied *vacuously* because a write confined to an exempt table is not tenant-touching. A fan-out would be strictly worse — every tenant with no custom domains, i.e. all of them initially, would get a queued job every tick. The base class's rule 3 was amended in the same increment to say so. **`dns_get_record()` takes no timeout**, so an unbounded batch of dead nameservers is the one way this job can blow its 300s budget — and with `$tries = 1` that means `failed_jobs` on every tick, forever. The batch is bounded and ordered oldest-checked-first, which makes the bound fair rather than starving.

- **D9 — Reads and deletes are NOT plan-gated; writes are.** `feature:custom_domain` gates claim and verify only. Verbatim the `api_access` precedent, and it matters more here: a tenant downgraded off Business keeps a **live, resolving hostname**, so it must remain able to see it and take it down. `RequireFeature` fails **open** on a null plan, so every gate test assigns a tier. **The resolver deliberately does not consult entitlement at all** — that would mean an RLS-scoped `subscriptions` read in the hottest middleware in the application, for a tenant that is not yet resolved. Stated consequence rather than a discovered one: a downgrade does not withdraw a live host; that belongs to whatever increment ships the downgrade/dunning flow.

- **D10 — `manage:domains` is a NEW ability mapped onto an EXISTING permission.** New, because an already-minted `manage:settings` token would otherwise retroactively gain the power to point the hostname a tenant's respondents visit somewhere else — the sharpest instance yet of the standing rule. Mapped onto `tenant.settings.manage` rather than coining a thirtieth permission, on the `read:analytics` precedent: that permission's audience (Owner + Admin) is already exactly right, and a new one would touch `RolePermissionSeeder`, the role matrix and `multi-tenancy-rbac-design.md` §5 for nothing.

- **D11 — The verification token is PUBLIC and is deliberately NOT redacted; and `OutboundUrlGuard` is not unified with the DNS seam.** The token is 256-bit CSPRNG, random and never derived (an HMAC would be unrotatable per claim and would make an APP_KEY compromise a domain-claim primitive). It is stored plaintext and kept out of `AuditRedactor::SECRETS` on purpose: it is looked up at one exact hostname, so knowing it helps nobody who does not already control that zone — it lives in public DNS by design. Recorded explicitly because ADR-0009's lesson is that an unregistered credential-bearing alias is silently un-redacted, and a reviewer will check. Separately, `OutboundUrlGuard` resolves A records to answer "is this address public" as an SSRF control on a security boundary; the new seam asks "did the tenant publish our token". They share the word DNS and nothing else; unifying them would widen a security-critical interface for no gain, and that class's tests avoid resolution entirely by using literal IPs.

- **D12 — The central-domain refusal is application-layer, NOT a CHECK constraint.** Baking `config('tenancy.central_domains')` into DDL would make the *schema* environment-dependent — `localhost` locally, `meridian.test` in CI, the real host in production — so `migrate:fresh` would produce three structurally different databases. That is a worse defect than the one it closes. Instead the refusal lives in `ClaimableDomain`, using **the same equality-plus-dot-boundary predicate as D2's routing and as `RequirePlatformHost`**, so what routes, what may be claimed, and what may render a login form cannot drift apart.

## Consequences

### Positive

- The authenticated app remains a **single origin**. No second login, no per-host logout, no `SESSION_DOMAIN` change, no CSRF review — none of it is reachable.
- Two live defects are closed as a by-product: every invitation and resume link now resolves, and every outbound tenant URL in the application is composed in exactly one place with two explicit arms.
- A latent non-determinism is closed with them. `$tenant->domains()->value('domain')` is `first()` with no `ORDER BY`; a second row would have made the emitted host depend on physical row order — the same shape as the double-subscription tie that once made a suite flip green-to-red because a file was added elsewhere in the tree.
- A phishing surface nobody had noticed is closed. Fortify registers `/login` with no domain constraint and `auth` is priority-ordered ahead of tenancy, so the platform's credential form would have rendered on a tenant-controlled hostname. `RequirePlatformHost` 404s it.

### Negative / accepted trade-offs

- **A tenant cannot self-serve all the way to a live domain.** Reaching `verified` is automatic; reaching `live` waits on a human. Deliberate (D6), and it is the honest state of the world until Track B exists.
- **A verified domain is never auto-demoted.** The sweep records consecutive failures but does not withdraw routing: a transient resolver outage must not take a paying tenant's production host out of service, and the takeover threat is blunted because `domains.domain` is globally unique — a new owner of a lapsed domain cannot claim the row. See *When to Revisit*.
- **Nothing shipped here can be sold in Phase 3.** Business is `is_active = false` (ADR-0008 §D6). This is build-and-gate.
- **The admin surface is H22b.** H22a ships the `/api/v1` write path because without one the verification service, the sweep and the resolver gate would be untestable dead code — a security control with no producer.

### Risks & Mitigations

| Risk | Mitigation |
|---|---|
| An unverified `evil.com` row turns the OAuth return URL into an open redirect | D7's global scope hides it from every reader; D1 keeps `/integrations` off custom hosts entirely; `ConnectorRedirector` reads the dotless row explicitly |
| A tenant claims a central domain or a subdomain of one, shadowing the console or another tenant | Refused at claim time (D12), unreachable at routing time (D2), and unverifiable in any case — only the platform controls that zone |
| Suffix confusion (`evilmeridian.test`) resolves another tenant | D2's dot-boundary predicate; asserted with a real tenant labelled `evilmeridian` |
| Name-squatting blocks a hostname's real owner | Pending claims expire on a TTL and are reaped by the sweep |
| Dangling DNS after a tenant abandons a domain | Periodic re-verification records the failure; the global unique index prevents a new owner claiming the row. Demotion deferred — see below |
| A custom domain served over plaintext | D6's operator gate: nothing routes until a human who installed the certificate says so |
| `dns_get_record` hangs the sweep into `failed_jobs` forever | D8's bounded, fairly-ordered batch |

## When to Revisit

- **Track B is stood up and TLS issuance is automated.** Then D6's operator gate can become an API action, and — because a stale verification could drive a certificate reissue — the deferred "demote after N consecutive TXT misses" becomes worth building.
- **The platform moves its authenticated app onto custom domains.** That is ADR-0009 §D2's own revisit trigger and it re-opens everything D1 deleted: `SESSION_DOMAIN` must stay null, `AuthenticatesSessions` must be reconsidered, logout becomes per-host, and the OAuth return URL needs a fresh open-redirect argument.
- **`DomainTenantResolver::$shouldCache` is ever enabled.** Under D7's scope, a domain being demoted is already excluded when the `saved` event fires, so its cache key would never be forgotten and a revoked host would keep routing for up to `$cacheTTL`. A test pins `$shouldCache === false` today; whoever flips it must override `getArgsForTenant()` with `unscopedQuery()` first.
- **A tenant needs two simultaneously-live custom domains with a chosen primary.** Today the public arm picks the oldest-activated, deterministically, so outstanding resume links keep resolving. An explicit `is_primary` belongs with H22b's UI, not before it.
