# ADR-0020: The Gamification Awarding Substrate — what records an achievement, and what may never rewrite one

## Status

**Accepted — 2026-08-17.** Authored alongside its own code increment (**K1a**), on the ADR-0012/H22a, ADR-0013/H25, ADR-0014/H23a1, ADR-0015/I7a, ADR-0016/P1a, ADR-0017/P2a and ADR-0018/P2b precedent.

This is the substrate decision for the **full gamification engine** — the 2026-08-09 decision of record's *very last increment before deployment* (`docs/PRD.md:128`), scheduled last on purpose so it is designed **once against the finished feature set** rather than retrofitted per feature. The engine's own specification is `docs/gamification-design.md` (doc #28); this ADR records only the choices that would be expensive to reverse.

## Context

1. **Nothing existed, and that was measured rather than assumed.** A sweep for *points / score / badge / achievement / streak / leaderboard / rank / xp / reward / milestone* across `app/ database/ resources/ packages/ config/ docs/` returned **zero** implementation hits before K1a. Every apparent match was a false positive: `MdsBadge` is the status pill, `score` is `FieldType::likert_matrix`'s `{row:score}` payload, `points` is GeoJSON vertices and `webhook_endpoints`.

2. **⚠️ There is no historical event stream to replay.** `App\Events\DomainEvent` subclasses are **in-memory Laravel events only** — nothing persists them. `webhook_deliveries` is an *outbound delivery* ledger that exists only where a tenant happened to subscribe an endpoint. An engine attached solely to listeners therefore starts **every** workspace at zero, including the seeded demo tenants the product owner tests on.

3. **`audits` is the one ledger that survives.** Append-only, tenant-scoped, carrying `user_id`, `event`, `auditable_type` and `created_at`, with an index its own migration describes as *"one actor's actions"* — which is literally a streak query. It is also **deliberately noise-reduced**: `docs/audit-compliance-logging-spec.md` §1 excludes ordinary profile edits, so "activity" there is not "everything a person did".

4. **J5's progress concept is 100% derived and cannot be built on.** `GettingStartedChecklist` recomputes done-ness per request from live KPI counts; the entire feature persists **one byte** (`tenant_users.onboarding_dismissed_at`). *When* a step became true is unrecoverable from it.

5. **Half the scorable acts are unbounded.** Review, edit, invite and publish can each be repeated indefinitely by one person against one object. Any scoring scheme without an exactly-once rule makes churning the queue the most efficient way to top the ladder.

6. **The production box does not run the scheduler.** `routes/console.php:40-41` records that `deploy.ps1` provisions no Task Scheduler task, which is why the SSO services trim on the write path. Any design here that depended on a nightly job would silently never run.

## Decision

**Record achievements as an append-only ledger of individual awards, written synchronously by listeners on signals that already exist, keyed so that every act can be awarded exactly once, and never rewritable — including by us.**

### The sub-decisions

**§D1 — An award LEDGER, not a derived read-model and not a maintained balance.** Three shapes were available. *Derive everything from `audits` on read* (J5's shape) works for points and streaks and was genuinely tempting — it needs no new write path and it is retroactive for free. It is rejected because it makes the **compliance** ledger load-bearing for a game: `audits` is noise-reduced by design (Context §3), so scores would quietly mean "what we happened to audit", and every future decision about what to audit would become a scoring decision made by someone not thinking about scoring. *A maintained `points` balance column* is rejected on `EntitlementService::countGauge()`'s own recorded argument — a running aggregate drifts, and unlike a usage gauge there is no authoritative table to reconcile it back from. The ledger keeps the good half of the derived approach: totals, streaks and standings are all `SUM`/`DISTINCT` over an indexed `(tenant_id, user_id, awarded_at)`, so nothing can disagree with anything.

**§D2 — Consume the existing signals; mint NO `DomainEventType` case.** `DomainEventType` is not a catalog — it is the webhook and native-connector **subscription vocabulary** and it feeds `openapi.json`, so a case there is a four-file act *with a published contract attached forever*. Gamification is an internal read-model; widening a public integration surface for it would be paid once and owed permanently. Seven of the eight listeners attach to events that already exist. The eighth act — form creation — had no event at all, so K1a adds `App\Events\FormCreated` as a **plain `Dispatchable`** on the `MemberJoined` precedent (`app/Events/MemberJoined.php:18-27` argues this exact trade). **The cost, stated rather than discovered: a tenant cannot fire a webhook when somebody starts a form.** Promoting it later is additive and breaks nothing.

**§D3 — The idempotency key is `(tenant_id, user_id, rule, subject_type, subject_id)`, every part NOT NULL, enforced by a unique index and honoured with `ON CONFLICT DO NOTHING`.** Two details are load-bearing and neither is obvious. **(a) No part may be nullable**, because in PostgreSQL a UNIQUE index treats NULLs as *distinct* — a nullable subject would let the same act be awarded repeatedly while the index looked like it was preventing exactly that. Every rule therefore has a real subject, including `member.invited`, whose subject is a **SHA-256 of the normalized email** (the event carries an address and no user id, and an address has no business in a scoreboard table). **(b) `ON CONFLICT DO NOTHING` rather than catching 23505**, because in PostgreSQL a constraint violation aborts the *whole* transaction: a caught duplicate would leave the caller's transaction poisoned. That is not hypothetical — `FormService::create()` is itself called from `TemplateService::instantiate()` inside an outer transaction, so a duplicate award raised there would take out a template instantiation that had nothing to do with scoring.

**§D4 — `append_only` RLS, and the weight is COPIED at award time.** `point_awards` gets the `audits` policy shape: SELECT and INSERT only, no UPDATE or DELETE policy at all, so FORCE RLS denies mutation to every role including the table's owner. Combined with `points` being written from `PointRule::points()` at award time rather than joined at read time, this makes one property structural: **re-weighting a rule moves future awards only, and the ledger keeps saying what it said.** A leaderboard that silently rewrites its own history the day somebody edits a constant is not a record of anything. It is also what lets the Settings → Modules card promise that switching gamification off *deletes nothing* as a fact about the schema rather than as an intention.

**§D5 — Streaks are DERIVED; the only stored history is the award ledger, which is BACKFILLED once from `audits`.** A streak is `DISTINCT awarded_at::date` walked backwards — nothing to drift, nothing to reconcile, and critically **no nightly job**, which Context §6 says would never run in production anyway. `awarded_at` is therefore a real column distinct from `created_at`: the K1c backfill writes rows *today* for acts that happened *months ago*, and a streak computed off `created_at` would show every historical workspace with one enormous single-day streak on install day. **Product decision 2026-08-17: backfill.** The alternative — everyone starts at zero — leaves the demo tenants empty and the feature untestable on arrival. ⚠️ The backfill must **not** run inside a migration: a migration executes with FORCE RLS and no tenant GUC, so `INSERT…SELECT` there writes zero rows. It is an operator command fanning out one `TenantAwareJob` per tenant.

**§D6 — `gamification` is a plan feature key granted on EVERY tier, including Free.** It is in `PlanCatalog::FEATURE_KEYS` only so the Settings → Modules card can render its toggle and the admin console can show `tenant_disabled` — `ToggleableModules::KEYS` may contain nothing the catalog does not, and `SettingsVocabularyTest` pins that. **Product decision 2026-08-17: not a commercial gate.** It is one of the six standing principles (PRD §3.7), and a tier ladder would make the principle invisible to precisely the tenants a first-run experience exists for. The consequence is that the **tenant's own toggle is the only control anyone has over it** — which is the intent, and which is why §D4's "nothing is deleted" guarantee matters more here than for any other toggleable module.

**§D7 — Leaderboard visibility reuses the org/own split; NO thirtieth permission key is minted.** **Product decision 2026-08-17.** Every member sees their own points, streak and standing ("4th of 12"); the **named** ranked list is gated on the existing `dashboard.org.view`. The 29-permission catalog (`RolePermissionSeeder::PERMISSIONS`) is closed and every addition has been argued individually; this one has no argument, because "who may see workspace-wide numbers about other people" is a question `dashboard.org.view` already answers for the dashboard and for submissions. Minting a key would also mean deciding which of five roles hold it — re-litigating a matrix that already encodes the answer.

**§D8 — A `guest` submission credits nobody.** `submission.collected` is awarded only where `submissions.respondent_user_id` is set — a member who encoded, synced or scanned it. The tempting alternative, crediting the form's owner, would turn the per-member ladder into a popularity contest decided by whoever published the busiest public link, which is not what *"who collected the most data"* means. Workspace-level "team progress" counts every submission. This is the **enumerator collection streak** the decision of record actually names.

**§D9 — A badge row stores its KEY and its DATE and nothing else — the inverse of §D4, and the inversion is the decision.** *(Added in place by K1b, 2026-08-17, on the ADR-0012 §D9 / ADR-0014 amendment precedent.)* `badge_awards` ships with **no `threshold` column**, and a reader who knows §D4 will otherwise assume that was an oversight and add one. §D4 copies `points` at award time because its **readers consume the number** — totals, the ladder and every future digest are `SUM(points)` — so *not* copying it would rewrite every historical total the day somebody edited a constant. **Nothing reads a badge's threshold**: the surface renders `BadgeKey::label()`, and the ladder counts rows. A stored copy would be a PHP constant duplicated on every row with no consumer, which is the shape this project refuses on the record twice already (`PointRule::isRepeatable()`, and `sso_auth_failures`' absent Google twin). **The asymmetry is exact: points are a derived quantity destroyed by not copying; a threshold is a rule that can be re-evaluated at any time, because `point_awards` is append-only and complete.** ⚠️ And `append_only` makes the column *worse*, not safer: with no UPDATE policy a threshold written wrong is permanent and uncorrectable, in a column nothing selects. **Two consequences accepted rather than hidden.** Lowering a threshold is retroactive in *effect* but not in *date* — the next qualifying award fires the badge stamped with **that** act's date. Raising one leaves existing holders standing, because there is no DELETE policy; that is the "persisted, not derived" claim made enforceable rather than promised. If either ever matters, the remedy is a re-evaluation mode on K1c's per-tenant fan-out, which is additive. ⚠️ **Why this is in the ADR at all, when the catalog is not:** the catalog is cheap to reverse (one PHP file, badges are additive, thresholds move) and lives in doc #28. *Adding the column later is not* — every historical row would be NULL forever and could never be retro-filled, which is the same irreversibility §D4 exists to name. It belongs beside the decision it inverts, not in a different document.

**§D10 — The backfill's source is `audits` AND `tenant_users`, because §D5's own sentence is not achievable; and the streak's day boundary is a stated literal rather than an inherited setting.** *(Added in place by K1c, 2026-08-18, on the §D9 / ADR-0012 §D9 / ADR-0016 amendment precedent — the correction belongs beside the decision it corrects, and discharging it from a new document is a cross-document discharge nobody would find.)*

**(a) TWO SOURCES.** §D5 says the ledger is *"BACKFILLED once from `audits`"*. Verified against the code before K1c wrote a line, that is impossible for three of the seven rules. **`TenantMembershipService::invite()` writes no audit row whatsoever** — it raises `MemberInvited` and nothing else, so `member.invited`, the second-highest-weighted rule in the engine, has zero historical evidence there. (`docs/audit-compliance-logging-spec.md` §1 claims the `tenant_users` `created` row covers *"invite sent"*; as built it does not.) **`accept()` writes neither an audit row nor an event**, so that `created` row covers only the three self-serve doors and misses the commonest one. And **`('submission','updated')` is written by two different services** — `SubmissionReviewService::apply()` and `SubmissionAnswerEditService::edit()` — so `(auditable_type, event)` cannot separate a 3-point review from a 1-point edit.

So: **`audits` is the authority for the five ACT rules, `tenant_users` for the two MEMBERSHIP rules** (`invited_by`, `invited_at`, `joined_at` — complete for every door, and the table the membership *is*). Review and edit are separated on the SHAPE of `new_values` (a review always carries `remarks`; an edit carries flattened `answers.<key>` entries and never does), with anything matching neither counted as **unmapped** rather than guessed. ⚠️ Note the trap this avoids: `member.joined`'s subject is the USER id while the audit row's `auditable_id` is the MEMBERSHIP uuid, and keying on the wrong one does not collide with the live award — the subject is part of the idempotency index — it writes a **second** row. A doubled score with no error.

**Why this is an amendment and not a new ADR.** Nothing about §D1's substrate choice changes: the ledger is still the only stored history, still append-only, still complete. What changes is a factual claim §D5 made about where the evidence lives — and a reader who found §D5 and not this would build the wrong thing, which is the definition of a correction belonging in place.

⚠️ **AND THE VERIFICATION FOUND A LIVE DEFECT, NOT MERELY A DOCUMENTATION ONE.** Because `accept()` raised no `MemberJoined`, an invited member who accepted earned no `member.joined` points and **no `welcome` badge** — the one badge whose stated purpose (doc #28 §7) is to keep a brand-new member's achievements surface from being blank — and the Owner who sent the invitation was told nothing. K1c fixes it rather than filing it, because the alternative is a scoreboard that permanently disagrees with itself: the backfill grants every historical invited member their join points, and the very next acceptance would grant none.

**(b) THE DAY BOUNDARY.** §D5 requires a streak to be `DISTINCT awarded_at::date` walked backwards but does not say whose date. **Decision: a stated literal, `StreakCalculator::DAY_BOUNDARY = 'UTC'`, passed as a parameter with that constant as its default.** It is deliberately **not** `config('app.timezone')`, and the fact that the two agree today is exactly what makes reading the config the tempting mistake — it would make the meaning of *a day* in every streak in the product depend on a setting nobody thinks of as a gamification setting, and moving it would re-cut every member's history at once with no migration, no announcement and nothing to notice. Nothing in the schema carries a per-tenant or per-user zone; the only `timezone` column anywhere is `forms.timezone`, whose own migration scopes it to authoring/display and says it is never consulted server-side. **When to revisit: the day tenants gain a timezone of their own**, at which point the caller supplies it and this class does not change — which is the whole reason it is an argument rather than a constant read inside.

⚠️ **The streak also survives "nothing yet today" and breaks only after a full missed day.** Requiring today's date would zero every member in the product between midnight and whenever they next act; the number somebody sees at breakfast would not be the one they saw the night before.

**(c) A CONSEQUENCE OF §D8 THAT IS EASIER TO READ AS A BUG THAN AS A DECISION, RECORDED HERE SO IT IS NOT "FIXED".** Workspace `responses` and the sum of members' `submission.collected` awards **do not match**, and the difference is exactly the guest submissions. §D8 is why: the ladder credits only the member on `submissions.respondent_user_id`, while a guest response is still a response the workspace collected. On a tenant collecting mainly through public links the gap is most of the total. Neither number is wrong; they answer different questions.

**§D11 — The ladder's roster is ACTIVE MEMBERSHIP, not the ledger; so the workspace totals and the ladder deliberately do not reconcile, in three places rather than one.** *(Added in place by K1d, 2026-08-18, on the §D9 / §D10 precedent — the correction belongs beside the decisions it follows from, and `0021` was again not taken: nothing about §D1's substrate changes.)*

**(a) THE QUESTION §D7 DID NOT ANSWER.** §D7 settles *who may see the named list*. It does not say **who is on it**, and the two obvious answers differ: group the ledger, or read the membership. **Decision: the membership.** `point_awards` is append-only and has no DELETE policy (§D4), so a departed member's rows outlive their membership by design — the table's own migration says so, calling their awards *"visible to nobody"*. A ladder built by grouping the ledger therefore names ex-colleagues forever, and the person who left keeps a rank on a board they cannot see. `LeaderboardService::roster()` reads `tenant_users` at `status = 'active'` and the ledger only supplies totals for the people that read returns.

⚠️ **AND THE `users` RLS POLICY WOULD HAVE PRODUCED THE RIGHT ANSWER BY ACCIDENT, WHICH IS PRECISELY WHY THE PREDICATE IS WRITTEN OUT.** `users_visibility` is *self OR an ACTIVE co-tenant membership*, and RLS applies at every reference to `users` — `MemberSearchArm` records this measured on the seeded corpus, where joining `tenant_users` to `users` returns the six active members and silently drops the invited one whose membership row is perfectly visible. Leaning on that would put this feature's roster rule in a 2026-07 migration, where nobody reading the service could find it, and would make a later widening of that policy change who appears on every leaderboard in the product with no test anywhere going red. The explicit `whereExists` is the same belt-and-braces `MemberSearchArm` argues for, and it is expected to **survive** mutation for the same reason: RLS holds the line underneath it.

**(b) THE DENOMINATOR IN "4th of 12" IS THE TEAM, AND TIES SKIP.** doc #28 §10 asks for that sentence without defining the twelve. It is **active members**, the same number `TeamProgress::$activeMembers` reports — not the number of people who have scored. A member who has earned nothing is *twelfth of twelve*, not absent: "you are not on the board" is a worse answer, and a denominator that grew as colleagues started earning would make somebody's own position appear to move on a day they did nothing. Rank is **competition ranking** — one plus the number strictly ahead — so a tie for 2nd is followed by 4th, which is the only reading under which "4th of 12" and "three people are ahead of me" agree.

**(c) THE THREE GAPS, NONE OF WHICH IS A BUG, ALL OF WHICH LOOK LIKE ONE.** §D10(c) already recorded the first. K1d adds two more of the same shape, and they are listed together because a surface showing them side by side has to say which is which:

| Pair | The workspace number is larger by | Because |
|---|---|---|
| `team.responses` vs the responses credited across the ladder | the GUEST submissions | §D8 — a public-link response credits nobody, or the ladder becomes a contest between links |
| `team.points` vs the sum of ladder entries | departed members' awards | (a) — the ledger outlives the membership |
| `team.contributors` vs ladder entries with points | departed members | (a), the same gap counted as people |

**(d) NO ROLLUP, NO NEW TABLE, AND NO THIRTIETH PERMISSION.** The ladder is one `SUM` and one `COUNT` grouped by member over `point_awards_tenant_user_awarded_idx`, whose leading column is `tenant_id`; Consequences already accept an aggregate here and reserve a rollup for when a real query proves slow. ⚠️ Points and badges are read in **two separate grouped statements and never joined**: joining both onto the roster multiplies a member's award rows by their badge rows and inflates `SUM(points)` silently — with two awards and three badges, threefold. Two keyed reads cannot fan out at all, so the failure is designed out rather than tested around.

**(e) THE MODULE GATE, AND THE ONE THING THAT CAN CATCH IT BEING GOT WRONG.** Consequences already require K1d to gate on the tenant's toggle rather than mounting `feature:gamification`, whose copy would tell a self-disabled tenant to buy something §D6 already gave them. K1d adds `RequireModule` (`module:<key>`) and `ModuleDisabledException` — **403 `module_disabled`**, distinct from the entitlement family's 402, because there is nothing to pay and the refusal is undoable from inside the workspace.

⚠️ **A property of the plan catalog makes this harder to test than it looks, and it is worth recording:** every tier that grants `api_access` also grants `gamification` (Starter upward is built by spreading the every-tier list), so **no plan fixture can tell the two gates apart** — a wrongly-mounted `feature:gamification` would pass every tier-based test. The only state that discriminates is a tenant that has switched the module off, where the wrong gate produces the wrong sentence. That single case is therefore load-bearing, and `GamificationApiTest` asserts on the string that must be **absent**.

⚠️ **A consequence of that same catalog, measured while building and stated rather than left to be discovered: a FREE tenant has `gamification` and cannot reach it over the API at all**, because the whole `/api/v1` group sits behind `feature:api_access`, which Free does not carry. That is a pre-existing property of the API group rather than anything this row chose — but it means the web surface K1e builds is the only door a Free tenant has to this feature, which is exactly the audience §D6 refused to put a tier ladder in front of.

**§D12 — A REVIEW IS FOUR VERBS AND ONLY TWO OF THEM SCORE; the replay discriminator is `new_values.status`, and §D10(a)'s sentence about `remarks` is corrected in place.** *(Added in place by M24, 2026-08-26, on the §D9 / §D10 / §D11 precedent — `0022` was again not taken, because nothing about §D1's substrate changes and the correction belongs beside the decision that caused it.)*

**(a) THE SENTENCE THAT WAS TRUE AND STILL WRONG.** §D10(a) specifies this map in one line: *"Review and edit are separated on the SHAPE of `new_values` (a review always carries `remarks`; an edit carries flattened `answers.<key>` entries and never does)."* Every clause is accurate. The sentence is nonetheless where the defect came from, because **it treats "a review" as one act and it is four.** `SubmissionReviewService` exposes `markUnderReview`, `approve`, `returnToRespondent` and `archive`; all four funnel through one private `apply()` and emit one fixed six-key `snapshot()`, with `remarks` present unconditionally — `applyRemarks()` decides only the *value*, and `AuditLogger::record()` stores the array it is handed without diffing it. So the review marker fires identically for all four, and `AuditReplayMap` awarded `submission.reviewed` to every one of them. **Two of the four have no live listener at all.** A replay therefore minted points and badges for acts the engine has never scored and never will — and, per §D4, could never take them back.

**(b) THE SPEC IS THE LIVE LISTENERS, NOT AN OPINION ABOUT WHICH VERBS DESERVE POINTS.** A backfill exists to make a workspace's history look as though the listeners had been running all along (§D5), so the question *"which review verbs score?"* has exactly one legitimate source: the ones that fire. `AwardPointsForSubmissionApproved` and `AwardPointsForSubmissionReturned` both award `PointRule::SubmissionReviewed`, on the same subject, from `SubmissionApproved` and `SubmissionReturned`. `markUnderReview` and `archive` raise nothing — deliberately, and §D-nothing decided that: `SubmissionReviewService`'s own docblock records that claiming is *"internal queue mechanics nobody outside this screen is waiting on"* and archival is *"a retention act"*. **Decision: `AuditReplayMap::SCORED_REVIEW_STATUSES = ['approved', 'returned']`**, which is that pair and is defined by them rather than chosen.

⚠️ **AND `returned` IS HALF OF IT, WHICH THE BUG REPORT'S OWN TITLE ARGUED AGAINST.** The row that found this is titled *"two verbs the live engine never scores"*, which reads as *"score approval only"*. Dropping `returned` would silently stop crediting every returned submission in every backfill — the same class of silent mis-scoring, pointed the other way. It is named here because the wrong fix is the one the defect's own description invites.

**(c) THE DISCRIMINATOR IS A VALUE, AND §D10's KEY-SHAPE PRINCIPLE IS NARROWED RATHER THAN ABANDONED.** `ReplayableAudit` carried key NAMES only, on an argued principle: a compliance ledger's redacted contents have no business travelling through a scoring service. That principle is kept. What is retired is the factual claim beside it — *"key names carry the whole discriminator"* — which held for review-versus-edit and is simply false for review-versus-review, where the key set is byte-identical across all four verbs. **The map was not reasoning badly; it was being handed insufficient evidence.** Exactly one value is admitted, `new_values.status`: a workflow enum, not ledger material. `AuditRedactor::PII['submission']` is `guest_ip`, `guest_user_agent`, `guest_contact_email` and `remarks` — `status` is not in it and never has been, so the field is always the true value rather than a placeholder. A row whose payload carries no `status` key yields SQL NULL and scores nothing, landing in the `unmapped` bucket §D10(a) already provides for.

⛔ **AND IT IS THE LEDGER'S STATUS, NOT THE SUBMISSION'S.** `GamificationBackfill::AUDITS_SQL` already `LEFT JOIN`s `submissions` for §D8, so `s.status` sits one word from the discriminator and is **wrong**: that is the row's *current* state. A submission approved in March and archived in July reads `archived` today, so keying on the join would erase the legitimate March award and keep nothing — the precise inversion of the defect. The historical value exists only in `new_values`, which is why the append-only ledger is read and the mutable table is not. Recorded because the cheaper join is the obvious thing to reach for and produces a *plausible* result on every submission whose status never moved twice.

**(d) THE ORDERING OF THE TWO CHECKS BECAME LOAD-BEARING, HAVING BEEN DECORATIVE.** `AuditReplayMap` tests the `answers.` prefix before the review marker. Until now that only settled precedence on a payload that cannot occur, since the two writers' key sets were disjoint on the markers. It is real work now: `SubmissionAnswerEditService::statusSnapshot()` emits `status` **too**, so an edit to an already-approved submission carries exactly the status the review branch scores on, and a status test reached first would price a 1-point correction as a 3-point review. The edit marker is checked first and returns first, and a unit case pins it there.

**(e) WHAT THIS COST, STATED RATHER THAN DISCOVERED.** Nothing in the schema moves — no column, no index, no migration, no change to the idempotency key. The blast radius is one added `SELECT` expression, one added readonly field with two construction sites, and one `match` arm. ⚠️ **The reason it was invisible for three increments is worth more than the fix:** every existing assertion about the review/edit split described a payload somebody had typed, including `BackfillTest`'s `replayAudit()` helper — whose review fixture happened to carry `'status' => 'approved'` and was therefore green before and after. **No test drove the real `SubmissionReviewService` and then ran the real backfill over the rows it actually wrote.** M24 adds that call-site sweep, and it is the only gate here that fails on the unfixed tree.

⚠️ **A CONSEQUENCE THAT LOOKS LIKE UNDER-COUNTING AND IS NOT.** A reviewer who claims a submission and then approves it produces three audit rows and **one** award — the idempotency key is `(tenant, user, rule, subject_type, subject_id)` (§D3) and both the claim and the approval name the same submission. That was true before this correction and is true after; it is also why the happy path never exposed the defect. The rows that actually inflated were the ones where an actor's *only* qualifying transition on a submission was a claim they abandoned or an archive of somebody else's work.

---

## Consequences

**Good.** Scores cannot drift from their evidence, because there is only one representation. The exactly-once rule is enforced by an index rather than by care, so the four unbounded acts are safe by construction rather than by review. Nothing about scoring can break a real user action: awarding is post-commit where post-commit is available, cannot raise, and swallows-and-logs. The engine adds **no** public API surface, no webhook contract, no permission key and no scheduled job — so the deployment checklist does not grow.

**Bad, and accepted.** A tenant cannot subscribe an integration to `form.created` (§D2). Points totals are computed rather than stored, so a leaderboard over a very large ledger is an aggregate query rather than a lookup — acceptable at any plausible per-tenant volume, and the shape that would fix it (a rollup table on the `usage_counters` precedent) is additive. Re-weighting a rule produces a ledger where two awards for the same act are worth different amounts; that is §D4 working as intended, but it will look like an inconsistency to anyone who has not read this ADR, which is why `PointRule`'s own docblock repeats the argument.

**⚠️ One inherited wart, recorded rather than fixed.** `RequireFeature` raises `FeatureGateException`, whose copy is *"Your plan doesn't include X. Upgrade your plan to use it."* Because §D6 grants `gamification` on every tier, the **only** way that gate can fire for this key is a tenant that switched the module off itself — for whom the sentence is simply wrong. The wrong-copy-on-self-disable shape is pre-existing and shared with all eleven toggleable keys; K1a adds the label arm (so no 402 renders a raw snake_case key), and **K1d discharged the second half: the gamification surfaces gate on the module toggle via `module:<key>` and never on `feature:gamification`** — see §D11(e), which also records why that is the one thing here no plan-tier fixture can test.

---

## Alternatives considered

- **Derive everything from `audits` on read** — rejected in §D1. Retroactive for free, but couples scoring to a compliance ledger whose contents are decided by a different set of concerns.
- **A `points` balance column on `tenant_users`** — rejected in §D1 on `countGauge()`'s recorded drift argument, and because it cannot express "earned on".
- **A `gamification_events` table mirroring `DomainEventType`** — rejected as a second event vocabulary; §D2's whole point is that the acts already emit.
- **Storing streaks in their own table, maintained nightly** — rejected in §D5: derivable exactly, and the nightly job would not run (Context §6).
- **A `gamification.view_leaderboard` permission** — rejected in §D7.

## When to Revisit

- **A tenant asks to integrate on form creation.** Promote `FormCreated` to a `DomainEventType` case (§D2) — additive, four-file, breaks nothing.
- **Somebody asks for a rolling leaderboard window ("this month").** Declined for K1d by the product owner on 2026-08-18 in favour of an all-time ladder alone, on the grounds that it is the smallest honest contract. It is additive — `awarded_at` leads no index but sits in `point_awards_tenant_user_awarded_idx`, so a window is one extra bound — but it adds a parameter to a **published** `/api/v1` contract, which is the part that is not free. The cost of NOT having one is also recorded: on an all-time ladder early members outrank newcomers permanently.
- **A leaderboard query becomes slow on real data.** Add a rollup on the `usage_counters` precedent; the ledger stays authoritative and the rollup is reconcilable from it, which is precisely the property §D1 preserved.
- **The weights need to become tenant-configurable.** §D4 already makes this safe — historical awards keep their recorded value — but the rule catalog would graduate from a PHP enum to a table, the same graduation `UsageMetric`'s docblock anticipates for itself.
- **Someone proposes an UPDATE or DELETE policy on `point_awards`.** That is not a refinement; it is the ledger becoming rewritable. `PointAwardRlsTest` asserts the *absence* of those policies for this reason. The same applies to `badge_awards`, where `BadgeAwardRlsTest` asserts it.
- **Someone proposes a `threshold` column on `badge_awards`, or badge thresholds need to become tenant-configurable.** The first is §D9 being re-argued and should be — it is a reasonable-looking symmetry with §D4 and the answer is in that section. The second graduates `BadgeKey` from a PHP enum to a table, which is the same graduation `UsageMetric`'s docblock anticipates for itself and which §D4 already makes safe for points.
