# Audit & Compliance Logging Spec

**Project:** Form-Builder SaaS (`dev_formbuilder_app`)
**Status:** Draft v1.0 — formalizes the scope and redaction rules for the `Auditable` trait / `audits` table already specified in `docs/data-dictionary.md` §13 (carried forward from legacy's confirmed-good `app/Traits/Auditable.php` mechanism) and referenced throughout `docs/PRD.md` Feature #12, `docs/multi-tenancy-rbac-design.md` §9, and `docs/security-threat-model.md`. This document does not redesign the mechanism — it specifies precisely *what* gets audited and *what gets redacted before it's written*, which no prior doc has pinned down exhaustively.

---

## 1. Scope — Which Models Are Auditable

`docs/data-dictionary.md` §13 gives `audits.auditable_type` examples ("e.g. `form`, `form_version`, `submission`, `webhook_endpoint`, `subscription`") without an exhaustive list. `docs/PRD.md` Feature #12 states the coverage principle: *"not limited to form/submission data: every settings change, every form publish/archive action, every role/permission change, and every billing-plan change is tracked."* This section makes that principle a definitive, checkable list:

| `auditable_type` | Audited events | Rationale |
|---|---|---|
| `form` | `created`, `updated`, `archived`, `deleted`, `restored` | Core business object. |
| `form_version` | `published` | The single most consequential event this schema tracks (`docs/form-versioning-schema-migration.md`) — every publish is audited, not just form-level metadata edits. |
| `submission` | `created`, `updated` (status transitions: approve/return; **and deliberate post-submission answer edits** via `submissions.edit` — **AS BUILT (I9c)**, see note), `exported` | Review-workflow accountability; `exported` covers a reviewer/admin pulling submission data out of the system. ⛔ **`deleted` AND `restored` WERE LISTED HERE FROM v1.0 UNTIL M70 (2026-09-04) AND WERE NEVER EMITTED — REMOVED AS *NOT BUILT*, WHICH IS NOT THE SAME CLAIM AS *NOT AUDITED*, AND THE DIFFERENCE IS THE WHOLE REASON THIS CELL SAYS SO RATHER THAN GOING QUIET.** A SIEM forwarder, a retention rule or an export filter built from this section would read a bare removal as a decision that destroying a response needs no trail. It is not that: **there is no delete or restore surface for a submission anywhere in the product.** `SubmissionPolicy` declares `create`, `viewAny`, `view`, `export`, `review`, `update` and `promote` and no `delete`/`restore`/`forceDelete`; `RolePermissionSeeder` mints no `submissions.delete`; no route in `routes/` matches such a verb; and there is no controller action and no UI affordance. The `deleted_at` column exists and is dormant. ⚠️ **The one code path that removes a submission does not and must not write these rows:** `ReapTenantDraftsJob` **hard**-deletes abandoned drafts (`forceDelete()`, for the `submissions_tenant_client_uuid_unique` reason its own docblock gives), and it runs as a queue job where `AuditLogger` is structurally malformed — it hard-codes `is_system_action = false` and would resolve a null actor off a worker, the same shape the `domain` row's *"deliberate gaps"* note refuses `activate`/`deactivate` for. **Whether to build the surface, and therefore owe these two events, is `D14`.** |
| `settings` | `created`, `updated` | Per PRD Feature #12's explicit callout; both tenant-level and (when actor is super-admin) platform-level rows. **`auditable_id` IS ALWAYS `tenants.id`, PERMANENTLY — including after Increment I5 creates a `settings` table.** Settings are a per-tenant singleton, so the tenant id is both the stabler key and the useful one; keying new rows on a settings-row uuid instead would split one resource's history across two `auditable_id` values and make it unqueryable by the `audits_tenant_auditable_idx` index the viewer's per-resource filter rides on. As built in I2: tenant draft settings (`TenantSettingsService`) and all four branding writes (`TenantBrandingService`) use this alias. **I5 built the table and honoured the rule** — `TenantSettingRegistry::put()` (Access, Modules) and `TenantSettingsService::updateMaintenance()` (the tenant maintenance columns) both emit `settings` / `tenants.id`, so two stores with different mechanics still read as one resource with one history in the viewer. Branding is deliberately NOT a separate `branding` alias — it renders inside `/settings`, gates on `tenant.settings.manage`, and a second alias would fragment one user-visible surface across two filter options. `tenants.brand_ramp` is never in a payload: it is ~2 KB of derived contrast tables that are a pure function of `primary_color`, so recording the colour records both. **The PLATFORM half is the one exception to the tenant-id rule, and it is a different kind of row entirely — see the `settings` (platform) entry below.** |
| `settings` *(platform, I5)* | `updated` | The super-admin console's own writes (open-signup, platform maintenance). **These rows carry `tenant_id = NULL`**, because the thing changed belongs to no tenant — which is why I5 adds `applySuperAdminBypass('audits', ['INSERT'])`, the deferred half of a decision H4 already took in writing (`create_audits_table.php`: *"A super-admin INSERT bypass would only be needed for a future NULL-tenant / cross-tenant PLATFORM audit action… deferred to that action"*). **INSERT only: the ledger stays immutable, and no UPDATE or DELETE policy may ever be added to `audits` for any role** — under FORCE RLS a command with no matching policy is denied for everyone, and that absence *is* the append-only guarantee. `auditable_id` is the ACTING SUPER-ADMIN's user id, this section's standing device for a target with no single addressable uuid (the change is a set of platform-wide keys, not one record), the same shape the role-grant and `domain` rows use. **Consequence, stated so it is not later mistaken for a bug: a NULL-tenant row is invisible to every tenant's `/audit-log`**, because the base SELECT policy stays strict (`audits` is deliberately not nullable-global, which *would* leak it). That is the intent — a tenant must not read the operator's platform actions. Do not "fix" the invisibility by widening the SELECT policy. **AS BUILT (I7b): the platform-side viewer is `GET /admin/audit-log`, and it did NOT take that widening.** It reads through a separate, deliberately narrower policy — `audits_platform_select`, from `TenantIsolation::platformRowsBypass()`, whose `USING` clause is `current_setting('app.is_superadmin_context', true) = 'true' AND tenant_id IS NULL`. The base `audits_tenant_select` is untouched, so the invisibility this row describes is unchanged; and because of that second conjunct the operator cannot read a TENANT row either. `applySuperAdminBypass('audits', ['SELECT'])` remains forbidden — its gate is unrestricted and would hand the operator every tenant's complete history. |
| `domain` *(I2)* | `created` (claim), `updated` (primary changed), `deleted` (released) | Custom-domain lifecycle (ADR-0012). **Keyed on `auditable_id = tenants.id`, NOT the domain row** — `domains.id` is a 4-byte `increments()` integer while `audits.auditable_id` is a `uuid`, the same addressing problem the role-grant row below solves the same way; a row keyed on the domain raises `SQLSTATE 22P02` at runtime, which no static gate catches. The hostname travels in `old_values`/`new_values.domain` so the entry reads without a join. Released domains are HARD-deleted, so that entry is the only surviving record the tenant ever controlled the name. The `verification_token` is deliberately absent from the payload (it is not a secret — see §2 — but it is not accountability-relevant either). **Deliberate gaps:** `verify()` (reached from HTTP *and* the console sweep, so a conditional audit would make the ledger depend on which caller won a race; and it records a check result the sweep rewrites every 15 minutes forever), `activate`/`deactivate` (artisan-only, no in-app actor — a row would carry `user_id = null` beside `is_system_action = false`, malformed by `AuditLogger`'s own contract), and expired-claim sweeps (bulk delete of never-verified, never-routed rows). |
| `sso_connection` *(P1a)* | `created` (first metadata import), `updated` (re-import, policy change, status change), `deleted` | The tenant's federated-identity trust anchor (ADR-0016). **Keyed on `auditable_id = tenants.id`, NOT the connection row — and NOT for the `domain` row's reason.** `sso_connections.id` *is* a `uuid`, so there is no addressing problem here; the argument is the **`settings`** one directly above. The connection is a per-tenant singleton (UNIQUE on `tenant_id`) that a tenant may hard-delete and re-create, and keying on the row uuid would split one workspace's SSO history across two `auditable_id` values — unqueryable by `audits_tenant_auditable_idx`, which the viewer's per-resource filter rides on. Do not "fix" it back to the row id on the grounds that the id is a uuid; being addressable is not the question. **It is deliberately NOT folded into the `settings` alias** the way branding is: that decision turns explicitly on branding *rendering inside* `/settings` with no page of its own, whereas this has its own page, its own lifecycle, and the largest blast radius of any tenant-writable configuration — rewriting the certificate is a complete authentication takeover for that tenant. **`idp_certificates` is registered in §2's unconditional list in this same increment**, per the standing rule below, and the reason is unusual enough to state: it is not a confidentiality secret (a signing certificate is public by construction) but `Model::getOriginal()` maps attributes through their casts and therefore returns the **decrypted** list, so the repo's ordinary snapshot idiom would write plaintext keys into a table that is append-only and never pruned. The service builds its payload by hand and never emits the column; the registration is the backstop against a later "simplification". `idp_certificates_fingerprint` travels instead — a complete substitute for the accountability question ("did the trust anchor change?") in 64 characters, on the `tenants.brand_ramp` precedent rather than the `connection` token one. ⚠️ The alias is the **singular** `sso_connection`, matching the `AuditRedactor::SECRETS` and `AuditableTypes::LABELS` keys; emitting `sso_connections` or `saml_connection` would write a valid-looking row with redaction silently switched off, which is verbatim the `feedback_reports` trap recorded below. |
| `audit_log` *(I2)* | `exported` | §3's self-referential entry, as built. `auditable_id = tenants.id` (there is no audit_log row to point at). `new_values` carries the applied filters and the format, and deliberately **no row count** — that would need a `count(*)` over an unbounded table before the stream starts, and the client can abandon the download mid-body, so an intended count they never received would be a false entry in the one table that exists not to contain those. Written in request scope BEFORE the stream, where the actor and request still exist; an accepted, test-pinned consequence is that **the exported file contains its own export row**. |
| `webhook_endpoint` | `created`, `updated`, `deleted` | Configuration changes to an outbound data-sharing surface. |
| `connection` *(H15a)* | `created` (OAuth grant completed), `updated` (re-connected, or marked dead after a refused refresh / rejected credential), `deleted` (disconnected) | The platform's OAuth grant on a tenant's third-party workspace (ADR-0009). Higher stakes than a webhook endpoint: the credential lets the platform act *inside* that workspace, so its whole lifecycle is on the ledger. Both token columns are unconditionally redacted (§2). |
| `connection_subscription` *(H15a)* | `created`, `updated`, `deleted` | Which events go to which destination on a connection — the routing half, holding no credential. |
| `subscription` | `updated` | Billing-plan changes, per PRD Feature #12. |
| `tenant_users` | `created` (invite sent; **and I5: a self-registration join**), `updated` (status transitions), `deleted`/`removed` | Membership lifecycle (`docs/multi-tenancy-rbac-design.md` §7). **I5 added a second door into a workspace** — registering on the subdomain of a tenant that has switched Access to open (PRD Feature #10) — and the two produce the SAME membership at the SAME role, so `new_values.via` (`self_registration`) is the only thing that distinguishes them in the ledger. Keyed on the membership's own uuid, which is legal here because `tenant_users.id` IS a uuid (unlike `domains.id` — see that row). The actor is the joining user themselves. |
| role grant/revoke — recorded against `auditable_type = users`, `auditable_id = <affected user's uuid>`, with the granted/revoked role captured in `old_values`/`new_values` | `permission_changed` | Every role grant/revoke — the RBAC doc's own `tenant.ownership.transfer` flow explicitly logs this event type. The assignment is audited against the affected `users` row rather than the `model_has_roles` pivot itself, because that pivot has a composite PK with no surrogate `id` (RBAC §4), and `audits.auditable_id` is a single `uuid` that cannot address a composite-key row. |
| `resource_grants` | `created` (access granted), `deleted` (access revoked) | Per-resource access changes (`docs/multi-tenancy-rbac-design.md` §8). Renamed from `form_collaborators` in Increment G10a, which generalized it: a grant now names either a form or a `scope_nodes` subtree, so the audit entry must record `scopeable_type`/`scopeable_id` and `includes_descendants` — a subtree grant can confer access to many forms at once, and the entry is unreadable without its reach. Grants are hard-deleted, so this trail is the ONLY record that a revoked grant ever existed. |
| `users` | `updated`, specifically limited to `is_super_admin` changes; **`impersonation_started` and `impersonation_ended` — AS BUILT (I11b), added to this row by Increment M46 (2026-08-29)** | The single highest-blast-radius flag in the schema (ADR-0002 §D3) — any change to it is audited regardless of how unrelated-looking the rest of the `users` update is; ordinary profile edits (name, theme preference) are **not** audited (see §2's noise-reduction principle). ⛔ **THE TWO IMPERSONATION EVENTS WERE MISSING FROM THIS ROW FROM I11b UNTIL M46, AND THIS IS THE SECTION THAT EXISTS TO BE EXHAUSTIVE** — a SIEM forwarder, a retention rule or an export filter built from it dropped the highest-privilege events in the ledger. `ImpersonationService::recordBoundary()` writes both against `auditable_type = 'users'` (plural — the registered alias) with **`auditable_id` = the impersonated user** and `acting_as_user_id` = the operator, so the pair reads as *what was done to this account, and by whom*. Note the direction: the subject of the row is the target, not the operator. ⚠️ **The `users` alias is covered by TWO rows in this table, not one** — role grant/revoke is recorded against the same alias with `permission_changed`, three rows above. Anyone reading a single row as the alias's whole scope will undercount it, which is how this omission survived. |
| `tenant` | `updated`, specifically limited to `status` changes (suspend/reactivate) and `owner_user_id` changes (ownership transfer) | Platform-level and ownership-level changes, not every cosmetic tenant-settings edit. |
| `feedback_reports` | `updated` (status transitions by platform support) | Support-team accountability for how a tenant's feedback report was handled. **AS BUILT (I7a):** emitted by `SuperAdminService::transitionFeedback()`, carrying `status` + `resolved_at` + `resolved_by` on both sides and nothing else. Two things about it are load-bearing. (1) **The write is UNELEVATED** — the console adopts the affected tenant's context — so the row lands in the **reporting tenant's own** ledger and is readable there, which is RBAC §9's transparency requirement; an elevated write would have produced a `tenant_id = NULL` row invisible to exactly the people entitled to see it. (2) **The alias is the plural `feedback_reports`**, matching the keys in `AuditRedactor::PII` and `AuditableTypes::LABELS` — unlike the singular `submission`/`attachment`. Emitting `feedback_report` would still write a valid-looking row while silently switching OFF redaction of `remarks`/`browser_info` for it. **Creating** a report is deliberately not audited: it has no before-state, it is not an act against tenant data, and the row is its own record. |

### 1.1 Who can READ each row (as built, I7b)

Stated as a matrix because it existed nowhere before I7b, and because both halves of it are enforced by
Postgres policies rather than by application code — so neither can be undone by a controller change.

| Row | Readable by | Through | NOT readable by |
|---|---|---|---|
| **Tenant rows** (`tenant_id` set) | that tenant's Owner/Admin (`audit_log.view`) | `/audit-log`, base `audits_tenant_select` | the platform operator — `audits_platform_select` carries `AND tenant_id IS NULL` |
| **Platform rows** (`tenant_id IS NULL`) | super-admins with confirmed 2FA | `/admin/audit-log`, `audits_platform_select` | every tenant — the base SELECT policy stays strict, and `audits` is deliberately not nullable-global |

**A super-admin action against a specific workspace is a TENANT row, not a platform row**, and that is RBAC
§9's transparency posture rather than an accident of implementation: `changeStatus()`, `assignPlan()` and
`transitionFeedback()` all adopt the affected tenant's context so the row lands in *its* ledger, where the
people entitled to see how their workspace was handled can read it. The platform ledger therefore holds
only what belongs to no tenant, which today is the `settings` row above. Cross-tenant audit SEARCH is
**not built, deliberately** — see RBAC §9.

### 1.2 Who ACTED on each row — two columns, not one (as built, I11a)

`user_id` is the **effective** actor: whose authority the action ran under. `acting_as_user_id` is the
**real** human when those differ — the platform operator driving an impersonated session — and is `NULL`
on every ordinary row. Together they satisfy the only requirement RBAC §9:433 states about impersonation,
and close the risk `security-threat-model.md` §8 names.

Three consequences worth stating once, because each has already caught something:

- **The direction is load-bearing.** `user_id` keeps its existing meaning, so every consumer that predates
  this column — the actor filter, `audits_tenant_user_idx`, the export's Actor column, `AuditResource` —
  keeps telling the truth. Reversing the sense would silently re-point all of them at platform staff.
- **It is written ambiently, at the single write path.** `AuditLogger::record()` reads
  `ImpersonationContext`, exactly as it reads the request IP; it is not a parameter, because a parameter is
  a thing to forget at each of ~15 call sites and forgetting it is silent.
- **The tenant is told THAT an operator acted, never WHICH ONE — and that is an enforced policy, not a
  side effect of RLS.** `/audit-log` and the CSV render the fixed string `Platform operator`;
  `actingAsLabel()` never reads the name. The first draft justified the label by claiming the name was
  unreachable anyway (staff hold no membership, so the join-shape `users` policy hides them) — **that was
  disproved against a live database**: `usersVisibilitySql()` says nothing about `is_super_admin`, and an
  operator who ALSO holds an active membership of the impersonated tenant is perfectly visible, at which
  point the presenter rendered their real name to every Owner of that workspace. It is now decided rather
  than inherited, and the relation is deliberately not eager-loaded so the name is not even in memory.
- **`/admin/audit-log` cannot show an impersonated row at all.** An impersonated action is written under the
  impersonated tenant's context and therefore carries a `tenant_id`, while the console reads the
  `tenant_id IS NULL` slice through `audits_platform_select` (`AND tenant_id IS NULL`) — excluded twice
  over. I11a's first draft resolved a name and rendered a marker there; both were dead code, and the test
  that "proved" them hand-wrote a `tenant_id = NULL` row carrying `acting_as_user_id`, a shape the writer
  cannot produce. Making the console see these rows would mean widening the very policy I7b narrowed, so
  the marker was removed instead. **Today `/api/v1`'s opaque uuid is the only surface that identifies the
  operator at all.**

⚠️ **The platform slice is not permanently "settings rows only", and the mechanism is easy to miss.**
`tenants` has no `SoftDeletes` and `audits.tenant_id` is `nullOnDelete`, so **hard-deleting a tenant
promotes its entire audit history into `tenant_id IS NULL`** — where it becomes readable at
`/admin/audit-log`, carrying `form`/`submission`/`tenant_users` aliases and tenant-authored (redacted, but
present) payloads. That is arguably the right outcome (the tenant is gone; §4 says the ledger is retained),
but it was invisible before a platform viewer existed and must not be discovered by surprise. Two
consequences follow: a future platform type-filter cannot simply reuse the tenant catalog, and the page's
own copy must not claim the ledger holds platform actions *exclusively*.

**Deliberately NOT audited** (noise-reduction principle, stated once rather than implied by omission): `form_sections`/`form_fields`/`form_field_validations` row-level edits **while still part of a draft** are not individually audited — a builder's draft is expected to be edited many times before publish, and per-keystroke-level audit noise on mutable, pre-publish content would drown out the events that actually matter. The moment those rows are frozen into a **published** `form_version`, the *publish itself* is the audited event (`form_version.published`), which is what matters for historical accountability — the content is captured in `schema_snapshot`, not in a pile of intermediate draft-edit audit rows. `submission_answers`/`submission_answer_index` are also not directly audited row-by-row — the owning `submission`'s status-transition events are what's tracked; individual answer values are covered by the submission's own lifecycle, not a separate audit stream. **One deliberate exception**: a *permissioned post-submission answer edit* (a Form Editor/Admin correcting a mis-keyed value via `submissions.edit`) **is** audited as a `submission` / `updated` event capturing which answer keys changed in `old_values`/`new_values` (subject to §2 PII redaction). **AS BUILT (I9c), with three details this paragraph did not anticipate.** (a) The changed keys are written **at the payload's TOP LEVEL as `answers.<key>` entries**, not nested under an `answers` object — `AuditRedactor::redact()` matches the top level only, so nesting them would make `$piiAnswerKeys` a silent no-op that looks wired up and returns `redacted_fields: null`. I9c is that parameter's first consumer anywhere in `app/`. (b) A PII field inside a **repeatable section** cannot be redacted individually (its answer lives at `answers[section][n][field]`), so the SECTION key is redacted instead — over-redaction, never under. (c) Only CHANGED keys are recorded, so an edit row is a **diff, not a snapshot**: reconstructing the document as of a point in time means replaying the diffs, and `submission_answers` is the current state. The approved → under_review demotion an edit causes is folded into the SAME row rather than emitted as a second event, so the ledger cannot be misread as someone having revoked the approval deliberately — because a human deliberately altering already-collected data is exactly the provenance an audit trail exists to preserve, distinct from not auditing the respondent's original keystroke-level fill.

**Also deliberately NOT audited (I3): `notifications` and `notification_preferences`.** Three reasons, recorded so the omission reads as a decision rather than a gap. (1) A notification is a *derivative* of an act that is already audited elsewhere — the submission transition, the invitation, the export — so auditing it would record the same event a second time under a second `auditable_type`, and the two would then have to be kept from contradicting each other. (2) `read_at` is written every time a recipient opens the notification center, which would pour high-frequency, zero-accountability rows into a ledger that is never pruned (§4) and whose whole value is signal density. (3) A preference is a personal display choice with no compliance claim on it — the same ground on which `user_ui_preferences` and `saved_report_views` are unaudited. Consequently **neither table has an entry in `AuditRedactor` or `AuditableTypes::LABELS`, and neither needs one.** The standing rule that a credential-bearing alias must be registered in the increment that creates its table is satisfied by the stronger guarantee that **neither table may hold a credential at all**: `notifications.data` is contractually limited to identifiers and display labels (stated in the migration docblock and in data-dictionary §22), never a token or a signed URL, because under the table's strict RLS those rows are readable by every member of the tenant and nothing redacts them.

## 2. Redaction Rules

**Principle**: `audits.old_values`/`new_values` record *that something changed and roughly what changed*, never a field's raw sensitive content — this is what `docs/data-privacy-gdpr-compliance.md` §9 depends on to reconcile "audits are append-only, never deleted" with GDPR erasure obligations elsewhere in the schema.

**Always redacted, unconditionally** (a fixed, code-defined list — not tenant-configurable, since these are platform-level secrets/credentials, not tenant content):
- `users.password`, `users.remember_token`
- `users.two_factor_secret`, `users.two_factor_recovery_codes` (Fortify 2FA credentials, PRD Feature #14)
- `webhook_endpoints.secret` (and `secret_previous`, H13b's rotation grace copy)
- `connections.access_token`, `connections.refresh_token` (H15a / ADR-0009 §D10 — third-party OAuth credentials, encrypted at rest and never returned by any API in any form). The audit snapshot deliberately *includes* them so the redactor is what strips them and records the strip in `redacted_fields`; a snapshot that quietly omitted them would leave no evidence the ledger ever saw a credential-bearing write.
- `tenant_users.invite_token`
- `sso_connections.idp_certificates` (P1a / ADR-0016 §D12 — the tenant's IdP signing certificates). **The one entry on this list that is not a secret**, and it is here anyway. A signing certificate is public by construction; the `encrypted:array` cast on it is an *integrity* claim, because anything that can silently rewrite the column can make the application trust assertions minted by a key of the attacker's choosing. It is registered because `Model::getOriginal()` maps every attribute through `transformModelValue()` and so returns the column **decrypted**, while `$hidden` guards only `toArray()`/`toJson()` — so the repo's ordinary `Arr::only($model->getOriginal(), …)` snapshot idiom would put plaintext keys into a table that is append-only by RLS policy and never pruned. `SsoConnectionService` builds its payload by hand and the column is structurally absent from it; this entry is what makes a later refactor to `getOriginal()` produce `[REDACTED]` plus a `redacted_fields` note instead of a silent wall of base64.
- Any Sanctum token value

> The list is hand-maintained by construction, keyed by the §1 auditable-type alias. A new credential-bearing
> alias that is not registered here is silently un-redacted and **nothing detects it** — so registering it
> belongs in the same increment that creates the table, not a follow-up.

**Redacted based on the Data Dictionary's own PII/sensitivity flags** (dynamic, not a fixed list, since these are tenant-declared or content-dependent):
- Any column the Data Dictionary marks **PII = Yes** or **PII = Yes (conditional)** — e.g., `submissions.guest_ip`/`guest_user_agent`/`guest_contact_email`, `attachments.original_filename`, `feedback_reports.remarks`/`browser_info`.
- **`submissions.remarks`** *(added in I2, when `SubmissionReviewService` started auditing the four review transitions)* — registered on exactly the reasoning `feedback_reports.remarks` already carries: it is internal free text with **no audience discipline**, and a reviewer can paste respondent PII copied straight out of the answers into it ("called the mother, number is …"). Since `audits` is append-only and never deleted, and `docs/data-privacy-gdpr-compliance.md` §9's entire reconciliation rests on this table never having stored raw PII, the ledger records *that* the remarks changed — via `redacted_fields` — without recording what they said.
  **`submissions.returned_reason` is deliberately NOT redacted, and the asymmetry is the decision, not an omission:** it is the reviewer's explanation *authored for the respondent* and already emailed to them, so "why was this returned" is precisely the accountability an audit trail exists to preserve.
- Any `submission_answers.answers` key corresponding to a `form_fields.is_pii = true` or `is_sensitive = true` field.

**Redaction replaces the value with a placeholder marker** (e.g., `"[REDACTED]"`), and the specific field names that were redacted are recorded in `audits.redacted_fields` (`docs/data-dictionary.md` §13) — a transparent record of *that* redaction happened, without defeating its own purpose by naming what the value *was*.

### 2.1 The erasure special case — a deliberate exception to normal diff behavior

**Normal audit behavior**: `old_values` shows the real prior content of a changed field (e.g., a form's `title` changing from "Draft Survey" to "2026 Health Survey" — both real strings, both legitimately useful for accountability).

**Erasure is different, and must be, on purpose**: when a GDPR erasure request scrubs a field via `submissions.pii_erased_at` (or the `users` anonymization flow, `docs/data-privacy-gdpr-compliance.md` §3), the resulting audit entry's `old_values` **must not** contain the pre-erasure raw value — logging it there would silently defeat the erasure the event is nominally recording. For an erasure-triggered update, **both** `old_values` and `new_values` show the redaction placeholder for the affected fields (not "old_values = real content, new_values = redacted" as a normal diff would), and `redacted_fields` lists them as erased. This is the one case in this schema where an audit diff's "before" side is deliberately not the real prior value, and it is called out explicitly here so a future implementer doesn't "fix" it back to showing real content under the mistaken assumption that audit diffs should always be literal.

## 3. Access & Export

- **Viewing**: the Audit Log screen is visible to **Owner/Admin roles only** (`docs/multi-tenancy-rbac-design.md` §5's `audit_log.view` permission) — not re-litigated here, restated for completeness. **Built in Increment I2** at `GET /audit-log` (`AuditLogController` → `AuditLogPresenter` → `resources/js/Pages/audit/Index.vue`), gated on `can:viewAny,Audit` with **no plan-feature gate** — an audit trail is a baseline obligation for every tenant, and `PlanCatalog` carries no audit key on any tier. Filters: event, target type, actor, and a date range that defaults to **no window at all**, because a ledger's value is "what happened, ever" and a defaulted range quietly implies older events are gone.
- **Exporting**: reuses the existing chunked/streamed export infrastructure (architecture plan §2.5) — no new export mechanism. **As built (I2)**, `GET /audit-log/export?format=csv|xlsx` clones `SubmissionExporter`'s lazy-chunked openspout stream, one file row per audit row with the diff pre-rendered into a readable cell (raw-JSON columns were rejected: they reproduce the unreadability the viewer exists to fix, and are the shape that trips XLSX's 32,767-character cell limit). Exporting the audit log is itself an auditable action, and it writes **one** new `audit_log.exported` entry — a self-referential but not infinitely-recursive case; it does not re-trigger for every historical row it contains. See the `audit_log` row in §1 for what that entry carries and why it carries no row count.

### 3.1 Keyword filtering — target and actor only (as built, J1e)

The viewer takes a `?q`. **It narrows to the row's TARGET and its ACTOR, and never reads `old_values`/`new_values`. That is a security rule, not a scope limit.** §2's redaction is the reason: those columns are placeholdered on both sides for every SECRETS and PII key, and `AuditableTypes::label()` **fails open**, so a newly registered alias is un-redacted until someone extends the catalog. A `::text ILIKE` over the diff would therefore be an oracle over exactly the values redaction removes — the screen hides a secret while a search that matched it would confirm it, one guess at a time, to the same viewer. `AuditKeywordFilterTest` seeds a distinctive token into a diff and requires it to be unfindable *while* a target-title search still works, so the refusal cannot quietly become a dead parameter.

The composed predicate is `(auditable_type = 'form' AND auditable_id IN (matching forms)) OR user_id IN (matching users)`. Three properties of that shape are load-bearing rather than incidental:

- **The `auditable_type` conjunct is required inside the branch, not implied by it.** `auditable_id` is a bare uuid with no type discriminator, so without it a *submission* row whose id collided with a matching form's would be returned under a form's name.
- **The forms subquery is `withTrashed()` and applies no form-visibility rule.** It mirrors the viewer, which already prints an archived form's title on the very row recording that it was archived — a keyword that could not find a row the page itself names would be the worse failure. `audit_log.view` is Owner/Admin, who hold `forms.edit.any` regardless.
- **The safe design is also the fast one, so there is no trade being made.** `audits` carries `audits_tenant_auditable_idx` and `audits_tenant_user_idx` and **no index a jsonb text scan could use**, on a table §4 never prunes. Keeping `@@` and `ILIKE` inside the subqueries also keeps every predicate *on* `audits` leakproof and therefore still promotable to an index qual under RLS — the forward application of J1b's measurement that a non-leakproof clause cannot be.

**The filter chain is shared with the export** (`App\Support\Audit\AuditFilterQuery`), and that sharing is itself a compliance property. The page builds the download URL from the same parameters it navigates with, precisely so *"I exported what I was looking at"* is a guarantee; until J1e the viewer and `AuditExporter` each spelled the clauses out separately and nothing compared them, so a filter added to one and not the other would have silently made that sentence false. The export's own `audit_log.exported` entry records the keyword alongside the other applied filters, for the same reason it records them at all — a ledger entry claiming a wider export than happened is worse than none.

## 4. Retention of Audit Rows

Audit rows are append-only and never deleted (`docs/data-dictionary.md` §13: "no `updated_at`/`deleted_at`: audit rows are immutable and never deleted, by design") — this document does not change that. `docs/data-privacy-gdpr-compliance.md` §9 already explains why this is GDPR-compatible: because of §2's redaction discipline, the audit log was never storing raw PII to begin with, only metadata about *what* changed.
