**Project:** Form-Builder SaaS (`dev_formbuilder_app`)
**Status:** Draft v1.0 — formalizes the testing pyramid around several pieces `docs/architecture/technical-architecture.md` and `docs/adr/0002-multi-tenancy-shared-db-rls.md` already committed to by name (the CI tenant-isolation fuzz suite, the expression-evaluator golden-file suite, Larastan/Pint/Playwright as the CI toolchain) plus the explicit CI gaps the architecture plan calls out relative to legacy (static analysis, code style, a real deploy stage, a controller-complexity check).

## 1. What's Already Decided (not repeated in full)

- **CI/CD toolchain**: Docker Compose + GitHub Actions, Larastan/PHPStan + Pint + Playwright + a real deploy stage (`docs/architecture/technical-architecture.md` §8) — legacy's confirmed gap was "CI that ran PHPUnit only."
- **Cross-tenant fuzz test suite**: seeds two tenants, attempts every plausible cross-tenant read/write/list operation, asserts each fails appropriately — runs on every PR touching a model or migration (ADR-0002 §D6, restated as CI layer 12 in `docs/architecture/technical-architecture.md` §5).
  - **Harness note (Increment A/B1)**: fuzz tests connect as the non-superuser `meridian_app` role and set context with `TenantContext::applyLocal()` (transaction-scoped; auto-reset by `RefreshDatabase`), then issue raw `DB::` queries so what is proven is the *database's* RLS, not the ORM scope (see `tests/Feature/Tenancy/CrossTenantIsolationTest.php`, `UserRlsTest.php`).
  - **Pre-auth connection gotcha (Increment B1)**: authentication resolves users on a separate `pgsql_auth` session (the `meridian_auth` role — see `app/Auth/RlsAwareUserProvider.php`) so login/registration/password-reset work despite the fail-closed join-shape RLS on `users`. Because `RefreshDatabase` wraps only the *default* (`meridian_app`) connection in a transaction, `pgsql_auth` cannot see uncommitted rows — so **auth feature tests that need to log a user in must seed that user with a COMMITTED write on the privileged connection (`User::on('pgsql_privileged')->forceCreate(...)`) and clean it up in `afterEach()`** (the same pattern as the `global_probes` seed). Registration tests need no such seed — they create their user on the default connection inside the transaction.
- **Expression-evaluator golden-file suite**: a shared test-vector set consumed by both the PHP (server-authoritative) and TypeScript (client UX) engines, treating any drift between them as a production defect (`docs/architecture/technical-architecture.md` §4.3, Risk R3).
  - **Template golden-file suite (Doc #26 §7) — SHIPPED in H6a, DUAL-ENGINE since H6b**: piping ships a **sibling** grammar, not a new mode of the expression grammar, so it has its own vector set (`tests/golden/templates/`, **76 vectors** across `literals`/`holes`/`escapes`/`parse-errors`/`formatting`) with its own `template_version` manifest and its own PHP⇄TS runner pair (`tests/Unit/Templates/TemplateGoldenVectorsTest.php` + `resources/public-runtime/engine/__tests__/golden-templates.test.ts`) **beside** the two expression suites — which stay pinned at `grammar_version` `2.0`, untouched (verified: still 288 sites, and `git diff` on both existing corpora is empty). Same drift-is-a-defect rule, same Risk R3. Coverage includes value *formatting*, not only hole parsing. H6a ran those vectors PHP-only (`"engines": ["php"]`, counted-but-skipped by the TypeScript runner) because `SchemaValueFormatter::displayValue()` had no twin; that was the right trade, since the method had *no direct unit test at all* and choice-label resolution, `yes_no`, the `'; '` join and every numeric rendering were entirely unpinned. **H6b built the twin (`engine/display-value.ts`) and the key is now gone from the corpus** — every vector runs on both engines. The TypeScript runner needed a net-new render branch to do it (its `expected` was cast to a segment array, so merely deleting the key would have failed all 13 on a shape mismatch rather than running them) plus the fourth guard below, which it was missing — a guard on one side only is itself runner drift, and the runners *are* the enforcement mechanism. `Coercion::toStr()` is explicitly **not** the primitive for a piped `decimal`/`calculated` value — its non-integral float→string parity is documented as unpinned. Two traps the vectors pin on purpose: `boolLabel()`'s truthy set is a case-sensitive closed list, and one field type can hold two runtime types (a respondent's `decimal` is the submitted *string*, a `calculated` value a native float). A fourth guard beyond the manifest three: **every vector must declare exactly one expected outcome**, because the existing runners' `?? []` defaulting lets a vector that asserts nothing pass vacuously.
- **Migration-review checklist item** for RLS-policy coverage on new tenant-scoped tables (Risk R2).
- **Published-version immutability pack (Increment H25, ADR-0013, Risk R5)** — `tests/Unit/PublishedVersionGuardTest.php` plus `tests/Feature/Forms/PublishedVersionImmutability{,Privileged}Test.php`. Worth its own entry because the migration that installs the guard is **alter-only**, so the migration linter skips it and its CI green is *vacuous*: these three files are the only things standing over the trigger. Three harness properties they encode, all reusable for any future DB-level guard:
  - **One throwing assertion per test.** A raised exception aborts the enclosing `RefreshDatabase` transaction, so it must be that test's final database interaction. (`FormVersionRlsTest` records the same rule.)
  - **Every refusal case opens with an anti-vacuity probe** — a bare `updated_at` touch that must affect exactly 1 row — because a mistyped `WHERE` would otherwise pass the test by not throwing at all.
  - **The superuser pack needs a COMMITTED fixture.** `pgsql_privileged` is a separate session and `RefreshDatabase` wraps only the default connection, so a row created the ordinary way is invisible to it: the UPDATE would match zero rows, nothing would throw, and the test would report success while proving nothing. Build on that connection and clean by hand (the `PlatformFieldLibrarySeedTest` shape).
  The unit half is deliberately **text-pinning rather than behavioural**, because the load-bearing properties are things the SQL does *not* say: no bare `<>` (NULL-unsafe against seven nullable columns), no content column named (a hand-list would be fail-open for future columns), and both sides of the row diff present (a one-sided `to_jsonb` is a silent no-op guard that every behavioural test would still pass).

## 2. Testing Pyramid

| Layer | Tooling | Scope |
|---|---|---|
| **Unit** | Pest (Laravel's modern PHPUnit-compatible test framework) | Expression evaluator (golden-file vectors, §1), individual validators, RBAC permission-matrix logic (`docs/multi-tenancy-rbac-design.md` §5 — one test per permission×role cell), DTOs/value objects (`SubmissionPayload`, per `docs/architecture/technical-architecture.md` §4.1). |
| **Integration** | Pest + a real (Dockerized) Postgres, not an in-memory/sqlite substitute (RLS behavior cannot be validated against sqlite) | The `SubmissionPipeline` exercised across **all six channels** (manual, guest, OCR-single, OCR-linelist, offline-sync replay, API-import) through **one shared, parametrized test suite** — not six independent suites — specifically because the architecture plan's central lesson from the legacy audit was "four divergent, duplicated validation code paths had drifted apart" (`docs/data-dictionary.md` reference); a single parametrized suite structurally prevents the six channels from silently drifting behaviorally apart the way legacy's four did, since a fix or regression shows up identically across every channel's row in the same test run. |
| **Contract** | Schema validation against the generated OpenAPI 3.1 document (`docs/api-specification.md`) — e.g., a Laravel test-response macro that validates every feature test's actual JSON response against its corresponding OpenAPI schema | Prevents the classic "the spec and the code silently drifted" failure mode this project explicitly wants to avoid (`docs/api-specification.md`'s own "docs-as-code" framing) — a contract-test failure means either the code or the spec is wrong, and CI cannot tell which without a human, but it *will* tell you they disagree. |
| **End-to-end (E2E)** | Playwright | Golden-path flows per persona (`docs/PRD.md` §2): a Form Editor building and publishing a form, a guest completing and submitting it, a Reviewer approving/returning a submission, an Admin managing tenant settings/roles, a Viewer's read-only boundaries. Also the home of the already-committed responsive-breakpoint checks (`docs/PRD.md` Feature #5) and the WCAG AA `axe-core` scans (`docs/non-functional-requirements.md` §5) — both run as part of the E2E suite against real rendered pages, not simulated separately. |
| **Load / performance** | A dedicated load-testing tool (e.g., k6 or Artillery — tool choice not architecturally significant, left to whichever team sets up the pipeline) | Validates `docs/non-functional-requirements.md` §1's stated response-time targets under §3's stated scalability assumptions — this document does not invent new performance numbers, it tests against the ones the NFR doc already set. Concrete scenarios: a burst of concurrent guest submissions against one form (the "concurrent ingest" case the architecture plan names explicitly), a webhook-delivery burst exercising the circuit breaker (`docs/webhook-integration-design.md`), and a sustained dashboard-query load. |

## 3. Security-Specific Test Requirements

Beyond the already-committed tenant-isolation fuzz suite (§1), this document adds test coverage for the *new* recommendations `docs/security-threat-model.md` introduced, so they don't remain permanently unimplemented recommendations:

- A test asserting the expression engine rejects (or safely times out on) a pathologically deep/recursive expression, per `docs/security-threat-model.md` §7's resource-limit recommendation.
- A test asserting a webhook endpoint URL resolving to a private/internal IP is rejected both at creation time and at delivery time (the DNS-rebinding re-validation `docs/webhook-integration-design.md` §2.2 adds).
- A test asserting an erasure-triggered audit entry never contains raw pre-erasure PII in `old_values` (`docs/audit-compliance-logging-spec.md` §2.1's deliberate exception) — this is exactly the kind of subtle, easy-to-regress behavior that needs an explicit regression test, not just a documented intention.
- The migration linter (ADR-0002 §D6) is itself CI-enforced, not a manual review step alone: a CI job fails the build if a new migration creates a `tenant_id`-shaped column with no corresponding RLS policy, or a new table appears on neither the tenant-scoped nor exemption lists.
- **One output-encoding test per server-rendered surface**, owned by the increment that owns the surface, per `docs/security-threat-model.md` §7's template-encoding table and the contract in Doc #26 §5. Each asserts an injection vector for its own context — a markup answer rendering as visible text in HTML (H6b, and H17 for the queued PDF — both shipped); a `[click](…)` form name staying literal in a markdown email (H3/H23); a `<https://…|text>` title not becoming a live Slack link (H6a); a `=HYPERLINK(…)` answer inert in a CSV/XLSX cell. **This is deliberately the whole enforcement mechanism**, and its weakness is recorded honestly as `docs/security-threat-model.md` §9 item 9: a surface added later escapes correctly only if its author reads that table, since nothing fails the build. Note for whoever writes them: `gitleaks` scans the whole tree, so a vector must be markup or a formula, never a token-shaped string.
  - **Shipped in H6a — two of the four:** `tests/Unit/Connectors/SlackMessageFormatterTest.php` (the `mrkdwn` row; **added, not updated** — the class had no test at all, and the repo's only assertion on a Slack message body was a `str_contains` on *trusted* copy, so the defect was entirely unpinned) and `tests/Feature/Security/InertiaDataPageEncodingTest.php` (the `data-page` row, whose Owner column reads "— (holds)" but whose test H6a owes). Both are regression tests for live behaviour, not preventative ones. **H6b then shipped the third:** the DOM/HTML row, in `resources/public-runtime/__tests__/components.test.ts`, which mounts the real component tree through the SHARED `FieldInput.vue` — the exact surface the table's first row names — and asserts a piped `<script>alert(1)</script>` answer renders as visible text, adds no `<script>` node to the document, and appears HTML-escaped in the markup. **H17 then shipped the fourth**, the queued-PDF row, in `tests/Feature/Submissions/SubmissionPdfRendererTest.php`. It asserts against the HTML handed to dompdf rather than the PDF byte stream — deliberately, because PDF text is Flate-compressed, so grepping the output for `<script>` would pass whether or not the escaping worked (the vacuous-green shape H6b's mutation pass caught). Four sites are asserted separately, not just the answer: the form title, the section heading, the field label and a **piped** label, because §5 decision (3) binds every untrusted value on the surface and the named failure mode is escaping the answer while leaving the title raw beside it. A fifth assertion covers the `ENT_QUOTES` half with an attribute-breaking payload, and a structural guard scans every PDF template for a raw-output directive — that guard was itself found **passing vacuously** by mutation (`->not->toContain($needle, $message)` is varargs *needles*, not an assertion message) and fixed. **Still owed:** the markdown-mail row (H3/H23) and the spreadsheet row (its own increment) — each increment deliberately closed only its own surface, since absorbing another's would have falsified §9 item 9's count. **H21 (workflow branching) adds no row to this table and owes no output-encoding test**, because it renders no new surface — it changes only *which* of the existing surfaces a given respondent reaches (Doc #27 §9). What it owes instead is a **mirror-pair** test, and **H21a shipped it — one increment earlier than planned, and in a different shape than prescribed** (Doc #27 amendment A6). The plan was the H17 device: a test that PARSES `resources/public-runtime/composables/useFormRuntime.ts`. That was **rejected as vacuous** on inspection. `PdfFieldRoleTest` works because it parses actual DATA — `RENDERS_NOTHING`'s members ARE the rule — whereas a step projection's rule is control flow, so parsing it would pin a list of predicate NAMES that either side could implement with inverted polarity and still satisfy. That is exactly the shape this document's own caution about vacuous assertions warns against.

The pair is therefore **behavioural, driven by a shared fixture**: `tests/fixtures/step-projection.json` holds sixteen cases of `(sections, sequences, repeat topology, field→section map, answers) → expected step keys`, and `tests/Unit/Forms/StepProjectionTest.php` and `resources/public-runtime/__tests__/steps.test.ts` each drive all sixteen through their own engine, so a difference in the resulting list is a projection difference and nothing else. Both halves carry the `PdfFieldRoleTest` anti-vacuity guards — a minimum case count, unique case names, and an assertion that the fixture holds at least one empty and one multi-step expectation, without which a projection that always returned `[]` (or always returned every section) would satisfy the whole file.

A `tests/golden/steps/` corpus stays rejected for its original reason: a step vector needs a section list, per-section sequences, a repeat topology and a field→section map, none of which the language-neutral vector shape carries. The fixture sits **outside** `tests/golden/` and carries no `grammar_version` key, so it is not a fifth corpus and **the count stays at exactly 296, the validation total at 114**.

**H21a's own new suites, registered here so the obligations are traceable:** `StepGraphInspectorTest` (the three publish-time notices, every case asserting the publish SUCCEEDS — a test asserting a refusal would pin the opposite of Doc #27 §6), `FormPublishWarningsTest` (the flash + toast delivery path, including the silence case and the case where a real gate refusal must still surface as an error), `clock.test.ts` (the session clock's exact ISO-8601 shape and zone), and extensions to `SemanticValidatorTest` / `engine.test.ts` carrying **twinned assertions for every settle-loop change**. That twinning is the point: all four of those changes live inside `evaluate()`, which IS the golden runners' entry, and no current vector discriminates any of them — a far weaker guarantee than "the runners cannot see them", and the reason each needed a hand-written test on both sides.

**H21b's own new suites, same reason:** the guest-runtime slice adds no golden vectors either, so every guarantee is hand-written. In `resources/public-runtime/__tests__/` — `runtime.test.ts` gains the store contracts (both empty-graph shapes, the outward rescue walk in **both** directions, the visited set, the `StepChange` record, all four `goToStep` resolutions); `components.test.ts` gains the same shapes **through the rendered DOM**, because Doc #27 §9 notes the store and the view fail differently, plus the §5.5 submit dead-end, the single-page section removal (asserting focus lands on a reachable element — an axe pass cannot catch a reset to `<body>`) and the resume-drift copy; `replay.test.ts` gains §5.4's version guard, whose non-vacuous half is that the row is **never POSTed**, not merely that it ends up `conflict`. `tests/Feature/Guest/GuestDraftRuntimeTest.php` gains §5.4's grace-window interaction as three cases that pin the pruning outcome rather than the absence of a 500. `tests/e2e/public-runtime-axe.spec.ts` gains the terminal state and a single-branch control over a new `Branching Router` seed — the only a11y gate that sees runtime pages, since the Storybook axe job globs `packages/design-system/src/**` and there are no stories under `resources/`. **The §9 caution earned its place twice.** Every empty-graph assertion is paired with the Submit control *by its exact label* and with a non-empty control mount, because an empty-graph test passes trivially against a component that renders nothing. And mutation testing found that the rescue walk's FORWARD arm was pinned by nothing at all: deleting it reddened zero tests until a case existed where the vanished step had no predecessor.

**H21c's own new suites, and the one shape they deliberately do NOT take.** The encode slice adds no golden vectors either, and the corpora stay byte-untouched (296 sites, 114 vectors). Its headline obligation — Doc #27 §9's "the encode path and the guest SPA produce the same step list" — is discharged by `tests/Feature/Submissions/EncodeStepParityTest.php`, the **third** consumer of `tests/fixtures/step-projection.json` after H21a's pair, driving all sixteen cases as REAL published forms. It does not run two projections and compare them: the encode page now mounts `createFormRuntime()` itself, so that comparison would be a tautology about one function wearing a cross-channel costume. It asserts the INPUT instead — the encode payload's `version.schema` is byte-identical to `PublicFormPresenter`'s, and rebuilding from that shipped snapshot reproduces each case's taken path — which is the link that can actually break. `EncodeStepPayloadTest` pins the envelope the agreement rides on (`single_page_mode` finally read, the ISO-8601 clock's exact shape, the `SchemaResponse` keys a browser would `TypeError` on, the hidden-only section dropped from the steps while its keyable row survives in `blocks`). `EncodePdfTakenPathTest` pins §9's cross-check against `SubmissionPdfPresenter` over three distinct taken paths, both sides on the submission's own pinned clock, with the two vocabulary exclusions asserted rather than glossed — and `SubmissionPdfPresenter` is deliberately not refactored onto `StepProjection`, because "shown, and empty" is a sentence only one of the two can form. `PrunedAnswerReportTest` pins §7's defect (b): nine cases, every one asserting the submission SUCCEEDED and the loss was NAMED, since a test asserting a refusal would pin the opposite of the design. An adversarial pre-merge review over the finished diff then found three real defects that every one of those suites had been green over — all three consequences of mounting the guest store rather than slips — and each is now pinned by a regression test **verified to redden against the unfixed code**. That verification is the part worth institutionalising: the first regression test written for the repeat-instance mask defect PASSED against the broken version, because with one surviving row and one pruned row the two implementations name different rows and render the identical string. A test written to prove a fix is exactly as vulnerable to this document's more-than-one-path caution as a test written to specify a feature. The client half is `resources/js/Pages/submissions/encode.test.ts` (17 cases), and two `Branching Router` encode journeys join `responsive-axe.spec.ts` — the only encode scans that see the stepped flow at all.

**H21d1's own new suites, and the one they do NOT owe yet.** The logic-canvas slice adds no golden vectors either; the corpora stay byte-untouched (296 sites, 114 vectors). 1. **The chart's text alternative is guarded by a unit test, not by axe.** `axe` cannot detect a *missing* text alternative for an SVG that carries a plausible `aria-label`, so the merge-blocking accessibility job will pass a chart that is an unreadable picture. Every chart primitive therefore carries a Vitest assertion that it renders a real data table with one row per plotted point (ADR-0011 §D12). "axe is merge-blocking" must not be read as "accessibility is covered" for data visualization.
2. **The e2e accessibility fixture must seed a Business-entitled tenant.** *(Discharged by H24a: `E2eSeeder` puts `acme` on Business — as an **upsert**, because the block is guarded by an `exists()` check and a plain tier edit would have silently no-opped on every already-seeded database, going green in CI while every developer's box stayed on Professional.)* The analytics surface is gated on `advanced_analytics`, whose tier is held from sale, so an ordinarily-seeded tenant cannot reach the route at all — the responsive-axe spec would stay green over a page it never loaded, and a brand-new visual surface would ship with zero coverage (ADR-0011 §D9).
3. **The streamed export needs a non-empty-body assertion, not a status assertion.** *(Discharged by H24a: `AnalyticsExportTest` parses `streamedContent()` and asserts rows. Two findings worth carrying: the first implementation materialized the rows in request scope, which made all three of §D13's "load-bearing" lines ceremony — deleting `applyLocal()` reddened NOTHING, and the aggregation was moved inside the closure so the protection is real; and §D13 names only `applyLocal()`, but the permissions TEAM id is torn down too, and `AnalyticsFormSet` consults `$user->can()`, so an org-wide reader could silently export their granted-forms subset instead.)* The export closure runs during `Response::send()`, after middleware has torn tenant context down; omitting the `TenantContext::applyLocal()` re-assertion inside the closure yields an **empty file with HTTP 200**, which every status-only test passes (ADR-0011 §D13). Assert on rows, not on the response code.

Two correctness invariants in the same increment are ordinary Pest tests but are easy to omit because the wrong behaviour looks like success: a cross-version aggregate over a key whose `indexed_data_type` changed must **refuse and name the version** rather than average the surviving rows (§D4), and an analytics count must exclude drafts and soft-deleted submissions and must never read the typed answer index without joining `submissions` (§D2).

## 4. Static Analysis & Code Style

- **Larastan/PHPStan at level 8** (Laravel-aware static analysis) — a concrete, CI-blocking level, chosen as the highest level realistically achievable without excessive `@phpstan-ignore` noise for a Laravel codebase at this project's start (level 9's stricter mixed-type handling is a plausible later tightening once the codebase's own type coverage matures, not a Phase 0 requirement).
- **Pint** (Laravel's official code-style fixer) — zero-config default ruleset, CI-blocking on any diff, auto-fixable locally via `pint --dirty` before commit.
- **Controller complexity/line-count gate** (the architecture plan §5 names this explicitly as a new discipline: "add a CI complexity/line-count check this time," citing legacy's 1,747-line `FormController.php` and 1,574-line `DataSubmissionController.php` as the concrete cautionary precedent). **Concrete thresholds**: a controller class fails CI at **250 lines** (excluding blank lines/docblocks) or a single method exceeding **cyclomatic complexity 10** — both enforced via a static-analysis rule (e.g., a custom PHPStan rule or PHP Mess Detector integrated into the same CI stage as Larastan), not a manual code-review convention alone, since legacy's own stated "thin controllers" rule existed but was never tooling-enforced and controllers grew unchecked anyway.

---

## 5. Test Data & Fixtures

- **Factories, not fixture files**, for every model (Laravel's standard `Model::factory()` pattern) — keeps test data generation co-located with the models it represents and trivially variable per test case.
- **No real PII in test fixtures, ever** — synthetic/generated data only (e.g., via a library like `fakerphp/faker`), consistent with `docs/data-privacy-gdpr-compliance.md`'s posture; this also means the tenant-isolation fuzz suite (§1) and integration suites can run against realistic-shaped data without any actual respondent information ever touching a CI environment or a developer's local machine.
- **Multi-tenant test seeding is a first-class factory concern**: every model factory accepts (or defaults to creating) a `tenant_id`, so writing a cross-tenant test (§1, §3) is a one-line factory call, not boilerplate tenant setup repeated per test file.

## 6. CI Pipeline Stages (order)

1. **Static analysis, style & security scanning** (Larastan, Pint, the controller-complexity gate, §4; plus the SCA/SAST/secret-scanning checks in §3) — fails fast, cheapest checks first; a high/critical dependency vulnerability or a detected committed secret blocks merge.
2. **Unit tests** (§2).
3. **Integration tests** (§2) — against a real, Dockerized Postgres service container.
4. **Contract tests** (§2) — depends on the OpenAPI document being up to date; a mismatch here blocks merge.
5. **Build** (the actual application build/asset compilation step).
6. **E2E tests** (§2) — against the built application, in a CI-provisioned ephemeral environment.
7. **Deploy** (per `docs/architecture/technical-architecture.md` §8's "a real deploy stage" — the concrete deploy mechanics belong to Doc #22, not re-derived here).

Load testing (§2) runs on a separate, less-frequent cadence (e.g., nightly or pre-release, not on every PR) given its cost/duration relative to the rest of the pipeline — flagged here as a scope decision, not an oversight.

- ~~Mutation testing~~ — **this line was stale and is corrected here (H21c).** No mutation-testing *tool* is adopted and none is planned; what IS now standing practice, unprompted by any framework, is a **hand-run mutation pass over the code an increment just wrote**, one edit at a time, recording which tests each reddens. H21a, H21b and H21c each ran one, and each found something a green suite had not: H21a that dropping the post-loop mask tightening was green for two compounding reasons (the assertion was an `if/else` invariant satisfied by both behaviours, and the settle bound means the field COUNT decides which phase of an oscillation the loop halts on); H21b that §4.2's forward walk was pinned by **nothing at all**, which corrected the design document rather than a test; H21c that passing the OMITTED-filtered field list to `StepProjection` reddens **nothing**, because two lists answering different questions happen to stand in a subset relation nothing enforces.
  **The standing lesson all three share: a mutation that reddens nothing is the loudest result you can get.** It does not mean the code is redundant — it means no test reaches that path, and the right response is to find out empirically *why* before trusting either the test or the mutation.
