## 1. What's Already Decided (not re-derived here)

This section is citations, not derivation. Nothing below is re-opened by this document.

- **Branching is relevance-derived step-skipping, not true goto.** Ratified as answered decision #1 on 2026-07-21 (`PROGRESS.md`, "The 5 open questions — ANSWERED"). No `ExpressionKind::Branch` — the enum stays at exactly three cases (`app/Enums/ExpressionKind.php:16-18`, `Relevant` / `Constraint` / `Calculate`). No PHP⇄TS evaluator-mirror change. No new golden vectors. The R3 dual-evaluator gate is untouched by the whole of H21.
- **The progress indicator is "Step X of N" with N dynamic**, recounted as if an irrelevant section had never existed for this respondent — never "Step 4 of 6 (skipped)". The alternative (a fixed count with skipped steps visibly grayed out) was explicitly rejected because it exposes the form's *entire possible* logic surface to every respondent regardless of their own path (`docs/ux/form-filling-ux-flow.md` §3.2).
- **One `form_sections` row is one step**, and a repeatable section is ONE step, not N — its per-instance "add another" affordance lives inside that single step (`docs/ux/form-filling-ux-flow.md` §3.1).
- **`relevant_expression` already exists on both fields and sections**, end to end: the DB (`form_sections` and `form_fields` migrations), the frozen snapshot (`app/Services/Forms/SchemaSnapshotSerializer.php:126` section / `:151` field), the wire, both engines, the publish gate (`app/Services/Forms/ExpressionValidationGate.php:63-70`), and the builder UI (`resources/js/components/builder/ConfigPanel.vue:388-390` field / `:511-513` section). This document adds no storage location and no fourth expression kind.
- **The draft-vs-close policy is a grace window, already ratified and built in H12a** — a save-and-resume draft started before the form closed may still be promoted after close, bounded by its own `draft_expires_at`; only a NEW submission or a NEW draft is blocked once closed, and a time close never waives the capacity cap (`app/Services/Submissions/FormAcceptanceGuard.php:14-25`, `assertCanStart()` `:34-45`, `assertCanPromote()` `:54-61`, `assertCapacity()` `:72-92`). The H-map assigned this doc the "draft-vs-close policy shared with H12" obligation; it is discharged **by citation**, not by re-deciding. §5.4 records the one interaction branching adds.

## 2. The Step Model (v1.0)

**A step is a projection, not a row.** There is no `steps` table, no `pages` table, no edge table and no `next_step_id` column anywhere in this system, and this document adds none. The persisted model is `forms → form_versions → form_sections → form_fields`, and the step list is computed — per respondent, per keystroke — from `(sections ordered by sequence, filtered by relevance)`.

**The step graph is a total order filtered by relevance, and this document declines to call it a graph.** `visibleSteps` (`resources/public-runtime/composables/useFormRuntime.ts:292-341`) walks `renderModel.sections` in `sequence` order, skips any section whose relevance is false, and emits a `RuntimeStep` for each survivor. Navigation is index arithmetic over that array: `attemptNext()` moves to `idx + 1` (`:821-850`), `goPrev()` to `idx - 1` (`:852-857`), `goToStep(key)` jumps to a member (`:859-863`). There is no successor edge, no branch target, and no author-drawn adjacency of any kind. Every "branch" in this product is a **predicate on a node**, never an edge between nodes.

> **Why not an author-drawn edge table.** A `form_step_edges` table is a new tenant-scoped table — a migration-linter obligation plus an RLS policy under Risk R2 — plus a new `schema_snapshot` key, plus a reachability / dead-end / termination validator that exists nowhere in `app/` today (the only cycle check in the entire application is `App\Exceptions\Scoping\ScopeNodeException::wouldCycle()`, for the org-unit tree, and G10a records that re-parenting was rejected precisely because a cycle check needs locks). It would also re-open answered decision #1 and drag R5's trigger back out of H25. The concrete cost of *not* doing it is exactly one authoring shape — "after section 3, jump forward to section 7" — which is expressible as relevance on sections 4–6 at the price of N predicates instead of one edge. §10 records that cost honestly rather than pretending it is zero.

> **Amendment A7 (H21a, as-built) — section keys and field keys are NOT globally unique, and a document elsewhere in the codebase says they are.** `ExpressionValidationGate.php` asserts, in a comment justifying its flat known-key union, that they are "globally unique per version, so there is no key collision." That is false. Uniqueness is two INDEPENDENT per-table composite indexes — `form_sections` and `form_fields` each carry `(tenant_id, form_version_id, key)` — and every application-level enforcer is table-scoped too (`UpdateSectionRequest` and `UpdateFieldRequest` each `Rule::unique` their own table; `FormBuilderService::uniqueKey()` plucks from one). The only place that enforces a shared namespace is `XlsformImportParser::sanitizeKeys()`, which is one of five writers.
>
> This matters directly to amendment A2: seeding a repeatable section's key into the settle context without a collision guard would re-admit the answer of a FIELD of the same name that relevance had just pruned — a hidden value flowing back into a downstream gate, mirrored into both engines so R3 would stay green and nothing would catch it. As built the seed skips any section key that matches a field key, checked against every field key in the version rather than only the currently-relevant ones. The stale comment is corrected in passing.

### 2.1 The step key namespace

A step key is either a `form_sections.key`, or the reserved sentinel `__lead__` (`useFormRuntime.ts:49`). The sentinel names a synthetic leading block holding every renderable field with no section — it is emitted first, before any section step (`:295-306`), and it is the one step that can never carry a `relevant_expression` of its own, because it has no `form_sections` row to hang one on. The reservation is structurally safe from the two authoring paths that validate keys — `UpdateSectionRequest`'s `regex:/^[a-z][a-z0-9_]*$/` rejects a leading underscore, and `XlsformImportParser::sanitizeKey()` prefixes `x_` to anything not starting with a letter — but `SchemaBlueprintMaterializer` (form templates) and `FieldLibrary` write through `Model::create` with no FormRequest in the path. So the reservation is **a convention with two verified enforcers and two unverified writers**, which is the same shape Doc #26 recorded for `*_translations`. H21a owes it a test, not a migration.

### 2.2 The visibility predicates

A step is emitted when **all three** hold. The first two are as-built; the third is new in H21a and is the one correctness change this document asks for.

1. **The section is relevant** — `sectionRelevance[section.key] !== false` (`useFormRuntime.ts:308-311`).
2. **The section holds at least one field that renders something** — the `rendersNothing(fieldType)` filter runs *before* the emptiness check on purpose, so a section holding nothing but `hidden` / `calculated` / `page_break` fields vanishes entirely rather than rendering a heading over a blank panel (`:319-325`, the H7 comment).
3. **The section holds at least one field that is *currently relevant*.** This does not hold today, and its absence is a live defect: predicate 2 filters on `rendersNothing(f.fieldType)`, a **static type predicate**, and never consults `fieldRelevance`. So a relevant section whose every field is individually gated off renders a heading, a Next button and zero questions — the grayed-out-skipped-step experience `form-filling-ux-flow.md` §3.2 explicitly rejected, arriving through a different door. `attemptNext()` then finds `relevantKeys` empty (`:836-841`) and advances, so the respondent clicks Next through a dead step. Under H21 this stops being an edge case: conditioning on *fields* is the more natural authoring style than hoisting the condition onto the section, so it becomes the default outcome.

> **The honest cost of predicate 3, stated rather than hidden.** Step *membership* becomes answer-reactive, where today only section relevance moves it. That is the same coupling `:329-334` deliberately refused for step *titles* — it kept piping out of the step model so that navigation would not depend on typing. The mitigation is that `fieldRelevance` is already a computed off the same `SemanticResult`, so no new evaluation is introduced and no new engine call is made; only a new dependency edge, reaching `currentStepIndex`, `erroredItems` and the autosave watcher. H21a takes the coupling knowingly, because the alternative is shipping a step the UX spec says must not exist.

### 2.3 Navigation is index arithmetic, and two of its edges are unspecified

`attemptNext()` validates the current step, then advances by index; on the last step it returns `advanced: true` with **no key change**, and the caller distinguishes the two by `isLastStep`. A step that vanishes under the respondent is rescued by `reconcileCurrentStep()`, which clamps to `min(lastValidIndex, length - 1)` (`:366-374`). §4 specifies the two shapes this arithmetic cannot currently express.

## 3. Relevance as the Branching Primitive

**The branching semantics are the relevance semantics.** Relevance settles to a bounded fixed point over the whole version — sections first, then fields, iterating until the field mask stops changing (`app/Services/Validation/SemanticValidator.php:262-306`, mirrored line-for-line at `resources/public-runtime/engine/semantic-validator.ts:260-299`). A field is relevant iff its owning section is relevant, its own `relevant_expression` holds, and no `skip_if`/`skip_with` unit holds. This document changes none of it. What follows is the three places that settled semantics under-specify *branching* specifically.

### 3.1 Forward references are legal at publish, and warned at authoring time

A section-level `relevant_expression` may reference a field that lives in a **later** section. This is legal today: `ExpressionValidationGate::assertExpressionsResolve()` checks that an expression parses and that every `${key}` resolves to a known field or section key (`:32-83`) — it says nothing about position. Piping, by contrast, is strict: a template hole may only reference something at a strictly earlier position, and a violation is `template_forward_reference`, a permanent publish refusal (`app/Services/Forms/TemplateValidationGate.php:201` via `TemplateScopeResolver::precedes()`).

**The piping ban does not transfer, and the reason is not consistency but arithmetic.** A forward piping hole is *permanently* empty — it renders at a moment the referenced answer cannot yet exist, and re-rendering it later is not a thing the surface does — so it is provably useless and refusing it costs the author nothing. A forward relevance reference is merely *late*: it evaluates false until the respondent reaches the referenced field, and true from then on. It is a legitimate authoring shape ("show the intro section only to respondents who later say they are a returning customer" is silly; "show the summary section only when the roster below is non-empty" is not), and it is the shape a visual canvas will produce by accident whenever an author drags a condition upward.

> **Why not refuse forward references at publish.** It is a retro-gate, and the shape of the damage is counter-intuitive. A publish gate is non-retroactive by construction, which sounds safe: the already-published version keeps serving, so no respondent is affected. The trap is the *next* publish. `PublishService` runs the gates against the draft (`:62-64`), and step 9 of `publish()` clones the just-published structure forward into a fresh draft — so a form that is live and collecting data becomes **un-editable**, and the error names a rule its author wrote before the rule existed. There is no grandfather mechanism for publish gates: H5c's `legacyOverrides()` seam covers entitlements only.

**What allowing it costs, and what H21b must therefore specify.** A step can become relevant *behind* the respondent. `reconcileCurrentStep()` fires only when the current key **vanishes**, never when an earlier step **appears**, so the respondent is not moved — but `currentStepIndex` silently shifts, and `ProgressIndicator` decides "done" by comparing indices (`resources/public-runtime/components/ProgressIndicator.vue:25`), so a step the respondent has never seen acquires a clickable "done" dot. The label jumps from "Step 2 of 2" to "Step 3 of 3" with no announcement, because `StepView.vue:45-54` watches `currentStepKey`, which did not change. **Specify:** a step that becomes relevant behind the respondent is inserted in document order; the count recomputes; the respondent is never teleported backwards; `ProgressIndicator` marks "done" from a **visited set** rather than an index comparison; and a change in N is announced.

### 3.2 Cycles keep the iteration bound, and the bound becomes normative

Two sections whose relevance depends on each other's fields produce no error. The settle loop is bounded at `fields.count() + sections.count() + 2` (`SemanticValidator.php:270`) and exits early on a fixed point (`:299`); a cycle simply runs to the bound and returns whatever mask that iteration count happened to produce. Nobody has characterised what the bound produces for any specific cycle shape, and this document does not pretend otherwise.

**PHP and TypeScript do not diverge on a cycle today — but the parity is a coincidence, not a contract, and this document makes it a contract.** Two unpinned facts hold it up. First, the break predicates differ: PHP compares `$next === $relevant`, which is array-order- and type-sensitive, while TS compares key sets. They agree only because both build their masks by iterating fields in the same order. Second, **the bound's operands come from different sources** — PHP counts Eloquent rows loaded from the database, TS counts entries mapped out of `schema_snapshot`. They match today only because `SchemaSnapshotSerializer` filters nothing. If either side ever drops a field type from its count, the two engines land on **opposite phases of the cycle** — a silent R3 break with no golden vector to catch it, because the corpus has no cyclic vector and this document adds none. **Normative:** the bound is `fields + sections + 2` in both engines, and both operands are counted over the *identical* schema set.

**A second bound-exhaustion artifact, which matters here specifically because the step model straddles the two masks.** The settle loop recomputes the section mask from the current field mask, then derives the next field mask from it, and returns both. On the normal exit — a fixed point — they describe the same state. On **bound exhaustion** the loop has already assigned the newer field mask while the section mask still holds the verdict computed from the *previous* one, so the two are returned one iteration apart. That is invisible to every consumer that reads only one of them, and the step model is the first consumer to read both: step *membership* comes from `sectionRelevance`, while step *contents*, `attemptNext()`'s validation set and `effectiveAnswers()`'s prune all come from `fieldRelevance`. In an oscillating graph that yields a step hidden from the rail whose fields nonetheless survive into the submitted document, or a step rendered over fields that are all masked off and whose answers are pruned anyway. Identical in both engines, so not an R3 break — a soundness hole the H21 step model would sit directly on. **H21a resolves it inside the ratified model**, by recomputing the section mask from the final field mask after the loop, or by deriving step membership from `fieldRelevance` alone per §2.2's predicate 3. Either is a same-file change with no grammar, AST or corpus impact.

> **Amendment A3 (H21a, as-built) — recomputing the section mask is NOT sufficient on its own.** The first remedy above, taken literally, relocates the inconsistency rather than removing it: the returned FIELD mask was derived under the *previous* section mask, so pairing it with a freshly recomputed section mask still permits a field marked relevant beneath a section marked irrelevant — it only flips the disagreement's sign. As built, `settleRelevance()` therefore does both halves once after the loop: recompute the section mask from the final field mask, then **tighten the field mask by that section gate**, so `field ⊆ section` holds by construction. Both halves are provable no-ops on the fixed-point path — the break fires *before* `$relevant` is reassigned, so the returned map is exactly the one the in-loop context and mask were built from, and every key in it already passed the gate — which is why no golden vector moves. Mirrored line-for-line in `semantic-validator.ts`.
>
> **The artifact is real, not theoretical, and the fixture that exposes it is parity-sensitive.** Verified empirically on an oscillating pair: with the loop bound at `fields + sections + 2`, the field COUNT decides which phase of the oscillation the loop halts on, and only one phase exposes the disagreement. At three and five fields the tightening is a genuine no-op; at four, the un-tightened engine returns `sectionRelevance[sec] = false` alongside `fieldRelevance[inside] = true` **and persists that field's answer**. A regression test built without that exact shape passes either way — which is how the first version of this increment's test was written, and what its mutation run caught.

> **Why not detect cycles at publish and refuse.** Detection is cheap — `ExpressionParser::referencedKeys()` already returns every reference, so the dependency edges are one walk away, and the check is O(V+E). Cost is not the reason to decline; §3.1's retro-gate argument is, plus one more. A detector must discriminate a genuine cycle from a legitimate **chain** — the `chained_fixed_point` vector in `tests/golden/validation/relevance.json` pins exactly such a chain as correct behaviour — and a detector that cannot tell them apart warns on correct forms, which is worse than not warning. H21a ships cycle detection as an **authoring warning**, never a refusal.

### 3.3 `count(${section})` is always zero inside a relevance expression

**This is a live, silent, always-false authoring trap, and "branch on whether they added any household members" is a first-rank H21 idiom.** The settle loop builds its evaluation context as `array_intersect_key($input->answers, $relevant)` (`SemanticValidator.php:275`), and `$relevant` is seeded from **field keys only** (`:266-268`) — never section keys. The repeat-instance array is therefore intersected away before any relevance expression sees it, `count()` reads ABSENT, and the result is 0 forever. Meanwhile `ExpressionValidationGate` *explicitly* adds section keys to the known-key set so that `count(${roster})` publishes cleanly (`:57-61`), and `computeCalculated` runs over the full effective answers **including** the merged repeat arrays — so the identical expression works correctly in a `calculated` formula and silently never fires in a branch condition. The behaviour is consistent across both engines, so it is not an R3 break; it is an author writing a correct-looking condition that can never be true. **H21a must either seed section keys into the settle context or refuse `count(${section})` in a `relevant_expression` at publish** (warn-only where the published version already contains one, per §6).

> **Amendment A2 (H21a, as-built) — seeded, and at TWO scopes rather than one.** H21a took the seeding route, because refusing would permanently foreclose an idiom the publish gate already blesses. Three implementation rules turned out to be load-bearing, each a bug if reversed:
>
> 1. **The section keys are unioned into the intersect ARGUMENT, never into `$relevant` itself.** `$relevant` is what the fixed-point compare tests, and it is built from fields only — seeding a section key into it makes `$next === $relevant` unsatisfiable, so every form would run to `$maxIterations` on every keystroke, turning this section's exhaustion artifact from exotic into the default.
> 2. **Only REPEATABLE sections are seeded.** A non-repeatable section key is never an answer key, so seeding it resolves ABSENT and leaves `count()` at 0 forever — the same always-false trap, wearing the appearance of a fix.
> 3. **A section key that collides with a field key is skipped** — see amendment A7.
>
> **The second scope this section did not name.** The identical trap exists inside a repeat MEMBER's `relevant_expression`: `settleInstanceRelevance()` builds its context from `$baseAnswers`, the top-level effective map captured *before* the repeat arrays are merged in, so the group's own key read ABSENT there too. "Ask this only when the household has more than one member" is the idiom that hits it. Leaving it half-fixed would have been worse than leaving it whole — the same expression working at one scope and silently failing at the other — so H21a seeds both, in both engines.
>
> **`count()` reads the RAW instance array**, because repeats are processed after the settle loop, where `computeCalculated` runs last and sees the relevance-PRUNED instances. Both engines do exactly this, so the difference between the two passes is a documented property of the pipeline order, not a divergence.

### 3.4 Relevance must be evaluated against a stamped clock on both sides

**Live PHP/TS divergence, invisible to the R3 gate.** `toSemanticInput()` returns `{ ...engineSchema, answers, locale }` (`resources/public-runtime/lib/schema-mapping.ts:604-606`) — it never passes `now`. `SemanticInput.now` is optional, so `EvaluationContext.now` falls to null, `hasNow()` is false, and both clock functions return ABSENT: `now()` at `resources/public-runtime/engine/evaluator.ts:195` and `today()` at `:242-244`. PHP never does this — `SemanticValidator::validate()` stamps `$now ?? Carbon::now()->toIso8601String()`. **The golden runner supplies `now` from each vector, so R3 stays green while the production wiring diverges.** An author who writes `${event_date} >= today()` on a section gets a branch that shows on the server and hides on the client, or the reverse: the respondent either fills a step the server then prunes (silent loss) or is required to answer a field the client never rendered (a 422 that §5.5 shows is also invisible). This is a **call-site** bug, not an evaluator bug — closing it touches nothing this document or answered decision #1 ratified. **Specify:** H21a threads a clock into `toSemanticInput`, and the doc states the contract plainly — the device clock drives the live client evaluation because there is nothing else to drive it, and **the server's clock is authoritative** at submit, exactly as H17 pinned the PDF replay to the submission's own `finalized_at` rather than to the moment someone clicked Generate.

> **Amendment A1 (H21a, as-built) — the motivating example above is WRONG, and the fix is narrower than this section claims.** `${event_date} >= today()` is already always-false **in both engines**, so it could never have produced the divergence described: `>` `<` `>=` `<=` route through numeric comparison (`ExpressionEvaluator::numericCompare()`, mirrored at `evaluator.ts:107-121`), and `Coercion::NUMERIC_RE` is `/^-?[0-9]+(\.[0-9]+)?$/`, which rejects `'2026-08-01'`. A non-numeric operand makes any ordering comparison false on both sides. Date ORDERING is not a working branching primitive in grammar v2.0 at all, and this document should not have implied it was.
>
> **What the clock fix actually buys** is equality against the clock (`${d} = today()`, which before H21a was true on the client exactly when `d` was EMPTY — actively wrong rather than merely inert), plus `count()`, `if()` and `int()` over `today()`/`now()`. That is worth fixing and is what shipped; the scope is recorded here so a later reader does not go looking for date-range branching that was never there.
>
> **The zone is UTC, not the device offset**, and that is the load-bearing choice this section left open. The server re-validates at submit under its own UTC clock (`config/app.php`'s `'timezone' => 'UTC'`), so stamping the local offset would make `today()` disagree across the evening window in every UTC+ zone: the client renders a step the server then prunes, `passed()` is true because an irrelevant field is never required-checked, and the respondent gets a 201 with silently dropped answers. UTC costs only that `today()` is the machine's calendar day rather than the respondent's — visible and arguable, not a silent data fault.
>
> **The FORMAT is itself a mirror surface.** Both engines return the injected clock verbatim from `now()`, so `isoClock()` emits PHP's exact `Carbon::toIso8601String()` shape — `2026-08-01T12:34:56+00:00`, seconds precision, explicit offset, never `Z` — which is also the shape every `now` literal in `tests/golden/**` carries. `new Date().toISOString()` would have emitted milliseconds and `Z`: a *new* divergence introduced by the increment that exists to close one.
>
> **Narrowing, recorded:** the clock is stamped once at session construction and frozen for its life (the H7 `search` precedent, which keeps the store DOM-free and pure). A session held open across midnight keeps its opening date; a resume re-mounts and re-stamps. A ticking clock was rejected because it would re-run the whole evaluation on every tick and invalidate `visibleSteps`, `erroredItems` and the autosave watcher with it.

## 4. Degenerate Graphs and Terminal States

### 4.1 The empty graph is a specified terminal state

`visibleSteps` can be empty — there is no guard against it, and H21 reaches it easily (a router form whose every section is gated on a hidden, URL-prefilled field, where the hidden field's own section vanishes under predicate 2). **What the respondent gets today is not a blank form; it is worse.** `currentStepIndex` is `-1` (`findIndex` over an empty array, `useFormRuntime.ts:348`), so `isLastStep` evaluates `-1 === -1` → **true** (`:357`), so `StepView.vue:107` renders **Submit** and not Next. `currentStep` is null (`:349-355` requires a non-empty list for the fallback), so `StepView.vue:98` renders nothing at all — and with no `[data-section-heading]` in the DOM, focus management falls back to `[data-runtime-main]` (`:32-34`). `ProgressIndicator` clamps the index to 0 and prints **"Step 1 of 0"** (`:13`, `:20`). And because nothing is relevant, nothing is required, so `passed` is true and the Submit **succeeds** — creating a real submission with an empty answer document, under a false step count, in one click.

**Specify:** at zero visible steps the progress indicator is **suppressed** rather than rendered at "Step 1 of 0"; a terminal panel explains that there is nothing further to complete; Back is unavailable; Submit is the single action and is explicitly labelled as submitting what has been answered. `isLastStep` becomes `length > 0 && index === length - 1` rather than an accident of `-1`.

**There is a second, worse shape in the same code, and H21b owes it the same fix.** If `visibleSteps` is empty at *construction*, `currentStepKey` is never seeded — the assignment is guarded on a non-empty list (`:344-346`) — so it stays `''`. The rescue watcher tracks `visibleSteps.some(s => s.key === currentStepKey)` (`:376-383`), which is false at t=0 and **stays false when steps appear**, so it never fires; and `reconcileCurrentStep()` early-returns on an empty list anyway (`:367-369`). With one step now visible: the index is still `-1`, `currentStep` falls back to `visibleSteps[0]` and renders, `isLastStep` is `-1 === 0` → false so **Next** shows, and `attemptNext()` validates, fails the `idx >= 0` guard, and falls through to `return { advanced: true }` with no key change. **Next does nothing, forever, and Submit never appears.** The fix is to reconcile on the **index** (`index < 0 && length > 0` self-heals) rather than on a membership boolean.

> **Amendment B1 (H21b, as-built) — both shapes are closed, and the second one needed a different watcher, not a better guard.** `isLastStep` is now `length > 0 && index === length - 1`; `isTerminal` is a new computed the view routes on, because with the guard in place `isLastStep` is correctly *false* at zero steps and the template would otherwise render **Next**. The terminal panel carries `data-section-heading`, so the existing focus walk still lands on something real, and Submit is labelled "Submit my answers".
>
> The never-seeded shape was not fixable by improving `reconcileCurrentStep()` — the bug was the watcher's SOURCE. It tracked `visibleSteps.some(s => s.key === currentStepKey)`, a boolean that is false at t=0 and *stays* false when steps appear, and a Vue watcher fires on change. So it never ran at all. As built, one `watch(visibleSteps, (next, prev) => …)` replaces it and does four things: seed-or-self-heal, rescue by identity (§4.2), record the visited set (§3.1), and publish a `StepChange` record (§4.4). Watching the list also hands the handler `prev` for free, which is exactly the identity anchor the rescue needs and the current list cannot supply.

> **Why not refuse to publish a form that can empty out.** Undecidable in general — emptiness depends on the answers. But the decidable special case is worth catching, so split it: **the mid-fill empty graph is legitimate and specified above; the empty-at-open form is a publish-time WARNING**, decided by running `SemanticValidator` over an empty answer map, exactly as `SubmissionPdfPresenter` runs it over a stored one. A warning and not a refusal, for §6's reason and because a form whose only entry condition is a URL-prefilled `hidden` field (H7) is legitimately empty under an empty context.

**A consequence this document records rather than solves:** an empty submit burns a capacity slot. `FormAcceptanceGuard::assertCapacity()` counts every submission whose status is not `draft` (`:72-92`), so on a `max_responses`-capped form, screened-out respondents consume the cap. This is not solvable without the `screened_out` state that §10 defers — so it is a recorded consequence of deferring, not an oversight.

### 4.2 The vanishing current step, and the boundary against screen-out

A step that hides itself mid-fill is rescued by index (§2.3), which can throw the respondent backwards further than intended: on steps `[Lead, A, B, C]` with the respondent on C, an answer in C that hides C, B and A leaves `min(3, 0) = 0` — back to step 1, with an announcement that says where they are but never **why** they moved. **Specify:** reconcile relative to the vanished step's *identity* — walk the previous ordered key list outward from the vanished key to the nearest survivor — and announce the reason, not just the destination.

> **Amendment B2 (H21b, as-built) — "nearest survivor" needs BOTH directions, and this section only specified one.** The text above says "walk the previous ordered key list outward from the vanished key to the nearest survivor", then illustrates only the backward case. As built the walk goes backwards first (the respondent's own history), then **forwards**, then gives up and lets the caller decide. The forward arm is not a nicety: a respondent standing on the FIRST step when it removes itself has nothing behind them, and a backward-only walk falls through to a caller fallback that lands them somewhere arbitrary.
>
> It is also the amendment mutation testing paid for. Deleting the forward arm reddened **nothing** — the first draft of this increment's suite had no case where the vanished step lacked a predecessor, so both halves of the rule were pinned by tests that only ever exercised one. Two tests were added and the mutation then reddened exactly those two. The two callers deliberately keep different fallbacks: the rescue watcher falls back to the first step, `goToStep()` falls through to §5.3's first-incomplete rule, and folding either into the walk would make the other unreachable.

**Where the boundary falls.** §4.1 delivers relevance-derived early exit as a runtime *experience*: an author can already write conditions that empty the remainder of the form, and after H21b that produces a coherent terminal screen instead of "Step 1 of 0". It does **not** deliver early exit as a *state*. See §10.

### 4.3 Repeatable sections are one step, and one of them can hide an unfixable error

**Pin, because H21b's step-count UI must know it:** a relevance-gated repeatable section is **one step regardless of instance count**. The progress indicator counts it once, and every instance's errors fold onto the section's own step key. Server-side, an irrelevant repeatable section drops the whole group and enforces nothing on it. Branch conditions reach *inside* instances too: per-instance member relevance is its own bounded fixed point, over the base answers merged with that instance's, so "show the second question only for household members over 18" works per row.

**The hole.** The server enforces `min_instances` on any repeatable section whose *section* relevance is true — it consults nothing else. The client, meanwhile, drops a section from the step list when every member renders nothing (§2.2 predicate 2), and will drop it again under predicate 3. So a repeatable section can vanish from the respondent's step list while the server still requires it to hold at least one instance: a permanent `min_instances` error that blocks Submit and is **invisible**, because the error-summary iterates the visible step list and the step is not in it. Same failure shape as §5.5, reached from the other direction. **Specify:** the emptiness predicates must not drop a section the server will still enforce — either the client keeps such a step, or the server stops enforcing bounds on a group the respondent was never shown. H21a owes the decision and the test.

> **Amendment A4 (H21a, as-built) — the server stops enforcing, and the fix had to be MIRRORED, which this section did not anticipate.** The decision went the server's way: a client that kept the step would render a heading over nothing, which is the grayed-out step §2.2 forbids. But the bounds check lives in `SemanticValidator::processRepeats()`, which has a byte-for-byte TypeScript twin — and **both are reached by the golden runners**. A PHP-only narrowing would therefore have been an R3 break in the exact class of section the change targets, invisible to CI because every repeat vector in the corpus uses an ordinary `short_text` member.
>
> Mirroring it forced a small relocation: `RENDERS_NOTHING` moved from `lib/schema-mapping.ts` down into `engine/field-roles.ts`, because the engine must not import from `lib/` and a second copy inside `engine/` would have been a THIRD definition of the same set. `schema-mapping.ts` re-exports `rendersNothing()`, so no import path changed, and `tests/Unit/Forms/PdfFieldRoleTest.php`'s regex was repointed at the new home — a change its `expect($matched)->toBe(1, …)` guard turns into a loud failure rather than a vacuous pass.
>
> **The predicate, identical on both sides:** enforce bounds only when the section is relevant AND at least one member renders something AND (there are no instances yet OR some instance still has a currently-relevant renderable member). **Zero instances is VACUOUSLY visible** — the step is what lets the respondent add the first one, so `min_instances = 2` on an empty group is a real, reachable, VISIBLE blocker and must still fire. Without that arm the narrowing would silently disable the rule instead of scoping it.
>
> **`max_instances` deliberately keeps its position ahead of the per-instance settle** and takes no narrowing: it is the abuse guard that rejects a huge array before anything settles it, and a max violation means instances were submitted, so the respondent was shown the group. Only `min` moved below the instance loop, because only `min` needs the per-instance masks.

### 4.4 Single-page mode, and the notice nobody sees

**Single-page mode renders the same step objects, all at once**, so branching lands here unchanged — but with none of the transitions the field level has. A field wrapper animates its collapse, rescues focus if the caret was inside it, and announces a one-time retained-value note; the single-page section list is a bare `v-for` over the visible steps with **no transition, no focus rescue and no announcement**. So when an answer flips a whole section irrelevant while the respondent is typing inside it, the section is removed synchronously — hundreds of pixels of layout jump under the scroll position, `document.activeElement` resets to the document body, and nothing is said. A live accessibility defect today, since section relevance already exists; central under H21. **Specify:** a transition on the section list, section-level focus rescue to the nearest preceding heading (the field-level rescue already implements exactly this walk), a section-level announcement, and explicit scroll anchoring. Note that single-page mode has no progress indicator by design, so there is no count to keep honest here.

**And the notice that never fires at all.** The retain-and-restore note is per-*field*, driven by a watcher inside the field wrapper — but in multi-step mode only the current step's section is mounted. When step 3 becomes irrelevant while the respondent is on step 1, no field wrapper for step 3 exists, no watcher fires, and the step simply disappears from the rail with the count silently dropping. **The data is safe** — verified across all four hops: answers are never deleted on hide, autosave persists the full retained map, the submit body is the pruned effective set, and the server re-prunes; so a reverted answer restores the step's answers intact. Nothing is *lost*; nothing is *said* either, which is precisely the affordance the UX spec's "no silent data loss without a clear affordance" rule exists to provide. **Specify:** a step-level equivalent. One constraint on the implementation: the runtime store is deliberately DOM-free and announcer-free, so this must be a value the store returns and the component acts on — the shape `attemptNext()` already uses — not an announcer call inside the store. (A smaller related fact worth pinning: the field-level "once per session" flag is a per-component-instance variable, so a section that vanishes, returns and vanishes again re-shows its note. "Once" means once per mount.)

> **Amendment B3 (H21b, as-built) — the section list gets a `<TransitionGroup>`, but deliberately not the standard one; and the focus rescue could not live where the field-level one does.** The transition copies `FieldRow.vue`'s tokens and its `prefers-reduced-motion` opt-out, and is the repo's first `<TransitionGroup>`. It omits the usual `position: absolute` on leave: a section is hundreds of pixels tall, and taking it out of flow mid-transition would draw it on top of the questions below. The gap closes after the fade rather than during — less balletic, and nothing ever overlays a question.
>
> The rescue could not be a watcher inside `SectionView`, the way `FieldRow` does it. `FieldRow` survives its own content because the control is `v-if`'d inside a wrapper that stays mounted; a section IS the thing removed, so by the time the removal is observable there is no component left to ask. As built, `PageView` tracks the focused section on the way IN (one `focusin` handler on the form, reading `closest('[data-section]')`), and `SectionView` stamps `data-section-key` so the removed section can be identified after it is gone. The walk itself is then the same one `FieldRow.rescueFocus()` performs, one level up: nearest preceding surviving `[data-section-heading]`, else `[data-runtime-main]`.
>
> **Amendment B4 (H21b, as-built) — the step-level notice reuses `RelevanceNote`, and it exists at BOTH levels.** The store publishes `removedWithAnswers` on its `StepChange` record and the components do the announcing, per this section's own DOM-free constraint. `RelevanceNote` gained an optional `text` prop that overrides its composed field sentence, so one primitive carries both scopes rather than a near-duplicate component; existing call-sites are untouched. "Holds an answer" is `FieldRow`'s exact predicate (`Coercion.isEmpty`, object-blind for grids) lifted into the store, so the two levels cannot drift into different ideas of what an answer is.

## 5. Progress, Resume and the Two Percentages

**There are two progress numbers in this system, they measure different things, and under branching they will visibly disagree.** This document names them apart and pins the denominator that `docs/data-dictionary.md` currently leaves undefined.

### 5.1 The step counter is position on the taken path

"Step X of N", where both the numerator and the denominator are relevance-filtered (`ProgressIndicator.vue:12-20` over `visibleSteps`). N shrinks and grows live. This is the ratified §3.2 behaviour and it is correct as-is; §3.1 and §4.1 only fix the two shapes it renders wrongly.

### 5.2 `completeness_percent` is coverage of the authored form, and stays relevance-unaware

**Pinned denominator:** every top-level field whose type is not `note`, `page_break`, `calculated` or `hidden`, plus **exactly one unit per repeatable section** regardless of instance count, counted over the Stage-1 normalized answers; a field inside a repeatable section folds into that section's single unit and is never counted on its own (`app/Services/Submissions/DraftCompleteness.php:50-83`, exclusions at `:86-92`). The numerator is key presence, not non-emptiness. Zero denominator returns 0.

> **Why not make it relevance-aware.** It would have to run the full `SemanticValidator` on every draft autosave — on field blur, on step navigation, and on the 30-second backstop — which is precisely why the class is documented as pure and static with no container, no database and no expression engine; and it would prune answers the respondent is in the middle of typing. The tenant-facing consequence is worse than the cost: the inbox column would become "% of the path this particular respondent happens to be on", which is **not comparable between two rows** — the one property a reviewer's column actually needs.

> **Why not a second column.** A second `submissions` migration and a second number to keep in sync, for a figure nobody has asked for. The step counter already answers "where am I", live, for free.

**The knock-on this document owns.** `WelcomeBackBanner.vue` tells a *respondent* "You're {n}% complete" and `form-filling-ux-flow.md` §5.2 blesses the copy. Under branching that sentence is **false**: a respondent on a short branch is at step 3 of 3 and 31% coverage. **Specify:** the respondent-facing percentage is dropped — the welcome-back banner confirms that saved answers were restored and where the respondent is, not a fraction. Coverage stays on the **tenant** surfaces (the inbox draft column), where "% of the authored form" is exactly the meaning a reviewer wants.

### 5.3 The resume cursor and step drift

`submissions.draft_current_step` is a nullable, un-FK'd `varchar` carrying the SPA's current step key verbatim. On resume it is replayed through `goToStep()`, which is a **guarded no-op** on a key that is not in `visibleSteps` (`useFormRuntime.ts:859-863`) — and `currentStepKey` was already seeded to `visibleSteps[0]` at construction. So all three drift cases land in the same silent place: **step 1, with no explanation**, while the banner says "welcome back, 60% done". The cases are (a) the key no longer exists in the resolved version; (b) the key exists but is now irrelevant — **the H21 case**, reached whenever replayed answers put the respondent on a different branch or the author republished the graph; (c) `__lead__` after a republish that moved the previously section-less fields into a section, which degrades case (c) into case (a).

**Specify:** an unresolvable stored step resolves by §4.2's nearest-surviving-predecessor rule and then, failing that, to the **first incomplete** step — not to step 1 — and the welcome-back banner says so.

> **Amendment B5 (H21b, as-built) — `goToStep()` now REPORTS how it resolved, and §5.3's case (c) needed one extra rule to degrade the way this section says it does.** The method returns `'exact' | 'nearest' | 'first-incomplete' | 'none'`; `RuntimeSession` threads that into `WelcomeBackBanner`, which explains a drifted landing instead of silently showing step 1. Existing callers that ignore the return value are unaffected — `ProgressIndicator`'s dots always pass a visible key.
>
> The extra rule: the authored order the walk runs over includes `__lead__` **only when the version still has section-less fields**. Without that, a stored `__lead__` after a republish that moved those fields into a section would resolve as `'nearest'` by walking forward from position 0 — whereas this section specifies case (c) degrades into case (a), an unknown key with no position to walk from, and therefore the first-incomplete fallback.
>
> "First incomplete" is the FIELD-level answer predicate, deliberately **not** `DraftCompleteness`'s key-presence numerator. The server counts coverage of the authored form for a reviewer's column; this answers a respondent's "where do I carry on", and a field they explicitly cleared answers that with "here". §5.2 keeps the two numbers separate on purpose — this is the same separation one level down, and converging them later would break both.
>
> **The percentage is gone from the respondent's banner** (§5.2's knock-on, shipped here): `WelcomeBackBanner` no longer takes `completeness`, and `draftCompleteness` continues to flow to `DraftFlowKey` untouched for the tenant-facing surfaces. The component test asserts the absence, so a re-added "%" cannot slip back in unnoticed.

> **Why not validate `draft_current_step` at write time.** It validates the wrong thing. The key is typically perfectly valid at save and merely *irrelevant* at resume, so a write-time FK or membership rule buys nothing for the case that actually happens — while adding a 422 path to autosave, which is fire-and-forget by design and must never fail, and breaking H10's version-drift resume, which legitimately carries a key from an older version through the reconciliation path.

**A drifted fact corrected here.** Two places claim single-page forms leave this column null — the migration docblock (`database/migrations/2026_07_23_000009_add_draft_current_step_to_submissions.php:16`, "Single-page forms never set it (there are no steps) and leave it null") and the SPA's save-draft payload type (`resources/public-runtime/lib/types.ts:341`, "omitted for single-page forms"). Both are false. `RuntimeSession.vue:301` sends `draftCurrentStep: runtime.currentStepKey.value` **unconditionally**, `currentStepKey` is seeded from `visibleSteps[0]` regardless of presentation mode, and the wire-level guard suppresses only an empty string. Single-page drafts do carry a step key, and it is harmless — but a reader planning H21b against those docblocks would plan against a column that does not behave as documented.

### 5.4 What branching adds to the close and expiry policies

Nothing, and that is itself the finding worth recording. H12a's grace window promotes a pre-close draft after close without re-examining anything about the respondent's path, and H10's version-drift reconciliation handles a *version* change on resume. Neither has ever been exercised against a **graph** change — a republish that moves the branch the respondent was on, resumed under grace after the form closed. §9 assigns H21b a test rather than a code change; the policies stand.

**Offline replay, however, is a real stale-graph hazard, and its guard is already sitting unused in the row.** An outbox row stores both the `form_version_id` and the `checksum` it was captured against — and the replay path reads **neither**. Replay re-mints a share token *before* posting, and a fresh token pins the form's **current** published version, so the server's version guard compares the current version against itself and can never fire. The consequence under branching: a submission whose answers were pruned client-side against version N's step graph is validated and persisted against N+1's. If N+1 makes a previously-relevant branch irrelevant, the server prunes those answers, returns 201, and the outbox marks the row **synced** — silent, unattributable data loss behind a green sync badge. (The two opposite drifts are at least visible: a newly-required branch 422s, and a removed field is rejected at normalization; both route to "needs attention".) The service-worker schema cache can also serve an old graph to a *new* session, but that path re-mints and hits the ordinary 409, so it is covered; **replay is the uncovered path.** Live today for any relevance change across a republish, and H21 makes republishing the branch graph the routine authoring act. **Specify:** replay compares the row's stored version against the freshly-minted token's and, on mismatch, routes to the conflict state rather than posting — the review-and-resubmit UX already exists from G8c. A replay-path change only: no schema, engine, grammar or corpus impact.

> **Amendment B6 (H21b, as-built) — the guard reads the schema rather than the token, and it parks resumed-draft rows the server would have accepted.** `MintResponse` does not carry the minted version, so "compare against the freshly-minted token's" had no zero-cost realisation. Decided with the user: replay calls the existing typed `client.fetchSchema()` after `remint()` and compares `version.id`, memoized **per pass** (not module-level, so a republish between two drains is seen) — one extra GET per form per drain, no backend change, and no coupling of the SPA to `GuestShareTokenService`'s wire format, which decoding the token's `vid` claim would have required. The guard sits BEFORE the media leg, because `GuestAttachmentController` carries the identical current-version check against the same fresh token and uploading first would land the blobs under N+1. `row.checksum` stays unread: the server compares the version id, and matching the server's rule exactly is the point.
>
> **Narrowing, accepted rather than designed around.** A row queued by a RESUMED draft session carries its pinned version, and the server's draft path skips its own version guard — that path is version-safe by construction, since `promote()` re-asserts the draft's version. Such a row now parks for review where it would have promoted. It fails safe and costs one review click; the alternative was a `from_draft` flag on `OutboxRow` read by exactly one branch, which buys back less than it complicates. Recorded here so a later reader sees a decision, not an oversight.
>
> §9's grace-window obligation is discharged as three Pest tests rather than a code change, and they pin the outcome rather than the absence of a 500: a pre-close draft on a branch promotes with the branch answer intact; an off-branch answer is still pruned at promote time after close; and a republish that moves the branch makes the draft fail **loudly** (`409 submission_version_superseded`) instead of promoting against a different graph. That last one is the server-side twin of the hole above — the drift the server catches by itself, next to the one it structurally could not.

### 5.5 Submit is a silent dead-end when the failing field is not on the current step

`bannerItems` is scoped to the current step (`StepView.vue:25-29`), but `flow.submit()` reports failure off form-wide validity. When the failing field lives on another step, `bannerItems` is empty, so the banner's `v-if="bannerVisible && bannerItems.length"` never renders (`:97`) and the announcer says **"0 fields need your attention before submitting."** (`:79-81`). Submit does nothing and says nothing, permanently. Pre-H21 this is near-unreachable, because `attemptNext()` gates each step on the way forward. **H21 makes it routine**, because branching is precisely the mechanism that mutates an already-passed step. `PageView` does not filter, so single-page mode is unaffected. **Specify:** at SUBMIT the multi-step banner falls back to form-wide `erroredItems`, keeping step-scoping only for a blocked Next. `ErroredItem` already carries `stepKey`, so `goToStep(item.stepKey)` plus the existing focus address is the whole fix.

> **As built (H21b).** `StepView` keeps two item lists behind a `bannerScope` ref — step-scoped for a blocked Next, form-wide for Submit — exactly as specified. The jump link needed one thing this section did not mention: `SummaryBanner.jumpTo()` resolves `getElementById('field-<address>')`, which cannot find a field on an unmounted step, so the banner gained an optional `beforeJump` prop it calls and then awaits a tick on before scrolling. `StepView` passes the navigation; `PageView` passes nothing, because single-page renders everything and its behaviour is unchanged.

## 6. Publish-Time Validation

**H21a adds warnings, not refusals. No new structural refusal is added by the whole of H21.** The three checks are: an **empty-at-open** notice (§4.1), a **forward-reference** notice naming the offending section/field pair (§3.1), and a **cycle** notice discriminated from a legitimate chain (§3.2). Each is decided from the two `relevant_expression` columns plus `ExpressionParser::referencedKeys()`, which the expression gate already calls — no new parsing machinery, and the positional machinery `TemplateScopeResolver` exposes for piping is directly reusable for the forward-reference case.

> **Amendment A5 (H21a, as-built) — three refinements the three checks needed to be honest.**
>
> **(a) The cycle graph needs STRUCTURAL edges, not just `${key}` references.** Strongly-connected components over reference edges alone miss the commonest real cycle: a section gated on a field it CONTAINS. That edge — field depends on its owning section — is structural, produced by the settle loop's `$sectionOk && $ownOk && ! $skipped` cascade, and appears in no expression. Without it, iteration 0 prunes the field, the gate reads ABSENT forever, the section can never become relevant, and the respondent can never answer the field because it never renders — a provably dead branch with no warning. As built the graph carries reference edges, field→owning-section **containment** edges, and `skip_if`/`skip_with` → `related_form_field_id` edges (those units participate in the settle too, so omitting them would make the detector silently incomplete). `chained_fixed_point`'s `gate → a → b` remains a DAG and stays silent, which is the property this section demanded.
>
> **Recorded honestly:** a mutually-referential pair that happens to settle to a fixed point is still reported. That is deliberate for a NOTICE — mutual dependency is a real design smell, the message names the members so the author can judge, and nothing is blocked either way.
>
> **(b) The forward-reference rule is the INVERSE of piping's, so a positional TIE is SILENT.** Piping refuses when the source does not precede the host; this fires only when the host **provably precedes** the source. Two nodes at the same position have no defined render order, so neither direction is provable and warning either way would be a guess — and an all-defaults fixture ties, since both `addFormField()` and the field factory default `sequence` to 0. `TemplateScopeResolver::precedes()` was promoted from `private` to `public static` to share the comparison; it is pure, so the promotion widens nothing.
>
> Note a fact worth writing down, because the opposite was assumed while planning: a section sits at `[sequence, -1]` and a field at `[sequence, fieldSequence]`, so **a section heading provably precedes every field in a section of the same sequence**. A template-materialized form that leaves every section at `sequence = 0` therefore still gets an honest diagnosis rather than silence. The section→own-member case is excluded here and handed to the cycle check, which diagnoses it correctly — telling an author to "move the field earlier" would fix nothing.
>
> **(c) The empty-at-open notice is SUPPRESSED for an H7 router form.** §4.1 concedes the false positive in the same breath as proposing the check; as built the suppression is structural rather than heuristic — if the version holds any `hidden` field whose `PrefillSource::for()` is `Url`, the notice is skipped, because such a form is legitimately empty under an empty context and the prefill simply has not happened yet. H7 shipped exactly that shape three increments earlier, so without this the notice would fire on every one of them and become the warning nobody reads twice.
>
> **Where they are computed:** in `FormPublishController::store()` **after** `publish()` returns, not inside `PublishService`. That keeps the service's contract binary, leaves `FormVersionApiController` untouched (so `openapi.json` stays drift-free), and means an exception from the real gates can never reach the inspector. Delivery is a new `flash.publishWarnings` list rendered as a dismissible banner on the builder — deliberately not a reuse of `flash.xlsformWarnings`, whose banner copy is hard-coded "Imported with N warning(s)" — plus the count folded into the toast, because publish is reachable from TWO pages and `back()` returns to whichever called it while only the builder renders a banner.

> **Amendment D3 (H21d1, as-built) — the notices got a SECOND caller, and it found a live defect in the first.**
>
> H21d1's canvas reuses these three checks against a **draft**, which this document specified and which
> `StepGraphInspector`'s own docblock anticipated — but only in one of the three checks. `referencesIn()`
> catches `Throwable` with a comment naming H21d1 as the reason; **`emptyAtOpen()` did not**, and it reaches
> the parser by a longer road: `SemanticValidator::validate()` → `evaluateRelevance()` →
> `ExpressionEvaluator::evaluateBoolean()` → `ExpressionParser::parse()`, which raises
> `ExpressionSyntaxException` on malformed input. On the publish path that is **unreachable** —
> `ExpressionValidationGate` runs inside `publish()` and refuses first — which is why it never fired in H21a
> and why no test caught it. Against a draft it is the **ordinary** case: a half-typed condition is what an
> author has most of the time, and an uncaught throw 500s the builder's sidecar.
>
> Fixed by catching `ExpressionException` (the abstract base, so syntax *and* evaluation failures) around the
> whole evaluation rather than one arm — **both settle loops can raise it**, because sections are swept
> separately from fields, and a guard over only the first would still let a field-level expression through.
> A graph that cannot be evaluated yields **no** empty-at-open notice: "empty at open" is a claim about what
> a respondent would see, and nobody sees anything through an expression that does not parse. The truer thing
> to say about that node is the syntax error, and the canvas says it client-side, between keystrokes.
>
> Both regression tests were **run against the unfixed code first** and both threw the predicted exception —
> the H21c standing lesson, applied to a defect found while planning rather than while reviewing.
>
> **The notices are now addressable.** `notices()` returns `GraphNotice` records naming the nodes each is
> about, and `warnings()` is the flash-shaped grouping wrapper over it, reproducing H21a's three sentences
> byte-for-byte (now pinned in FULL, not by needle — the H21a tests assert with `toContain`, which cannot see
> a dropped clause). The record carries **two** strings, and that is the design rather than a convenience:
> the banner wants one line per kind joining every instance, because it appears once above a page the author
> is leaving; the canvas wants each instance under the node it names. The cycle case proves one string cannot
> be both — its joining fragment is `“a” ⇄ “b”`, which reads as nothing on its own.

> **Amendment D4 (H21d1, as-built) — a correction to this section's own framing.** §6 says the checks are
> "publish-time", and as of H21d1 that is no longer true: the same three run on demand against the draft,
> which is the point of the canvas — an author meets them while there is still something to do about it,
> rather than in a banner after a publish that has already succeeded. The **posture** is unchanged and is
> what the section is really about: they are still warnings, never refusals, and nothing about H21d1 makes
> any of them bite. A **fourth** notice kind — a per-node *syntax error* — exists only on the canvas and only
> client-side, and it is deliberately not in `GraphNoticeKind`: server-side, an unparseable expression is
> simply the publish gate's refusal, said by a different class at a different time.

**The retro-gate argument, stated once and referenced from §3.1, §3.2, §3.3 and §4.1.** Every one of these checks would run at `PublishService.php:62-64` against the **draft**, and step 9 of `publish()` clones the just-published structure forward into a new draft. So any form already live with a cycle, a forward reference or a `count(${section})` condition could never be republished — its author locked out of editing a live form for a property that was legal when they published it. That is the shape H5c had to answer for entitlements, and its answer was to grandfather indefinitely with zero merge-day regression. The seam for doing the same here already exists and was built for exactly this purpose: `TemplateValidationGate::confirmationMessageViolations()` is the **returning, non-throwing twin** of its throwing check, added by H6a's amendment A3 so a caller can warn instead of refuse. H21a follows that shape. Where a check must eventually bite, the rule is: **warn when the currently-published version already violates it; refuse only a violation introduced in the draft** — and even that is deferred out of H21 (§10).

**What is deliberately not checked.** Unreachable sections (a constant-false relevance) — cheap but heuristic, and a heuristic that fires on a deliberately-parked section is a warning nobody will read twice. And the asymmetry between the two reference media stands: piping is strictly positional and refuses; relevance is positionally free and warns. §3.1 gives the reason; this document **ratifies the asymmetry rather than removing it**.

**Nothing new is frozen.** The `schema_snapshot` already carries section `relevant_expression`, `sequence`, `is_repeatable`, `min_instances`, `max_instances` and each field's `section_key` and sequences (`SchemaSnapshotSerializer.php:112-161`) — that **is** the step model, frozen per publish since F-phase. H21a adds no snapshot key and no new freeze step. The H-map's "frozen into `schema_snapshot`" line item for H21a is already discharged by construction.

## 7. Surface Parity — the Encode Path

**The Inertia encode path has no client relevance engine at all, and this document is the first to write that down.** `EncodeFormPresenter::present()` returns a flat, ordered `blocks` list — ungrouped fields lead, then one block per section — with **no step key, no `single_page_mode` read, and zero occurrences of `relevant_expression`** (`app/Services/Submissions/EncodeFormPresenter.php:82-158`). `Encode.vue` wraps the lot in one `<form>` with one submit button. And `makeSemanticValidator` has **zero hits anywhere under `resources/js/`** — the TypeScript engine ships only under `resources/public-runtime/`. Encode-channel relevance is applied server-side, at submit, and nowhere else.

**The consequence is live data loss with a success message.** A staffer keying a paper form sees every section, including branches the respondent's own answers exclude. At submit, Stage 1 accepts the keys (they are known), Stage 3 masks the irrelevant ones off, `effectiveAnswers()` drops them, and `passed()` is **true** — an irrelevant field is never required-checked. Stage 4 persists the pruned document. The controller then discards the `SubmissionResult` entirely and redirects with a flat `'Submission recorded.'` (`app/Http/Controllers/Tenant/SubmissionController.php:42-51`). The keyer is never told that half of what they typed was dropped.

**Specify, and accept the resizing.** H21c is not "port a presenter" — it is "give the Inertia application a client relevance engine and a step model it has never had", and the H-map's `full-stack, M` under-states it. The cheap half is available immediately and should not wait for the expensive half: the `semantic` result is already on `SubmissionResult`, so **reporting the pruned keys back to the staffer is a controller change, not an engine one**, and H21c should land it first. The server-side half is tractable and has a working precedent — `SubmissionPdfPresenter` already drops a whole section block on `sectionRelevance` via `SemanticValidator` with a pinned clock (H17), which is the same projection H21c needs, computed in PHP, already shipped and already tested.

> **Amendment C1 (H21c, as-built) — the Inertia app did not need a client relevance engine BUILT; it needed one IMPORTED, and `createFormRuntime()` turned out to be importable as it stood.** This section sized the work as "give the Inertia application a client relevance engine and a step model it has never had", and that framing survives — but the cheapest correct way to do it is not to write either. `resources/public-runtime/composables/useFormRuntime.ts` imports only `vue`, `../engine`, `../lib/schema-mapping`, `../lib/prefill`, `../lib/uuid` and `../lib/types`: no api-client, no Dexie, no outbox, no DOM. Its own docblock pins that ("deliberately DOM-free and announcer-free so it is pure and unit-testable"), and `steps.test.ts` already drove it in a bare Vitest process. So `Encode.vue` mounts the **same function the public SPA mounts**, and the two channels' step lists are equal because there is only ONE implementation, not two that agree.
>
> The two hazards a tenant-app mount could have hit were already handled: `randomUuid()`/`uuidv7()` are secure-context-safe (the tenant app is plain HTTP on localhost in dev), and `buildPrefill(schema, '')` is a no-op for `url` sources, which is the correct reading of H7 on this channel — a keyer is the SOURCE of such a value, not a recipient of one. The import crosses `resources/js/` → `resources/public-runtime/` for the first time; the reverse edge already existed, since the runtime imports the tenant app's `FieldInput.vue`.
>
> **The store owns the MODEL, `blocks` stays the RENDER source.** `EncodeFormPresenter` grows `version.schema` (the frozen snapshot), `version.checksum`, `version.now`, `form.single_page_mode`/`default_locale`/`supported_locales` and a server-computed `steps` — additively. `blocks` is untouched, and the PHP↔TS normalizer duplication it carries (`geo()`/`media()`/`cascade()`/`matrix()`/`options()` are hand-mirrors of `schema-mapping.ts`) is **deferred by name in §10** rather than collapsed: §9's obligation is the step list, and the collapse would put every G4a/G4b/G5b2/G6/H7 encode test in the blast radius.
>
> **THE CLOCK IS STAMPED BY THE SERVER on this channel, and that is a deliberate divergence from the guest.** The SPA builds its own with `isoClock(new Date())` at `App.vue`; the encode payload carries `version.now` in Carbon's exact `toIso8601String()` shape and hands it to `RuntimeOptions.now`. The server-rendered `steps` and the client's first `visibleSteps` therefore evaluate `today()` against one clock — let the browser stamp its own and a keyer working near midnight, or on a skewed machine, gets a step list that disagrees with the one just rendered, on a page whose whole purpose is that the two agree.
>
> **Amendment C2 — the keyable-hidden asymmetry is resolved OUTSIDE the step list, not by widening the projection.** `RENDERS_NOTHING` drops `hidden`, so a section holding nothing but a `url`-prefilled hidden gate can never be a step — and that is exactly the seeded `Branching Router`, this document's own §4.1 example. H7 and `data-dictionary.md` record that a keyer *must* be able to key such a field and that the asymmetry must not be flattened. Two options were weighed: give `StepProjection` and the TS store an audience axis (`Respondent | Keyer`), or keep the projections identical and render the orphaned rows in a labelled block outside the step list. **The block wins**, because it keeps the two channels' step lists byte-identical, which is what makes §9's parity assertion a clean equality rather than an equality-modulo-hidden-only-sections, and because it needs no change to either engine and no new axis on the shared fixture. A `url` hidden field sitting *alongside* ordinary questions still renders inline where its author put it; only one whose whole section is absent from the step list moves.
>
> **Amendment C3 — NEXT DOES NOT BLOCK on this channel.** `attemptNext()` refuses to advance past a step holding errors, which is right for a respondent answering about themselves and wrong for a keyer transcribing a document that may simply be incomplete; it would be a new refusal on a channel whose F4b contract is "server-authoritative: the pipeline is the sole authority". The consequence is taken seriously rather than waved through: a keyer who walks past everything and submits would hit exactly §5.5's dead end, so the pipeline's per-field 422s are fed into the store via `setServerErrors()` and Submit raises a **form-wide** summary whose jump links change step *before* they focus — §5.5's rule reached from the opposite direction. The submitted body is also the FULL answer map rather than `effectiveAnswers`, deliberately: posting everything is what keeps the pruned-answer report meaningful as a divergence alarm instead of a message that can never fire.
>
> **Amendment C5 — three defects an adversarial pre-merge review found, all three created by C1's own decision to mount the store, and all three now pinned.** They are recorded because each is a consequence of the port rather than a slip, and a reader repeating the port on another surface (H21d's canvas has the same shape) would meet them again.
>
> **(a) The pruned-answer report was reading a neighbour's relevance mask.** `SemanticResult::$repeatFieldRelevance` is index-aligned to the NORMALIZED instance list, but the report walked the RAW request map. `normalizeRepeatSection()` drops an empty instance and re-indexes, so every dropped row shifts every later mask by one — the report named an answer that had been persisted while staying silent about the one actually pruned. **Reachable on the ordinary flow, not in theory**: `addInstance()` pushes a literal `{}`, this increment seeds `min_instances` starter rows, and clearing a row's last value deletes the key, so a blank row among filled ones is a normal state. The fix is to re-run Stage 1 inside the report and walk the NORMALIZED document — one pure pass over an array the pipeline has already accepted, which cannot throw there — rather than to reconstruct which rows were dropped, which would put a second copy of "what counts as unanswered" in a class that has no business owning one.
>
> **(b) `fixed`-prefill hidden values started reaching the payload, so the report named answers nobody typed.** The report's own docblock asserted that such a value "never reaches the payload", and that was true on `main`: `Encode.vue` seeded an answer slot only for `supported` rows, and a `fixed` hidden row is not one. Mounting the store made it false — `createFormRuntime()` seeds those literals through `buildPrefill()`, correctly, because a label piping `${batch_id}` has to resolve on the first paint — and the page posts the full map. When such a field's section is irrelevant it was reported to a keyer as an answer that "was not saved", for a server-authored value they never saw and cannot act on. The fix asks the right question — *could the keyer have typed this* — so a `fixed` row is excluded and a `url` row is deliberately NOT, since on this channel the keyer IS its source.
>
> **(c) The error-summary jump links pointed at anchors this page never renders.** They looked for `field-<address>`, the id the guest runtime's `FieldRow`/`InstanceField` stamp; `Encode.vue` renders `FieldInput` directly, and `MdsFormField` derives its input id from Vue's `useId()` — a `v-0` token with no relation to the field key. Every lookup returned null, so a jump changed step and then did nothing, and in single-page mode was completely inert. The page now stamps its own `encode-field-<address>` wrapper and focuses the first focusable INSIDE it, because the wrapper is a plain `div` and `.focus()` on it is a silent no-op — the same reason `SummaryBanner.vue` reaches for a control.
>
> **The methodological note is the one worth carrying.** The first regression test written for (a) PASSED against the broken code: with one surviving row and one pruned row, the broken version names the survivor against its neighbour's mask and the fixed version names the pruned row, and both render the identical string. Two pruned rows separate them by count. **Every regression test here was run against the pre-fix code before being believed**, and that step is what caught it — the §9 caution about expectations reachable by more than one path applies to the tests written to prove a fix as much as to the ones written to specify a feature.

## 8. What the Visual Canvas Can Honestly Draw

**The canvas draws a rail with predicates, not a flow chart.** §2 leaves nothing else to draw: nodes are sections in `sequence` order, the edges between them are implied by that order and are not editable, and the only editable object is a predicate hanging off a node (a section's `relevant_expression`) or off a field inside it. An author who expects to drag an arrow from section 3 to section 7 will not find one, and H21d must be designed to say so rather than to imply otherwise.

**H21d1 (canvas) is read-derived and writes nothing.** It parses the existing `relevant_expression` strings and renders the rail, the per-node predicates and the inline graph warnings from §6. It is, in effect, the "logic testing / preview / logic-map tool" the backlog has carried since Phase 2, and it discharges most of that row.

> **Amendment D1 (H21d1, as-built) — where it lives, and the one architectural decision worth stating twice.**
>
> **It is a second view of the builder's centre pane**, not a page. An `MdsSegmentedControl` swaps
> `BuilderCanvas.vue` for `LogicRail.vue`; both stay mounted, both read the same `useBuilderStore`, and
> selecting a node on the rail drives the same `ConfigPanel` the Structure view does — so an author reads the
> map and edits in place rather than moving between two editors that would each need their own copy of the
> draft. No new page, no route for the view, no `BuilderPresenter` change, and the existing ≤1024px pane
> linearization is inherited rather than re-solved.
>
> **THE RAIL IS CLIENT-DERIVED AND LIVE; THE GRAPH ANALYSIS IS SERVER-DERIVED AND FLUSH-SCOPED.** Two sources,
> one fact each:
>
> - *Client, live* — node order, each raw predicate, its plain-English reading, its `${key}` chips and its
>   syntax-error state, parsed with the TypeScript `ExpressionParser` off the engine barrel. An author must
>   see the rail change as they type; a round-trip per keystroke is the wrong shape for any of it.
> - *Server, flush-scoped* — the three §6 notices, over a read-only `GET /forms/{form}/graph` sidecar on the
>   ScopeNode `impact`/`grants` precedent, refetched after `store.whenIdle()` settles and debounced. A forward
>   reference, a cycle and an empty-at-open form are facts about the WHOLE graph; none can be decided from the
>   node being edited.
>
> **Mirroring `StepGraphInspector` in TypeScript was rejected**: it would be a sixth R3-style mirror pair with
> no corpus standing over it — the hazard §9 and amendment A6 argue at length. The price is that the notices
> lag the rail by one save, and that price is **shown** (a "rechecking" line, and a failed check that says so)
> rather than hidden, because a stale clean bill of health that looks current is the failure worth avoiding.
> The refetch is gated on `whenIdle()` and not on a timer for the same reason: the endpoint reads the
> persisted draft, so a fetch that overtakes an in-flight PATCH reports notices about text the author has
> already changed. It is also keyed on a **logic fingerprint** (keys, sequences, containment, expressions) and
> not on the whole store — a label edit cannot create or clear a cycle, and re-asking on every character typed
> into a placeholder would be a request per keystroke for an answer that cannot have moved.
>
> **The `${key}` chips are a display affordance, not an authority.** The client collects references by walking
> its own parsed AST. That resembles `ExpressionParser::referencedKeys()` and is deliberately **not** its
> twin: nothing behavioural rests on it, and whether a reference resolves is still decided by
> `ExpressionValidationGate`, at publish, in PHP. Recorded here so a later reader does not count it as an R3
> pair and go looking for the vectors that would pin it.
>
> **One static fact from the step model is carried onto the rail**, because an author will otherwise find the
> absence baffling: a section whose every field satisfies `rendersNothing()` can never be a step at all
> (§2.2's predicate 2), and no condition they write will change that. It is H21c's keyer-only "Reference
> fields" block seen from the authoring side, and the set is imported from `engine/field-roles.ts` rather than
> hand-copied. What the rail does **not** carry is the taken path: it is not built on `StepProjection` /
> `visibleSteps`, because there are no answers when an author is editing a form. A simulator is the residue
> `docs/feature-backlog.md` keeps after this increment.

> **Amendment D2 (H21d1, as-built) — the reading, and why the classifier belongs to H21d2.**
>
> Each node shows its `relevant_expression` **verbatim** and, where the shape can be expressed in full, a
> sentence beside it ("Shown when *Your age* is more than 18"). There is no partial reading and no
> "…and 2 more conditions": one operand this module cannot express makes the WHOLE reading opaque, and the
> author gets their own text back unannotated. Grouping is preserved rather than flattened — `(A or B) and C`
> and `A or (B and C)` are different conditions, and rendering both as "A or B and C" would be a confident
> wrong answer about a form that decides who is asked what.
>
> The describable set is small and closed by decision: a comparison of bare references and literals,
> `selected()` and its `not()` negation, `count(${section})` against a number literal, and `and`/`or` chains
> of those at any depth. Arithmetic, `if()`, `int()`, the clock functions and a `not()` over a whole chain are
> **opaque**, each because its reading would be either wrong or longer than the expression it explains.
> `${key} = ''` reads as "is blank", tested on the AST node rather than on the rendered string.
>
> **This is the predicate H21d2 needs, one increment early and in its harmless direction.** The editor must
> render anything it cannot represent read-only and never rewrite it, which requires a "can this shape be
> represented?" test; `status: 'opaque'` here becomes `read-only` there. Building the classification twice —
> once for prose, once for editing — is exactly how the two would come to disagree about which expressions are
> safe to touch. And nothing here **prints** an expression: prose is not syntax and cannot be fed back to a
> parser, which is why it is safe to run over text that will never be rewritten. The AST→text printer H21d2
> owes still does not exist.

**H21d2 (condition editor) owns the write path, and it has no printer to reuse.** `relevant_expression` is a `text` column, frozen into the snapshot as a **string**, and re-parsed at publish — and **there is no AST→expression-string printer anywhere in this repository** (verified: every occurrence of `unparse`, `toExpressionString`, `printAst` or `astToString` in the tree is the word "unparseable" in an unrelated docblock). The H-map's line for this row — "emit ASTs via `StructuredRuleLowering`" — **is not implementable as written**: that class lowers structured `form_field_validations` rows into the AST the evaluator consumes, one-directionally, and never touches relevance at all. So H21d2 must choose:

- **(a) A serializer** — structured condition → canonical expression text, written into the existing `text` column. One new component, no schema change; but a *third* place expression syntax is constructed, and therefore a new drift surface against the two parsers. **Recommended.**
- **(b) A structured sibling** — a column or config key holding the structured condition, with the text derived from it. No round-trip risk; but a new snapshot key, a new publish-gate clause, and two representations that can disagree. **Recorded as the revisit trigger** if the serializer's canonical output ever surprises an author.

> **Why not a bidirectional canvas over free-text expressions.** Round-tripping author-typed text through a structured model and back is lossy in parenthesisation, whitespace and operand order; and an author who typed something the canvas cannot represent — arithmetic, `count(${roster})`, `if(...)`, all legal at grammar v2.0 — would either have it silently rewritten or be locked out of the canvas on their own form. Both failures are silent, which is the disqualifier. **Specify: a non-representable expression renders read-only and is never rewritten.**

H21d also inherits two existing contracts it must not break: `builderClient`'s typed 409 conflict result, which is the builder's optimistic-concurrency contract and which any new write endpoint is the obvious place to lose; and the free-text relevance inputs in `ConfigPanel.vue`, which a structured editor must either replace outright or coexist with — and coexistence means answering which one wins when they disagree.

## 9. Required Test Vectors

**No new golden vectors — as a consequence, not a concession.** The branching semantics *are* the relevance semantics, and those are already dual-engine and already pinned: `tests/golden/validation/relevance.json` carries vectors whose `expected.relevance.sections` map is **literally the input to the step projection**, and `chained_fixed_point` pins the settling behaviour §3.2 makes normative. Nothing in H21 changes the grammar, the AST, either evaluator or the wire shape they agree on. The corpora therefore stay byte-untouched: `grammar_version` at **296** sites, validation at **114** vectors, expressions at **180**, templates at **76**. A changed count with no deliberate note is drift.

> **Why not a `tests/golden/steps/` corpus.** A step vector needs a section list, per-section sequences, a repeat topology and a field→section map — none of which the language-neutral vector shape carries. That is the same argument Doc #26's amendment A4 used to keep scope violations out of the template corpus. And adding one would move `grammar_version` off 296, falsifying the corpus's own byte-untouched marker for an increment that changed no grammar.

**The step projection is a fifth R3 mirror pair, not a fifth corpus.** Once H21c gives PHP a step projection, `visibleSteps` exists twice. Follow the H17 precedent already recorded in R3's inventory (`PdfFieldRole::Omitted` ↔ `RENDERS_NOTHING`): pin it with a test that **parses the TypeScript source**, because a hand-copied list keeps passing after someone edits the `.ts`.

> **Amendment A6 (H21a, as-built) — the pair is BEHAVIOURAL, driven by a shared fixture, and it ships in H21a rather than H21c.** The prescribed source-parsing device does not transfer. It works for `PdfFieldRole` because it parses actual DATA: `RENDERS_NOTHING`'s members ARE the rule. A step projection's rule is control flow, so parsing it would yield a list of predicate NAMES — and either side could implement one with inverted polarity and still pass. That is precisely the vacuous shape this section's own closing caution warns about, so it was not built.
>
> Instead, `tests/fixtures/step-projection.json` carries sixteen cases of `(sections, sequences, repeat topology, field→section map, answers) → expected step keys`, and BOTH `tests/Unit/Forms/StepProjectionTest.php` and `resources/public-runtime/__tests__/steps.test.ts` drive it — each through its own engine, so a difference in the resulting list is a projection difference and nothing else. It sits deliberately OUTSIDE `tests/golden/`, carries no `grammar_version` key and no manifest, and therefore moves neither the 296-site count nor the 114-vector total: the objection above to a `tests/golden/steps/` corpus was that the language-neutral VECTOR shape cannot carry a section list, per-section sequences, a repeat topology or a field→section map. A purpose-built fixture carries all four.
>
> The PHP half is `App\Support\Forms\StepProjection` — pure and static like `LocaleVariant`, consuming the masks a `SemanticResult` already carries rather than evaluating anything itself. That split keeps the projection out of the dual-engine settle loop (so it needs no TypeScript mirror of its own) and lets the fixture pin the projection alone, leaving the evaluator to the corpus that already pins it. **It is not the first PHP projection**: `SubmissionPdfPresenter::answerBlocks()` already groups by section and drops a block on `sectionRelevance`. H21c is the increment that collapses them, and it inherits the cross-check that the encode path and the PDF agree about what the respondent saw.
>
> Both halves carry the `PdfFieldRoleTest` anti-vacuity guards: a minimum case count, unique case names, and an assertion that the fixture contains at least one empty and one multi-step expectation — without which a projection that always returned `[]`, or always returned every section, would satisfy the whole file.

**What each slice owes instead of vectors.**

- **H21a** — the source-parsing mirror-pair test above; a projection suite whose fixtures carry **distinct `sequence` values** (the field factory defaults `sequence` to 0, and Doc #26's amendment A2 made a positional tie a rejection, so a fixture left at the default passes or fails for the wrong reason); publish-gate tests that assert the publish **succeeds** and the warning is surfaced (a test asserting a refusal would pin the opposite of §6); a `DraftCompleteness` denominator test pinning each exclusion and the one-unit-per-repeatable-section rule independently, because `isAnswerable()` is a `match` with a `default => true` arm that will absorb a 32nd field type as answerable silently — the H8 hazard, here left unfixed by construction and therefore owed a test; and coverage for §3.2's mask artifact (an oscillating pair must not return a section mask and a field mask that disagree), §3.3, §3.4, and §4.3's `min_instances`-on-a-vanished-section case, which must be asserted from the respondent's side — that the blocker is either absent or visible, never present and invisible.
- **H21b** — the empty graph asserted three ways (no counter rather than "Step 1 of 0"; no section renders; Submit present and labelled); §2.2's predicate 3 asserted through **both** `visibleSteps.length` and the rendered DOM, because the store and the view fail differently; the reappearing-step case from §3.1; resume drift asserting the **announcement**, since `goToStep` silently no-ops today and a test asserting only "did not throw" is vacuously green; the §5.5 submit dead-end; the §5.4 branch-drift-under-grace interaction; §5.4's replay guard, asserting that a row captured against an older version routes to **conflict** rather than posting and reporting `synced`; §4.4's single-page section removal, asserting focus lands somewhere reachable and the removal is announced (an axe pass alone will not catch a focus reset to `<body>`); and §4.4's step-level retained-answer notice. A standing caution in the H6b house style: any test whose expectation is reachable by more than one path is not pinning what its name claims — the empty-graph assertions in particular pass trivially against a component that renders nothing at all.
> **Amendment B7 (H21b, as-built) — the obligation above is discharged in full, and the caution it ends with was earned twice.** The suites are `resources/public-runtime/__tests__/runtime.test.ts` (the store: both terminal shapes, the outward walk in both directions, the visited set, `StepChange`, all four `goToStep` resolutions), `components.test.ts` (the same shapes through the rendered DOM, plus the §5.5 dead-end, the single-page removal and the resume-drift copy), `replay.test.ts` (§5.4) and `tests/Feature/Guest/GuestDraftRuntimeTest.php` (the grace-window interaction). Each empty-graph case pairs its absences with the Submit control **by its exact label** and with a non-empty control mount, per the caution above.

> The e2e half is a seeded `Branching Router` in `E2eSeeder` — this document's own §4.1 example built literally, a URL-prefilled `hidden` gate alone in its section — scanned bare (the terminal state) and as `?role=staff` (one ordinary branch). That is the only a11y gate that sees runtime pages; the Storybook axe job globs `packages/design-system/src/**` and there are no stories under `resources/`.

- **H21c** — a parity suite asserting that the encode path and the guest SPA produce the **same step list** for the same version and answer set; this is the increment's whole point and the first test in the repository to compare the two channels at all. Plus a test that the encode path applies client relevance (it applies none today), that `single_page_mode` is now read on this path, and a cross-check that the encode path's step visibility agrees with `SubmissionPdfPresenter`'s taken-path section drop — if those two disagree, one of them is lying about what the respondent saw.

## 10. Out of Scope / Deferred

- **Screen-out / disqualification as a submission state.** §4.1 ships early exit as a runtime *mechanism*; `screened_out` as a *state* is a data-model change with knock-ons into `SubmissionStatus`, `assertCapacity()`'s non-draft predicate, the inbox filter, the exporter, the domain-event catalog and the webhook contract. `docs/feature-backlog.md` scopes that row to Phase 3 "with the visual workflow builder", so H21 leaves it **half-discharged, not closed** — and the backlog row is amended to say so rather than left for a reader to assume.
- **True goto / author-drawn edges.** §2's rejected alternative. The revisit trigger is external and specific: a customer asking for a jump the predicate form cannot express in a reasonable number of conditions — not an internal preference, and not a competitor comparison.
- **The O(N) authoring burden that follows from §2.** A twenty-section form where section 3 skips to section 18 needs fourteen predicates, each independently editable and independently wrong. The canvas makes this *visible*; it does not make it *cheaper*. Recorded, and deliberately not solved with a "skip to" sugar, which would be an edge in disguise.
- **Refusing anything at publish.** §6. A future increment may promote a warning to a draft-introduced-violations-only refusal; H21 does not.
- **Structured storage for relevance conditions** — §8's option (b).
- **Collapsing `EncodeFormPresenter`'s render normalizers onto the client's `buildRenderModel()`** (H21c, amendment C1). `geo()`, `media()`, `cascade()`, `matrix()` and `options()` are hand-mirrors of `schema-mapping.ts`'s `buildGeo`/`buildMedia`/etc. — each documented as such in its own docblock — and since H21c the encode payload ships the frozen snapshot the client builds from anyway, so `blocks` could shrink to a per-key overlay carrying only `supported`, `prefill`, `prefill_value` and `upload.url`. Deferred deliberately: it is a render-model change, not a step-model one, and it would put every G4a/G4b/G5b2/G6/H7 encode test in the blast radius of an increment already resized to L. The revisit trigger is specific — the first time the two normalizers are found to disagree about a control's config, which is a drift surface with no test standing over it today.
- **`SchemaChangeClassifier` does not diff relevance**, so a change that alters *which respondents are asked what* currently classifies as ordinary non-breaking metadata. Doc #26 §6.1 deferred hole-diffing on the same grounds; this is strictly higher-stakes and is recorded here so the next classifier change starts from the right list.
- **The R5 DB-level immutability trigger** — H25, per §1.
- **XLSForm round-tripping of a canvas-authored condition** — the import/export path is text-in, text-out and is unaffected by §8's serializer; a canvas that cannot represent an imported `relevant` renders it read-only per §8.
- **One-question-per-screen presentation.** A third presentation mode, unrelated to branching, not requested.

**Finally, the honest limit of everything above.** This document adds no golden vectors and no evaluator change, which means **CI cannot tell you H21 shipped correctly.** The R3 gate — the strongest automated guarantee in this codebase — is by design silent about this increment. Every guarantee here is a hand-written test in a suite that did not exist before, which is the same posture Doc #26 §5.1 recorded for the output-encoding contract: a convention with test coverage, not a compiler error.
